## Context

Four gaps were found on 2026-10-01 while checking that every agent test ends with a real assertion. This change closes three of them. All three are in the unit test suite of `apps/ascend-agent` and need no Docker. The production code under test is `config/StartupLogConfig.java` (the readiness banner and its AscendMemory probe) and the vector store start-up in `AppConfig`. The fourth gap, the request factory tests of `ChatModelResolver.buildRequestFactory`, is left to `upgrade-spring-boot-4` (owner decision, 2026-10-02), which deletes that method and carries the same two wire tests in its task 2.2 (see the proposal).

This change also owns the shared end-to-end harness (owner answer 67.1 of 2026-10-04, dependency fix of 2026-10-05). It is build group 3, position 1 of the owner build order of 2026-10-04, so the harness exists before every change that uses it. The harness was designed as D23 and task 12.6 of `add-agent-skills` and moves here as a whole (D5). It is built against today's agent, read on 2026-10-05:

- Spring Boot 3.5.14 and Spring AI 1.1.5 (`apps/ascend-agent/gradle/libs.versions.toml`, `spring-ai = "1.1.5"`), with `spring-ai-starter-model-openai`, `spring-ai-starter-model-anthropic` and `spring-ai-starter-mcp-client-webflux` in `apps/ascend-agent/build.gradle.kts`.
- Chat providers are the agent's own map `app.ai.providers.<name>` in `apps/ascend-agent/src/main/resources/application.yaml` (`lmstudio`, `openai`, `gemini`, `anthropic`, `minimax`), each with `enabled`, `type` (`openai` or `anthropic`), `base-url`, `api-key`, `model`, `memory-extraction-model`, `temperature`, `timeout-seconds` and `default-embedding`. `ChatModelResolver.initializeProviders` registers every enabled entry of the map by its name, so a new entry with `type: openai` becomes a provider a prompt can select with `provider=<name>`. An unknown provider name answers 400 through `IllegalArgumentException`.
- `ChatModelResolver.buildOpenAiChatModel` builds `OpenAiApi` and `OpenAiChatModel` with no retry template and no error handler of its own, so Spring AI 1.1.5's defaults apply: `RetryUtils.DEFAULT_RESPONSE_ERROR_HANDLER` turns a 4xx answer into `NonTransientAiException` and every other error status into `TransientAiException`, both with the message `<status> - <body>`, and `RetryUtils.DEFAULT_RETRY_TEMPLATE` retries only `TransientAiException` and `ResourceAccessException`, at most 10 attempts, with an exponential backoff of 2 seconds, multiplier 5 and at most 180 seconds (read in the 1.1.5 sources of `spring-ai-retry`, `spring-ai-openai` and the agent on 2026-10-05).
- MCP connections are Spring AI's `spring.ai.mcp.client.streamable-http.connections.<name>.url` (`ascend-audio-scribe`, `ascend-weather-mcp`, `ascend-web-hunter`, overridden in `application-docker.yaml` with the container addresses), with `spring.ai.mcp.client.initialized: false` and the agent's own startup initializer.
- `compose.yaml` sets the agent's `SPRING_PROFILES_ACTIVE=docker` as a fixed value. This change leaves that line and every other line of `compose.yaml` as they are (owner answer 98.1 of 2026-10-08).
- `apps/ascend-agent/Dockerfile` sets `WORKDIR /app` in its runtime stage, runs as the user `app` and creates no `/app/config` folder (only `/app/app.jar`, owned by `app`), read on 2026-10-08.

## Goals / Non-Goals

Goals:

- Each test reaches the branch its name describes and asserts the result a user or operator would see.
- No new test dependency in the agent build.
- One shared end-to-end harness that a deterministic spec uses to make the model call a tool, answer a fixed text or fail with a fixed HTTP status, with no real model and the same answer on every run.
- The provider 429 and 502 handling of today's agent is proved end to end.

Non-Goals:

- No production code change. A defect a test exposes is reported to the owner first. The shipped `application.yaml` and `application-docker.yaml` do not change, and no production configuration names the provider `scripted` or the connection `e2e-fake`. `compose.yaml` does not change either (owner answer 98.1 of 2026-10-08).
- No coverage work outside these three gaps and the harness.
- The harness never runs beside an AI-run spec (owner answer 70.4 of 2026-10-04, D5).
- No test of `ChatModelResolver.buildRequestFactory`. It is deleted by `upgrade-spring-boot-4`, which tests the HTTP/1.1 and read timeout behaviour of the new transport itself.
- No end-to-end spec for the three unit test gaps (end-to-end coverage pass of 2026-10-04). The readiness banner lines for an AscendMemory answer of 500 and for the HTTPS address are log lines, and the e2e contract never passes or fails a spec on a log line. The restored interrupt flag is the state of one thread inside the agent and has no effect a request from outside can observe. All three are proved by the unit tests of this change, and the agent's existing specs already cover the start-up of a healthy stack.

## Decisions

### D1: A local JDK `HttpServer` for the network test

`com.sun.net.httpserver.HttpServer` ships with the JDK, binds to `127.0.0.1` on port 0 (a free port chosen by the system), and lets a handler record the request and choose the answer and its timing. It is started in the test's `// given` step and stopped in an `@AfterEach`, so each test is isolated and repeatable. A mock server library was considered and rejected because it is a new dependency for one test.

### D2: AscendMemory non-200 branch

The fake server answers `500` on the probe path. The test asserts the banner line for AscendMemory carries the status the non-200 branch writes (read from `StartupLogConfig` at implementation time, not guessed here) and not the connection refused text. The existing test keeps its body and is renamed `onReadinessChange_AscendMemoryConnectionRefused_LogsFailed`, with its misleading comments removed, so the name matches what it checks.

### D3: Interrupted vector store start-up

The test stubs the list call with a `ListenableFuture` whose `get()` throws `InterruptedException` directly (a small anonymous subclass of Guava's `AbstractFuture` or a Mockito mock of `ListenableFuture`). After the call the test asserts `Thread.currentThread().isInterrupted()` is true, then clears the flag with `Thread.interrupted()` in the `// then` step so later tests on the same thread are not affected. It also asserts that no collection was created.

### D4: SSL banner port

The `anyString()` stub on the port property is replaced by a stub on the exact property name and default value the code passes, returning `9917`. The test asserts both banner lines contain `https://localhost:9917`.

### D5: The shared end-to-end harness: a scripted model, a fake MCP server and an e2e overlay

Owner answer 67.1 of 2026-10-04: one shared harness serves every change whose end-to-end tests need a model to call a tool on cue. Moved here from `add-agent-skills` D23 by the dependency fix of 2026-10-05, so it exists before the first change that uses it. Every later change only uses it and adds its own routes and rules to the one Mockoon environment file, its reply files and vector files in its own subfolders and its own overlay lines, never a second harness.

- The scripted model: Mockoon, the `mockoon/cli` container image pinned by version and digest (owner answer 76.2 of 2026-10-08, which replaced WireMock). It runs as the container `e2e-scripted-model` on the stack's network and listens on port 3000, the default port of a new Mockoon environment (checked in the Mockoon documentation, Context7 `/websites/mockoon`, on 2026-10-08), kept as the `port` of `scripted-model.json`, so its address on the stack's network is `http://e2e-scripted-model:3000` (owner answer 79.2 of 2026-10-08). It is published on the host only as `127.0.0.1:7033` (container port 3000), so Bruno on the host reaches its admin API at `http://127.0.0.1:7033/mockoon-admin/...`, while every container keeps using `http://e2e-scripted-model:3000` (owner answer 81.3 of 2026-10-08, D8). Its OpenAI routes are `/v1/chat/completions` and `/v1/embeddings`: Spring AI 1.1.5 appends these paths to the base URL `http://e2e-scripted-model:3000` that the overlay gives the agent (`upgrade-spring-boot-4` D4). AscendMemory never calls the scripted model (owner answer 91.1 of 2026-10-08, the AscendMemory bullet below). Task 4.3 checks both paths on the pinned image. Its files live under `apps/ascend-agent/e2e/fixtures/scripted-model/`: `scripted-model.json`, the one Mockoon environment file with every route and rule, the reply files in `responses/<change subfolder>/` (this change's in `responses/harness/`), referenced by the rules through Mockoon file paths, and the fixed embedding vectors in `embeddings/<change subfolder>/<vector name>.json`. All rules live in this one environment file, shared by every change, so each change adds its own routes and rules to it and its reply files to its own subfolder. It answers the OpenAI chat completion format. A request whose last user message holds `E2E-SCRIPT <script name>` gets the step that script names: a tool call with fixed arguments, or a fixed text answer. A script may hold several steps, chosen by the number of tool results already in the request, and the arguments of a tool call may hold another `E2E-SCRIPT` marker, so a subagent run that the call starts follows a script of its own. A request whose last message is a tool result and whose script has no further step gets `E2E-SCRIPT-DONE <script name>:` followed by the first 2000 characters of that result. A last user message holding `E2E-SCRIPT-ERROR` gets HTTP 400 with an OpenAI error body. A last user message holding `E2E-SCRIPT-HTTP-429` gets HTTP 429 with an OpenAI error body of type `rate_limit_exceeded` (owner answer 68.5 of 2026-10-04). A last user message holding `E2E-SCRIPT-HTTP-502` gets HTTP 502 with an OpenAI error body on its first request, and the fixed text `E2E-SCRIPT-RECOVERED` on the next request with the same marker, through the Mockoon global variable `scripted_http_502_seen`: the 502 reply sets the variable with `setGlobalVar`, and a response placed before it, whose rules (AND) need the marker and that variable, answers `E2E-SCRIPT-RECOVERED`. The spec clears the variable with `POST /mockoon-admin/state/purge` (D6 says why). Any other request gets the text `E2E-SCRIPT-NO-MATCH`, from the route's default response. A request with `stream: true` gets the same answer returned whole as a `text/event-stream` body of OpenAI chat completion chunks, so the streaming path of `add-chat-streaming-and-conversations` uses the same scripts. Every answer carries a fixed `usage` block that its script sets, so token counts and cost are the same on every run. The scripted model's request log, `GET /mockoon-admin/logs` of the Mockoon admin API (paginated with `page` and `limit`), shows every request the agent sent with its body, and a spec may read it as observable state of the fake, never as a log line of the agent. `POST /mockoon-admin/logs/purge` clears it.
- How the rules choose a reply, checked in the Mockoon documentation (Context7 `/websites/mockoon`) on 2026-10-08: a route response rule targets the request body (the full body or a path in object-path or JSONPath syntax, with the operator regex match) or custom templating, rules are combined with OR or AND, the first response whose rules match is served, and the default response is served when none matches. So the marker in the last user message chooses the reply. The step of a script with several steps is chosen by a custom templating rule that counts the tool messages of the request (`len` over `bodyRaw`). The `E2E-SCRIPT-DONE` answer reads the last tool result with `bodyRaw` and cuts it with `substr`. Reply files are templates too (templating works in the file content and in the file path), so a reply file can give the plain or the streamed form from the request's `stream` field. The request log keeps request bodies unchanged and redacts sensitive headers (authorization, cookies, API keys), so every check of the request log reads bodies only.
- One container for every HTTP fake (owner answer 82.5 of 2026-10-08): `e2e-scripted-model` is the only HTTP fake container of the end-to-end suite. It serves the OpenAI-format scripted model of this change and every other HTTP fake of the plans: the Microsoft Graph stub of `add-document-connectors`, the fake quotes service of `add-self-built-integrations` and the fake GitHub REST API of the Bruno requests of `add-coding-agent-delegation` task 8.5. Every rule of every fake lives in `scripted-model.json`, and every reply file under `responses/<subfolder>/`. No change starts a second HTTP fake container, so the deterministic phase runs exactly two test containers, `e2e-scripted-model` and `e2e-fake-mcp`. Unit tests keep the JDK `HttpServer` of D1 (owner answer 78.3 of 2026-10-08). The routes of different fakes are kept apart by their first path segment, so they cannot collide:

  | Fake | Owner change | Path prefix | Reply files | Global variables |
  | --- | --- | --- | --- | --- |
  | OpenAI-format scripted model (chat and embeddings) | this change, used by every change | `/v1/` (only `/v1/chat/completions` and `/v1/embeddings`) | `responses/<change subfolder>/`, vectors in `embeddings/<change subfolder>/` | names starting with `scripted_`, for example `scripted_http_502_seen` |
  | Microsoft Graph stub and its token endpoint | `add-document-connectors` | `/graph-stub/` | `responses/graph-stub/` | names starting with `graph_stub_` |
  | Fake quotes service | `add-self-built-integrations` | `/fake-quotes/` | `responses/fake-quotes/` | names starting with `fake_quotes_` |

  `/mockoon-admin/` belongs to the Mockoon admin API, and no route may use it. The OpenAI routes keep `/v1/`, because the agent appends those paths to the base URLs of owner answer 79.2 of 2026-10-08. The five prefixes `/v1/`, `/graph-stub/`, `/fake-quotes/`, `/github/` and `/ascend-memory/` and the state names `scripted_http_502_seen` and `graph_stub_state` stay as they are (owner answer 86.4 of 2026-10-08). The same file `scripted-model.json` is also the environment of every Mockoon container that a Testcontainers integration test starts for an HTTP fake (owner answer 86.1 of 2026-10-08), so an integration test and an end-to-end spec answer from the same rules, and no integration test keeps an environment file of its own. A new fake takes a first path segment named after its reply subfolder, never `/v1/` and never `/mockoon-admin/`, and its change adds its row to this table. Every client that a fake replaces gets its base address from a setting, pointed at `http://e2e-scripted-model:3000/<prefix>` in the e2e overlay. A request log read filters the logged requests by path prefix, so a spec counts only the requests of its own fake. `POST /mockoon-admin/state/purge` clears the global variables and the request log of every fake at once, which is why every spec that calls it runs serial with every other spec that uses the harness (Concurrency below).
- Scripted embeddings (owner answer 72.8 of 2026-10-06): the scripted model also answers the OpenAI embeddings format, `POST` on the embeddings path of the OpenAI API under its base URL, so a deterministic spec that ingests a document or retrieves context calls no real provider and stays fully offline. The answer is deterministic: an input that holds the marker `E2E-EMBED <vector name>` gets the fixed vector stored in `apps/ascend-agent/e2e/fixtures/scripted-model/embeddings/<change subfolder>/<vector name>.json`, and every other input gets one fixed default vector that is orthogonal to every named vector. A request with several inputs gets one vector per input, in the order of the inputs, and a fixed `usage` block. Every vector, the default one included, is 1536 long, because the agent's scripted embeddings go to the 1536 dimension collection `ascendai-1536` (owner answer 78.1 of 2026-10-08, the provider bullet below, task 4.1 confirms the collection). How a test scripts an embedding: it puts the same marker into the text it ingests and into the prompt it sends, and adds the vector file in its own change subfolder next to its chat scripts. The same marker gives the same vector, so the chunk that holds the marker has cosine similarity 1 to the prompt and ranks first, above every real vector already in the collection and above every other scripted input, which all get the orthogonal default. Choosing a vector per input of a batch, checked in the Mockoon documentation on 2026-10-08: `each` over `bodyRaw 'input'` walks the inputs of a batch, but the file path of a response is chosen once per response, and the documentation names no helper that reads a file inside a template, so templating cannot pick one vector file per input. A Mockoon callback does not help, because a callback is an extra outgoing call with its own body and does not change the response. What replaces it: each named vector gets one response whose rule matches its marker, and its vector file is a template that walks the inputs with `each` and writes the named vector for the input that holds the marker (`includes`) and the default vector for every other input, in input order. The default vector is kept once in a data bucket of `scripted-model.json` (read with `dataRaw`), and the default response of the embeddings route, for a request with no named marker, writes it once per input. One embeddings request therefore carries at most one named vector, which every planned spec already does, and the markers do not change. Task 4.3 checks this on the pinned image and checks the request shape the agent's embeddings batch sends. Every spec that ingests with scripted embeddings deletes its points in its Post-run cleanup, so no scripted vector stays in a collection an AI-run spec reads.

### D6: The provider error checks read the scripted model's request log

Owner answer 68.5 of 2026-10-04: deterministic Bruno checks read the scripted model's request log, and the checks of the provider 429 and 502 handling live in this change, through the markers `E2E-SCRIPT-HTTP-429` and `E2E-SCRIPT-HTTP-502`. One new deterministic spec, `<N>-provider-errors-scripted` (the next free spec number of the ascend-agent suite at implementation time), carries them, together with a smoke step that proves the harness itself works. No existing spec can carry them: specs 1 to 11 of the ascend-agent suite are all AI-run specs against real providers (weather, image description, summarization, semantic memory, RAG, attach sources, RAG dedup, the two prompt cache specs and the two compaction specs), so none of them may run while the harness is up (D5), and none of them asserts a provider failure. The deterministic specs that `upgrade-spring-boot-4` adds in its task group 14 land after this change, and the problem details spec of its task 14.3 refuses every request before any provider call, so it cannot carry a provider answer either. That is why this one spec is new (owner rule 2026-10-04 and answer 67.2: a new spec only where no existing spec can be updated).

What today's agent answers, read from the code on 2026-10-05 (`exception/GlobalExceptionHandler.java`, `service/chat/ChatExecutor.java`, `service/provider/ChatModelResolver.java` and the Spring AI 1.1.5 sources), and therefore what the spec asserts:

- `E2E-SCRIPT-HTTP-429`: the scripted model answers 429. The default error handler raises `NonTransientAiException` with the message `429 - <body>`, which the default retry template does not retry. `ChatExecutor` rethrows it, because no cache strategy treats it as a cache error, and `GlobalExceptionHandler.handleNonTransientAi` answers HTTP 429 with the JSON body `{"status": 429, "error": "Too Many Requests", "message": "AI provider error: 429 -", "timestamp": "<instant>"}`: the message keeps only the text before the first `{` of the provider body. The request log holds exactly one chat request with the marker (no turn succeeds, so no extraction request follows). This count holds for today's agent only: after `upgrade-spring-boot-4` the provider SDK retries a 429 too, and with the SDK default of two retries after the first request the request log holds exactly three requests, which that change writes into this row in place (its D9 and task 15.1, owner answer 90 of 2026-10-08, which removed the retry count setting `max-retries` as a test setting). Owner rule 98 of 2026-10-08 brings `max-retries` back in that change as an operational setting whose default is the SDK default, and no test, overlay or spec sets it, so the count stays three.
- `E2E-SCRIPT-HTTP-502`: the scripted model answers 502 on the first request. The default error handler raises `TransientAiException`, which the default retry template retries after 2 seconds. The second request gets `E2E-SCRIPT-RECOVERED`, so the prompt answers 200 with that text, and the request log holds exactly two chat requests with the marker. The memory extraction request that follows the successful turn carries the marker too and is excluded from the count by the rule of D5. This proves that a provider 502 is retried and that the retry reaches the user's answer.
- What is not checked end to end: a provider that answers 502 on every attempt. Today the default retry template makes 10 attempts with waits of 2, 10, 50 and then 180 seconds, about 19 minutes in all, and then the `TransientAiException` reaches the catch-all handler, which answers HTTP 500 with the message `An unexpected error occurred. Check server logs for details.` That run is far above the time cap of an end-to-end spec, so the spec does not hold it. Owner answer 72.6 of 2026-10-06: no end-to-end spec is written for today's 19-minute retry. The deterministic 502 check of this spec, which `upgrade-spring-boot-4` runs again and updates in place after the upgrade (its task 15.1), covers the new behaviour. Owner answer 73.2 of 2026-10-06: after the upgrade this spec gets one extra row, which `upgrade-spring-boot-4` adds in place (its task 15.4 and its MODIFIED delta of the requirement "Provider 429 and 502 handling is checked end to end"): the scripted model answers 502 on every attempt, and the agent gives up after the provider SDK's default retry count (three requests in all) and answers 502 within a bounded time (owner answers 90 and 98 of 2026-10-08: no test or overlay sets a retry count, so the row counts the default of `max-retries`, which is the SDK default). That row needs the upgraded agent, because today's agent retries for about 19 minutes and answers 500, so this change does not carry it.

The status and body above are pinned by the spec on today's agent. `upgrade-spring-boot-4` changes the error body to the RFC 7807 problem detail of its D19 and the provider transport to the vendor SDKs, so its re-check task runs this spec again after the upgrade and updates its expected body in place (owner answer 67.2 of 2026-10-04: a changed feature updates its existing spec).

## Risks / Trade-offs

- [A later change edits a rule or a reply file of another change and breaks its spec] → all rules live in the one shared environment file `scripted-model.json`, so every change adds only its own routes and rules there, keeps its reply files and vector files in its own subfolders, and never edits another change's rules, and the "Shared e2e harness" section of the suite README says so.
- [The harness containers are left running after a sweep, or a failed spec leaves the agent pointed at the fakes, and an AI-run spec meets them] → the end step of D7 always runs, also after a failed spec, removes both containers and recreates the agent from its image, which removes the copied overlay, and its check must pass before the AI-run part starts. AscendMemory is never pointed at a fake, so a failed phase cannot leave it wrong (owner answer 91.1 of 2026-10-08).
- [Two fakes in the one Mockoon environment answer the same path, or one fake's global variable changes another fake's answer] → every fake has its own first path segment and its own global variable name prefix (the table of D5), and a request log read filters by path prefix.
- [The global variable of the 502 check leaks into the next run] → the spec calls `POST /mockoon-admin/state/purge` in its Reset state and Post-run cleanup, and the variable also resets when the scripted model restarts.
- [The request log of the scripted model holds more transactions than one page] → the spec purges the log in its Reset state and reads it page by page with `page` and `limit`. Task 4.3 records how many transactions the pinned image keeps.
