## Why

A review of the ascend-ai-agent tests on 2026-10-01 found four places where tests pass without proving what their names say. Each one stops short of the branch it is named after, so a defect in that branch would ship with a green build. This change closes three of them:

- `StartupLogConfigTest.onReadinessChange_AscendMemoryNon200_LogsWarning` only reaches the connection refused path. Its own comments say the non-200 branch needs a live server, and its assertion checks `[FAILED]`, which is the connection refused outcome.
- `AppConfigVectorStoreInitTest.initVectorStore_ListCollectionsInterrupted_HandledGracefully` never reaches the `InterruptedException` branch. `Futures.immediateFailedFuture(new InterruptedException(...))` makes `get()` throw `ExecutionException` with the interruption as its cause, so the test runs the execution failure branch a second time.
- `StartupLogConfigTest.onReadinessChange_SslConfigured_UsesHttps` asserts only the `https://localhost:` prefix. An `anyString()` stub leaves the server port null, so the test cannot check the full address a user would copy.

The fourth finding is left out on purpose. `ChatModelResolverProviderRegistrationTest.buildRequestFactory_Http1Required_CreatesHttp1Factory` and `buildRequestFactory_NullTimeoutSeconds_UsesDefaultTimeout` only check the type of the returned chat model, so neither proves that the HTTP/1.1 setting or the read timeout reaches the wire. The owner decided on 2026-10-02 that this change lands before `upgrade-spring-boot-4` without its former task group 3, the request factory tests. That upgrade deletes `ChatModelResolver.buildRequestFactory` and the JDK request factory it builds, and its own task 2.2 carries the same two wire tests (HTTP/1.1 and read timeout) against the new transport. Tests written here would test code that is about to be removed.

The agent also has no way to test, end to end and without a real model, anything that needs a model to call a tool on cue or to fail on cue. Owner answer 67.1 of 2026-10-04 asked for one shared end-to-end harness for this, and the dependency fix of 2026-10-05 (owner build order of 2026-10-04) makes this change its owner, because it is the first change of the base group and every later change that needs the harness lands after it. Until then `add-agent-skills` (build group 4) planned to build it, which was too late for `add-chat-streaming-and-conversations` and `add-keycloak-login` (build group 3). The harness also makes two provider failures testable end to end for the first time: a provider that answers 429 and a provider that answers 502 (owner answer 68.5 of 2026-10-04). A live provider cannot be made to answer either on demand.

## What Changes

- No production code changes. If a test exposes a real defect, the defect is reported to the owner before any production change.

## Impact

- Unit tests, all in `apps/ascend-agent/src/test/java/com/lukk/ascend/ai/agent/`: `config/StartupLogConfigTest.java` and `config/AppConfigVectorStoreInitTest.java`. `service/provider/ChatModelResolverProviderRegistrationTest.java` is not touched (see Why).
- Production code: none. No class under `apps/ascend-agent/src/main` changes, and the shipped `application.yaml` and `application-docker.yaml` stay as they are.
- Configuration: none. `compose.yaml` does not change (owner answer 98.1 of 2026-10-08), and neither do the `ascend-memory` service and the price table. No `.env` variable is added and no setting, so no configuration reference row is added.
- End-to-end fixtures and harness files: `apps/ascend-agent/e2e/overlay/application-e2e.yaml`, the scripted model's Mockoon environment file `apps/ascend-agent/e2e/fixtures/scripted-model/scripted-model.json` with this change's reply files in `responses/harness/` and vector files in `embeddings/harness/`, the fake MCP server class in the agent's test sources and its image folder `apps/ascend-agent/e2e/fakes/fake-mcp-server/`, the new spec with its tasks template, the Bruno folder `docs/api/request/AscendAI/ascend-agent/testing/provider-errors-scripted/`, the "Shared e2e harness" and allowlist sections of `apps/ascend-agent/e2e/README.md`, and the harness phase of `docs/E2E_RUN_SCENARIOS.md`.
- Dependencies: none in the agent build. The harness runs a Mockoon container (`mockoon/cli`) pinned by version and digest and builds one test image from the fake MCP server class, which uses the MCP Java SDK server transport already on the agent's test classpath.
- Gates: `./gradlew test` with the module's coverage gate, run from `apps/ascend-agent`, and one run of the new deterministic spec against the live stack.
- The three unit test gaps get no end-to-end spec, because each is a log line or the state of one thread, which no end-to-end spec may assert or can observe (design, Non-Goals).
