## Context

Documents enter the RAG knowledge base through exactly two hand-driven paths today:

1. `POST /api/v1/ingestion/upload` (`controller/IngestionController.java`): multipart upload, filename sanitization (`util/IngestionSecurity`), Tika MIME sniffing against `app.ingestion.upload.allowed-mime-types`, then a `StorageService` write into object storage under `markdown/` or `documents/`.
2. Out-of-band drops into the object storage bucket followed by `POST /api/v1/ingestion/run`. `service/ingestion/ManualIngestionService.java` scans the bucket, dedupes on ETag through a `ConcurrentMetadataStore` (`manual-ingestion:<key>:<etag>` markers), and pushes content through `IngestionService` and `DocumentRouter` into Qdrant.

A Spring Integration S3 poller exists (`config/IngestionPipelineConfig.java`) but is disabled by default (`app.ingestion.auto.enabled=false`). Downstream parsing is already rich: `DocumentRouter` routes to the markdown parser, Docling, ascend-ocr, or Unstructured, with per-page PDF classification. There is no connector or sync concept anywhere in the codebase.

This change layers automated source sync on top, without touching the parse path. It was split out of `add-document-connectors` on 2026-10-04 to follow the owner rule of that day: the personal assistant comes first, nothing personal may depend on company work, and company work comes last and only plugs in through extension points with safe defaults. The framework is personal, because the first connector type is the personal assistant's Obsidian vault (`add-obsidian-vault`). The SharePoint connector, its access list rules and the deferred permission capture design stay in `add-document-connectors` (company), which adds the `SHAREPOINT` type to this framework. Decision numbers below are the numbers these decisions had in `add-document-connectors` before the split, so a cross-reference written against those numbers (for example the required edits of `add-obsidian-vault` to D3, D21 and D22) lands on the right text here. D24 and D25 are new.

Dependencies on sibling changes (their scope is not re-specified here):

- `add-keycloak-login` (build group 3, position 3): provides the `ADMIN` role that guards the connector API, the authenticated user recorded on connector mutations, the authorization matrix this change adds its row to (its D4), and `TenantContext` with `currentTenantId()` and `runAs(tenantId, action)` (its D3 and task 3.9, D25).
- `add-document-management-api` (build group 3, position 8): owns the document metadata and status model, the document registry, `IngestionRunService` and the single-document deletion machinery (stored object plus Qdrant chunks plus metadata row). Deletion propagation in this change calls that path, and does not build its own.
- `upgrade-spring-boot-4` (build group 3, position 2): Flyway, and the RFC 7807 problem detail of its D19 that every error of the connector API uses (D23).
- `add-deployment-modules` (build group 3, position 6): `ASCEND_MODULES`, `@ConditionalOnModule` for a connector type that belongs to a switchable module, and the skip reason `module_denied` (D20). Document search (`rag`) is core and always on and is not a module (owner decision of 2026-10-03), so the framework itself carries no module marking.
- `add-shared-scheduler` (build group 3, position 7): the shared scheduler that runs every connector sync and the freshness check, its registration contract for system tasks, `SchedulerTaskName` and `CronRule` (D2, D19).
- `add-agent-skills` (build group 4, position 1): the shared problem code `unavailable` (503) (D23). The code `forbidden` (403) and the `AccessDeniedHandler` that writes the 403 body come from `add-keycloak-login` (owner answer 76.9 of 2026-10-08).

This change is build group 4, position 7 of the owner build order of 2026-10-04. Company changes plug in later and nothing here waits for them: `add-tenant-isolation` registers its `TenantPrefixResolver` implementation and stamps the access list on every chunk, `add-usage-metering-and-quotas` stores its BYOK provider keys through `ConnectorCredentialStore`, and `add-document-connectors` adds the `SHAREPOINT` type.

## Goals / Non-Goals

Goals:

- A provider-agnostic connector framework: per-tenant persisted configuration, scheduled and on-demand incremental sync, sync-run history with per-file outcomes, deletion propagation, `ADMIN` CRUD API.
- Connectors land bytes and trigger the existing pipeline. Nothing else.
- A connector that has quietly stopped syncing is visible as a stale connector rather than as a knowledge base that keeps answering from content that stopped being current.
- Encrypted connector credentials with no dependency on a company change.

Non-Goals:

- Any concrete connector type. `OBSIDIAN` is `add-obsidian-vault`, `WEB_CRAWL` is `add-web-crawl-rag-connector`, `SHAREPOINT` is `add-document-connectors`. Google Drive, Confluence and network shares are named follow-ons there.
- Any new parsing capability. `DocumentRouter` and its parsers are untouched.
- Real-time (webhook or subscription based) change notification from a remote source. A connector that notices a change itself uses the `EVENT` trigger (D22).
- Access lists on chunks, tenant enforcement and permission capture. `add-tenant-isolation` stamps the access list on every chunk the ingestion pipeline writes, and `add-document-connectors` owns the rules for what a connector-landed document carries.
- Single-document delete mechanics, consumed from `add-document-management-api`.

## Decisions

### D1: Connector to object storage to existing pipeline, no parallel parse path

A connector's contract is bytes. The source file's bytes are written to object storage under the tenant prefix (D25) (markdown to the markdown folder, everything else to the documents folder, same routing rule as `IngestionController.determineFolder`), at the object key segment the connector chooses inside that folder or, when it chooses none, at the sanitized source-relative path (D21). Before the ingestion run starts, the framework registers each landed file in the document registry of `add-document-management-api` with the `source_type`, `origin_uri` and connector id the connector supplies (D21). Then a bucket-scan run is started for the affected prefix through `IngestionRunService` from `add-document-management-api`, the same entry point `POST /api/v1/ingestion/run` uses. The sync run waits for that ingestion run to reach a terminal state (polling the run record, bounded by the connector's sync timeout) before it records per-file outcomes, so `ADDED`, `UPDATED`, `SKIPPED` and `FAILED` reflect what ingestion actually did. The bucket scan reaches `DocumentRouter` only because `add-document-management-api` moves `ManualIngestionService` onto it (that change's tasks 3.2a and 3.2b). Parsing, chunking and embedding stay the existing pipeline's job, and so does every chunk field the pipeline writes, the access list of `add-tenant-isolation` included once that change lands.

*Why:* one parse path means one set of parser bugs, one dedup semantics, one metrics surface. The alternative, connectors calling `IngestionService` directly with in-memory streams, would bypass the dedup and the object storage source of truth, and would make the `add-document-management-api` metadata model inconsistent (documents in Qdrant with no stored object).

*Consequence:* connector-fetched files pass the same hygiene as uploads, filename sanitization from `util/IngestionSecurity` and MIME sniffing against `app.ingestion.upload.allowed-mime-types`, applied by the framework before the object storage write, so a compromised or misconfigured source cannot smuggle disallowed content types past the controller-level checks.

*Consequence:* a connector never writes to the vector store. Not through the ingestion pipeline's own path, and not around it. The framework interfaces expose no vector-store handle at all. The permission-only payload update that `add-document-connectors` designed and deferred (its Deferred D11) would be the one reviewed exception, and it is not part of this framework.

### D2: Framework shape: `DocumentConnector` interface plus sync orchestrator

- `DocumentConnector` (interface, `service/connector/`): `ConnectorType type()`, `ChangeSet fetchChanges(ConnectorConfig, SyncCursor)` returning added, modified and deleted entries plus the next cursor. Each entry carries the source item id, path and content version, and the registry values and optional object key segment of D21. Implementations are stateless, and all state lives in the database.
- `ConnectorSyncOrchestrator` (framework): starts a run for one connector, resolves credentials through `ConnectorCredentialStore` when the connector type needs them (D21, D24), calls `fetchChanges`, applies hygiene, object storage writes, registry registration and deletion propagation, records the sync run and per-file outcomes, and persists the new cursor only after the run completes. A failed run keeps the previous cursor so the next run retries the same window.
- Scheduling is the shared scheduler of `add-shared-scheduler`. Each enabled connector whose type takes its schedule from the connector's own cron has one execution `connector-sync/<connectorId>` (task name `connector-sync` in `SchedulerTaskName`, task instance the connector id), whose next time comes from the connector's five-field cron and its time zone through `CronRule`. Creating, updating, enabling, disabling and deleting a connector creates, reschedules or removes that execution in the same transaction as the connector row. The shared scheduler runs each firing on exactly one agent instance, so multiple agent instances never double-sync one connector. An overdue execution after downtime runs once, and the next time is computed from the moment the run finished, the rule of `add-shared-scheduler` D3. A connector type whose schedule comes from a system task (D21) has no `connector-sync` execution.
- At most one run of a connector is in progress at a time, whatever started it. A manual trigger while a run is in progress answers 409 (code `connector_run_in_progress`, D23). An `EVENT` trigger, and a `SCHEDULED` start, while a run is in progress start no second run: they mark the connector dirty, and exactly one follow-up run starts when the current run ends (D22).
- A run that starts without a request (a `connector-sync` firing, an `EVENT` trigger, a system task of a connector type) of a connector type that belongs to a switchable module first checks that the connector's tenant holds that module's grant and is skipped with the reason `module_denied` when it does not (D20).

*Why the shared scheduler and not a scheduler of our own:* the agent has one scheduler for all shared timed work, chosen in `add-shared-scheduler` D1 (db-scheduler, after Quartz was rejected there for its weight), so a connector sync is one more execution on it rather than a second mechanism with its own tick and its own row lock. *Why not Spring Integration poller reuse:* `IngestionPipelineConfig` polls one bucket with one filter, while connectors need per-source cursors, credentials and run history, which is a different problem.

### D3: Data model (Flyway, new versioned SQL migration `V<n>__connectors.sql` in `db/migration/`, where `<n>` is the next free version at implementation time, Spring Data JDBC entities, never JPA)

Five tables, all tenant-scoped. Each carries `tenant_id VARCHAR(64) NOT NULL`, written from `TenantContext.currentTenantId()` of `add-keycloak-login` (`default` in the personal deployment), with no foreign key. `add-tenant-isolation` (company, build group 5) adds the foreign key to `tenants(id)` on all five later, and this change does not wait for it:

- `connector`: id (UUID), tenant id, type (enum string, admitted by a named check constraint of this migration, which admits `OBSIDIAN`, the required edit of `add-obsidian-vault`), display name, credentials reference (opaque handle into `ConnectorCredentialStore`, nullable, empty for a connector type that needs no credential, D21, D24), source scope (JSONB, provider-specific shape validated by the connector implementation), cron schedule (five fields, nullable, empty for a connector type whose schedule comes from a system task, D21), `time_zone VARCHAR(64) NOT NULL` (default `Europe/Warsaw`), maximum sync age, enabled flag, `last_successful_sync_at`, `stale` flag, `dirty_trigger` (nullable, `EVENT` or `SCHEDULED`, set while a follow-up run is owed, D22), created and updated audit columns. There is no `next_run_at` column: the next time of a sync lives in the connector's `connector-sync` execution of the shared scheduler. The index `connector(enabled, last_successful_sync_at)` serves the freshness check.
- `connector_sync_run`: id, tenant id, connector FK, trigger (`SCHEDULED`, `MANUAL`, `EVENT`, `FRESHNESS_CHECK`), status (`RUNNING`, `SUCCEEDED`, `PARTIAL`, `FAILED`), started and finished timestamps, counters (added, updated, deleted, skipped, failed), error summary.
- `connector_sync_file_outcome`: id, tenant id, sync-run FK, source item id, source path, action (`ADDED`, `UPDATED`, `DELETED`, `SKIPPED`, `FAILED`), object key, failure reason (nullable).
- `connector_sync_cursor`: tenant id, connector FK plus a discriminator (a connector type may keep one cursor per sub-source, for example one per drive), opaque content cursor value, updated timestamp.
- `connector_credential`: id (UUID, the opaque reference), tenant id, ciphertext, nonce, key version, created and updated timestamps (D24).

A later connector type admits its own enum value with its own Flyway migration that replaces the named check constraint (`add-document-connectors` admits `SHAREPOINT`, `add-web-crawl-rag-connector` admits `WEB_CRAWL`).

*Why JSONB scope instead of typed columns:* each provider scopes differently (SharePoint: site, drive, folder. Obsidian: vault name and folders. Web crawl: start addresses). A typed-per-provider table set would multiply migrations per connector, while a JSONB blob validated by the owning connector keeps additions additive (OCP).

### D5: Deletion propagation reuses `add-document-management-api`

When a connector reports a deleted entry, the orchestrator maps source item to object key (recorded in the file-outcome history and in the document metadata model owned by `add-document-management-api`) and invokes that change's single-document deletion path, which removes the stored object, the Qdrant chunks for that source, and the metadata row. This change adds only the mapping and the trigger. It is applied after `add-document-management-api` (build group 3, position 8, which lands earlier).

### D19: The freshness control measures the connector, and changes no document

What can fail silently in a sync is the sync itself: a revoked credential, a cursor stuck in a resync loop, a scheduler that never fires after a deployment, a connector left disabled after a migration. When that happens nothing errors, the corpus keeps answering, and it answers from content that is weeks out of date, including from documents that have since been deleted at the source. That is the worst failure a RAG product has.

The freshness check, then:

- The system task `connector-freshness-check` of `add-shared-scheduler` compares each enabled connector's `last_successful_sync_at` against its configured maximum sync age. It is registered under that change's contract: its name in `SchedulerTaskName`, the five-field cron `app.scheduler.system-tasks.connector-freshness-check.cron` (default `*/5 * * * *`) and its zone `.time-zone` (default `UTC`, the zone that change gives a sweep). It carries no module marking, because the framework is core. It is run by exactly one agent instance through the shared scheduler, so two instances cannot both act on one connector.
- A connector past its maximum sync age is marked stale on its configuration row. The flag is returned by the connector read and list endpoints, and it is exposed as a gauge: seconds since the last successful sync, per connector, plus a count of stale connectors.
- A connector that syncs successfully clears the flag on that run.
- The check records a run with trigger `FRESHNESS_CHECK` only when a connector's stale state changes, so a long outage produces one row rather than one per tick.
- It writes nothing to object storage and nothing to Qdrant, and it does not read the source. That independence matters: the thing that failed is the sync, so the control that notices must not depend on the sync working.
- It closes, as `FAILED` with the error summary `interrupted`, every `RUNNING` run whose connector lock of D22 is free, because the instance that ran it is gone (answer 87). This writes only the run row and starts no run.
- Its own run never moves `last_successful_sync_at`. Only a `SCHEDULED`, `MANUAL` or `EVENT` run does. Without that, a check completing successfully would look like a successful sync and clear the very condition it was recording.

A connector's maximum sync age has to be greater than the interval its cron schedule fires on, or a healthy connector marks itself stale on its first check. The interval is `CronRule`'s shortest gap among the next firings of the connector's cron in its time zone, and for a connector type whose schedule comes from a system task (D21) the shortest gap of that system task's cron. The framework rejects that configuration at write time rather than discovering it at check time, because that misconfiguration is silent until every connector reads stale at once.

The `sync-freshness-check-replaces-the-sweep` record under `decisions/` records this decision. It was written in `add-document-connectors`, where it replaced the access-list staleness sweep that is deferred there with permission capture, and it moved here with the freshness check on 2026-10-04.

### D20: The connector framework is core, a connector type may belong to a switchable module

Document search (`rag`) is core and always on and is not a module (owner decision of 2026-10-03), and the connector framework is part of it. `ConnectorController`, the orchestrator, the `connector-sync` task bean and the `connector-freshness-check` task bean carry no `@ConditionalOnModule`, always exist, and no tenant module grant guards `/api/v1/connectors`.

A connector type that needs a switchable module of `add-deployment-modules` carries that module's marking, for example `@ConditionalOnModule("web-search")` on the `WEB_CRAWL` type of `add-web-crawl-rag-connector`. The `OBSIDIAN` type of `add-obsidian-vault` carries the marking that change gives it. With that module not in `ASCEND_MODULES` the type does not exist, and a create of a connector of that type answers 400 with code `validation`. An unknown type answers the same.

Tenant narrowing follows the rules of `add-deployment-modules` for such a type. A run of it that starts without a request (a `connector-sync` firing, an `EVENT` trigger, or a system task of the connector type) checks the connector's tenant grant for the type's module at its own start and is skipped with the reason `module_denied` when the tenant does not hold it. A skipped run writes one INFO line naming the connector and the reason, records no `connector_sync_run` row and does not move `last_successful_sync_at`, so a connector whose tenant lost the grant becomes stale on the normal rule.

### D21: What a connector type declares and supplies

Each `ConnectorType` declares two facts that the framework acts on:

- Whether it needs a credential. For a type that needs one (for example `SHAREPOINT` of `add-document-connectors`), a create without a credential is refused with HTTP 400 and code `validation`. For a type that needs none (`OBSIDIAN`), the credentials reference is empty and the framework does not resolve one.
- Where its schedule comes from. By default it is the connector's own five-field cron and time zone, run through the `connector-sync` execution of D2. A type may instead declare that its schedule comes from a named system task of `add-shared-scheduler` (`OBSIDIAN` declares `obsidian-vault-rescan`). For such a type the framework creates no `connector-sync` execution, refuses a cron in a create or update with HTTP 400 and code `validation`, and measures the maximum sync age against the shortest gap of that system task's cron (D19).

Per landed file, the connector supplies to the framework:

- Optionally, the object key segment. The framework keeps the tenant prefix and the markdown or documents folder it chooses, and puts the connector's segment below that folder. It refuses a segment that is absolute, that holds a `..` segment or that would leave the folder. A connector that supplies no segment gets the sanitized source-relative path of D1.
- The registry values: `source_type` (the form `connector:<name>`, for example `connector:obsidian`), `origin_uri` (the address of the item at its source) and its connector id. The framework registers the landed file in the document registry of `add-document-management-api` with exactly those values before the ingestion run starts. That change keeps `source_type` and `origin_uri` on a later bucket-scan of the same object key and copies `source_type` onto every chunk. The connector id is this change's own (below).

`documents.connector_id` (owner answer 93 of 2026-10-08, moved here from `add-document-management-api`): this change's Flyway migration adds `connector_id UUID NULL` to the `documents` table of `add-document-management-api`, with no foreign key (deleting a connector leaves its documents in place), and an index `idx_documents_connector_id`. When the framework registers a landed file through `DocumentRegistryService.register` (with `source_type` `connector:<name>` and the source address as `origin_uri`), it sets `connector_id` on that row in the same transaction. A later bucket scan never changes the column, because the scan upsert of `add-document-management-api` writes only its own columns. The framework registers a `ChunkPayloadContributor` of `add-document-management-api` (its D15) that adds `connector_id` to every chunk of a document whose row has one, and nothing for a document without a connector, so every ingestion run (bucket scan, reindex, single-document run) carries it. At startup the framework creates a keyword payload index on `connector_id` on every RAG collection, together with the other payload indexes, so a filter on it (for example the vault filter of `add-obsidian-vault`) is served by an index.

### D22: Event-triggered runs, and the one follow-up run

A connector run has one of four triggers: `SCHEDULED` (a `connector-sync` firing, or a system task of the connector type), `MANUAL` (`POST /api/v1/connectors/{id}/sync`), `EVENT` (a change the connector itself noticed at the source, for example a file watcher of `add-obsidian-vault`) and `FRESHNESS_CHECK` (D19).

At most one run of a connector is in progress, across every agent instance (answer 87, CANON 26.1). The one mechanism is a Postgres session advisory lock per connector: a start takes `pg_try_advisory_lock` in the two-key form, with the class key from the enum `AdvisoryLockClass`, whose value `CONNECTOR_RUN(1)` is the connector framework's own (owner answer 98.10 of 2026-10-08, so it never meets the note write lock that `add-obsidian-vault` keys by the same connector id), and a key derived from the connector id, on the connection the run holds until it ends, and releases it when the run ends. A start that cannot take the lock finds the connector's run in progress, wherever that run executes. A start that takes the lock and finds a `RUNNING` row of the connector knows that the instance that ran it is gone, because Postgres released that instance's lock with its connection: it closes that row as `FAILED` with the error summary `interrupted` before it runs. Nothing in process memory decides whether a run is in progress, and no timeout value is needed. When an `EVENT` or a `SCHEDULED` start finds a run of the same connector in progress, it starts no second run and does not answer 409. It sets `dirty_trigger` on the connector row to its own trigger (`SCHEDULED` wins when both asked). When the run in progress ends, whatever its status, the framework clears `dirty_trigger` and starts exactly one follow-up run with that trigger. Several starts during one run therefore cause one follow-up run, not several, and no change is lost. `dirty_trigger` is written with one conditional update on the connector row, so starts on several instances during one run still leave one owed trigger. When the instance that ran the run dies before it starts the follow-up run, `dirty_trigger` stays set on the row and the next start of any trigger runs and clears it, so the owed run is late but never lost. The freshness check of D19 also closes, as `FAILED` with `interrupted`, a `RUNNING` row whose connector lock is free, so the history and the 409 of the manual trigger never point at a run of a dead instance. The manual trigger keeps its 409 while a run is in progress, because an administrator asking for a run now should learn that one is already running.

### D23: Error bodies are RFC 7807 problem details

Every error of the connector API is the problem detail of `upgrade-spring-boot-4` D19: media type `application/problem+json`, `type` `https://ascend.ai/errors/<code with - for _>`, `title`, `status`, `detail`, `instance` and the top level extension field `code` from `ApiErrorCode`. The codes:

- 400 `validation` for a refused configuration: a maximum sync age not greater than the schedule interval (the `detail` names both values), a cron that `CronRule` refuses or that does not have five fields, an unknown time zone, a cron for a type whose schedule comes from a system task, a missing credential for a type that needs one, and an unknown connector type or one whose module is off. A bean validation failure carries the `errors` field of D19 point 5.
- 401 `unauthorized` and 403 `forbidden` from the filter chain rule, the 403 written by the `AccessDeniedHandler` that `add-keycloak-login` adds to `SecurityConfig` (owner answer 76.9 of 2026-10-08).
- 404 `not_found` for an unknown connector or run id, or one of another tenant.
- 409 `connector_run_in_progress` for a manual trigger while a run is in progress. This change adds that one value to `ApiErrorCode` and reuses the existing codes for every other case.
- 503 `unavailable` (the shared code of `add-agent-skills`) for a create or update that carries a credential while no `CONNECTOR_CREDENTIALS_KEY` is configured (D24).

The `ADMIN` rule is this change's row in the authorization matrix of `add-keycloak-login` (its D4): `/api/v1/connectors/**` needs `ADMIN`. That matrix leaves every path it does not name at merely authenticated, and its coverage test fails the build for a mapping with no row, so the row is part of this change. A connector row holds a credentials reference and a source scope, so an authenticated non-administrator reaching that surface is a credential-adjacent exposure and not only a tidiness question.

### D24: Credentials sit behind a port with an encrypted store of the framework's own

The `connector` row stores an opaque credentials reference. The secret material lives behind the port `ConnectorCredentialStore` (`String put(String tenantId, char[] secret)`, `char[] resolve(String tenantId, String reference)`, `void delete(String tenantId, String reference)`). The framework ships one implementation, registered with `@ConditionalOnMissingBean`: the table `connector_credential` of D3, AES-256-GCM with a fresh nonce per write, the key read from `CONNECTOR_CREDENTIALS_KEY` (32 bytes, base64), and the key version on each row so a later key rotation can re-encrypt row by row. A write while no key is configured is refused (D23), so a deployment with only connector types that need no credential, such as the personal Obsidian vault, runs without the key. A resolve whose tenant does not match the row is refused as not found.

API responses never echo secrets (write-only field). Logs and sync-run records carry the reference only. Rotating a secret is an update through the store with no connector-table change. A connector type that declares it needs no credential (D21) has an empty credentials reference, and the framework resolves nothing for it. Deleting a connector deletes its stored credential.

The default store is the agent's one encrypted secret store (owner answer 89.9 of 2026-10-08). It treats a secret as opaque characters owned by a tenant, so it also holds a second kind of secret: the BYOK provider keys of `add-usage-metering-and-quotas` (company, build group 5), which that change writes, resolves and deletes through this port with the same `CONNECTOR_CREDENTIALS_KEY` and references from its own `tenant_provider_key` rows by the opaque handle. That change registers no store of its own and edits nothing here, so this default is the only `ConnectorCredentialStore` bean in every deployment. Tenant erasure, which deletes every `connector_credential` row of the tenant, therefore also removes the tenant's provider keys. This change does not wait for that change.

### D25: The tenant of a connector and the prefix of a landed object

A connector's tenant is taken from `TenantContext.currentTenantId()` of `add-keycloak-login` (its D3) when it is created, and stored on the row. Every run, also one that starts without a request (a `connector-sync` firing, an `EVENT` trigger, a system task of a connector type, a follow-up run), binds the tenant on the row with `TenantContext.runAs(tenantId, action)` of the same change for the whole run, so code inside the run that reads `TenantContext.currentTenantId()` sees the connector's tenant, and a read with nothing bound fails closed. `TenantContext` answers `default` in the personal deployment, so every connector is in tenant `default` there. `add-auth-and-identity` (company, build group 5) changes which tenant a resolved identity carries later, with no edit here. All connector reads and writes filter on the caller's tenant from the start, so nothing changes in this change's code when several tenants appear.

The object key prefix comes from the port `TenantPrefixResolver` (`String prefixFor(String tenantId)`, settled on 2026-10-01 as open question 2). The default implementation, registered with `@ConditionalOnMissingBean`, answers the empty prefix, so a landed object sits at today's key layout (`markdown/...` and `documents/...`), the layout an upload uses before `add-tenant-isolation`. That change registers its implementation answering `tenant/{tenantId}/`, the layout of its decision 5, and the default bean then does not exist. The framework never builds a tenant segment itself, so there is one place that knows the key layout.

## Risks / Trade-offs

- [A connector stops syncing silently and the corpus answers from content that is weeks stale, including documents deleted at the source]: the freshness check in D19 marks the connector stale, surfaces the flag on the read and list endpoints, and reports seconds since last successful sync as a gauge. It changes no document, so the cost of a false positive is a flag rather than an outage.
- [Freshness check marks a healthy connector stale because the maximum sync age was configured below the connector's cron interval]: the framework refuses that configuration at write time, and the message names both values.
- [Deletion propagation ordering, file deleted and re-added between syncs]: the orchestrator processes entries in the order the connector returns them per item id, so the last state wins. A connector type documents how its source orders a change feed.
- [Filename collisions, two source files sanitize to the same object key]: connector keys include a source-scoped path segment (sanitized relative path, not just the leaf name) under the tenant prefix. Collisions within one connector then require identical relative paths, which a source forbids.
- [Scheduler drift with multiple agent instances]: handled by `add-shared-scheduler`, which runs each `connector-sync` firing and each `connector-freshness-check` firing on exactly one agent instance. Its overdue gauge `scheduler.executions.overdue` is the signal for a scheduler that never fires after a deployment.
- [Secret leakage via logs or API echoes]: write-only credential fields, reference-only persistence, explicit test asserting no credential material appears in logs at any level during a sync (including failure paths).
- [The credentials key is lost]: every stored credential becomes unreadable and each affected connector fails its runs, which the freshness check surfaces. The operator sets a new key and enters each credential again. `docs/CONNECTORS.md` says the key belongs in the backup next to the database.
- [The connector endpoints are reachable by any authenticated caller]: the matrix row of D23 requires `ADMIN`, with a test asserting 401 unauthenticated and 403 for `USER` on every endpoint including the sync trigger, and the coverage test of `add-keycloak-login` fails the build if the row is missing.
- [Sibling-change coupling]: the framework needs `upgrade-spring-boot-4`, `add-keycloak-login`, `add-deployment-modules`, `add-shared-scheduler`, `add-document-management-api` and `add-agent-skills`, which land before it. It needs no company change, and `tasks.md` states which tasks use what.

## Migration Plan

The owner decided on 2026-10-02 (confirmed by owner answer 73.1 of 2026-10-06) that there is no existing data to keep, so this plan has no backfill, no copy step and no rollback script that restores data. This holds only until the first real customer deployment.

1. One Flyway migration creates the five tables in their final form and adds the nullable column `connector_id` with the index `idx_documents_connector_id` to the `documents` table of `add-document-management-api` (answer 93), a column add with no default, so no existing row is rewritten. Flyway runs forward only, and there is no manual rollback script.
2. The framework ships with no connector type and no connector rows, so default behaviour is byte-identical to today until a type change lands and an `ADMIN` creates a connector.
3. Disabling a connector stops scheduling immediately, because its `connector-sync` execution is removed in the same transaction. Its already-landed documents stay retrievable. The connector itself is marked stale once it passes its maximum sync age, which is the intended signal.
4. Deleting a connector removes its configuration, cursors, stored credential and run history but leaves already-ingested documents in place (removal is an explicit document-management operation, not a side effect of connector deletion).
5. Rollback: disable connectors, which removes their `connector-sync` executions, then revert code. The tables stay and are inert, or a later forward migration drops them if the change is abandoned.
