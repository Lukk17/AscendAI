## Why

The agent can already write skills, subagent definitions, user facts and semantic memories, but nothing decides when it should, nothing checks that a change made it better, and nobody is told what changed. The owner wants the assistant to improve itself over time like Hermes Agent: remember, write skills for future use, change itself without asking, and afterwards tell the owner what it changed, why, and how to undo it (owner direction of 2026-10-02).

## What Changes

- Four review triggers: a finished multi step task, a correction by the owner, an error that the agent solved, and a periodic review job. The model flags a lesson with a new `request_self_review` tool, the way the Hermes prompt tells its agent to use `skill_manage`, and code detects many tool steps and a tool error followed by success. Triggers of one conversation are merged into one review that starts after the conversation is quiet.
- The review runs in the background as a run of the kind `self_review` that `add-agent-subagents` owns, on its run table and tool loop, with fixed instructions, a cheap model, count limits and no tool that reads outside content.
- The review never sees raw tool output, retrieved documents or attachments. Its input is evidence captured when the request ends: the user's typed text, the assistant's answers, the tool names with their arguments and ok or error, and the lesson the model flagged.
- What the agent changes alone: skills it wrote, subagent definitions it wrote, semantic memories and user facts of the user in the conversation. What it only proposes: the personality file, through `personality_propose` and the shared approval service. What it never changes: shipped skills, skills and definitions of the owner, the review instructions, policy, limits and approval rules. The `self_review` run is the one documented exception to the rule of `add-agent-soul` that `user_facts_update` and `personality_propose` are never offered to background runs.
- Targeted patches: new tools `skill_patch` and `subagent_definition_patch` replace exactly one text with another, so an existing skill is never rewritten whole by the review.
- A regression guard: every self-written skill and definition has two or three test prompts, the first one replayed from the conversation that taught the lesson. A change from a review is checked before it is kept. A change written during a chat goes live at once, as `add-agent-skills` decided, is checked right after, and is reverted automatically when it makes a test fail that passed before.
- A content scan refuses self-written skill and definition text with invisible characters, the prompt's reserved markers, a web address the user never wrote, or long encoded blobs.
- Protection against prompt injection: every trigger stores the `RequestProvenance` value (`clean`, `retrieved` or `untrusted`) and the `ProvenanceSource` set that `add-agent-soul` computes for each request (its D15), and this change uses that value directly, with no provenance code and no mapping of its own. The results of finished background runs make a request `untrusted`, and `skill_patch`, `subagent_definition_patch` and `request_self_review` are trusted tools in the closed list of `add-agent-soul` (owner decision 49.3 of 2026-10-03). Changes from a review apply live and are marked and reported when the source was not clean. A skill or definition write made during a chat right after outside content was read in the same request is held for one tap of approval, as approval kind `self_change` (owner answer 38.1).
- The change report: every change becomes a record with what, why, the trigger and its conversation, the guard result and an undo command and button. Every report is created and sent at once, when the change happens, with no daily digest, because the app may not run at a fixed hour (owner answer 38.2). Each report is an owner notification of `add-shared-scheduler`: stored, readable through `GET /api/v1/notifications`, and delivered and retried through its `OwnerNotificationChannel` port, on Discord once the plugin host implements that port.
- Undo with one call or one button for every change, through one in process method `SelfImprovementService.undo(changeId, identity, channel)` that REST and the Discord Undo button of the plugin host both call, with a refusal that names newer changes when the item changed again.
- Integration events of `add-self-built-integrations` (registered, activated, updated, disabled by the model, disabled automatically) become change records with their undo (disable, roll back or enable). A review never gets an integration tool and never starts a build.
- Count limits per tenant and day, the day counted in `Europe/Warsaw` (the owner's zone): reviews and applied changes, plus size limits on patches and new skills, a cap on self-written skills, and a freeze of an item the guard reverted twice. There is no dollar limit (owner answer 38.3). Cost is measured and shown, never used as a limit.
- Timed work on the shared scheduler of `add-shared-scheduler`, with no scheduler of its own: each delayed review is one execution, system tasks run the daily review of conversations skipped for limits and the retry of waiting checks, by default in `Europe/Warsaw`, and retention is two entries of the one retention task of `add-shared-scheduler` (answer 89.7 of 2026-10-08).
- The whole feature is the module `self-improvement` of `add-deployment-modules`. There is no `app.self-improvement.enabled` flag.
- Audit actions through `AuditEventPort` of `add-deployment-modules`, tenant scoping through `TenantContext` of `add-keycloak-login` (scheduler threads bind the row's tenant with `TenantContext.runAs`), metrics for skills written, reverted and used afterwards, and log lines. Erasure and export of the four tables are added by `add-audit-and-gdpr-compliance` (company) later.
