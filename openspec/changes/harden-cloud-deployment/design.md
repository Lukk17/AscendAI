# Design - Harden Cloud Deployment

## Context

The stack was built for one developer's Windows workstation. The target is one VM per external customer, running the same compose stack, reachable from outside only through TLS on ports 80 and 443.

Hard constraint from the owner: `compose.yaml` is the single compose entry point. It pulls in `compose.ascend-web-hunter.yaml` through `include:`, and every compose command runs against the main file with no `-f` flag. Local `docker compose up` from the repo root must keep working.

Build order: build group 3, position 4 of the owner build order of 2026-10-04, as changed by owner answer 72.1 of 2026-10-06. This change was never started, so it left build group 1 and lands directly after `add-keycloak-login` (build group 3, position 3). It needs `add-observability` (build group 1, position 1), `fix-linux-docker-host-access` (build group 1, position 4, the `ascend-audio-scribe` `extra_hosts` line and volumes), `add-ascend-python-common` (build group 2, position 1, the `ALLOWED_PRIVATE_HOSTS` name), `upgrade-spring-boot-4` (build group 3, position 2) and `add-keycloak-login`. When it starts, the agent already validates Keycloak tokens, `app.security.*` and the HTTP Basic user are gone, the `keycloak` service runs on host port 8180 with its production start mode, and the production guard of `add-keycloak-login` D21 refuses a public start without an issuer or `SERVICE_AUTH_TOKEN`. This change owns the network, TLS, secrets transport, container hardening and the datastore credential check of D3, and writes no authentication code. It adds the Keycloak site block and the login and token rate limits to the `gateway/Caddyfile` it creates (former tasks 1.6 gateway part and 1.7 of `add-keycloak-login`). Keycloak is a separate service on its own host address and port and is never routed under a path of the agent's site. Every later change that plugs into a file of this change adds its own part when it lands (proposal, Build order, dependency fix of 2026-10-05). The build group 2 changes edit both compose files first (`remove-flaresolverr-tier` removes `flaresolverr`, `add-file-download` adds `clamav` under its profile), so the compose line numbers in this change are re-checked when it starts.

The four data stores (Postgres, Redis, Qdrant, the S3-compatible object store, which is Floci on host port 9070 locally) are external prerequisites. `compose.yaml` does not define them. Locally they come from the owner's separate local-dev stack. In the cloud they are either containers of a separate stack on the same VM or managed services.

## Goals / Non-Goals

Goals:

- Only ports 80 and 443 reachable from outside a cloud VM.
- TLS at one gateway, ACME in the cloud, internal certificate locally.
- No credential in the tree that a production deployment accepts. Startup fails under the `production` profile when a development default is still in use.
- The object store is never public.
- Personal-machine artifacts are opt-in.
- SSRF allowlists without a loopback default.
- `docker compose up` from a fresh clone still gives a working local stack.
- An operator guide in `docs/DEPLOYMENT.md`.

Non-Goals:

- New authentication and Keycloak itself (`add-keycloak-login`, which lands before this change), and tenant isolation, metering and audit (company changes of build group 5).
- Kubernetes, Terraform, orchestration beyond compose on a VM. Company plans a scaled deployment later in `plan-scaled-deployment` (build group 5, a Kubernetes Helm chart with a Horizontal Pod Autoscaler, owner answer 99.1 of 2026-10-08), and this change does not wait for it.
- Running the four data stores as services of `compose.yaml`.
- Several tenants on one VM.

## Decisions

### D1 - One file, bind address from the environment, profiles for optional services

Every published port except the gateway's becomes `"${EXPOSE_BIND:-127.0.0.1}:${<SERVICE>_HOST_PORT:-<host>}:<container>"`: the bind address is this change's setting `EXPOSE_BIND`, and the host port is the setting the change that owns the service already made (owner answer 100.6 of 2026-10-09), which this change keeps. That covers, in `compose.yaml`: docling-serve `5001`, unstructured-api `9080`, ascend-ocr `7022`, ascend-agent `9917`, ascend-memory `7020`, ascend-weather-mcp `9998`, ascend-audio-scribe `7017`, prometheus `7077`, grafana `7078`. keycloak `8180` (added by `add-keycloak-login`). In `compose.ascend-web-hunter.yaml`: searxng `9020` (today a literal `127.0.0.1:` prefix) and the web-hunter edge proxy `ascend-web-hunter-edge` `7021` (the `ascend-web-hunter` service itself publishes no port since `scale-web-hunter-across-containers`, build group 2, position 11, owner answer 96 of 2026-10-08). `flaresolverr` no longer exists, because `remove-flaresolverr-tier` (build group 2) removed it. The bundled `redis` service publishes nothing and stays that way. loki, otel-collector, tempo and container-metrics-exporter publish nothing and stay that way (`vector` no longer exists, owner answer 89.12 of 2026-10-08). They talk only over the compose network.

Services of later changes follow the same rule when they land: a later change that publishes a port uses `${EXPOSE_BIND:-127.0.0.1}`, and a service that needs no host access publishes none.

`ngrok-ascend-web-hunter` keeps starting by default while this change lands. `add-deployment-modules` (build group 3) later puts it behind the profile `captcha-intervention`, a companion of the deployment module `web-search` (former task 1.5, dependency fix of 2026-10-05).

Rejected: a second production compose file used with `-f` (breaks the single entry point and creates container name conflicts), an auto-loaded override file (a fresh clone would get the hardened stack and local dev would need a copy step), profiles for exposure (profiles gate whole services, not ports).

### D2 - Gateway: Caddy and the agent

Caddy 2, image pinned by version and digest like every other pulled image. Only service publishing on all interfaces, its container ports 80 and 443 on the host ports `${GATEWAY_HTTP_HOST_PORT:-80}` and `${GATEWAY_HTTPS_HOST_PORT:-443}` (owner answer 100.6 of 2026-10-09). It carries no compose profile and runs in every deployment.

- Site address `{$ASCEND_DOMAIN:localhost}`. A real domain gets ACME certificates. `localhost` gets Caddy's internal CA.
- The agent's site. Its one upstream is `reverse_proxy ascend-agent:9917`. No Grafana route, no object store route, no route to the agent's management port `9918`, and no Keycloak path under this site.
- The Keycloak site. A second site address with Keycloak's own host name (for example `auth.{$ASCEND_DOMAIN}`), whose one upstream is `reverse_proxy keycloak:8080`, matching the `KC_HOSTNAME` of the production start mode of `add-keycloak-login`. It carries a per-client-address rate limit on `/realms/ascend-ai/login-actions/authenticate` and `/realms/ascend-ai/protocol/openid-connect/token`, answering 429 over the limit, with the limit values read from the gateway's environment, `{$KEYCLOAK_LOGIN_RATE_LIMIT_EVENTS:10}` and `{$KEYCLOAK_LOGIN_RATE_LIMIT_WINDOW:1m}`, 10 events per 1 minute per client address by default (owner answer 102.2 of 2026-10-09), which the `gateway` service passes as `${VAR:-default}` with the same defaults (owner rule 98 of 2026-10-08, task 2.6). The stock Caddy image has no rate limit directive, so the gateway image is Caddy built with `xcaddy` and the rate limit module `github.com/mholt/caddy-ratelimit` (checked on 2026-10-06), pinned by version and digest like every other image, and the module version is recorded in this design when the task is done. The agent serves its actuator endpoints only on `9918` (`add-observability` D4, owner decision 65.6 of 2026-10-04), so `/actuator/*` through the gateway answers 404, and the agent's health is its container healthcheck on `http://localhost:9918/actuator/health`.
- The NoVNC site (owner answers 95.1 and 96 of 2026-10-08, task 2.7). A third site address with its own host name (for example `novnc.{$ASCEND_DOMAIN}`), never a path under the agent's site. It forwards every request under `/novnc/` unchanged, WebSocket upgrades passed through, to `ascend-web-hunter-edge:7900`, the NoVNC listener of the web-hunter edge proxy that `scale-web-hunter-across-containers` (build group 2, position 11, its D2 and D9) adds, and answers 404 for every other path. The edge proxy routes `/novnc/{name}/*` to `http://{name}:7900` with the prefix removed, so a human reaches the NoVNC display of the ascend-web-hunter copy whose host name is `{name}`, and it accepts only ascend-web-hunter host names: `ascend-web-hunter`, or the 12 lowercase hexadecimal characters of a copy's short container ID, which Docker gives as host name to a copy without a fixed `hostname` and which the compose network resolves. Every other name answers 404 there, and the upstream port is fixed to 7900, where only ascend-web-hunter serves NoVNC. The name rule therefore lives once, in the edge proxy, and this gateway adds only TLS and the site's host name. `NOVNC_PUBLIC_URL` of `open-several-novnc-windows-at-once` (Decision 11) is the address of this site, one value shared by every ascend-web-hunter copy, and each copy builds its `vnc_url` from it and its own host name. The owner answer named port 6080, and the route uses 7900 because the NoVNC server of the image listens there (`apps/ascend-web-hunter/supervisord.conf` line 21). Neither ascend-web-hunter nor its edge proxy publishes a NoVNC port, and ascend-web-hunter scales as one compose service. The gateway has no login of its own (the agent checks the Keycloak token itself), so the site carries the gateway's TLS and no other rule, and the VNC password of each display stays the check a human passes.
- Caddy sets `X-Forwarded-For` and `X-Forwarded-Proto` by default.
- No rate limiting on the agent's site in this change.
- One gateway runs per deployment, in front of every agent instance, so the per-client-address counters of the Keycloak site are counted in that one gateway even when several agent instances run (owner answer 87 of 2026-10-08). If a deployment ever runs more than one gateway, the counters must be shared between them, and task 2.6 records from the module's documentation how it shares them.
- Later changes add their own parts to `gateway/Caddyfile` when they land (dependency fix of 2026-10-05): `add-chat-streaming-and-conversations` the unbuffered route for `POST /api/v1/ai/prompt/stream`, and `add-openclaw-plugin-host` the channel webhook routes `/hooks/<platform>/*` and the 404 for `/api/v1/channel-host/*`.

Rejected: Traefik (label sprawl for a small set of routes), nginx (needs a certbot sidecar).

### D3 - Secrets: `.env` interpolation, production startup checks

- `GRAFANA_ADMIN_PASSWORD` uses `${GRAFANA_ADMIN_PASSWORD:?GRAFANA_ADMIN_PASSWORD must be set in .env}`. `SEARXNG_SECRET` already uses this form. Grafana runs in every deployment, so every deployment sets both.
- Development defaults stay legitimate locally: Postgres user and password, Redis password (empty), Qdrant API key (empty), object store access and secret key, ascend-ocr result store keys. The built-in login of `SecurityConfig` no longer exists, because `add-keycloak-login` deleted `app.security.*` before this change starts. In `application.yaml` these use `${VAR:devdefault}`. In compose they are passed through as `${VAR:-devdefault}` or `${VAR:-}`.
- The datastore credentials join the one production startup guard of `add-keycloak-login` D21 (owner answer 89.10 of 2026-10-08). This change adds no guard class of its own. It extends the guard in its two parts. First, `application-production.yaml` of `add-keycloak-login` gains required placeholders, with no default, for `app.s3.access-key` (`S3_ACCESS_KEY`), `app.s3.secret-key` (`S3_SECRET_KEY`), `spring.datasource.username` (`POSTGRES_USER`), `spring.datasource.password` (`POSTGRES_PASSWORD`), `spring.data.redis.password` (`REDIS_PASSWORD`) and `spring.ai.vectorstore.qdrant.api-key` (`QDRANT_API_KEY`), so under the `production` profile an unset variable stops start-up with Spring's own error naming it, and the development defaults of `application.yaml` never apply there. Second, one `ProductionStartupCheck` bean, `DatastoreCredentialCheck`, refuses a value a placeholder cannot catch: a blank value, or a value on its own list of known weak values, which holds every development default of today (`admin`, `password`, `local`, and blank for the Redis password and the Qdrant key). The refusal names the property and never prints its value, through the guard's one `FailureAnalyzer`, so the start-up log holds one ERROR entry with no stack trace and the process exits non-zero. There is no test that copies the defaults of `application.yaml`: the placeholders already keep those defaults out of a production start, and the weak value check is tested by its own cases. The earlier `ProductionCredentialGuard`, its copied-defaults drift test and the two throwaway agent containers of the former task 11.6 are removed (owner answers 89.10 and 91.3 of 2026-10-08).
- No login check is added here (owner answer 72.1 of 2026-10-06). The production login checks are part of the one guard of D21 of `add-keycloak-login`, which lands before this change and refuses a `production` start when the `dev` profile is active, when no issuer is configured or when `SERVICE_AUTH_TOKEN` is blank. The deployment guide of this change names that guard in its production checklist. The earlier interim `ProductionSecurityGuard` (refusing `app.security.enabled` false) and the login password entry of `ProductionCredentialGuard` are removed.
- A public deployment never runs with the HTTP Basic user of today, because this change lands after `add-keycloak-login` (owner answer 72.1 of 2026-10-06).
- Secrets of later changes come from `.env` the same way, and each later change adds its own `.env.example` lines and compose guards when it lands: `SANDBOX_RUNNER_TOKEN` (`add-agent-sandbox`), `GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY` and `OPENCODE_API_KEY` (`add-coding-agent-delegation`), and the integration secrets file `integration-secrets.env` (`add-self-built-integrations`), which never goes into `.env`. `SERVICE_AUTH_TOKEN` and the Keycloak issuer of `add-keycloak-login` are already in `.env.example` and the agent environment when this change starts. `DatastoreCredentialCheck` covers only the datastore credentials above. A later change that needs a production start-up refusal adds a placeholder or a `ProductionStartupCheck` bean to the same guard.
- Rejected: Docker secrets (needs file plumbing in every service, the Python services read environment variables), Vault or SOPS (not needed for one VM per customer).

### D4 - Personal mounts

- ascend-audio-scribe volumes become `"${HF_CACHE_ROOT:-hf-cache}:/hf-cache"` and `"${ASCEND_AUDIO_SCRIBE_MEDIA_ROOT:-ascend-audio-scribe-media}:/audio"`, with both named volumes declared. A value with no path is a named volume, a path is a bind mount, so the owner restores today's behavior with two `.env` lines. `fix-linux-docker-host-access` (build group 1, position 4) makes this edit and writes both `.env.example` lines before this change starts, because the Windows host paths break the stack on Linux Docker Engine (owner answer 83 of 2026-10-08, former task 4.1).
- `MCP_FILE_URI_ROOT` becomes `${ASCEND_AUDIO_SCRIBE_FILE_URI_ROOT:-}`. Empty means `file://` is disabled, which is the existing contract of ascend-audio-scribe.

### D5 - Drop `SYS_ADMIN` from ascend-web-hunter

Chromium's sandbox needs `clone`, `unshare` and `setns` with namespace flags that the default Docker seccomp profile blocks. `SYS_ADMIN` allows far more. Replace it with `security_opt: ["seccomp=./security/chromium-seccomp.json", "no-new-privileges:true"]` and `init: true`. `shm_size: 2gb` stays. The profile is the Docker default profile plus the namespace calls, checked in at `security/chromium-seccomp.json`. The path is relative to `compose.ascend-web-hunter.yaml`, which sits at the repo root next to `security/`.

Rejected: `--no-sandbox` (removes the layer that matters for untrusted content), AppArmor (not on every host).

### D6 - SearXNG limiter stays off

Owner decision, confirmed 2026-10-01: the limiter stays off, and no change in `openspec/changes/` turns it on.

`infra/searxng/settings.yml:37-41` turns the limiter off on purpose: every caller reaches SearXNG from the ascend-web-hunter container, so all requests share one Docker network address and the per-address limiter blocks them together. The earlier plan of this change was to turn the limiter on and forward the client's `X-Forwarded-For`. That does not answer the reason: ascend-web-hunter is called by the agent over MCP, not by end users, so the forwarded address would still be the same for every request. The change therefore keeps `limiter: false` and keeps the `SEARXNG_X_REAL_IP` and `SEARXNG_X_FORWARDED_FOR` values ascend-web-hunter sends (`compose.ascend-web-hunter.yaml:190-191`). Protection comes from the network: SearXNG is reachable only on the compose network and on host loopback, and ascend-web-hunter rate-limits upstream. `infra/searxng/settings.yml` and its byte-identical copy `apps/ascend-web-hunter/deploy-standalone/searxng/settings.yml` are not changed.

### D7 - SSRF allowlists and object store privacy

- `ALLOWED_PRIVATE_HOSTS` on ascend-ocr and ascend-audio-scribe becomes `${ALLOWED_PRIVATE_HOSTS:-}`. Empty is the strict block that both services already implement. There is no object store host on the compose network, so no in-network name can be a useful default. `add-ascend-python-common` (build group 2) renamed the setting from `MCP_ALLOWED_HOSTS` before this change starts, and every Python service refuses to start while the old name is set (owner answers 68.2 of 2026-10-04 and 72.3 of 2026-10-06), so this change writes only the new name.
- Local development sets `ALLOWED_PRIVATE_HOSTS=host.docker.internal` in `.env`, because Floci listens on host port 9070. `.env.example` shows this line. `ascend-ocr` already declares `extra_hosts: ["host.docker.internal:host-gateway"]`, and `ascend-audio-scribe` gets the same line from `fix-linux-docker-host-access` (build group 1, position 4, owner answer 83 of 2026-10-08), because on Linux Docker Engine the name does not resolve without it (`close-agent-test-gaps` D8, rule 3). On Linux the call arrives at the host's address on the default bridge network, so it reaches Floci only while the local object store publishes port 9070 on an address other than `127.0.0.1` alone. That publication belongs to the other repository's compose project and is not changed here.
- In the cloud the operator sets the object store's private host name, and nothing else.
- Object store addresses come from the environment:
  - agent: `app.s3.endpoint` from `S3_ENDPOINT`, `app.s3.public-endpoint` from `S3_PUBLIC_ENDPOINT` (defaults keep today's values: `http://localhost:9070` in `application.yaml`, `http://host.docker.internal:9070` and `http://localhost:9070` in `application-docker.yaml`).
  - ascend-ocr: `OCR_RESULT_S3_ENDPOINT=${OCR_RESULT_S3_ENDPOINT:-http://host.docker.internal:9070}` and `OCR_RESULT_S3_PUBLIC_ENDPOINT=${OCR_RESULT_S3_PUBLIC_ENDPOINT:-http://localhost:9070}`.
- The object store is never public. In production both public endpoint variables are set to the same private address as the endpoint, because only containers on the private network follow those presigned links: the agent reads ascend-ocr results in-network. The gateway has no route to the object store. A presigned link handed to a public client would not resolve, which is the intended result. `add-document-management-api` (build group 3) later gives public clients `GET /api/v1/documents/{id}/content` for RAG sources.

### D8 - Observability exposure and hardening

Monitoring is core and always on (owner answer 52 of 2026-10-03, `add-observability` D7): no observability service carries a compose profile, so the rules below apply in every deployment.

- Grafana: `GF_AUTH_ANONYMOUS_ENABLED=false`, `GF_AUTH_ANONYMOUS_ORG_ROLE` removed, `GF_SECURITY_ADMIN_USER=${GRAFANA_ADMIN_USER:-admin}`, `GF_SECURITY_ADMIN_PASSWORD` required. Loopback-bound, reached on a VM through an SSH tunnel.
- Prometheus: loopback-bound, `--web.enable-lifecycle` removed.
- loki, otel-collector, tempo, container-metrics-exporter: no published port. otel-collector and container-metrics-exporter keep the read-only Docker socket mount they need (D10), and otel-collector also mounts `/var/lib/docker/containers` read-only to read the container logs (owner answer 89.12 of 2026-10-08), and every observability service gets `security_opt: ["no-new-privileges:true"]`, the logging anchor and a healthcheck.

### D9 - Runtime posture

- `compose.yaml` gets its own `x-logging: &default-logging` anchor (json-file, `max-size: "10m"`, `max-file: "3"`), the same values as `compose.ascend-web-hunter.yaml:6-10`, and every service in `compose.yaml` uses it. Anchors do not cross `include:`, so the two files each keep one. Both values are settings, `${DOCKER_LOG_MAX_SIZE:-10m}` and `${DOCKER_LOG_MAX_FILE:-3}`, in all three anchors, the two development files and the standalone bundle (owner rule 98 of 2026-10-08, tasks 1.4 and 1.7).
- Healthchecks added to docling-serve, unstructured-api, ascend-weather-mcp, prometheus, grafana, loki, otel-collector, tempo and gateway. Each check uses a tool that exists in that image. The implementer confirms with `docker run --rm --entrypoint sh <image> -c "command -v wget curl"` and falls back to the service's own binary or a Python one-liner when neither exists.
- ascend-agent `depends_on` becomes long form with `condition: service_healthy` on ascend-memory, docling-serve and unstructured-api, and keeps the `keycloak` entry with `condition: service_healthy` that `add-keycloak-login` added. `add-deployment-modules` (build group 3) later adds `required: false` on every `depends_on` entry for a service under a module profile and passes `ASCEND_MODULES` to the agent (former part of task 7.2, dependency fix of 2026-10-05).
- `security_opt: ["no-new-privileges:true"]` on every service that lacks it.
- Every pulled image is already pinned by version and digest (ngrok uses tag `3` plus a digest, which pins it). The gateway image follows the same form.

### D10 - The Docker socket

The agent never gets the Docker socket. Only the observability services otel-collector and container-metrics-exporter mount it, read-only, to find the containers whose logs the collector reads and to read container statistics (D8, owner answer 89.12 of 2026-10-08, which removed `vector`).

A read-only socket mount (`:ro`) is not a restriction. It only stops writes to the socket file, while the Docker API behind it still accepts every call, so a service that mounts the socket read-only can still start containers. The rule is therefore about which services mount the socket at all, never about the mount mode. `add-agent-sandbox` (build group 4) later adds `ascend-sandbox-runner` as the one service allowed to mount it for sandbox work, under the other rules of this change (`no-new-privileges`, no published port, its token from `.env`, the logging anchor). `add-mcp-tool-servers` keeps MCP servers off the socket for the same reason.

### D11 - Host steps of later changes in the deployment guide

The cloud VM section of `docs/DEPLOYMENT.md` ("one cloud VM per customer") is written so later changes can add their host steps to it. Each later change adds its own step when it lands (former tasks 10.4 to 10.6, dependency fix of 2026-10-05): `add-agent-sandbox` the gVisor (`runsc`) install and `DOCKER_SOCKET_GID`, `add-coding-agent-delegation` the coding project area partition and the GitHub App setup, and `add-self-built-integrations` the sizing of integration containers, the `integrations-ingress` network and `integration-secrets.env`.

## Risks / Trade-offs

- Loopback ports still exist on the VM, so any process on the VM can reach them. Acceptable with one customer per VM. Documented in the guide.
- Chromium updates may need new system calls. The ascend-web-hunter Playwright tests are the check, and the profile is one file in the repo.
- The required Grafana password adds one `.env` line for local development. `.env.example` shows it.
- Caddy's internal CA causes a browser warning locally. Local work can keep using `http://localhost:<port>`.
- The weak value list of `DatastoreCredentialCheck` names today's development defaults. A development default changed later is refused in production only once it is added to that list, so the change that changes a default also adds it there. An unset value is always refused by its placeholder.
- The SearXNG limiter stays off. If SearXNG is ever exposed beyond loopback this decision must be revisited.

## Migration Plan

1. Land the compose and configuration changes. Developers add `GRAFANA_ADMIN_PASSWORD`, `ALLOWED_PRIVATE_HOSTS=host.docker.internal` and, for the owner, the two media lines to `.env`, then run `docker compose up -d`.
2. A cloud deployment follows the new `docs/DEPLOYMENT.md` section: DNS record, `.env` with real values (`KEYCLOAK_ISSUER_URI` and a non-default `SERVICE_AUTH_TOKEN` among them, which the D21 guard of `add-keycloak-login` checks), `docker compose up -d`, external port scan shows only 80 and 443.
3. Rollback is `git revert`. No data migration exists in this change.
