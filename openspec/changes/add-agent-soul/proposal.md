## Why

The agent has no stable character. Its only standing text is the global `app.system-prompt`, which is the same for every tenant and is about grounding rules, plus a per-user "User Instructions" block from `UserInstructionService` that sits in the second system message and that nothing can write today (no endpoint or tool calls `updateInstructions`). There is no way for an owner to say once how the agent must always behave, and no guarantee that such text would survive a long conversation: nothing reserves room for it, history is sent until the provider refuses, and the provider's attention to the start of a long context fades. OpenClaw (`SOUL.md`, `USER.md`) and Hermes Agent (`SOUL.md` in slot 1, `USER.md` and `MEMORY.md` with hard character limits) show the pattern that works: a short personality file that always comes first, a separate small file of facts about the user, both plain Markdown the owner can read and edit.

## What Changes

- Each tenant gets one personality file, `SOUL.md`, which defines how the agent must always behave: persona, tone, rules and boundaries. The owner writes its content himself. A minimal placeholder seeds it on first start.
- The personality file is always the first system message of every chat request. Its space is reserved before anything else is assembled, it is never trimmed, never summarised and never written into chat history.
- A short fixed reminder, written by this change, tells the model to read and follow the personality file again. It sits at the end of every prompt, right before the user's own typed text. Retrieved document context and attached document text move before the reminder, so the reminder and the user's words come last, and a task measures answer quality before and after this move. The reminder is part of the user message, not a system message, so it never moves the prompt cache breakpoint and is never stored in history.
- Each user gets one user facts file, `USER.md`, with stable facts and preferences about that user. It replaces `UserInstructionService` and the `user_instructions` table, which a Flyway migration of this change drops with no copy of its rows.
- A new context budget makes "reserved first" real: per request it reserves the personality file, the global system prompt, the reminder, the user's own text, the tool definitions and an output reserve, then fills what is left and trims in a fixed order (oldest history first, the user facts file last). A request whose protected parts alone do not fit is refused with HTTP 413 before any provider call.
- The prompt always has exactly three system messages in a fixed order: personality file, global system prompt, then one dynamic block (user facts, semantic memory, conversation summary and other per-request blocks). The conversation summary that compaction writes moves from history into the dynamic block. This also fixes a defect found while planning: today, once a conversation is compacted, the summary is a fourth system message, Spring AI puts the Anthropic cache breakpoint on the second-to-last system block, which is then the dynamic block, and the cache never hits again for that conversation.
- Both files live on disk per tenant with git history through `VersionedFolder`, in the same agent home root and the same layout as skills and subagent definitions: the root is `app.agent-home` of `add-agent-skills`, and each tenant folder `<root>/tenants/<tenantId>/` holds the personality repository `soul/` and one repository per user `users/<userKey>/`, next to `skills/` and `.claude/agents/`. `userKey` is a hash, so erasing one user deletes one folder and never rewrites history. Neither the root nor a tenant folder is a git repository.
- One validated write path per file, used by chat tools and by REST endpoints: `/api/v1/personality` (read, replace, history, revert, and the read only proposal list and view) and `/api/v1/user-facts` (read, replace, delete, history, revert). Every accepted change is a git commit with its origin, and every change or proposal made during a chat request is reported in the response metadata, whether or not the model mentions it.
- The agent may add, change and remove entries in the user facts file on its own, with no approval. It may never change the personality file alone. Its `personality_propose` tool, offered only to an owner caller in a request whose request provenance is `clean`, hands a proposal with a before and after view to the shared `ApprovalService` of `add-action-approvals`, where it is one approval request of kind `personality_change` and stored nowhere else (owner answer 89.4 of 2026-10-08). The tool is offered once that change is applied. The owner approves it once through `/api/v1/approvals/{id}/approve`, from REST now and from the app and Discord later. Only then is the file changed. A denied approval marks the proposal `rejected` and a timed out approval marks it `expired`, and neither changes the file.
- Every chat request gets one request provenance value, `RequestProvenance`, computed once in the one chat executor `StreamingChatExecutor` of `add-chat-streaming-and-conversations` from the request: `clean`, `retrieved` when retrieved document context was added, or `untrusted` after an attachment, a turn written by a peer bot of `add-openclaw-plugin-host`, the result of a finished background run added by the finished runs block, or a tool whose result can carry outside content. It only moves towards `untrusted`. The two tools of this change read it (`personality_propose` needs `clean`, `user_facts_update` needs `clean` or `retrieved`), and `add-self-improvement` reuses the same value instead of computing its own.
- Runs of `add-agent-subagents`, of every kind, get the personality file as their first system message and the same reminder, because it holds the rules every model call acting for the tenant must follow. They never get the user facts file. No run is offered `personality_propose` or `user_facts_update`, with one documented exception: a `self_review` run of `add-self-improvement` may be offered both, and `personality_propose` there still only stores a proposal that waits for the owner.
- **BREAKING (internal)**: the "User Instructions" block disappears from the prompt, `UserInstructionService` with its Redis key `user:{userId}:instructions` is removed, and the `user_instructions` table is dropped in this change.

## Capabilities

### New Capabilities

- `agent-personality`: the per-tenant personality file, its storage and git history, the shipped placeholder, validation and size limit, its fixed first position, the end-of-prompt reminder, the owner write path through REST, the agent's proposals, stored only as approval requests of the shared approval service and read back through its port, and their `expired` status on timeout, the change report, subagent use, and the related metrics and logs.
- `agent-user-facts`: the per-user facts file, its storage in one repository per user, validation and size limits, its place in the dynamic block, the entry operations the agent uses, the REST endpoints, and the removal of `user_instructions`. Erasure and export of the files are company work of `add-audit-and-gdpr-compliance`.
- `chat-context-budget`: the per-request budget that reserves protected parts first, the fixed trim order, the refusal when protected parts do not fit, the shared context window table, the three-system-message layout, and the report of what was trimmed.

### Modified Capabilities

- `prompt-caching`: the static prefix becomes the tenant's personality file followed by the global system prompt, the prompt always carries exactly three system messages so the breakpoint stays on the global prompt, and the conversation summary is no longer a separate system message. Per-user content still never enters the cached prefix.
- `chat-history-compaction`: compaction never reads, summarises or replaces the personality file or the reminder, and its token trigger reads the context window from the shared table of the context budget.
