The runner talks to the Docker Engine through `/var/run/docker.sock`.
- Health endpoints: every Python service and the sandbox runner answer `GET /health` (no dependency touched) and `GET /ready` (dependencies), the agent serves its actuator only on the management port 9918 (`add-observability` D4), ascend-weather-mcp on 9998.

Facts checked through Context7 on 2026-10-09:

- Helm (`/helm/helm-www`, `docs/topics/charts.mdx`, "Schema Files"): a `values.schema.json` (JSON Schema) is applied to the final values on `helm install`, `helm upgrade`, `helm lint` and `helm template`, and to every subchart's schema too. `docs/chart_best_practices/dependencies.mdx`: an optional dependency is switched with `condition: <name>.enabled`. `docs/chart_template_guide/debugging.md`: `helm lint` checks the chart against best practices and `helm template --debug` renders it locally without a cluster.
- Kubernetes (`/websites/kubernetes_io`, "Horizontal Pod Autoscaling" and the walkthrough): `autoscaling/v2` scales on a `Resource` metric `cpu` with `target.type: Utilization` and `averageUtilization`, computed as a percentage of the containers' CPU request, so a container with no CPU request gives the autoscaler nothing to act on. The resource metrics API (Metrics Server) must run. The control loop runs every 15 seconds by default. Default behavior: scale up with no stabilization window, at most 4 pods or 100 percent every 15 seconds, scale down with a 300 second stabilization window.

## Goals / Non-Goals

Goals:

- One Helm chart that installs the whole platform on a Kubernetes cluster for a company, with the five busy services scaled by a Horizontal Pod Autoscaler.
- The same settings, defaults, secrets and health checks as the Compose stack, from one source: the configuration reference.
- Proof by `helm lint`, a schema check of the rendered manifests and one install on kind with a scale-up under load.

Non-Goals:

- Replacing Docker Compose. Compose stays for local work and for a single server (the bundle and the customer installer included).
- Tuning the dependency charts of D9 for production (high availability, backups, upgrades of the stores). They are off by default, because a company usually brings its own database, and the chart only switches them on and connects the services to them.
- A CI workflow for the chart (owner rule: no CI workflow unless asked).
- Autoscaling on custom metrics. The autoscaler uses CPU only.
- Changing any service, image or API.

## Decisions

### D1: One chart, one component per compose service

`deploy/helm/ascend-ai/` is one chart (`apiVersion: v2`, `type: application`). `values.yaml` has one block per component, named like its compose service (`ascendAgent`, `ascendWebHunter`, `ascendOcr`, `ascendAudioScribe`, `ascendMemory`, `ascendWeatherMcp`, `doclingServe`, `unstructuredApi`, `searxng`, `clamav`, `ascendSandboxRunner`, `mcpEgressProxy`, `ascendOpenclawHostChannels`, `ascendOpenclawHostApps`, `otelCollector`, `redisExporter`, `postgresExporter`, `novncRouter`), each with `enabled`, `image` (repository, tag and digest, the same pins as the compose files), `replicaCount` (default 1, the compose default of one copy), `resources` and `env`. A component of a switchable module (`add-deployment-modules`) is enabled when its module is in the value `modules`, which holds the same list as `ASCEND_MODULES` with the same default, so the chart and compose switch the same services. Core services (owner rule of 2026-10-03: chat, monitoring, RAG, memory, sandbox) are always enabled. Services that exist only for Docker Compose are not rendered: `gateway` (the Ingress takes its role, D5), `ascend-web-hunter-edge` for the API (D6), `ngrok-ascend-web-hunter` (NoVNC goes through the Ingress, D6), `container-metrics-exporter` (it reads the Docker socket for container metrics, and on Kubernetes the kubelet's cAdvisor endpoint gives the same series) and the e2e harness containers.

Workload kinds: `Deployment` for every component, except `ascend-web-hunter` (a `StatefulSet`, D6) and `ascend-sandbox-runner` (a `DaemonSet`, D7). Every component other than the five of D2 keeps the copy count of its compose service as `replicaCount` and gets no autoscaler, because owner answer 99.1 names only those five.

### D2: Autoscaling for the five busy services

`ascendAgent`, `ascendWebHunter`, `ascendOcr`, `ascendAudioScribe` and `ascendMemory` each render a `HorizontalPodAutoscaler` (`autoscaling/v2`) when `autoscaling.enabled` is true (default true for these five), on `Resource` `cpu` with `target.type: Utilization`. Values per component: `autoscaling.minReplicas`, `autoscaling.maxReplicas`, `autoscaling.targetCPUUtilizationPercentage`, and an optional `autoscaling.behavior` that is passed through unchanged (empty by default, so the Kubernetes default behavior of Context applies). The defaults are the same for each of the five (owner answer 103.2 of 2026-10-09): `minReplicas` 1, `maxReplicas` 5, `targetCPUUtilizationPercentage` 70. They are chart values set per install. A company customer has its own install, so these are per-customer values that the customer's values file changes, and the chart README says so. `values.schema.json` requires them as integers (`minReplicas` at least 1, `maxReplicas` at least `minReplicas`, the target between 1 and 100) whenever `autoscaling.enabled` is true, so a values file that sets one of them to an empty or wrong value is refused. The minimum of 1 is below the minimum of 2 that the `deployment-patterns` skill names for a production workload. The owner's answer decides it, and a customer that wants two copies at all times sets `minReplicas` 2 in its own values. When the autoscaler is on, the workload renders no `replicas` field, so `helm upgrade` never resets the count the autoscaler chose.

Every container of the five has a CPU and memory request and limit, because the autoscaler computes utilization from the CPU request. The defaults are the compose values of the same service: the request from `deploy.resources.reservations` and the limit from `deploy.resources.limits` (or `mem_limit` where compose uses it), read from the compose files at implementation time. A compose service with no reservation gets the limit as its request only for memory, and its CPU request defaults to `250m`, a chart value per component set per install like the autoscaler numbers (owner answer 103.2 of 2026-10-09).

The autoscaler needs the Metrics Server. The chart does not install it: it is a cluster prerequisite (D9), and the kind test installs it (D10).

Each of the five gets a `PodDisruptionBudget` with `maxUnavailable: 1` when its autoscaler or its `replicaCount` allows more than one copy, so a node drain never removes every copy at once.

### D3: Probes from the existing endpoints

- ascend-memory, ascend-ocr, ascend-audio-scribe, ascend-web-hunter: `livenessProbe` `GET /health` and `readinessProbe` `GET /ready` on the container's API port (`API_PORT`, 7020, 7022, 7017, 7021). ascend-ocr reports `not-ready` during a worker replacement, which the readiness probe turns into "no traffic" without a restart, the behaviour its plan wants.
- ascend-agent: `livenessProbe` `GET /actuator/health/liveness` and `readinessProbe` `GET /actuator/health/readiness` on the management port 9918. Spring Boot enables these two health groups by itself when it runs on Kubernetes, and the chart also sets `MANAGEMENT_ENDPOINT_HEALTH_PROBES_ENABLED=true` so the groups exist on every cluster. A `startupProbe` on the liveness path with the agent's start budget keeps a slow first start (Liquibase or Flyway, the capability index) from being killed.
- ascend-weather-mcp: `GET /actuator/health` on 9998 for both probes.
- ascend-sandbox-runner: `/health` and `/ready` on 9940.
- Other components: the healthcheck command or path their compose service uses, turned into an `httpGet` or `exec` probe.

Probe timings are chart values per component, with the compose healthcheck `interval`, `timeout`, `retries` and `start_period` of the same service as defaults (`periodSeconds`, `timeoutSeconds`, `failureThreshold`, `initialDelaySeconds`).

### D4: Settings as chart values, secrets from a Kubernetes Secret

Each component's `env` block lists every setting of that service from the configuration reference, under the same environment variable name and with the same default. The chart renders them as `env` entries of the container. A setting that compose interpolates under a service prefix (for example `MEMORY_API_PORT` into `API_PORT`) is written under the name the container reads (`API_PORT`), with the default compose gives it. A setting whose compose default names a compose service address (for example `http://ascend-ocr:7022`) keeps it, because the chart names every Service like its compose service, so the same addresses resolve inside the namespace. A setting whose default is a Docker host address (`host.docker.internal`) has no meaning in a cluster: its chart default is the address of the prerequisite value of D9 (for example `REDIS_URL` from `prerequisites.redis.url`), and the chart README says so. Host port settings (`*_HOST_PORT`) and `EXPOSE_BIND` are Compose-only and are not chart values, because a Service is reached by its name and the Ingress replaces host ports.

One script keeps the values and the reference equal: `deploy/helm/scripts/check_values_match_reference.py` reads every row of `docs/CONFIGURATION.md` and of the four per-service references (variable and default), reads the `env` blocks of `values.yaml`, and fails when a setting of an enabled-by-default service is missing, has a different default, or is in the values but not in a reference. The Compose-only settings above are the only names it skips, from a list in the script.

Secrets: the value `secrets.existingSecret` names a Secret the operator creates in the namespace before the install. The chart never renders a Secret with a value and never has a default for one. Every secret setting of the configuration reference (the rows that say `(none, secret in .env)`) becomes an `env` entry with `valueFrom.secretKeyRef` on that Secret under the same key name. `helm install` fails with a clear message (`required`) when `secrets.existingSecret` is empty. The chart README lists every key the Secret must hold, generated from the same reference rows the script reads.

### D5: Public routing through an Ingress

The Compose gateway (`harden-cloud-deployment` D2) terminates TLS and routes the agent's site, the Keycloak site and the NoVNC site. On Kubernetes an `Ingress` (`networking.k8s.io/v1`) takes that role: `ingress.className`, `ingress.agentHost` (the agent's site, routed to the `ascend-agent` Service on 9917), `ingress.novncHost` (the NoVNC site, D6), `ingress.tls` (the name of a TLS Secret per host, created by the operator or by a cert-manager the operator runs) and `ingress.annotations`. Keycloak is not routed by this chart when it is an external prerequisite. When the optional Keycloak subchart is on, `ingress.keycloakHost` routes its site. The ascend-web-hunter API gets an Ingress rule only when `ingress.webHunterHost` is set (empty by default), because in Compose its port is bound to loopback and the agent reaches it inside the cluster. Every other Service is `ClusterIP` and is not routed.

Behaviours of the Compose gateway that depend on the Ingress controller are written in the chart README as the operator's controller settings, not as chart templates: the unbuffered streamed chat route of `add-chat-streaming-and-conversations`, the Keycloak login and token rate limit of `harden-cloud-deployment` (10 per minute per address by default, owner answer 102.2 of 2026-10-09) when Keycloak sits behind this Ingress, and WebSocket pass-through for NoVNC.

### D6: ascend-web-hunter: a StatefulSet, a Service for the API, a NoVNC router for one copy

The API role of the edge proxy (spread requests over every copy) is the `Service` `ascend-web-hunter` (port 7021) plus the optional Ingress rule of D5. The agent keeps its address `http://ascend-web-hunter:7021`.

The NoVNC role cannot be an Ingress rule: an Ingress sends a path to a Service, never to one named pod, and the standard Ingress has no prefix removal. A human must reach the window of the one copy that owns the flow (`open-several-novnc-windows-at-once` Decision 11). So:

- ascend-web-hunter is a `StatefulSet` with a headless `Service` `ascend-web-hunter-pods`. Each copy's host name is its pod name (`ascend-web-hunter-0`, `ascend-web-hunter-1`, ...), which the container reads at start as today, so each copy builds its `vnc_url` as `<NOVNC_PUBLIC_URL>/novnc/<pod name>/vnc.html?autoconnect=true&path=novnc/<pod name>/websockify` with no code change, and the headless Service resolves `<pod name>.ascend-web-hunter-pods` to that copy. The Horizontal Pod Autoscaler scales the StatefulSet through its scale subresource.
- The component `novncRouter` runs the Caddy image the edge proxy of `scale-web-hunter-across-containers` pins, with one listener `:7900` and the chart's own `files/novnc-router.Caddyfile`: a request whose path matches `^/novnc/(ascend-web-hunter-[0-9]+)/` has the prefix `/novnc/<name>` removed and goes to `<name>.ascend-web-hunter-pods:7900`, WebSocket passed, every other path answers 404. The name rule allows only StatefulSet pod names of ascend-web-hunter, so the router reaches nothing else. The Ingress rule of `ingress.novncHost` sends `/novnc/` to the `novncRouter` Service on 7900. `NOVNC_PUBLIC_URL` of ascend-web-hunter defaults to `https://<ingress.novncHost>` when that host is set.
- The edge proxy's API listener `:7021`, its `lb_policy` and its DNS refresh are not used on Kubernetes (the Service balances), so `WEB_HUNTER_EDGE_DNS_REFRESH_SECONDS` and `WEB_HUNTER_EDGE_TRY_DURATION_SECONDS` are Compose-only settings for the check of D4, and `FORWARDED_ALLOW_IPS` keeps its default `*` on the copies, because they sit behind the Ingress.

Owner answer 99.1 says that the Service and the Ingress take the edge proxy role. They take its API role. The NoVNC router is the one part that stays, because no Ingress can route to one named copy. Owner answer 103.4 of 2026-10-09 confirmed this design: ascend-web-hunter runs as a StatefulSet so each copy has a fixed name, with the small Caddy router for `/novnc/<copy>/`.

### D7: The sandbox runner, one per node

`ascend-sandbox-runner` is a `DaemonSet` on the nodes that carry the label of the value `sandboxRunner.nodeSelector` (default `ascend.ai/sandbox-runner: "true"`). Such a node must run Docker Engine with its socket at `/var/run/docker.sock` and the `runsc` runtime, the same host requirements as the Compose stack (`add-agent-sandbox` D10), because the runner drives Docker through that socket, which a containerd-only node does not offer. The pod mounts the socket with a `hostPath` volume, joins the socket's group through `supplementalGroups` from the value `sandboxRunner.dockerSocketGid` (the same setting and default as `DOCKER_SOCKET_GID`, 0), and exposes port 9940 as a `hostPort` on the node.

Each agent copy uses the runner of its own node: the agent's `APP_SANDBOX_RUNNER_BASEURL` is `http://$(HOST_IP):9940`, with `HOST_IP` from the downward API `status.hostIP`. So the base URL a workspace row records (`sandbox_workspace.runner_base_url`) names the runner of the node that created it, and every later call of that workspace from any agent copy reaches that same runner, as the plan of owner answer 98.9 requires. When the `sandbox` part is on, the agent pods carry a required node affinity to the same label, so no agent copy starts on a node without a runner. A `NetworkPolicy` allows ingress to the runner only from agent pods. `SANDBOX_RUNNER_TOKEN` comes from the Secret of D4. The hostPort is reachable on the node's address by anything on the node network that the NetworkPolicy does not cover (Risks).

### D8: Security and isolation defaults

Every pod runs with `runAsNonRoot: true` and the image's own non-root user where the image has one (read from each Dockerfile at implementation time), `allowPrivilegeEscalation: false`, `capabilities.drop: [ALL]` and `seccompProfile: RuntimeDefault`, the same posture as the compose services of `harden-cloud-deployment`. The exceptions are written per component in the chart README with the reason the compose service gives (the sandbox runner's socket group, ascend-web-hunter's browser and display). A default-deny `NetworkPolicy` for the namespace plus one allow policy per component, built from the calls the services make in Compose (the agent to the MCP servers, the memory service, docling-serve, unstructured-api, the runner and the prerequisites, the copies of ascend-web-hunter to SearXNG and Redis, the collector from every service, the Ingress controller to the routed Services). The allow rules toward the prerequisites name their addresses from D9 (an `ipBlock` or a namespace selector value).

### D9: Prerequisites and optional subcharts

Keycloak, PostgreSQL, Redis, Qdrant and the S3-compatible object store are external prerequisites by default: the values `prerequisites.keycloak.issuerUri` (the setting `KEYCLOAK_ISSUER_URI`), `prerequisites.postgres.*`, `prerequisites.redis.url`, `prerequisites.qdrant.*` and `prerequisites.objectStore.*` fill the settings of the services that use them, and their credentials come from the Secret of D4. The observability back ends (Prometheus, Grafana, Loki, Tempo) are handled the same way: the chart runs the OpenTelemetry collector (`otelCollector`) and points it at the addresses in `prerequisites.observability.*`. Each prerequisite can instead be installed from a dependency chart declared in `Chart.yaml` `dependencies` with `condition: <name>.enabled`, every one false by default, because a company usually brings its own database (owner answer 103.3 of 2026-10-09, Helm documentation of Context). With every switch on, the platform runs on its own in a cluster. When a switch is on, the prerequisite value of that store defaults to the address of the dependency chart's Service in the same release (for example `prerequisites.redis.url` to the Redis Service of the `redis` dependency), so the services find it with no extra value, and the dependency chart reads its password from the operator's Secret of D4 where the chart offers an existing-secret value (read from each chart's `values.yaml` at implementation time). Each dependency chart is pinned to one chart version, `helm dependency update` writes `Chart.lock`, and the lock file is committed.

### D10: Tests

- `helm lint deploy/helm/ascend-ai` with the default values and with `ci/kind-values.yaml`, both exit 0.
- `helm template` of the chart with each values file, piped into `kubeconform -strict -summary -kubernetes-version <the version of the kind node image>` (the Kubernetes JSON schemas of that version), exits 0 with no invalid resource. `values.schema.json` is checked by Helm itself during `lint` and `template` (Context), and a values file with a wrong type or a missing required autoscaler number makes both fail, which task 7.2 proves.
- One install on a local kind cluster: a one-node kind cluster, the Metrics Server installed with `--kubelet-insecure-tls` (kind's kubelet serves a self-signed certificate), Redis started from the test manifest `ci/kind-redis.yaml` (the same pinned image as the bundled `redis` of `compose.ascend-web-hunter.yaml`), the operator Secret created from dummy test values, and the chart installed with `ci/kind-values.yaml`, which enables only `ascendWebHunter` and `searxng`, the web-hunter shape of the standalone bundle, so the install needs no other prerequisite. ## Risks / Trade-offs

- [The sandbox runner needs Docker Engine on its nodes] → Many managed clusters run containerd only. The chart documents the node requirement, and the DaemonSet schedules no runner on a node without the label.
- [The runner's hostPort is reachable on the node address] → It still requires the bearer token of at least 32 characters (`add-agent-sandbox`), and the NetworkPolicy limits pod traffic. Traffic from the node network itself is the operator's firewall, written in the chart README.
- [StatefulSet scale-down removes the highest ordinal, which may own a NoVNC flow] → The flow record in Redis expires with its lease and the human gets the join or busy answer of `open-several-novnc-windows-at-once`, the same as when a Compose copy stops.
- [CPU is a weak signal for ascend-ocr, which reads one document at a time per worker] → Accepted for this plan (owner answer 99.1 names the autoscaler). Custom metrics are a Non-Goal.
- [Settings drift between the chart and the reference] → The check script of D4 runs in task 3.4 and in every later change that adds a setting (rule written in `docs/CONFIGURATION.md`, task 8.3).
- [Ingress controller differences] → The chart keeps only portable Ingress fields and writes controller-specific behaviour as settings of the operator's controller (D5).
