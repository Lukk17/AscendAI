# Tasks - Plan Scaled Deployment

Build order: build group 5, position 9 of the owner build order of 2026-10-04 (order decision of 2026-10-09 for owner answer 99.1), after every other change except `update-docs-and-architecture` (position 10). Every command runs from the repository root. The Helm, kind, kubectl and kubeconform versions are read at implementation time and written into the chart README (task 8.2). ## 2. Workloads and autoscaling

- [ ] 2.1 Write one template per component (`templates/<component>/deployment.yaml` or `statefulset.yaml` or `daemonset.yaml`, `service.yaml`, `configmap.yaml` where the component has a configuration file) for every component of design D1: a `Deployment` for each, except ascend-web-hunter (task 5.1) and the sandbox runner (task 5.2). Container ports, volumes and command lines are those of the compose service. A component whose module is not in `modules` renders nothing. Acceptance: `helm template` with the default values renders each enabled component once and none of `gateway`, `ascend-web-hunter-edge`, `ngrok-ascend-web-hunter` or `container-metrics-exporter`.
- [ ] 2.2 Resources (design D2): every container of every component gets requests and limits with the compose values of its service as defaults (`deploy.resources.reservations` as the request, `deploy.resources.limits` or `mem_limit` as the limit), read from the compose files at implementation time and listed in the chart README. A component whose compose service has no CPU reservation gets the CPU request `250m` as its default (owner answer 103.2 of 2026-10-09), a chart value per component that each install can change. Acceptance: every rendered container has `resources.requests.cpu`, `resources.requests.memory` and `resources.limits.memory`, and every container without a compose CPU reservation renders `cpu: 250m`.
- [ ] 2.3 Write the autoscaler defaults of owner answer 103.2 of 2026-10-09 into `values.yaml` for each of `ascendAgent`, `ascendWebHunter`, `ascendOcr`, `ascendAudioScribe` and `ascendMemory`: `minReplicas` 1, `maxReplicas` 5, `targetCPUUtilizationPercentage` 70 (design D2). They are chart values set per install, and the chart README says that each company customer sets its own in its values file. Then write `templates/<component>/hpa.yaml`: `autoscaling/v2`, `scaleTargetRef` to the component's workload, one `Resource` metric `cpu` with `target.type: Utilization` and the value, `behavior` only when the value is not empty. The workload template drops `replicas` while `autoscaling.enabled` is true. Acceptance: `helm template` renders five `HorizontalPodAutoscaler` resources with those values and no `replicas` field on their five workloads, and with `ascendOcr.autoscaling.enabled=false` renders four and an `ascend-ocr` Deployment with `replicas: 1`.
- [ ] 2.4 PodDisruptionBudget (design D2): `templates/<component>/pdb.yaml` with `maxUnavailable: 1` for each of the five when its autoscaler is on or its `replicaCount` is above 1. Acceptance: `helm template` renders five PDBs with the default values and none for a component with `autoscaling.enabled=false` and `replicaCount: 1`.

Acceptance: the tests fail before the code and pass after, and `python deploy/helm/scripts/check_values_match_reference.py` exits 0 on the repository.
