## Why

AscendAI has no tenant concept anywhere. Every data plane is a single shared pool, which makes it impossible to host two companies on one deployment and blocks consolidating today's per-company deployments later:

1. **RAG is fully shared.** Both Qdrant collections (`ascendai-768` / `ascendai-1536`, `apps/ascend-agent/src/main/resources/application.yaml` `app.vectorstore.collections`) hold everyone's chunks. `RagRetrievalService.retrieve(...)` builds its `SearchRequest` with query + topK + threshold only - no owner filter of any kind (`apps/ascend-agent/src/main/java/com/lukk/ascend/ai/agent/service/rag/RagRetrievalService.java:77-88`). Ingestion stamps only `source` / `type` / `title` metadata (`service/ingestion/IngestionMetadataKeys.java`). Any prompt retrieves any company's documents.
2. **the object store (Floci) is one shared bucket.** Uploads land in `knowledge-base` under `markdown/` or `documents/` keyed by sanitized filename only (`controller/IngestionController.java:101-105`). Two tenants uploading `handbook.pdf` silently overwrite each other, and the `attachSources` presigning path (`service/rag/S3PresignedUrlService.java`, `RagRetrievalService.buildSourceRefs`) will happily hand tenant A a signed download link to tenant B's document.
3. **Chat history and instructions key on userId alone.** Redis key is `"chat:" + conversationId` where conversationId == userId (`memory/PersistentChatMemory.java:69,183`), Postgres `chat_history` has only `user_id` (the initial schema, today `db/changelog/01-initial-schema.xml`, which `upgrade-spring-boot-4` moves to Flyway), and user instructions live at `"user:" + userId + ":instructions"` (`service/user/UserInstructionService.java:31`). A userId collision across companies merges their conversations. `add-agent-soul`, which lands before this change, removes `UserInstructionService`, its Redis key and the `user_instructions` table, so this change scopes only chat history of these.
4. **AscendMemory trusts the caller-supplied `user_id`** and partitions shared Qdrant collections by it, so the same collision leaks long-term memories across companies.
5. **Inside a company, everything is readable by everyone.** A company's documents are not uniformly readable by that company: the board pack, the salary bands, and the postmortem naming a customer are not for everyone, and SharePoint and Google Drive enforce exactly that on every file open. Once those files are chunked into Qdrant, nothing carries who may read them: `IngestionMetadataKeys` records `source`, `type`, and `title`, none of which says anything about readers. So separating companies is necessary and not sufficient. A deployment that isolates tenants perfectly still answers a support engineer's question out of the board pack.
6. **The agent's own features add more stores.** The changes that land before this one add tables, folders under the agent home `app.agent-home` and buckets that each carry a tenant id but have no `tenants` table to point at: `owner_notification` (`add-shared-scheduler`), the skills and the capability index (`add-agent-skills`), `subagent_run` and the subagent definitions (`add-agent-subagents`), `sandbox_workspace` and the `sandbox-output` bucket (`add-agent-sandbox`), the personality and user facts folders (`add-agent-soul`), and `approval_rule` and `approval_request` (`add-action-approvals`). The later personal changes add more of the same (listed under Stores of the personal changes below). Until this change they all run as tenant `default`, read through `TenantContext.currentTenantId()` of `add-keycloak-login`, which answers `default` by default.

`add-keycloak-login` introduces authenticated identity, and the sibling company change `add-auth-and-identity` adds a JWT `tenant` claim and a resolved set of group principals per caller. This change consumes both and makes every data plane enforce them, fail-closed, on two axes: the tenant that owns a chunk, and the access list that says who inside that tenant may read it. The settled model behind the second axis is [permission-aware retrieval](../../../docs/architecture/permission-aware-retrieval.md), recorded as ADR-M004 through ADR-M009.

## What Changes

- **Tenant model**: new `tenants` table plus a `tenant_id` column on `chat_history`, the one tenant-owned table that predates the tenant rule, backfilled with `default` (ruling 13.4 of the dependency fix of 2026-10-05), all in one Flyway versioned SQL migration with indexes. Every personal, base and web-hunter change lands before this one, and its tables already carry `tenant_id VARCHAR(64) NOT NULL` with no foreign key. The same migration adds the foreign key to `tenants(id)` on every such table that exists when this change lands, listed by name in design decision 8 and task 2.3: `conversations`, `documents`, `document_index_state`, `ingestion_runs`, `owner_notification`, `owner_notification_delivery`, `subagent_run`, `sandbox_workspace`, `approval_rule`, `approval_request`, `connector`, `connector_credential`, `connector_sync_run`, `connector_sync_file_outcome`, `connector_sync_cursor`, `obsidian_vault_file`, `channel_link`, `channel_pairing`, `channel_conversation`, `channel_inbound_message`, `channel_outbox`, `coding_project`, `coding_run`, `scheduled_job`, `scheduled_job_firing`, `self_review`, `self_change`, `self_check_case`, `self_capability_use`, `integration`, `integration_version`, `integration_destination` and `integration_credential`. Tenant identifiers are constrained slugs (`[a-z0-9-]{1,64}`) so they can be embedded safely in Redis keys, S3 prefixes, folder names and composite ids.
- **Tenant context and principal set, fail-closed**: the agent resolves the current tenant from the JWT `tenant` claim and the caller's group principals from the resolution that `add-auth-and-identity` delivers. The one tenant seam is `TenantContext.currentTenantId()` of `add-keycloak-login`, which every earlier change already reads, and background workers bind the tenant of their row with `TenantContext.runAs` of the same change. This change needs no seam change: the tenant comes from the claim-reading implementation that `add-auth-and-identity` registers behind `TenantContext`, and `TenantContext` already fails closed. Any tenant-scoped operation (RAG search, presign, chat history, memory, skills, subagent definitions, personality and user facts, and every other store this change lists) executed without a resolved tenant fails with an error, and search and presign additionally fail without a resolved principal set, never falling through to unfiltered behaviour, a shared key, or a filter carrying only the tenant conjunct. An empty resolved principal set is a valid answer that matches nothing; an unresolved one is a failure.
- **Qdrant isolation on both axes**: every ingested chunk is stamped with `tenant_id` plus the access-list contract `acl`, `acl_source`, `acl_version`, and `acl_synced_at`; every similarity search applies one mandatory Spring AI `FilterExpression` composed of both conjuncts, `tenant_id == '<currentTenant>' AND acl IN <principalSet>`, built through `FilterExpressionBuilder` at the single place a search request is constructed. Direct uploads stamp `acl` as `["tenant:everyone:{tenantId}"]`, which reproduces today's tenant-wide readability as an explicit grant. A chunk whose list is absent or empty is retrieved by nobody, and that follows from the filter rather than from special-case code. **BREAKING** for existing collections: a point without `tenant_id` and `acl` is retrieved by nobody. Tenant isolation starts from empty stores (owner answer 88.1 of 2026-10-08, design decision 15), so no point written before this change is stamped, and nothing stamps a point written without them afterwards.
- **One search call site, pinned**: one method, `TenantFilteredVectorSearch.search`, becomes the only production caller of `VectorStore.similaritySearch(...)`, and an architecture test fails the build when a second call site appears. `RagRetrievalService.performSimilaritySearch` and `CapabilityIndex.search` of `add-agent-skills` both call it, the first with the target `KNOWLEDGE` (tenant and access list filter) and the second with the target `CAPABILITIES` (global entries or the caller's tenant), so the capability index search has no second call site. A mandatory filter is only mandatory when there is one place it can be applied. The one search method accepts an optional narrowing conjunct, built with `FilterExpressionBuilder` and always joined with AND to the mandatory tenant and access list filter, never in its place, so `add-obsidian-vault` can search only one vault's notes.
- **Payload indexes on both filter fields**: keyword payload indexes on `tenant_id` and on `acl` in both collections, created together by the agent at startup when either is missing. Without the `acl` index the access conjunct degrades to a walk of the collection.
- **the object store (Floci) isolation**: object keys become `tenant/<tenantId>/markdown/...` and `tenant/<tenantId>/documents/...`; presigning refuses any key outside the caller's tenant prefix and additionally re-checks the reference's access list against the caller's principal set, dropping a refused reference from the response entirely; manual ingestion scans (`POST /api/v1/ingestion/run`) are scoped to the caller's tenant prefix. **BREAKING** key layout change. Objects stored under the old layout are not moved, because tenant isolation starts from empty stores (owner answer 88.1 of 2026-10-08, design decision 15).
- **Chat history and conversations scoping**: the per-conversation Redis key `chat:{conversationId}` from `add-chat-streaming-and-conversations` becomes `chat:{tenantId}:{conversationId}`. `conversations.tenant_id VARCHAR(64) NOT NULL`, which `add-chat-streaming-and-conversations` already creates, gets its foreign key to `tenants(id)`, and Postgres reads and writes filter on tenant. User instructions are not rekeyed, because `add-agent-soul` has already removed `UserInstructionService`, the Redis key `user:{userId}:instructions` and the `user_instructions` table.
- **Tenant folders under the agent home**: below `app.agent-home`, each tenant has the folder `tenants/<tenantId>/` with its skills in `skills/` (`add-agent-skills`), its subagent definitions in `.claude/agents/` (`add-agent-subagents`), its personality in `soul/` and its user facts in `users/<userKey>/` (`add-agent-soul`), each its own git repository. Skills in the read-only folders stay global. Capability index entries carry the tenant id, and every capability index search goes through `TenantFilteredVectorSearch.search`. `TenantContext.currentTenantId()` fails closed for every read and write of these folders.
- **Other buckets**: the object store prefix `tenant/<tenantId>/sandbox-output/` in the `sandbox-output` bucket of `add-agent-sandbox` is a tenant-scoped store like `knowledge-base`.
- **Worker threads bind the tenant first**: every background worker that acts for a tenant (a subagent run, a scheduler thread of `add-shared-scheduler` that runs work of one tenant, a connector run, a download ingestion run, a scheduled firing) already binds the tenant stored on its row with `TenantContext.runAs` of `add-keycloak-login` before any other step, added by the change that owns the worker. This change verifies that with real tenants and that a worker with no tenant fails closed.
- **Personal deployment**: the personal deployment runs as tenant `default`, through the same tenant resolution as any other tenant, never as a fallback.
- **Stores of the personal changes**: `add-openclaw-plugin-host`, `add-file-download`, `add-scheduled-tasks`, `add-self-improvement`, `add-coding-agent-delegation` (`coding_project`, `coding_run`, `tenants/<tenantId>/projects/`, `tenant/<tenantId>/coding/`) and `add-self-built-integrations` (its integration tables, `tenants/<tenantId>/integrations/`, `tenant/<tenantId>/integration-builds/`), with `add-download-ingestion` for the agent part of the downloads, keep their tables, folders, buckets and worker threads under the same rules from their first day, as tenant `default`. Under the owner rule of 2026-10-04 (the personal assistant comes first, and company work comes last and only plugs in), every personal, base and web-hunter change lands before this change, which is company work of build group 5. Their tables carry `tenant_id VARCHAR(64) NOT NULL` with no foreign key, and this change's own Flyway migration adds the foreign key to `tenants(id)` on every one of them, listed by name in design decision 8 and task 2.3. The stores are listed in the `tenant-isolation` capability. The capability also lists the crawl results bucket `web-hunter-crawls` of `enhance-web-search-crawl-at-scale`, whose keys sit under `tenant/<tenantId>/` (owner answer 54). The earlier rule that a change landing after this one adds its own foreign keys (owner decision of 2026-10-03) is superseded by the owner build order of 2026-10-04, because no change with a tenant-scoped table lands after this one.
- **Documents registry and OCR results**: the `documents`, `document_index_state` and `ingestion_runs` tables of `add-document-management-api` already carry `tenant_id` and get their foreign keys to `tenants(id)`, new object keys are written under `tenant/{tenantId}/`, and every document management endpoint filters on tenant. The agent records the tenant of every ascend-ocr job it submits and never hands a result in the `ocr-results` bucket, or its presigned link, to another tenant.
- **AscendMemory scoping**: the agent sends tenant-qualified user ids (`{tenantId}:{userId}`) on every AscendMemory call, so memories cannot cross tenants without any AscendMemory code change.
- **Data written before this change**: rows the earlier changes wrote already carry `tenant_id` `default` and point at the `default` row once it exists, and `chat_history`, which predates the tenant rule, gets its `tenant_id` column with the column default `default` in the Flyway migration (ruling 13.4). Tenant isolation starts from empty stores (owner answer 88.1 of 2026-10-08, which supersedes answer 72.2 of 2026-10-06): the owner starts from clean stores after these changes are built, so no Redis chat key, Qdrant point, object or AscendMemory entry written before this change is converted, moved or backfilled, and the agent has no backfill step and no readiness hold. How the personal changes write their data does not change. The data that exists today in the development database, Redis, Qdrant, object storage and AscendMemory is disposable and out of scope (owner answer 73.1 of 2026-10-06, which confirms the owner decision of 2026-10-02 for that data). The Flyway migration creates the reserved `default` tenant row, and every `tenant_id` column is `NOT NULL` with no default after it runs.

## Capabilities

### New Capabilities

- `tenant-isolation`: the isolation model itself, meaning the two axes and their vocabulary, tenant entity and persistence, the chunk access-list payload contract (`acl`, `acl_source`, `acl_version`, `acl_synced_at`), the `tenant:everyone:{tenantId}` pseudo-group, the mandatory payload indexes on both filter fields, fail-closed resolution of tenant context and principal set, tenant id format rules, the reserved `default` tenant and the start from empty stores, the tenant-scoped tables, folders and buckets of the agent's own features, worker threads that bind the tenant first, and the stores of the personal changes that land before it.

### Modified Capabilities

- `rag-retrieval`: similarity search gains one mandatory filter expression carrying both the tenant equality and the access-list intersection; a chunk with no access list is retrieved by nobody as a consequence of that expression; exactly one method issues the search and an architecture test holds it there, and that method accepts an optional narrowing conjunct joined with AND; retrieval without tenant context or without a resolved principal set fails closed.
- `rag-source-attachments`: presigned URLs are only issued for objects under the caller's tenant prefix whose access list intersects the caller's principal set, and a reference failing either check is dropped from the response entirely rather than returned without a link, which is the presigner's existing `Optional` shape rather than a new response shape. Every source entry that is returned still carries a non-blank `downloadUrl` and `expiresAt`, exactly as the baseline guarantees. `add-document-management-api` (build group 3, which lands before this change) adds `documentId` and `contentPath` beside that link as further mandatory fields, and its `GET /api/v1/documents/{id}/content` endpoint enforces the same per-tenant and per-access-list ownership on the resolved document id, so both download paths carry both checks and neither of them is the primary one.
- `ingestion-security`: storage keys gain the tenant prefix on top of filename sanitization; ingested chunks are stamped with tenant metadata and with an explicit access list, defaulting to the tenant-everyone pseudo-group for direct uploads.
- `ingestion-correctness`: upload idempotency (replace-on-re-upload) becomes per-tenant; identical filenames in different tenants coexist.
- `chat-history-persistence`: Redis key scheme and Postgres persistence of chat history become tenant+user scoped.
- `semantic-memory-client`: all AscendMemory calls carry tenant-qualified user ids.

## Impact

- **Build order** (owner build order of 2026-10-04, which supersedes the earlier orders): build group 5 (company), position 2. It needs `upgrade-spring-boot-4` (Flyway, build group 3, position 2), `add-keycloak-login` (build group 3, position 3) and `add-auth-and-identity` (build group 5, position 1), and it lands after every web-hunter, base and personal change, whose stores it scopes. `add-chat-streaming-and-conversations` and `add-document-management-api` (build group 3) have already added the `conversations` table, the per-conversation Redis keys and the `documents` registry table, and `add-passage-level-citations` (build group 4) the passage citations, and this change scopes all of them. `add-tenant-policy`, `add-tenant-administration`, `add-audit-and-gdpr-compliance`, `add-usage-metering-and-quotas` and `add-document-connectors` plug into it later. The order of 2026-10-01 (groups A, B and D, then `harden-cloud-deployment`, then `add-auth-and-identity`, then this change) is superseded by the owner build order of 2026-10-04.
- **Dependency**: `add-keycloak-login` and `add-auth-and-identity` must land first, because this change consumes the resolved identity and `TenantContext` of the first and the JWT `tenant` claim and the resolved principal set of the second, and re-specifies neither authentication, principal identifier format, nor membership resolution. A filter built from anything a client can type is not a filter. It also depends on `upgrade-spring-boot-4`, which replaces Liquibase with Flyway in ascend-agent (owner decision, 2026-10-02), so the schema change here is a Flyway versioned SQL migration.
- **Dependency on the earlier changes**: the agent change order of 2026-10-02 (with number 2 inserted by owner answer 56 of 2026-10-03 and number 3 by owner answer 60.6 of 2026-10-03) is superseded by the owner build order of 2026-10-04. This change scopes the stores of the changes that land before it: `add-shared-scheduler` (`owner_notification` and its scheduler threads), `add-agent-skills` (the tenant skill folders and the capability index), `add-agent-subagents` (`subagent_run`, the definition folders and the run threads), `add-agent-sandbox` (`sandbox_workspace` and the `sandbox-output` bucket), `add-agent-soul` (which removes user instructions and adds the `soul/` and `users/` folders), `add-action-approvals` (`approval_rule` and `approval_request`), `add-connector-framework` (its `TenantPrefixResolver` port), and the stores of decision 14 of the design. - **Successor**: `add-document-connectors` fills the access lists this change makes enforceable, replacing the tenant-everyone default on connector-sourced documents with lists captured from the source. Until it lands, access lists are correct and coarse.
- **ascend-ai-agent code**: `TenantFilteredVectorSearch` (the one search call site and the composed filter), `RagRetrievalService` (searches through it, `acl` carried onto `SourceRef`), `CapabilityIndex` of `add-agent-skills` (searches through it), `S3PresignedUrlService` (both re-checks, context captured before the async fan-out), `IngestionController`, `ManualIngestionService`, ingestion producers stamping `IngestionMetadataKeys`, `PersistentChatMemory`, `SemanticMemoryClient` call sites, the `TenantPrefixResolver` implementation for `add-connector-framework`, plus principal-set accessor consumption and the `Tenant` entity/repository. `TenantContext` of `add-keycloak-login` is consumed unchanged.
- **Build**: an architecture-test dependency (ArchUnit, test scope only) for the single-call-site assertion.
- **Database**: new Flyway versioned SQL migration `V<n>__tenant_isolation.sql` (tenants table with the `default` row, the `chat_history.tenant_id` column backfilled with `default`, composite indexes, named foreign keys `<table>_tenant_fk` from every tenant-scoped table that exists when it runs) in `apps/ascend-agent/src/main/resources/db/migration/`, with `<n>` taken at implementation time.
- **Data stores**: Qdrant point payloads (new `tenant_id`, `acl`, `acl_source`, `acl_version`, `acl_synced_at` keys plus keyword payload indexes on `tenant_id` and `acl`), object-store object key layout, Redis key namespace, the tenant folders under `app.agent-home`.
- **Config**: one new setting, the access list cap `app.ingestion.acl.max-principals` (environment variable `APP_INGESTION_ACL_MAXPRINCIPALS`, default 64), passed by compose as `${VAR:-default}` with the same default in code, with its row in `apps/ascend-agent/docs/CONFIGURATION.md` (owner rule 98 of 2026-10-08).

- **No AscendMemory / Python service changes**: isolation rides on the `user_id` namespace they already partition by.
