## Context

ascend-ai-agent today is effectively a single-tenant application that happens to accept a `userId` form field. All four data planes are shared pools:

- Qdrant: two collections (`ascendai-768`, `ascendai-1536`) with no owner metadata beyond `source`/`type`/`title` (`IngestionMetadataKeys`), searched with no filter (`RagRetrievalService`).
- the object store (Floci): one `knowledge-base` bucket, keys are `markdown/<file>` or `documents/<file>` (`IngestionController.determineFolder`).
- Redis: `chat:{conversationId}` lists, one per conversation since `add-chat-streaming-and-conversations` (`PersistentChatMemory`). The `user:{userId}:instructions` values of `UserInstructionService` are gone, because `add-agent-soul` removes the service and its key.
- Postgres: `chat_history` keyed by `user_id` only (`V1__initial_schema.sql` of `upgrade-spring-boot-4`). `add-agent-soul` drops `user_instructions`.
- AscendMemory: partitions by caller-supplied `user_id` inside shared Qdrant collections and trusts it blindly.
- The agent's own features, from the personal changes that land before this one: the tables `owner_notification` (`add-shared-scheduler`), `subagent_run` (`add-agent-subagents`), `sandbox_workspace` (`add-agent-sandbox`), `approval_rule` and `approval_request` (`add-action-approvals`) each carry `tenant_id VARCHAR(64) NOT NULL` with no foreign key, because no `tenants` table exists yet. Below the agent home root `app.agent-home`, each tenant has the folder `tenants/<tenantId>/` with `skills/` (`add-agent-skills`), `.claude/agents/` (`add-agent-subagents`), `soul/` and `users/<userKey>/` (`add-agent-soul`), each its own git repository. The capability index of `add-agent-skills` holds global entries and tenant entries. The `sandbox-output` bucket holds run and chat archives under `tenant/<tenantId>/sandbox-output/`. The later personal changes add more tenant-scoped tables of the same shape, listed in decision 14. Every one of them takes its tenant from `TenantContext.currentTenantId()` of `add-keycloak-login`, which answers `default` until `add-auth-and-identity` registers its claim-reading tenant resolution behind it, and every background worker binds the tenant stored on its row with `TenantContext.runAs` of the same change.

**Two axes, not one.** Isolation here has a tenant axis and an access axis, and the change is only complete when both are enforced at the same points. The tenant axis answers which company owns a chunk. The access axis answers which people inside that company may read it, because a company's documents are not uniformly readable by that company: the board pack, the salary bands, and the postmortem naming a customer are not for everyone. Wherever this document says isolation, it means both axes. A filter, a guard, or a migration step that handles only the tenant predicate is incomplete, not partially done, and the settled model behind the access axis is [permission-aware retrieval](../../../docs/architecture/permission-aware-retrieval.md) with its decision records ADR-M004 through ADR-M009.

**Dependency**: this change DEPENDS on `add-keycloak-login` (personal, build group 3), which delivers authenticated requests and the resolved identity with `TenantContext.currentTenantId()`, and on the sibling company change `add-auth-and-identity`, which adds the JWT `tenant` claim through its claim-reading tenant resolver and resolves the caller's group principals from the token claim. This design consumes a resolved tenant id and a resolved principal set per request, and does not re-specify token validation, claim extraction, principal identifier format, membership resolution, or identity storage. The integration contract is two request-scoped accessors (referred to below as `TenantContext.currentTenantId()` and `PrincipalContext.currentPrincipals()`) that each either return the authenticated value or signal its absence.

**Build order and the conversation and document changes**: build group 5, position 2 of the owner build order of 2026-10-04 (which supersedes the order of 2026-10-01 that put this change after groups A, B and D and `harden-cloud-deployment`). It needs `upgrade-spring-boot-4`, `add-keycloak-login` and `add-auth-and-identity`, all earlier. `add-chat-streaming-and-conversations` and `add-document-management-api` (build group 3) already shipped the `conversations` table, the per-conversation Redis key `chat:{conversationId}`, the `documents` registry table, and `add-passage-level-citations` (build group 4) the passage citations. `conversations.tenant_id` and `documents.tenant_id` are already `VARCHAR(64) NOT NULL`, so this change adds no column to them: it adds their foreign keys to `tenants(id)` (decision 8), keys Redis as `chat:{tenantId}:{conversationId}`, and scopes the `ocr-results` bucket reads the agent makes. Nothing here lands later in another change.

**Build order and the agent changes**: the agent change order of 2026-10-02 (with number 2 inserted by owner answer 56 of 2026-10-03 and number 3 by owner answer 60.6 of 2026-10-03) is superseded by the owner build order of 2026-10-04. Under it every web-hunter, base and personal change lands before this change, which is company work of build group 5 (the owner rule of 2026-10-04: the personal assistant comes first, and company work comes last and only plugs in). The stores of `add-shared-scheduler`, `add-agent-skills`, `add-agent-subagents`, `add-agent-sandbox`, `add-agent-soul` and `add-action-approvals` are listed in the context above and scoped in decisions 6, 12 and 13. The stores of the other personal changes, `add-connector-framework`, `add-obsidian-vault`, `add-download-ingestion`, `add-openclaw-plugin-host`, `add-coding-agent-delegation`, `add-scheduled-tasks`, `add-self-improvement` and `add-self-built-integrations`, are covered by decision 14. None of them waits for this change. They run as tenant `default` until it lands.

## Goals / Non-Goals

**Goals:**

- Hard, fail-closed data isolation between tenants across Qdrant, the object store (Floci), Redis, Postgres, and AscendMemory.
- Zero cross-tenant reads: a similarity search, presign, history load, instruction load, or memory search can never return another tenant's data - even under bugs like userId collision or forged form fields.
- Zero unpermitted within-tenant reads: a similarity search or presign inside the caller's own tenant can only return chunks whose access list intersects the caller's resolved principal set, and a chunk with no list is returned to nobody.
- One filter composition point carrying both axes, so there is a single place a filter can be got wrong rather than two things that each believe they own filtering.
- Tenant isolation starts from empty stores (owner answer 88.1 of 2026-10-08, which supersedes answer 72.2 of 2026-10-06). The owner starts from clean stores after these changes are built, so no Redis key, Qdrant point, object or AscendMemory entry written before this change needs to survive, and nothing converts, moves or backfills them. Rows of the earlier changes already carry `default`, and `chat_history`, the one tenant-owned table that predates the tenant rule, gets its `tenant_id` column with the column default `default` while the migration adds it (ruling 13.4 of the dependency fix of 2026-10-05). The data that exists today in the development stores is disposable and out of scope (owner answer 73.1 of 2026-10-06, which confirms the owner decision of 2026-10-02 for that data).
- Compatibility with the sibling conversation-model and document-management changes.

**Non-Goals:**

- Authentication and JWT validation (owned by `add-keycloak-login`), the `tenant` claim and tenant onboarding (owned by `add-auth-and-identity`).
- Principal identifier format, the typed principal factory, group membership resolution, the Redis principal-set cache, and the cross-provider identity join (all owned by `add-auth-and-identity`). This change consumes the resolved set and defines only the `tenant:everyone:{tenantId}` pseudo-group.
- Capturing access lists from a source system, the deduplication key that pairs content version with access-list version, the payload-only update path, and the staleness sweep (owned by `add-document-connectors`). This change defines the payload fields those steps write.
- The administrator surface for assigning narrower lists to direct uploads. Direct uploads land on `tenant:everyone:{tenantId}` here. The surface is `PUT /api/v1/documents/{id}/access` of `add-tenant-administration` (its D8, moved there from `add-document-management-api` in the dependency fix of 2026-10-05) with the retrieval groups of the same change (owner decision 65.3 of 2026-10-04).
- Per-tenant quotas or usage metering (owned by `add-usage-metering-and-quotas`).
- Tenant-aware audit logging or GDPR export/erasure (owned by `add-audit-and-gdpr-compliance`).
- Physical isolation (separate databases/collections/buckets per tenant) - this change delivers logical isolation within shared infrastructure.
- Changes to AscendMemory, ascend-audio-scribe, ascend-web-hunter, ascend-weather-mcp, or ascend-ocr service code.

## Decisions

### 1. Logical isolation via mandatory filters, not physical isolation

Shared collections/bucket/tables with a mandatory `tenant_id` discriminator, enforced at every read and write path.

- **Alternative - collection/bucket/schema per tenant**: stronger blast-radius isolation, but Qdrant collection count grows with tenants × embedding dims, object-store bucket limits bite, Flyway per-schema migration multiplies, and per-request provider routing (`VectorStoreResolver`) would need a second dimension. Rejected as disproportionate for the current scale; the fail-closed filter gives the same observable guarantee.
- The discriminator approach also matches what apps/ascend-memory/mem0 already does with `user_id`, so one mechanism covers all stores.
- The same reasoning applies harder to the access axis, and is why it is a second payload field rather than a second partitioning: groups are far more numerous than tenants, so a collection per group would multiply collections by groups times embedding dimensions. Qdrant offers no per-principal authorization model to fall back on, which is recorded upstream as ADR-M009.

### 2. Fail-closed tenant context

Every tenant-scoped operation requires a resolved tenant id. When `TenantContext` is empty (unauthenticated path, misconfiguration, internal caller that forgot to propagate), the operation throws - it never degrades to an unfiltered query or a shared key. HTTP surfaces a request with no resolved identity, and so no tenant, as 401, and an authenticated request whose tenant claim is malformed or whose principal set is unresolved as 403, both as `application/problem+json` (the 401 and 403 of the matrix of `add-keycloak-login` D4 and the problem body of `upgrade-spring-boot-4` D19). Service-layer callers get an exception.

The principal set gets identical treatment. Similarity search and source presigning additionally require a resolved principal set, and when `PrincipalContext` is empty they throw for the same reason and in the same way. In particular they do not degrade to a search filtered by tenant alone, which would be the natural-looking shortcut and is exactly the leak this change exists to close: a tenant-only search hands the caller every document their company owns, including the ones the company deliberately restricted.

An empty resolved set and an unresolved set are different things and must not be conflated in code. An empty set is a successful answer that legitimately matches nothing, and it arises for real callers, for example one whose identity link is broken and who is left holding only `tenant:everyone`. An unresolved set is a failure. Representing the accessor's result as an `Optional<Set<Principal>>`, rather than as a possibly-empty set, keeps the two distinguishable at the type level.

- **Alternative - fall back to `default` tenant when context is missing**: rejected. A silent fallback turns a propagation bug into a cross-tenant leak into the default tenant's pool. The `default` tenant is an ordinary tenant that the migration creates, reached through normal authenticated context like any other tenant.
- **Alternative, fall back to a tenant-only filter when the principal set is missing**: rejected for the same shape of reason. It degrades an authorization failure into a successful-looking response that over-shares inside the tenant, and it is invisible: the request returns 200, the answer is fluent, and nothing indicates that the access axis was skipped.

### 3. Tenant id format: constrained slug

`tenant_id` is `[a-z0-9-]{1,64}`, validated at the trust boundary. This makes it safe to embed in Redis keys (`:`-delimited), S3 key prefixes (`/`-delimited), Qdrant payload values, and the `{tenantId}:{userId}` composite sent to AscendMemory - no escaping layer anywhere. The reserved id `default` is created by migration.

### 4. Qdrant: metadata stamp + one composed Spring AI FilterExpression

Ingestion adds five metadata keys to every chunk: `tenant_id`, plus the access-list contract `acl`, `acl_source`, `acl_version`, and `acl_synced_at` (all new constants in `IngestionMetadataKeys`). Direct uploads stamp `acl` as `["tenant:everyone:{tenantId}"]` with `acl_source` of `tenant-default`; connector-captured lists come later from `add-document-connectors` and write the same fields.

Retrieval builds the `SearchRequest` with one filter expression carrying both axes:

```text
tenant_id == '<currentTenant>' AND acl IN <principalSet>
```

Both conjuncts are built through the `FilterExpressionBuilder` API, never by string concatenation, and they are composed into a single expression at a single place rather than added by two pieces of code that each think they own filtering. Spring AI's `IN` operator against a keyword-array payload field maps to Qdrant's match-any semantics, which is the set-intersection test this needs: the chunk is a candidate when its `acl` holds at least one principal the caller holds. That translation is the one part of the design that rests on library behaviour rather than our own code, so it is pinned by an integration test against a real Qdrant rather than a mocked `VectorStore`, which would confirm whatever we assumed.

The existing Java-side threshold filtering and score logging are unchanged. They operate on what Qdrant returned, and after this change what Qdrant returns is already permitted. Both filters apply server-side, so a chunk of another tenant, or of this tenant that the caller may not read, never reaches the candidate list, the score logs, the `topK` budget, or the model.

Deny-by-default falls out of this expression and is not written as code anywhere. A chunk whose `acl` is absent or empty intersects no principal set, so nothing retrieves it, including a caller holding every group in the tenant and including a caller holding role `ADMIN`, because a role is not a principal and does not widen the expression. There is deliberately no branch that inspects a missing list and decides what to do about it; the absence of such a branch is the property to preserve in review.

The one search method accepts an optional narrowing conjunct from its caller, for example `connector_id == <vault's connector id>` of `add-obsidian-vault`, which searches one vault's notes. `add-obsidian-vault` lands earlier and already adds that narrowing filter to `RagRetrievalService` itself (its D10 and task 6.3), so when this change moves `RagRetrievalService` onto the one search method it passes that filter on as the narrowing conjunct. The conjunct is built with `FilterExpressionBuilder` and always joined with AND to the mandatory tenant and access list filter. It can only narrow the result: it never replaces the mandatory filter and never removes one of its two conjuncts. The architecture test of decision 10 that pins the single call site stays unchanged. That one method is `TenantFilteredVectorSearch.search` (decision 10).

Both payload fields need a keyword payload index. Without an index on `acl` the access conjunct is evaluated by walking the collection, which turns the pre-filter that makes this design correct into the thing that makes it unusably slow. Both indexes are created in the same startup step (decision 8), so a deployment cannot end up with one axis indexed and the other scanned.

- **Alternative, filter the candidate list in Java after the search**: rejected, and this is the decision the whole design turns on. `topK` is spent before a post-filter runs, so a caller permitted only chunks ranked below the cut receives nothing while an unpermitted caller's query looks fine. It does not leak, it suppresses, so the obvious test passes and the design looks correct. With `topK` of 5 and a caller whose only permitted chunk ranks eighth, post-filtering returns an empty context and the model answers from its own weights. Pre-filtering returns that chunk. The symptom lands hardest on narrow-access callers, which is to say on the new joiner, the contractor, and the person the customer's security team sent to check whether permissions work. Recorded upstream as ADR-M005.
- **Alternative, over-fetch then filter in Java**: rejected. It makes the failure rarer rather than fixing it, and whether it works depends on what else is in the collection when the question is asked, so the same question can succeed today and fail after an unrelated ingest. A non-deterministic correctness property is worse than a deterministic failure, because it cannot be tested.

### 5. The object store (Floci): tenant prefix + presign guard

The agent's own bucket is `knowledge-base` on Floci, the S3-compatible store on host port 9070, which the integration tests also run as a Testcontainer. Its object keys become `tenant/{tenantId}/markdown/...` and `tenant/{tenantId}/documents/...`. The `documents` registry rows carry the same `tenant/{tenantId}/` prefix in `object_key`. Four enforcement points:

- **Upload** (`IngestionController`): key is built from the resolved tenant context, never from user input.
- **Manual scan** (`ManualIngestionService` via `POST /api/v1/ingestion/run`): the caller-supplied `prefix` parameter is interpreted relative to the tenant prefix; the effective scan prefix is always `tenant/{tenantId}/...`.
- **OCR results** (`ocr-results` bucket): ascend-ocr is a job API (`POST`/`GET`/`DELETE /v1/ocr/jobs`) that writes each result to its own `ocr-results` bucket, never to `knowledge-base`. The agent records the tenant of every OCR job it submits and fetches a job's status or result link only when that recorded tenant equals the caller's tenant. A job id of another tenant is answered as not found, so a result link is never handed across tenants.
- **Presign** (`S3PresignedUrlService`): before signing, the reference must pass both axes. The key must start with `tenant/{tenantId}/` for the caller's tenant, and the chunk's access list must intersect the caller's principal set, evaluated with the same test the search filter uses. Anything else is refused and logged. This is defense in depth: the composed Qdrant filter should already prevent foreign or unpermitted `SourceRef`s from reaching the presigner, but the presigner must not rely on that. The reference list is assembled by `buildSourceRefs`, handed across a service boundary, and will one day be reachable from a path that did not filter, because that is what happens to every check that lives in only one place.

  A refused reference is dropped from the response entirely rather than returned as an entry with a missing link. That is not a new response shape: `presign` already returns an `Optional<SourceFile>` and `presignAll` already filters empties out of the result list, so this change adds a second reason to return empty and nothing else. It preserves the decision in section 9 that every returned entry always carries a working link.

  Two mechanics this needs. First, the access list has to reach the presigner: `buildSourceRefs` reads chunk metadata already, so it carries `acl` onto the `SourceRef` record, and the presigner evaluates that rather than making a second Qdrant round trip per source. Second, `presignAll` fans out onto `taskExecutor`, and request-scoped context does not propagate to those threads on its own, so the tenant id and principal set are captured on the request thread and passed into the asynchronous work. Reading the accessors inside the async lambda would throw on every request, which fails closed but is a fail-closed outage rather than a fail-closed control.

  The connector framework of `add-connector-framework` builds no tenant key segment itself: it asks its `TenantPrefixResolver` port (its D25), whose default answers the empty prefix. This change registers the implementation answering `tenant/{tenantId}/`, so connector-landed objects follow the same layout with no edit of the framework.

  `add-passage-level-citations` (build group 4, position 15) is archived before this change and modifies `SourceFile DTO shape` and `De-duplication by source object identity` of `rag-source-attachments`. This change modifies only the presign requirement of that capability, so its delta is written against the text `add-passage-level-citations` leaves. Its tenant filter on retrieval wraps the retrieval path that already labels passages and builds the `citations` array, and a citation of another tenant's passage can never be issued because the passage is never retrieved.

  The `sandbox-output` bucket of `add-agent-sandbox` follows the same prefix rule: every run and chat archive lives under `tenant/<tenantId>/sandbox-output/`, and that bucket is a tenant-scoped store like `knowledge-base`.

  What this check cannot do is reach a link that was already handed out. A presigned URL is self-contained, so a revocation does not invalidate one issued two minutes earlier. That window is bounded by the presign TTL, 15 minutes by default and one hour at most, and it is disclosed rather than closed, because closing it means proxying every download through the agent and that collides with the settled decision in section 9.

### 6. Redis and Postgres key/row scoping

- Redis: `chat:{tenantId}:{conversationId}`. TTL semantics unchanged. User instructions are not rekeyed: `add-agent-soul` lands first and removes `UserInstructionService`, the Redis key `user:{userId}:instructions` and the `user_instructions` table, so the rekeying to `user:{tenantId}:{userId}:instructions` and the `tenant_id` column and composite key on `user_instructions` are dropped from this change.
- Postgres: `chat_history` gets its `tenant_id VARCHAR(64) NOT NULL` column here, backfilled with `default` (decision 8), and index `(tenant_id, user_id)` replacing the single-column index. `conversations` (`add-chat-streaming-and-conversations`) and `documents`, `document_index_state` and `ingestion_runs` (`add-document-management-api`) already carry `tenant_id VARCHAR(64) NOT NULL`. The tables of the agent's own features, `conversations`, `documents`, `document_index_state`, `ingestion_runs`, `owner_notification`, `owner_notification_delivery`, `subagent_run`, `sandbox_workspace`, `approval_rule`, `approval_request`, `connector`, `connector_credential`, `connector_sync_run`, `connector_sync_file_outcome`, `connector_sync_cursor`, `obsidian_vault_file`, `channel_link`, `channel_pairing`, `channel_conversation`, `channel_inbound_message`, `channel_outbox`, `coding_project`, `coding_run`, `scheduled_job`, `scheduled_job_firing`, `self_review`, `self_change`, `self_check_case`, `self_capability_use`, `integration`, `integration_version`, `integration_destination` and `integration_credential`, already carry `tenant_id VARCHAR(64) NOT NULL` with no foreign key, and this change adds their foreign keys to `tenants(id)` (decision 8). All repository queries add the tenant predicate.

### 7. AscendMemory: tenant-qualified user id, qualified inside `SemanticMemoryClient`

The agent sends `{tenantId}:{userId}` as `user_id` on every insert/search/wipe/delete. Qualification happens in one place - `SemanticMemoryClient` composes the id from `TenantContext` - so no call site can forget it (single choke point, mirrors how the client already owns snake_case naming).

- **Alternative - add a `tenant_id` parameter to the AscendMemory API**: rejected. It widens the API surface of a service that would still have to trust the caller (ascend-ai-agent is the only client inside the trust boundary), and namespacing the existing partition key achieves identical isolation with zero Python changes.

### 8. Migration: one Flyway migration, one backfilled Postgres column, named foreign keys

Under the owner build order of 2026-10-04 the personal deployment runs before this change, but the owner starts from clean stores after these changes are built (owner answer 88.1 of 2026-10-08, which supersedes answer 72.2 of 2026-10-06), so no data written before this change needs to survive. The data that exists today in the development stores is disposable and out of scope, and nothing here converts it or depends on it (owner answer 73.1 of 2026-10-06). For Postgres: every table of an earlier change already holds `default`, and `chat_history`, created before the tenant rule, gets its `tenant_id` column with the column default `default` while the migration adds it (ruling 13.4 of the dependency fix of 2026-10-05). No personal change adds a column to a table it does not own.

One new Flyway versioned SQL migration, `V<n>__tenant_isolation.sql` under `db/migration/`, where `<n>` is the next free version at implementation time: create `tenants`, insert the `default` row, add `chat_history.tenant_id VARCHAR(64) NOT NULL DEFAULT 'default'` (so every existing row reads `default`) and then drop the column default, so a later insert must name its tenant, add its foreign key `chat_history_tenant_fk`, and add the foreign key `<table>_tenant_fk` to `tenants(id)`, on delete no action (tenant erasure deletes the rows first), on the `tenant_id` column that every table of the earlier changes already carries, listed by name: `conversations`, `documents`, `document_index_state`, `ingestion_runs`, `owner_notification`, `owner_notification_delivery`, `subagent_run`, `sandbox_workspace`, `approval_rule`, `approval_request`, `connector`, `connector_credential`, `connector_sync_run`, `connector_sync_file_outcome`, `connector_sync_cursor`, `obsidian_vault_file`, `channel_link`, `channel_pairing`, `channel_conversation`, `channel_inbound_message`, `channel_outbox`, `coding_project`, `coding_run`, `scheduled_job`, `scheduled_job_firing`, `self_review`, `self_change`, `self_check_case`, `self_capability_use`, `integration`, `integration_version`, `integration_destination` and `integration_credential`, and swap indexes. The list is fixed when this change is implemented: a tenant-scoped table that an earlier change adds and that is missing here is added to the list, because every change with such a table lands before this one. Rows that the changes before this one wrote with `tenant_id` `default` already point at the `default` row once it exists, so their foreign keys need no data step. `user_instructions` gets nothing, because `add-agent-soul` drops it. `scheduler_execution` of `add-shared-scheduler` holds executions, not tenant-owned rows, so it gets no key. The tables `connector_sync_run`, `connector_sync_file_outcome` and `connector_sync_cursor` of `add-connector-framework` carry `tenant_id VARCHAR(64) NOT NULL` like its other tables and are in the list above (owner answer 75.1 of 2026-10-07, review item 27). The source changes keep their own other keys (for example `coding_run_project_fk`, the integration child keys through `(tenant_id, integration_id)`, `obsidian_vault_file` to `connector`). Flyway runs the file in one Postgres transaction, so a failure leaves the schema at the previous version.

Qdrant indexes are not Flyway's job. At startup the agent checks each collection it uses and creates the keyword payload index on `tenant_id` and on `acl` when either is missing, in one step, logs one INFO line per index it created, and refuses to start when it cannot create one. The other stores need no data step, because tenant isolation starts from empty stores (decision 15). A point without `tenant_id` and `acl` matches no filter, so nobody retrieves it (fail-closed, decision 2).

### 9. The presigned link stays mandatory under the tenant prefix check (owner decision, 2026-09-03)

An earlier draft of this change framed the presigned link as conditional. Its `rag-source-attachments` delta spoke of "any in-network presigned URL (`AiResponse.sources[*].downloadUrl`, when populated)" and called `GET /api/v1/documents/{id}/content` from `add-document-management-api` the primary client-facing download path, and the proposal repeated that framing by saying the client-facing download path moves to the agent endpoint. Both readings contradict the `rag-source-attachments` baseline, which guarantees a non-blank `downloadUrl` and `expiresAt` on every source entry.

The owner decided on 2026-09-03 that the link stays mandatory. Every source entry that is returned always carries a non-blank `downloadUrl` and `expiresAt`, `add-document-management-api` adds `documentId` and `contentPath` beside the link as further mandatory fields rather than instead of it, and neither download path is the primary one. The reason is that a caller must never have to implement two different ways of fetching the same source: a sometimes-absent link forces every client to carry both code paths plus the logic to choose between them. The same decision is recorded as D8 in `add-document-management-api/design.md`.

Nothing this change actually enforces is weakened by that. The tenant prefix check still refuses to presign any key outside `tenant/{tenantId}/`, and a refused `SourceRef` is dropped from the response entirely rather than returned as an entry with a missing link, so the guarantee that every returned entry carries a working link holds alongside the guarantee that no entry ever points outside the caller's tenant. The agent endpoint enforces the identical per-tenant ownership on the resolved document id, so both paths carry the same check and neither is a fallback for the other.

The object store stays private, as `harden-cloud-deployment` (build group 3, position 4) requires, and `GET /api/v1/documents/{id}/content` of `add-document-management-api` is the one public download path for a RAG source (its D8). This change does not change that posture.

### 10. Exactly one method calls the similarity search, and an architecture test says so

A mandatory filter is only mandatory if there is one place it can be applied. Before this change there are two production calls to `VectorStore.similaritySearch(...)`: `RagRetrievalService.performSimilaritySearch` for the knowledge base, and `CapabilityIndex.search` of `add-agent-skills` (its D19) for the capability index, which `skill_search` and the `toolSearchTool` of `add-mcp-tool-servers` both use. This change turns one call site into a property. It moves the call into one method, `TenantFilteredVectorSearch.search` in `com.lukk.ascend.ai.agent.service.search`, which composes the mandatory filter and is the sole production caller of `similaritySearch`. An architecture test asserts that no other production class calls `similaritySearch`, failing the build with the offending class named when one appears.

`TenantFilteredVectorSearch.search` takes a search target, the embedding provider, the query, `topK`, the similarity threshold and the optional narrowing conjunct of decision 4. It picks the vector store itself from the target and the provider, so a caller never hands it a store, and it composes the mandatory filter from the target:

- Target `KNOWLEDGE`, the RAG collections: `tenant_id == '<currentTenant>' AND acl IN <principalSet>`. It fails closed when the tenant or the principal set is unresolved (decision 2). `RagRetrievalService.performSimilaritySearch` keeps its name and its job of building the query, and calls this method instead of the store.
- Target `CAPABILITIES`, the capability index collections `ascendai-capabilities-<dimensions>` of `add-agent-skills` (its D18): `scope == 'global' OR tenant == '<currentTenant>'`, on the payload fields that change defines. It fails closed when the tenant is unresolved. A capability entry carries no access list, so the access axis does not apply to it, and the per-request policy filter stays the `entry_key` list the caller passes as its narrowing conjunct (`add-agent-skills` D19). `CapabilityIndex.search` calls this method instead of the store, so no second call site exists, and a search never returns an entry of another tenant.

A caller cannot choose a weaker filter for a store, because the target fixes both the store and the filter, and no target exists without a tenant conjunct. A later index that needs vector search adds a target with its own mandatory tenant conjunct to this method, never a call of its own.

Without that test the guarantee is a convention, and a convention is exactly what a future feature breaks: someone adds a second retrieval path for a new surface, builds their own `SearchRequest`, gets working results in review because their test fixture holds one tenant's data, and the access axis is gone on that path with nothing to say so. ADR-M009 accepts that a security control living in application code is mitigated by tests rather than by architecture, and this is that test.

ArchUnit is the mechanism, added as a test-only dependency, since the alternative of grepping the source tree in a test is the same assertion written worse.

- **Alternative, wrap the vector store in a decorator that refuses an unfiltered request**: attractive, and weaker than it looks. A decorator can check that a filter expression is present, but not that it is the right one for this caller, so the check it can enforce is the one least likely to be got wrong. It also adds a bean between the resolver and the store for every provider. The architecture test costs one test dependency and asserts the thing that matters.
- **Alternative, trust code review**: rejected. The failure this prevents is invisible in a diff that looks like a legitimate new feature.

### 11. `tenant:everyone:{tenantId}` is a real principal, written on purpose

Tenant-wide readability is expressed by writing `tenant:everyone:{tenantId}` onto a chunk's `acl`, never by leaving the list off. Every authenticated caller of a tenant holds that principal, and direct uploads stamp it.

The point is that a broadly readable chunk and a chunk whose capture failed then look completely different from each other. One has a principal in its payload that says who may read it; the other has an empty list and is invisible. Under the alternative where a missing list means tenant-wide, those two states are identical in the payload and identical in behaviour, so every capture bug becomes a silent widening of access that nobody discovers by using the product. Recorded upstream as ADR-M006.

This change owns the pseudo-group because it owns the tenant identifier that names it and the ingestion path that first writes it. `add-auth-and-identity` puts it into every caller's principal set, using the tenant id resolved from the token.

### 12. One tenant seam, and tenant folders under the agent home

The one seam every change reads is `TenantContext.currentTenantId()` of `add-keycloak-login` (its D3 and task 3.9, owner decision 65.23 of 2026-10-04). It answers the tenant of the resolved identity of the current request and throws when nothing is resolved, so it already fails closed. A background worker binds the tenant stored on its row with `TenantContext.runAs(tenantId, action)` of the same change. The tenant folders below the agent home root `app.agent-home` are tenant-scoped stores like the tables:

### 13. Worker threads bind the tenant before any other step

Request-scoped context does not reach a thread the request did not run on. Every background worker that acts for a tenant therefore binds the tenant stored on its row with `TenantContext.runAs(tenantId, action)` of `add-keycloak-login` before any other step, which clears it at the end, and fails closed when it cannot bind it. The change that owns each worker already does this from its first day as tenant `default`, so this change adds no binding code and verifies it with real tenants (task 1.10):

- A subagent run of `add-agent-subagents` binds the caller's tenant on its run thread.
- A scheduler thread of `add-shared-scheduler` that runs work of one tenant binds that tenant.
- The workers of decision 14 (a scheduled firing, a connector run, a download ingestion run, a coding run, an integration reconcile) bind the tenant of their row.

The same rule as the presign fan-out of decision 5: reading the request accessor on a worker thread would throw on every run, which is an outage, and falling back to `default` would be a leak.

## Risks / Trade-offs

- [Missed enforcement point, some future code path queries Qdrant/the object store (Floci)/Redis without the tenant discriminator] → centralize: one `TenantContext`, one `PrincipalContext`, one metadata key constant, one key-builder per store, one similarity-search call site pinned by the architecture test in decision 10; integration tests assert cross-tenant and unpermitted within-tenant reads return zero results; `add-audit-and-gdpr-compliance` adds the second net later.
- [Qdrant filter cost on large collections] → Qdrant supports payload indexes; create keyword payload indexes on both `tenant_id` and `acl` per collection in the same startup step, so both conjuncts are index lookups rather than scans and neither can be forgotten separately.
- [Spring AI's `IN` operator does not translate to Qdrant match-any semantics the way the API shape suggests] → pin it with an integration test against a real Qdrant rather than a mocked `VectorStore`, since a mock confirms whatever was assumed. This is the one correctness property that depends on library behaviour rather than our code.
- [The access list on `SourceRef` goes stale between retrieval and presigning within one request] → the window is milliseconds and the presigned link's own 15-minute window dominates it; a revocation landing inside that window is covered by the disclosed staleness table in the permission-aware retrieval design rather than by a second read.
- [Request-scoped tenant and principals do not propagate to the presign task executor] → capture both on the request thread and pass them into the asynchronous work; reading the accessors inside the async lambda fails closed on every request, which is an outage rather than a control.
- [`{tenantId}:{userId}` composite could collide with a raw userId containing `:` from the pre-tenant era] → there is no pre-tenant era to keep: tenant isolation starts from empty stores (decision 15), so every AscendMemory entry carries the composite id from its first write.
- [`add-chat-streaming-and-conversations` already changed `PersistentChatMemory` to per-conversation keys] → this change only inserts the tenant segment into the one key-builder helper, so the conversation shape is kept and no second key scheme exists.
- [Fail-closed breaks existing unauthenticated local workflows the day this merges] → the dependency on `add-keycloak-login` and `add-auth-and-identity` is explicit. Local dev profile behavior (the dev identity with tenant `default`) is owned by `add-keycloak-login`, and its principal set by `add-auth-and-identity`.
