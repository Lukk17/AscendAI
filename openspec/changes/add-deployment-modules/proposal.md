## Why

AscendAI is first the owner's personal assistant with every feature on, and may later be sold to companies with fewer features, because a company does not want that much AI power or token use for every employee (owner, 2026-10-02). Today every service in `compose.yaml` starts on every `docker compose up`, every agent bean exists in every deployment, and active changes already plan their own on and off switches in three different ways: `add-mcp-tool-servers` passes `COMPOSE_PROFILES` to the agent as `APP_MCP_MODULES`, `add-openclaw-plugin-host` (then named `add-openclaw-channel-host`) passes the same value as `ASCEND_MODULES`, and seven other changes add their own `app.<feature>.enabled` flag. Without one shared list of module names and one switch, the deployments the owner wants to sell cannot be built, and each new feature adds a further way to disagree.

The owner decided on 2026-10-03 (answers 51 and 52) which parts can be switched off at all: only services the system works without. Chat, document search, memory, the sandbox, monitoring and the data stores are the core and are always on.

## What Changes

- The core is always on and is never a module a deployment can switch off (owner answer 52 of 2026-10-03). It holds:
  - core chat: chat, conversations, streaming, login, approvals, the personality file and user facts, background runs, the shared scheduler engine, notifications, and the skill and tool search index
  - monitoring: Prometheus, Grafana, Loki, Tempo, the OpenTelemetry collector and the container metrics exporter
  - document search (`rag`): knowledge search, Docling, Unstructured and the connectors
  - memory: ascend-memory
  - the sandbox: the sandbox runner and the shell and file tools
  - the prerequisites: PostgreSQL, Redis, Qdrant, object storage and Keycloak (a core prerequisite of every deployment, the personal one included, owner answer 70.2 of 2026-10-04)
- Tenant policy, metering, audit and every other company part are not core. Each company change of build group 5 adds its own parts to the deployment when it lands, and the core list above does not name them.
- One catalog of the switchable modules, each with a stable name, a title, a short description, the modules it requires, the modules it can use when present, its companion compose profiles and the agent secrets it needs. The catalog is one JSON file shipped with the agent and is the only list of names. It holds one always-on entry, `core-chat`, which stands for the whole core, and these switchable modules: `ocr`, `audio`, `web-search`, `web-download`, `weather`, `obsidian`, `channels`, `openclaw-apps`, `coding`, `self-built-integrations`, `subagents`, `skills`, `self-improvement` and `scheduler`. This change adds the five that exist when it lands (`ocr`, `audio`, `web-search`, `weather`, and `web-download` with its companion `clamav`, whose services `add-file-download` added earlier), and each later change adds its own entry.
- One setting decides which switchable modules are on: `COMPOSE_PROFILES` in the root `.env`. Every service of a module carries the compose profile of that module's name, and the agent receives the same value as the environment variable `ASCEND_MODULES`. This settles the disagreement between `add-mcp-tool-servers` and `add-openclaw-plugin-host`: the operator sets `COMPOSE_PROFILES`, the agent reads `ASCEND_MODULES`, and `APP_MCP_MODULES` and `app.mcp.modules` are not used.
- **BREAKING**: services of a switchable module start only when their module is listed. `docker compose up` with `COMPOSE_PROFILES` empty starts the core alone. `.env.example` ships the `personal` preset line, so a fresh clone that copies it keeps today's full stack.
- Core services carry no compose profile, so they start on every `docker compose up`. Monitoring stays always on, as `add-observability` has it, and every service always exports its traces.
- Compose `:?` guards: `SEARXNG_SECRET` keeps its guard (owner answer 41.2). Compose checks that guard even when the web search profile is off (measured with Docker Compose v5.1.0), so every deployment must set `SEARXNG_SECRET`, also one without web search. It is the only guard allowed under a module profile. The `GRAFANA_ADMIN_PASSWORD` guard of `harden-cloud-deployment` and the `SANDBOX_RUNNER_TOKEN` guard of `add-agent-sandbox` sit on always-on services, so they never conflict with a switched-off module. Every deployment sets all three, and the installer always generates them.
- Agent gating: every bean of a switchable module is created only when its module is on, through one `@ConditionalOnModule` annotation. A switched-off module has no bean, no tool, no route, no MCP connection attempt and no metric of its own. A unit test fails when a controller, tool, scheduled task or outbound client is neither marked nor on the explicit list of core classes.
- Startup check: the agent refuses to start, with one clear message, when `ASCEND_MODULES` names an unknown module, names a part of the core (`rag`, `memory`, `sandbox` or `observability`), lists a module without a module it requires, or lists a companion profile without its parent module. Under the `production` profile it also refuses a missing agent secret of an active module.
- Presets: named module lists in the catalog. `personal` holds every switchable module, `core` holds none, and `company-docs` holds `ocr`. Document search is core, so a company that only searches documents runs `core`, and `company-docs` is the recommended company preset for a company that also stores scanned paper or photos, which are refused without `ocr` (design D13, kept by owner answer 53 of 2026-10-03). No preset holds the virus scanner companion `clamav` (owner answer 51.2).
- Tenant narrowing: inside one deployment, a tenant can be granted fewer switchable modules than are on. The effective modules of a request are the active modules narrowed by a module access port for the tenant that `TenantContext` of `add-keycloak-login` answers. Its default allows every active module. `add-tenant-policy` (company, build group 5) registers its tenant grants later. A switchable module the tenant lacks hides its tools and answers its routes with 403 `module_denied`. The core is never narrowed by a module grant.
- Company extension ports with safe defaults (D21), owned here in the package `com.lukk.ascend.ai.agent.extension` and used by every later change: `AuditEventPort` with `record(AuditEvent)`, whose default `LogAuditEventPort` writes one structured INFO log line with the event name, tenant, actor, target and outcome and never a secret or content, `UsageEventPort` with `record(UsageEvent)`, whose default `NoOpUsageEventPort` does nothing, `QuotaGate` with `check(QuotaRequest)` before a metered action, whose default `AllowAllQuotaGate` allows every call, and `ModelAccessPolicy`, which says whether a tenant may use a provider and model and whose default `ConfiguredModelAccessPolicy` allows every provider the deployment has enabled. `ChatModelResolver` asks `ModelAccessPolicy` before it builds a client, and a refusal answers 403 `provider_denied` or `model_denied`. Every default is registered with `@ConditionalOnMissingBean`, so a company change replaces it by registering a bean and edits nothing here.
- A read endpoint `GET /api/v1/modules` returns the caller's effective modules, so the mobile app can hide what is not there, and the startup banner shows the active modules.
- With `ocr` off there is no OCR reading at all (owner answer 41.3). An image, or a PDF with a page without a text layer, is refused with a 422 problem detail with the code `module_required` that names the module `ocr`, and is never sent to Docling or its OCR engine.
- MCP connections: only a connection of an active module gets a connection, so the readiness banner lists only those, and a failed MCP server is retried in the background instead of never again. This change owns `McpReconnectScheduler` and the delta of `mcp-startup-resilience` that covers connections, the banner and the retry, and `add-mcp-tool-servers` reuses the scheduler and builds on the delta. `upgrade-spring-boot-4` carries its own delta of the same capability, which replaces only the deferral flag requirement, so the two deltas touch different requirements.
- Tests: catalog and startup check unit tests, a compose consistency test that parses both compose files, the annotation coverage test, and one integration test per preset that boots the agent and checks the exact routes, tools, MCP connections and meters that exist.
- Docs: a new `docs/MODULES.md` that explains the core and why it is always on, every switchable module with its services, tools, routes, settings, dependencies, secrets and memory cost, the presets, how to switch, how tenant policy narrows further, a text diagram and the troubleshooting of every startup refusal. Also a monorepo decision record and updates to the root `README.md`, the root and module `AGENTS.md` files, `docs/DEPLOYMENT.md`, `docs/E2E_RUN_SCENARIOS.md`, `docs/INGESTION.md` and `.env.example`.
- How a module is licensed or sold is out of scope, and so is module access per employee group inside a tenant (owner answer 41.4). The project is under development, so there is no data migration. Owner answer 73.1 of 2026-10-06 confirms that the data in today's development stores is disposable.

## Capabilities

### New Capabilities

- `deployment-modules`: the core and the module catalog with its stable names, the single switch and the variable the agent reads, the startup check, presets, compose profiles for module services and companions, the always-on core services, and the installer contract.
- `module-gating`: what "a module is off" means inside the agent: no bean, no tool, no route, no connection and no metric, the core that works with no switchable module, tenant narrowing of the active modules, the modules endpoint and the banner.
- `company-extension-ports`: the audit, usage, quota and model access ports that every personal change calls, their safe defaults, and the rule that a company change replaces a default by registering a bean.

### Modified Capabilities

- `mcp-startup-resilience`: a connection of a switched-off module gets no connection, so it is never initialised or retried, offers no tool, and has no line in the readiness banner or the aggregate. A failed client of an active module is retried in the background every `app.mcp.reconnect.interval`, which replaces the rule that a `FAILED` client is never tried again. A client demoted after a stale session is retried the same way. `upgrade-spring-boot-4`, which lands first, also changes this capability, but only the deferral flag requirement, which this delta does not touch.
- `production-deployment` (created by `harden-cloud-deployment`): `ngrok-ascend-web-hunter` sits behind the companion profile `captcha-intervention`, and `required: false` applies to every `depends_on` entry on a service under a module profile.
- `ascend-agent-containerization`: the agent receives `ASCEND_MODULES`, uses `required: false` for module services, is part of the always-on core, and `.env.example` describes `COMPOSE_PROFILES` as the module list.
- `observability-stack` (created by `add-observability`): the Prometheus target check runs with the `personal` preset, so every scraped service runs, and the always-on scenario names the `core` preset.

- `.env.example`: `COMPOSE_PROFILES` set to the `personal` preset, with the other presets as comments and the three variables every deployment must set marked so.
