## Why

AscendAI has no real authentication. `apps/ascend-agent/src/main/java/com/lukk/ascend/ai/agent/config/SecurityConfig.java` ships with `app.security.enabled=false` (permitAll on every request), and flipping the flag only buys a single in-memory HTTP Basic user whose defaults are `admin`/`admin` (`config/properties/SecurityProperties.java`, `application.yaml` lines 68-74, read from `SECURITY_ENABLED`, `SECURITY_USERNAME` and `SECURITY_PASSWORD`), with CSRF disabled. User identity, the key for chat history, RAG scoping and semantic memory, is a client-supplied `X-User-Id` header (`controller/PromptController.java` lines 86-88) falling back to `app.user.default-id=user1`. Anyone who can reach port 9917 can read or write any user's conversation and memories by typing a header. The downstream services are fully open as well: AscendMemory (:7020), ascend-audio-scribe (:7017), ascend-web-hunter (:7021), ascend-ocr (:7022) and ascend-weather-mcp (:9998) accept unauthenticated REST and MCP calls, including AscendMemory's destructive `POST /api/v1/memory/wipe` and `DELETE /api/v1/memory`.

The personal assistant itself needs real login (owner answer 70.2 of 2026-10-04). The mobile app logs in to Keycloak and receives OAuth tokens, and the backend authenticates every request with those bearer tokens. So basic Keycloak login is personal work, not company work. Owner rule of 2026-10-04: the personal assistant comes first, nothing personal, web-hunter or base may depend on company work, and company work comes last and only plugs in through extension points with safe defaults. This change is therefore the personal half of what `add-auth-and-identity` used to hold: one Keycloak realm for the one tenant `default`, the agent as an OAuth2 resource server, two roles, the app client, the confidential clients the personal assistant needs, the service token for our own services, and a guard that keeps a public deployment from starting without login. Everything a company needs on top (corporate sign-on, several tenants, directory groups and group principals for retrieval access lists) stays in `add-auth-and-identity` and plugs into the extension points this change defines.

Build order (owner build order of 2026-10-04, which supersedes the earlier orders): build group 3 (base), position 3. It needs `upgrade-spring-boot-4` (group 3, position 2) for Spring Boot 4, Spring Security 7.1.1 and the RFC 7807 problem detail of its D19, `close-agent-test-gaps` (group 3, position 1) for the shared end-to-end harness its identity spec uses (task 10.8), and `add-ascend-python-common` and `add-python-runtime-upgrades` (group 2) for its Python service section (the `ascend-python-common` library and FastMCP 4). `harden-cloud-deployment` (group 3, position 4) lands directly after it (owner answer 72.1 of 2026-10-06): it adds the Keycloak site block and the login and token rate limits to the `gateway/Caddyfile` it creates, and it writes the production checklist around the D21 guard of this change, which is the one production login guard. The changes that land after it add their own rows to its authorization matrix (D4) and read the tenant only through its `TenantContext` (D3): in build group 3 `harden-cloud-deployment`, `add-deployment-modules`, `add-shared-scheduler`, `add-document-management-api` and `add-chat-streaming-and-conversations`, and in build group 4 every personal change from `add-agent-skills` to `add-flutter-chat-app`. Company work of build group 5 (`add-auth-and-identity`, `add-tenant-isolation` and the rest) plugs into its ports later. This change does not wait for it.

## What Changes

- ascend-ai-agent becomes an OAuth2 resource server on Spring Security 7.1.1, the version `upgrade-spring-boot-4` brings with Spring Boot 4. JWT validation against a configurable `issuer-uri`. That issuer is the platform's own Keycloak realm `ascend-ai`, added as a docker-compose service with a checked-in realm export. The export provisions the public app client `ascend-flutter` (authorization code with PKCE `S256`, direct access grants off, redirect URIs `http://127.0.0.1/callback`, `com.lukk.ascend:/callback` and the exact web address, owner decision 65.2 of 2026-10-04), realm roles `USER` and `ADMIN`, the `email` protocol mapper, a password policy with brute-force detection, and explicit realm session and token lifetimes. It also provisions two confidential clients the personal assistant needs: `ascend-openclaw-host`, with only the client credentials grant and the only client holding the client scope `channel.relay`, and `ascend-agent-directory`, with only the service account role `view-users` of `realm-management`, used to resolve a user offline for scheduled jobs and for the plugin host. Validating a different issuer's tokens directly remains possible as an escape hatch.
- One tenant. Every identity this change resolves carries the tenant `default`. The tenant comes from a `TenantResolver` port whose default implementation answers `default`. `add-auth-and-identity` replaces it with the tenant claim when company work lands. Nothing in this change reads a `tenant` claim.
- Password sign-in is the default and the path everything else is built on. A person types their password on Keycloak's own login page, and the application receives an authorization code. The application never handles the password. The direct access grant stays disabled on the app client.
- **BREAKING**: `X-User-Id` header trust is removed. User identity is derived from validated token claims (`sub`, `preferred_username`, `email`). `app.user.default-id` survives only in the `dev` profile.
- Role model. `USER` may chat (`POST /api/v1/ai/prompt`) and upload documents (`POST /api/v1/ingestion/upload`). `ADMIN` additionally may trigger ingestion runs (`POST /api/v1/ingestion/run`). Roles map from Keycloak realm roles to Spring authorities. `USER` is the realm default role. `ADMIN` is assigned deliberately. The authorization matrix holds a row for every endpoint that exists when this change is implemented. Each later change adds the rows of its own endpoints in its own tasks, and a coverage test fails the build when an endpoint has no row (D4). The path `/api/v1/channel-host/**` of `add-openclaw-plugin-host` needs the scope `channel.relay` in every profile, `dev` included, and that change adds its row. A scope is not a role.
- Dev-mode escape hatch. A `dev` profile keeps today's permitAll and default-user behaviour for local single-user work and ad-hoc Bruno calls, except on `/api/v1/channel-host/**`. The docker-compose posture defaults to secured.
- Production guard. When the Spring profile `production` is active (a public deployment), the agent refuses to start if the `dev` profile is also active, if no issuer is configured, or if `SERVICE_AUTH_TOKEN` is unset or empty (D21). It is the one production startup guard of the agent (owner answers 72.1 of 2026-10-06 and 89.10 of 2026-10-08): `application-production.yaml` with required placeholders for the values a public deployment must supply, and one guard class, `ProductionStartupGuard`, that runs every `ProductionStartupCheck` bean for what a placeholder cannot express. `harden-cloud-deployment`, which lands directly after this change, adds no guard of its own: it adds its datastore credentials to the same file and one check bean, and writes the guard into its production checklist.
- Service-to-service authentication. Every Python service (AscendMemory, ascend-audio-scribe, ascend-web-hunter, ascend-ocr) and ascend-weather-mcp requires a bearer token on both REST and MCP surfaces, a static service token injected through the environment variable `SERVICE_AUTH_TOKEN`. ascend-ai-agent attaches the token on all outbound calls to our own services: the `SemanticMemoryClient` RestClient, the ingestion clients that call ascend-ocr, and the MCP client connections to our own MCP servers. When `add-mcp-tool-servers` lands it moves the MCP attachment into its connection customizer and limits it to entries with `trust: internal`.
- An identity without a token. A request on the channel host path of `add-openclaw-plugin-host` names a chat platform account linked to a user, and a firing of `add-scheduled-tasks` has no request at all. For both, one resolver builds the identity of a known user through Keycloak's admin API with the `ascend-agent-directory` client: the enabled flag and the realm roles, cached for at most the realm access token lifetime in a bounded cache that every agent instance invalidates through a Postgres notification on the channel `identity_cache_evict`, delivered by `PostgresNotificationListener`, the one `LISTEN` connection per instance that later changes reuse (owner answer 87 of 2026-10-08), and failing closed for a disabled or unknown user or an unreachable Keycloak. Next to it, an offline lookup of the enabled users with the `ADMIN` role lets `add-self-improvement` address a report to each of them.
- One tenant seam for every later change (D3): `TenantContext.currentTenantId()` answers the tenant of the current request, and `TenantContext.runAs(tenantId, action)` binds the tenant stored on a row for a background worker (a scheduler firing, a connector run, a subagent run thread, a download ingestion run). With nothing bound it throws. Every later change reads the tenant only through `TenantContext`.
- Extension points with safe defaults, for company work to plug into (D22): `TenantResolver` (default: always `default`), the internal provider port that decides which tenant a resolved identity carries and that no other personal change names, and `IdentityContributor` (default: none registered), which adds typed values to the resolved identity, for example the group principal set of `add-auth-and-identity`. Personal code never reads a value a contributor adds.
- Swagger UI and actuator exposure rules under the secured posture: health and prometheus stay reachable for infrastructure on the management port, OpenAPI docs stay readable, everything else needs a token.
- The old `app.security.*` HTTP Basic block, its `SecurityProperties` binding, the in-memory user and the `SECURITY_ENABLED`, `SECURITY_USERNAME` and `SECURITY_PASSWORD` environment variables are removed (superseded, not deprecated, nothing external depends on them).
- Keycloak is a separate service on its own host address and port (host port 8180 in compose), never routed under a gateway path such as `/auth/`. Development runs `start-dev`, production runs `start` with `KC_HOSTNAME`.
- The production start mode of Keycloak in `compose.yaml` (`start --import-realm` with `KC_HOSTNAME`). The gateway site block for Keycloak's own host name and the rate limits on the Keycloak login and token endpoints belong to `harden-cloud-deployment`, which creates `gateway/Caddyfile` and lands directly after this change (owner answer 72.1 of 2026-10-06).
- End-to-end tests for one tenant: Keycloak e2e users of tenant `default` in the development overlay (`e2e-user`, `e2e-user-2`, `e2e-admin`), one shared Bruno token helper, and deterministic specs for the token claims, the PKCE login, the role matrix and the service token of each service.

## Capabilities

### New Capabilities

- `agent-authentication`: ascend-ai-agent validates JWTs as an OAuth2 resource server, the endpoint authorization matrix (`USER` and `ADMIN`, public infrastructure endpoints, Swagger and actuator rules, the rule that each later change adds its own rows, and the coverage test), the dev-profile fallback, the production guard, and the end-to-end coverage for one tenant.
- `user-identity`: user identity resolved from validated token claims (`sub`, `preferred_username`, `email`), the tenant from the `TenantResolver` port with the default `default`, `X-User-Id` no longer trusted, the identity extension point, the identity of a known user resolved without a token for a linked chat platform account or a scheduled firing, and the offline lookup of the `ADMIN` users.
- `identity-provider`: Keycloak as the platform's identity layer, one realm and one issuer, password sign-in through Keycloak's own login page as the default (the login and token rate limits are added by `harden-cloud-deployment` to this capability, owner answer 72.1 of 2026-10-06), the checked-in realm export whose contents are a contract (roles, PKCE client with direct access grants off, the `email` mapper, password policy, session and token lifetimes, the confidential clients `ascend-openclaw-host` with the scope `channel.relay` and `ascend-agent-directory` with `view-users`), the development overlay with the e2e users of tenant `default`, and the issuer swap escape hatch.
- `service-authentication`: bearer-token enforcement on the REST and MCP surfaces of all five downstream services, plus ascend-ai-agent attaching the token on every outbound call to them.

### Modified Capabilities

- `semantic-memory-client`: outbound requests to AscendMemory gain a mandatory `Authorization: Bearer` header carrying the service token.
- `ascend-agent-containerization`: `.env.example` lists the secrets `SERVICE_AUTH_TOKEN`, `KEYCLOAK_DIRECTORY_CLIENT_SECRET` and `E2E_USER_PASSWORD`, the issuer variable `KEYCLOAK_ISSUER_URI` has a default and so only a row in the configuration reference (owner rule 98 of 2026-10-08), and no compose file or `.env.example` names the removed login variables.

`production-deployment` is not touched by this change. `harden-cloud-deployment` creates it after this change lands, already with the Keycloak site, the rate limits, `SERVICE_AUTH_TOKEN` among the credentials and the issuer variable in the production checklist (owner answer 72.1 of 2026-10-06).

(`ingestion-security` was reviewed and left unchanged. Its requirements cover upload hygiene (filename sanitization, MIME allowlist, size limits), not authentication posture. The authorization matrix for ingestion endpoints lives in `agent-authentication` to keep one source of truth.)

## Impact

- ascend-ai-agent: `SecurityConfig.java` rewritten on Spring Security 7.1.1 (resource server plus role rules, HTTP Basic path deleted), a matrix coverage test, a production guard, `SecurityProperties.java` replaced, `PromptController.java` and `IngestionController.java` switch from header identity to the authenticated identity, a resolved identity record with the `TenantResolver` and `IdentityContributor` ports, the `TenantContext` seam with `currentTenantId()` and `runAs(tenantId, action)` for background workers, a linked identity resolver through Keycloak's admin API with the `ascend-agent-directory` client and the offline `ADMIN` lookup, outbound token propagation on `SemanticMemoryClient`, the ingestion clients and the MCP connections to our own servers, `build.gradle.kts` swaps `oauth2-client` for `oauth2-resource-server`, `application.yaml` and `application-docker.yaml` gain issuer-uri and service-token config and lose the `app.security` block.
- Python services (AscendMemory, ascend-audio-scribe, ascend-web-hunter, ascend-ocr): the bearer token check is written once in the `ascend-python-common` library of `add-ascend-python-common`, as a FastAPI dependency that `create_service_app` installs on every REST router and a FastMCP auth hook on `/mcp`, with `/health`, `/ready` and `/metrics` open. It is tested once in the library, and each service adds one wiring test. No service gets a token spec of its own or a throwaway container (owner answer 91.3 of 2026-10-08). New `SERVICE_AUTH_TOKEN` env var, a field of the library's `ServiceSettings` base.
- ascend-weather-mcp: a Spring filter enforcing the same bearer token.
- compose.yaml: new `keycloak` service and realm import volume, `SERVICE_AUTH_TOKEN` and `KEYCLOAK_ISSUER_URI` wiring for all services, and every operational value of the agent and of the realm export as a `${VAR:-default}` setting with its row in the configuration reference (owner rules 98 and 98.3 of 2026-10-08, tasks 1.13, 3.11 and 9.8). The realm import splits into a production export and a development overlay, so the seeded users and the password-grant clients the e2e suite needs never reach a production deployment.
- Operations: an administrator runbook in `docs/SECURITY.md` covering account creation, the password policy and role assignment, plus the standing cost of running Keycloak: a database, certificates, backups with a tested restore, and an upgrade habit.
- e2e and Bruno: the collection at `docs/api/request/AscendAI/` gets one shared token helper, every existing spec is updated in place for the secured posture (owner answer 67.2 of 2026-10-04), and the five service suites send the service token. The role matrix spec has no expired-token row, because an expired token is proved by a slice test with a locally signed token and no short-lived Keycloak client exists (owner answer 90 of 2026-10-08). The identity spec runs in the deterministic phase of `close-agent-test-gaps` D7 with AscendMemory faked, so it wipes no memories (owner answer 91.1 of 2026-10-08).
- Docs: root `AGENTS.md`, per-module `AGENTS.md` files, and a new `docs/SECURITY.md` (auth setup, token flow, issuer swap recipe, the matrix row procedure for later changes, and rotating the secrets of the two confidential clients).
- Plugs in later: `add-auth-and-identity` (company, build group 5) adds the tenant claim, identity brokering, Keycloak Organizations, SAML, directory group mapping, group principals for retrieval access lists and the test tenants `e2e-acme`, `e2e-globex` and `e2e-soul` on top of this change, through `TenantResolver` and `IdentityContributor` and through its own realm export additions. This change does not depend on it.
- This change ships no schema change.
