## Context

ascend-ai-agent's security surface today is a placeholder. `SecurityConfig.java` is a two-branch filter chain: with `app.security.enabled=false` (the default) every request is permitAll, and with it enabled a single in-memory HTTP Basic user (`admin`/`admin` defaults from `SecurityProperties.java`) guards everything except `/actuator/health` and the Swagger paths. CSRF is disabled, sessions are stateless. User identity, the partitioning key for Redis chat history, Postgres persistence, Qdrant memory and RAG scoping, comes from an `X-User-Id` request header (`PromptController.java:86-88`) that any client can set to any value, falling back to `app.user.default-id=user1`.

The five downstream services have zero inbound auth. Their only middleware is request-id propagation and security response headers (for example `apps/ascend-memory/src/observability/request_context.py`, which `add-ascend-python-common` moves into the `ascend-python-common` library). AscendMemory's `POST /api/v1/memory/wipe` and `DELETE /api/v1/memory` are destructive and reachable by anyone on the docker network or exposed port. ascend-ai-agent talks to them through a `RestClient` in `SemanticMemoryClient`, through ingestion REST clients (ascend-ocr), and through Spring AI's MCP client (`spring.ai.mcp.client.streamable-http.connections` in `application.yaml` lines 391-398: ascend-audio-scribe, weather, ascend-web-hunter).

Useful groundwork already exists: `spring-boot-starter-security` and `spring-boot-starter-oauth2-client` are on the classpath (`build.gradle.kts` lines 75 and 45, aliases declared in `gradle/libs.versions.toml`), and the `SecurityConfig` Javadoc earmarks the OAuth2 and Keycloak swap as a separate change. This is that change, for the personal assistant.

Owner answer 70.2 of 2026-10-04: the personal assistant itself needs real Keycloak login. The mobile app logs in to Keycloak and receives OAuth tokens, and the backend authenticates every request with those bearer tokens. Owner rule of 2026-10-04: the personal assistant comes first. Nothing personal, web-hunter or base may depend on company work. Company work comes last and only plugs in through extension points with safe defaults. This change was split out of `add-auth-and-identity` on 2026-10-04 to follow that rule. It holds everything one person needs to log in and to call the agent safely. `add-auth-and-identity` keeps the company parts and plugs into this change.

Constraints:

- The changes that land after this one key on the identity this change resolves: `userId` from `sub`, the tenant `default`, and the roles `USER` and `ADMIN`. Every later change of build groups 3 and 4 of the owner build order of 2026-10-04 that adds endpoints adds its own rows to the matrix of D4 and reads the tenant only through `TenantContext` (D3). `add-openclaw-plugin-host`, `add-scheduled-tasks` and `add-self-improvement` use the two confidential clients, the `channel.relay` scope and the identity resolved without a token (D2, D20).
- The e2e suite and the Bruno collection (`docs/api/request/AscendAI/`) currently send `X-User-Id` and no credentials. Local single-user workflows must keep working without a Keycloak round trip.
- `harden-cloud-deployment` owns network and TLS. This change is app-level auth only, and tokens travel over plain HTTP inside the compose network, which is accepted here.
- Keycloak is now a service the platform operates. If it is down, nobody signs in. It needs a database, certificates, backups and a standing upgrade habit. This is a cost of the decision and it is priced in the risk list.

## Goals / Non-Goals

Goals:

- Verified user identity: every request to a protected ascend-ai-agent endpoint carries a JWT validated against a configurable OIDC issuer, and identity fields are read from claims, never from client-controlled headers.
- Role-based authorization: `USER` (chat, upload) and `ADMIN` (ingestion run and the administrator endpoints of later changes) mapped from realm roles, with one visible matrix that every later change extends.
- Closed downstream perimeter: no unauthenticated call reaches any Python service or ascend-weather-mcp, on either the REST or the MCP surface.
- Keycloak as the product's identity layer: one self-hosted realm is the issuer in development and in production, provisioned from a checked-in export, with `docker compose up` yielding the same realm shape an operator deploys.
- Password sign-in that works on its own: an administrator creates an account, sets a password policy and assigns roles, and that is a complete, usable product.
- A public deployment never runs without login (D21).
- Extension points with safe defaults that company work plugs into without editing this change's code (D22).

Non-Goals:

- More than one tenant. Every identity carries the tenant `default` here. The `tenant` claim, its protocol mapper and tenant enforcement belong to `add-auth-and-identity` and `add-tenant-isolation`.
- Groups, group principals and retrieval access lists. Those belong to `add-auth-and-identity` (company), which plugs in through `IdentityContributor`.
- Corporate single sign-on through identity brokering, Keycloak Organizations and SAML. `add-auth-and-identity`.
- TLS, network segmentation, secret-manager integration, which are `harden-cloud-deployment`.
- Login UI. The Flutter app does the authorization code and PKCE flow itself against Keycloak's own login page, and we provision its client and nothing more.
- Per-user rate limits or quotas, and audit logging of auth events. Company changes.
- Roles beyond `USER` and `ADMIN`.

## Decisions

Decision numbers follow the numbers these decisions had in `add-auth-and-identity` before the split of 2026-10-04, so a cross-reference written against those numbers still lands on the right text. The decisions that stayed in `add-auth-and-identity` keep their numbers there.

### D1 - OAuth2 resource server with issuer-uri, not oauth2-client or a Keycloak adapter

ascend-ai-agent validates tokens and never initiates a login. So the correct Spring artifact is `spring-boot-starter-oauth2-resource-server` (Nimbus JWT decoder plus `issuer-uri` discovery), replacing the currently unused `spring-boot-starter-oauth2-client` dependency in `build.gradle.kts`. Configuration is the standard `spring.security.oauth2.resourceserver.jwt.issuer-uri`. The resource server DSL is the one of Spring Security 7.1.1, which `upgrade-spring-boot-4` brings with Spring Boot 4.1.1, and this change writes its filter chain against that version. The decoder pulls JWKS from the issuer's discovery document. Under D2 that issuer is our own Keycloak realm. The property remains the escape hatch for a deployment that validates a provider's tokens directly. The deprecated Keycloak Spring adapter is not an option (end of life), and rolling our own JWT filter would re-implement what Nimbus already does.

Alternatives considered: keep HTTP Basic and harden it, which has no identity claims, no roles, and no mobile-app story. Session-based `oauth2Login` in the agent, which is the wrong topology, because the Flutter app is the OAuth client and the agent is a pure API.

### D2 - Keycloak is the identity layer, one realm, one issuer, and the realm export provisions it

Keycloak is the product's identity provider in production as well as locally. One realm, `ascend-ai`, is the only token issuer ascend-ai-agent validates against.

The compose service is `quay.io/keycloak/keycloak` with the export at `keycloak/realm-ascend-ai.json` mounted into `/opt/keycloak/data/import/`, backed by the external PostgreSQL on a dedicated `keycloak` database. Keycloak is a separate service on its own host address and port. It is not routed under a path such as `/auth/` behind the agent's gateway. The host port is 8180, mapped to the container's 8080, chosen because no service in `compose.yaml` or `compose.ascend-web-hunter.yaml` publishes it. Development runs `start-dev --import-realm`. A production deployment runs `start --import-realm` with `KC_HOSTNAME` set to the public Keycloak address (for example `https://auth.<domain>`), `KC_HTTP_ENABLED=true` and `KC_PROXY_HEADERS=xforwarded` behind the TLS proxy that `harden-cloud-deployment` adds directly after this change, and the difference between the two is a command and an environment block, not a different realm.

Login and token rate limits are set in the reverse proxy in front of Keycloak: a per-client-address limit on `/realms/ascend-ai/login-actions/authenticate` and on `/realms/ascend-ai/protocol/openid-connect/token`, answering 429 over the limit. Keycloak's own brute-force detection locks an account after repeated failures, and the proxy limit slows a guessing run across many accounts before it reaches Keycloak at all. The limit values are configuration in the proxy file, not code. That proxy is the gateway of `harden-cloud-deployment` (build group 3, position 4), which lands directly after this change (build group 3, position 3), creates `gateway/Caddyfile` with a Keycloak site of its own and adds these limits there (owner answer 72.1 of 2026-10-06, former tasks 1.6 gateway part and 1.7 of this change). This change adds the production start mode to the `keycloak` service of `compose.yaml` (task 1.6). There is no separate production compose file. Keycloak is a separate site address with its own host name, and no path of the agent's site reaches it.

The export is the provisioning of a real system, so what it must contain is a contract rather than a convenience:

| Element | Why it is in the export |
| :--- | :--- |
| Realm `ascend-ai`, realm roles `USER` and `ADMIN`, with `USER` as the realm default role | The role model D4 maps from, and the reason a new account has a role at all on its first sign-in |
| Public client `ascend-flutter`, authorization code with PKCE `S256`, no secret, no direct access grants, redirect URIs `http://127.0.0.1/callback` (desktop, Keycloak accepts any port for this loopback address as RFC 8252 section 7.3 asks), `com.lukk.ascend:/callback` (Android and iOS) and the web build's exact hosting address followed by `/callback`, read from `${ASCEND_CHAT_WEB_URL}` at realm import and left out when that variable is empty, with the same address as the only web origin, and never a wildcard (owner decision 65.2 of 2026-10-04) | The application client. Direct access grants stay off, because a password grant is prohibited by the security standard this repo follows, and it is not what password sign-in means (D2a) |
| A realm password policy: minimum length, and brute-force detection enabled | Password sign-in is the default path, so the policy that protects it is part of the provisioning rather than something an operator remembers |
| A protocol mapper emitting `email` into the access token | The claims contract D3 reads |
| Realm SSO session and access token lifetimes | The staleness bound for a role change and for the cache of D20. They are a product disclosure, so they are checked in rather than left at whatever the default happens to be |
| Confidential client `ascend-openclaw-host` with only the client credentials grant, whose secret only the `channels` containers of `add-openclaw-plugin-host` hold, and a client scope `channel.relay` assigned to it and to no other client | The channel host is not a user, so it gets a scope rather than a third role (D4). Only a token holding `channel.relay` may call `/api/v1/channel-host/**` |
| Confidential client `ascend-agent-directory` with the service account role `view-users` of `realm-management` and nothing else | The identity resolved without a token (D20) reads a user's enabled flag and realm roles through Keycloak's admin API with it |
| Nothing else | No seeded human user, no direct access grants, no group mapper, no tenant mapper, no brokered provider |

The group mapper, the `tenant` mapper and the brokered-provider template are company additions of `add-auth-and-identity`, which adds them to this export in its own tasks.

The seeded development user, the password-grant client that the Bruno collection and the e2e suite need, the e2e users of tenant `default` (`e2e-user`, `e2e-user-2`, `e2e-admin`) and the `ascend-openclaw-host` client with a development secret are a development overlay, imported only in the development compose posture. They are not in the production export, because a seeded account with both roles is a backdoor and a password grant is one the standard forbids outright.

Why an export rather than Terraform or keycloak-config-cli: one file, no extra tooling, and the same provisioning shape this repo already uses for Grafana dashboards. The export is the source of truth. A console edit that is not reflected back into it is lost at the next clean deploy, and the runbook in `docs/SECURITY.md` says so.

Beyond role mapping (D4), nothing in the agent depends on a Keycloak-specific token shape.

### D2a - Password sign-in is the default, and it is not the direct access grant

The default and primary way a person signs in is with a Keycloak account and a password. The application redirects to Keycloak's own login page, the person types their password there, Keycloak returns an authorization code, and the application exchanges that code for tokens using PKCE. The application never sees, holds, or forwards the password. This is the authorization code flow, and it is what the `ascend-flutter` client is provisioned for.

The direct access grant, commonly called the resource owner password credentials grant or the password grant, is a different mechanism. There the application itself collects the password and posts it to Keycloak's token endpoint. It looks like the same feature because both involve a password, and it is not: it puts the person's credential inside our application, it defeats any interactive step Keycloak might add later such as a second factor or a forced password reset, and OAuth 2.1 removes it outright. The repo's security standard prohibits it.

So the two statements below are both true at once:

- Password sign-in is the default path and must work end to end.
- Direct access grants are disabled on `ascend-flutter` and on every client a person uses.

The one place a password grant survives is the development overlay's own clients, so the e2e suite and the Bruno collection can obtain a token without driving a browser. Those clients are not in the production export (D2), and importing the production export alone yields no client that accepts a password grant. The realm-export verification asserts exactly that.

This is written out at length because the two mechanisms are one word apart. A future reader asked to "turn on password login" could reasonably reach for `directAccessGrantsEnabled`, which would undo a defect already caught and fixed.

### D3 - Identity claims

The user identifier used for Redis, Postgres and Qdrant partitioning is the token's `sub` claim: stable, unique inside one application, never reassigned, which is everything a partition key needs. `preferred_username` is carried for logging and display only, because it can change and storage must never be keyed on it.

The resolved identity carries:

| Field | Source | Job |
| :--- | :--- | :--- |
| `userId` | `sub` | Storage partition key for chat history, semantic memory, RAG scoping and log attribution |
| `username` | `preferred_username` | Display and logging only |
| `email` | `email` | Display and logging only |
| `tenant` | the `TenantResolver` port (D22), `default` in this change | The tenant every later change keys on |
| `roles` | role claim through the D4 converter | Endpoint authorization only |
| `extensions` | the `IdentityContributor` beans (D22), empty in this change | Typed values company work adds, for example the group principal set of `add-auth-and-identity` |

Which claim carries the email is configuration under `app.identity.claims`, not a branch in code. The value object is a Java record, resolved once per request by a dedicated resolver component and injected into controllers in place of the `userIdHeader` parameter in `PromptController` and its equivalent in `IngestionController`. The same record is also built without a token, for a linked chat platform account and for a scheduled firing (D20), so every consumer sees one identity type whatever produced it.

`TenantContext` in the package `com.lukk.ascend.ai.agent.security` is the one tenant seam every later change reads (owner decision 65.23 of 2026-10-04, dependency fix of 2026-10-05). No later change names `TenantResolver` (D22), which stays the internal provider port of this change, and no later change adds a tenant accessor of its own.

- `TenantContext.currentTenantId()` returns the tenant bound to the current thread. Inside a request that is the tenant of the resolved identity of the request. It fails closed: with nothing bound it throws rather than answering a default.
- `TenantContext.runAs(tenantId, action)` binds a given tenant on the calling thread for the duration of `action` and restores the previous binding afterwards, also when `action` throws. A background worker that acts for a stored row (a scheduler firing of `add-shared-scheduler`, a connector run of `add-connector-framework`, a subagent run thread of `add-agent-subagents`, a download ingestion run of `add-download-ingestion`) binds the tenant stored on that row before any other step and reads it through `currentTenantId()` the way request code does. A blank tenant id is refused.
- Code that hands work to another thread without such a row passes the value captured on the request thread through `runAs` on the new thread, and never reads the accessor there with nothing bound.

In a personal deployment every bound tenant is `default`. `add-tenant-isolation` (company, build group 5) needs no change to this seam: the tenant comes from `TenantResolver`, which `add-auth-and-identity` replaces, and `TenantContext` already fails closed. The `PrincipalContext.currentPrincipals()` accessor of the same owner decision belongs to `add-auth-and-identity`, which adds the principal set.

There is no data migration. The data that exists today in the development stores is disposable (owner answer 73.1 of 2026-10-06), so this change neither converts the `user1`-keyed local data nor depends on it, and it may start from empty stores. Data written under the dev profile after this change lands belongs to the dev-profile identity (D5).

Trade-off acknowledged: switching identity providers later changes `sub` values and orphans per-user data. Accepted, because user data migration tooling is out of scope and `sub` is the only claim with a stability guarantee inside one issuer. Under D2 that risk is small, because `sub` is Keycloak's own subject.

### D4 - Role mapping via a converter, and one matrix every later change extends

Keycloak puts realm roles at `realm_access.roles`, Entra ID uses `roles`, and others use `scope`. A single `JwtAuthenticationConverter` with a custom granted-authorities converter reads `realm_access.roles` when present, else a top-level `roles` claim, and maps entries to `ROLE_USER` and `ROLE_ADMIN`. That keeps role mapping issuer-agnostic. The converter also keeps the scope authorities Spring Security derives from the `scope` claim, so a client credentials token of `ascend-openclaw-host` carries `SCOPE_channel.relay`. A scope is not a role: it names what a client may call, and it never reaches the resolved identity of a person.

`USER` is the realm's default role in the export, granted to every new account, so a person who has just signed in for the first time can use the product. `ADMIN` is assigned deliberately by an administrator.

### D5 - Dev profile keeps permitAll, docker defaults to secured

Spring profile `dev`: permitAll chain plus a synthetic identity (`app.user.default-id`, username `dev`, tenant `default`, roles `USER` and `ADMIN`) so every service layer downstream sees a fully populated identity and there is exactly one identity code path. Ad-hoc Bruno calls and quick local runs use this. The default (no profile) and `docker` profiles require JWTs. One path is not open under `dev`: `/api/v1/channel-host/**` requires the scope `channel.relay` in every profile, because a request there names its sender as data, and anyone who could call it without a credential could act as any linked user. That rule is written in the `dev` chain by this change, so `add-openclaw-plugin-host` only adds its row to the secured chain. The boolean `app.security.enabled` toggle and the `app.security.user` block are deleted, so posture is a profile decision rather than a flag. A startup WARN fires when the `dev` chain is active. D21 keeps `dev` away from a public deployment.

The dev identity runs `IdentityContributor` beans like any other identity, so company work that adds one (for example the dev principal set of `add-auth-and-identity` D5b) needs no edit of this chain.

### D6 - Service-to-service auth: static bearer token now, client credentials as upgrade path

Baseline: one shared secret, `SERVICE_AUTH_TOKEN`, injected through the environment into all five downstream services and into ascend-ai-agent. Downstream enforcement:

- Python services: a FastAPI dependency (HTTPBearer plus constant-time compare) applied to every REST router, and the same check on the FastMCP surface through its auth hook, so `/mcp` is not a bypass. `/health` (and `/ready`, `/metrics` where present) stay open for compose healthchecks and Prometheus. The check is written once, in the `ascend-python-common` library of `add-ascend-python-common`: a FastAPI dependency that the library's `create_service_app` installs on every REST router of a service, and a FastMCP auth hook on the MCP endpoint, with `/health`, `/ready` and `/metrics` open. The MCP check is written against the `auth` or middleware API of FastMCP 4, which `add-python-runtime-upgrades` puts in the library, and it holds for both protocol eras: a sessionless 2026-07-28 request carries the bearer token on every request, and a handshake session carries it on each HTTP request of the session, so every one of those requests is checked. `SERVICE_AUTH_TOKEN` is a field of the library's `ServiceSettings` base, and the startup posture rule below is checked there too. No service holds its own copy, and each service only adds one wiring test.
- ascend-weather-mcp: a `OncePerRequestFilter` doing the same compare ahead of the MCP endpoints, health excluded.
- An unset or blank `SERVICE_AUTH_TOKEN` in a service means fail-fast at startup in the docker posture (refuse to boot open). A dev or local run without the env var logs a WARN and stays open, to keep today's uvicorn and bootRun workflow.

ascend-ai-agent attaches `Authorization: Bearer ${SERVICE_AUTH_TOKEN}` on the `SemanticMemoryClient` RestClient (default header on the builder), the ascend-ocr and ingestion clients, and the MCP client connections to our own MCP servers (ascend-audio-scribe, weather, ascend-web-hunter), through a Spring AI 2.0 `McpClientCustomizer`, the type that replaces the 1.1.5 customizer under `upgrade-spring-boot-4`. Every MCP connection configured when this change lands is one of our own servers. `add-mcp-tool-servers`, which lands later, introduces servers that are not ours and the `trust` field of a server entry. It moves this attachment into its `McpServerConnectionCustomizer` (its D3) and sends the token only to entries with `trust: internal`, never to `trust: external` (its required edit, made there).

Why not client credentials from day one: it doubles the moving parts (every Python service becomes a resource server needing a JWKS fetch and clock sync against Keycloak, and the agent needs a token-refresh loop) for a perimeter that is compose-internal. The upgrade path is real and cheap later: Keycloak already runs, so add a confidential client per service, switch the FastAPI dependency from string compare to JWT validation against the same issuer, and swap the static header for `client_credentials` acquisition in the agent. The spec requirements are written against "a valid bearer token" so the upgrade does not change observable contracts. Known trade-offs of the baseline: one shared secret means no per-service identity or revocation granularity, and rotation is a coordinated env change plus restart, accepted for the current single-operator deployment and revisited by `harden-cloud-deployment`.

### D20 - An identity without a token, for a linked chat account and a scheduled firing

Two later changes act for a known user with no token in hand. A message on the channel host path of `add-openclaw-plugin-host` names a chat platform account that a user linked to their account, and the request is authenticated as the channel host, not as that user. A firing of `add-scheduled-tasks` runs on a scheduler thread with no request at all. Both need the same identity a token gives: `sub`, tenant and roles.

One resolver serves both. It builds the identity of a known user through Keycloak's admin API with the confidential client `ascend-agent-directory` (D2), which holds only `view-users`: the user's enabled flag and realm roles. The tenant comes from the `TenantResolver` port and the extensions from the `IdentityContributor` beans, given the Keycloak user representation instead of a token, so a user resolves an equal identity whether they arrive with a token or through a link. The result is cached per user for at most the realm access token lifetime, so a role change is never staler than with a token, and the cache holds a bounded number of users, at most 10000 by default (owner answer 87 of 2026-10-08, rule R1, and owner answer 98.4). Its lifetime is derived from the same setting the realm export reads for the access token lifetime, so the two cannot disagree (task 3.11). Several agent instances run at once, and each has its own cache, so the cache also gets shared invalidation: when any instance's fresh lookup finds that a user's enabled flag or roles differ from what it had cached, or finds the user disabled or unknown, it sends `pg_notify('identity_cache_evict', <sub>)`, and every instance drops that user's entry, so no instance keeps acting for a disabled user while another has already refused them. Any later agent code that changes a user's roles or enabled flag (a company administrator action, for example) sends the same notification through the one method `IdentityCacheInvalidator.evict(sub)` this change adds, and needs no edit of the resolver. The notifications reach every instance through `PostgresNotificationListener`, which this change adds as the agent's one Postgres `LISTEN` connection per instance: a bean registers a `PostgresNotificationHandler` with its channel name, the listener reconnects with a backoff that starts at 1 second, doubles after each failed attempt, stops growing at 30 seconds and adds random jitter (owner answer 98.4 of 2026-10-08), and after a reconnect it calls each handler's `onReconnect()`, because notifications sent while it was disconnected are lost. The identity handler clears its whole cache there. Every later agent change that needs a cross-instance signal registers a handler on this listener with its own channel name and opens no `LISTEN` connection of its own (sent to every change through the inbox of this round). A payload is the user's `sub`, never a secret. When Keycloak cannot be reached, or the user is disabled or unknown, the resolution fails closed: the caller refuses the message or the firing, and never answers with an older identity. Under the `dev` profile it resolves to the dev identity of D5.

Next to it, the same client gives an offline lookup of the enabled users holding the `ADMIN` role, filtered to one tenant through the `TenantResolver` port (in this change every user is in tenant `default`), so `add-self-improvement` can address a report to each of them. Until this change lands, the deployment's single owner is the only recipient.

This is not the deferred identity link of `add-auth-and-identity` D11 and D12, which joins one person's identities at two identity providers. The link here joins a chat platform account to a user of this realm, and `add-openclaw-plugin-host` owns it. Storing a snapshot of the user at link time was rejected, because a disabled user would keep acting through the chat platform for as long as the link lives.

`docs/SECURITY.md` carries the runbook for rotating the secrets of `ascend-openclaw-host` and `ascend-agent-directory`.

### D21 - A public deployment refuses to start without login, through one production startup guard

A public deployment runs with the Spring profile `production` (`SPRING_PROFILES_ACTIVE=docker,production`, which `harden-cloud-deployment` writes into its deployment guide when it lands directly after this change). Owner answer 89.10 of 2026-10-08: there is one production startup guard for the whole agent, made of two parts, and this change creates both.

- `apps/ascend-agent/src/main/resources/application-production.yaml`, read only while the profile `production` is active and listed after `docker`, so it wins over `application-docker.yaml`. It sets every value a public deployment must supply from its environment variable with no default, a required placeholder: `spring.security.oauth2.resourceserver.jwt.issuer-uri: ${KEYCLOAK_ISSUER_URI}` and `app.service-auth.token: ${SERVICE_AUTH_TOKEN}`, the property that the record `ServiceAuthProperties` of task 6.1 binds (owner answer 98.3 of 2026-10-08). An unset variable then stops start-up with Spring's own error that names the missing placeholder, before the agent accepts a connection. No guard class repeats a check a placeholder already makes.
- One guard class, `ProductionStartupGuard`, active only with the profile `production`, for the checks a placeholder cannot express. It runs every bean of the small interface `ProductionStartupCheck` at start-up, and each check that refuses is reported through one `FailureAnalyzer` as one ERROR line that names the property or the check and never a value, with no stack trace, and a non-zero exit before the agent accepts a connection. This change registers three checks: the `dev` profile is not active, because its chain lets every request through, the issuer is not blank, and the service token is not blank, because a variable set to an empty string passes a placeholder.

This is the one production guard (owner answers 72.1 of 2026-10-06 and 89.10 of 2026-10-08). `harden-cloud-deployment` lands after this change and extends it, never adds a guard of its own: it adds the datastore credentials to `application-production.yaml` and one `ProductionStartupCheck` bean that refuses a blank or known weak datastore credential (its D3). Any later change that needs a production start-up refusal adds a required placeholder or a `ProductionStartupCheck` bean. The guard is a start-up check rather than a flag, so no environment variable can turn it off. Without the `production` profile neither `application-production.yaml` nor the guard is read, so local work and the e2e stack run as before. Several agent instances each run the guard at their own start, which needs no shared state (owner answer 87 of 2026-10-08).

### D22 - Extension points for company work, with safe defaults

Company work plugs into this change and never edits its classes (owner rule of 2026-10-04). Two ports exist for that, both in the package `com.lukk.ascend.ai.agent.security`:

- `TenantResolver`: answers the tenant of an identity, given either the validated `Jwt` or the Keycloak user representation of D20. The default bean, registered with `@ConditionalOnMissingBean`, answers `default` for both. `add-auth-and-identity` registers its claim-reading resolver, which reads the `tenant` claim and the `tenant` user attribute, and the default bean then does not exist.
- `IdentityContributor`: given the same input, adds typed values to the immutable `extensions` of the resolved identity, keyed by their Java type. No contributor is registered by this change, so `extensions` is empty. `add-auth-and-identity` registers the contributor that adds the group principal set, and its own `PrincipalContext` reads that value.

Both ports run on all three paths that build an identity: a token, the dev identity and the resolution without a token. A contributor that throws fails the request or the resolution, it never leaves a half-built identity. Personal code reads the five named fields only and never reads an extension value, so removing every contributor changes nothing a personal feature does.

Why ports and not fields for groups and principals: a field would make every personal class carry company data it never uses, and an empty list in a field cannot tell "this deployment has no groups" from "nothing resolved the groups", the distinction `add-tenant-isolation` decision 2 depends on. A missing extension is that distinction.

## Risks / Trade-offs

The first risk is not a bullet, because it is the standing cost of the platform decision rather than a hazard with a mitigation. Choosing self-hosted Keycloak is choosing to operate it. If it is down, nobody signs in, and there is no degraded mode where the product half works. It needs a database, certificates, backups with a restore that has actually been tested, and an upgrade habit that does not slip. There is no long-term support release to sit on. Minor releases land roughly quarterly and patches roughly monthly, breaking changes have shipped inside patch releases, and sixteen security advisories were published this year through August. The mitigations are ordinary ones: a staging realm on the same version as production, the export as the source of truth so a rebuild is deterministic, and release notes read before every upgrade.

- Somebody reads "password sign-in is the default" and enables the direct access grant on the app client. D2a states the distinction at length, the realm export asserts `directAccessGrantsEnabled` false on `ascend-flutter`, and the export verification is a task rather than a review item.
- A later change forgets its matrix rows, and its administrator endpoint is open to every user. The coverage test of D4 fails the build for any request mapping without an explicit row.
- A shared static service token is a single secret with no rotation story. Mitigated by a constant-time compare, env injection only (never in YAML defaults or logs), fail-fast when unset in the docker posture, the production guard of D21, a documented rotation procedure, and D6's client credentials upgrade path.
- Keycloak adds a boot-order dependency, so the agent fails a JWKS fetch if the issuer is down. Mitigated by compose `depends_on` with a healthcheck on Keycloak, and by the resource server's JWKS fetch being lazy and cached, so brief outages do not kill a running agent.
- A role change is only as fresh as the token that carries it, bounded by the access token lifetime that the realm export sets explicitly. This is a product disclosure in `docs/SECURITY.md`.
- Bruno and e2e breakage, because every existing request lacks credentials. Mitigated by a dedicated migration task, one shared token helper, seeded e2e users of tenant `default` to make it deterministic, and the dev profile as the manual escape hatch.
- `sub` re-keys user data if the issuer is ever swapped. Accepted (D3) and documented in `docs/SECURITY.md`.
- MCP client header injection depends on the Spring AI 2.0 `McpClientCustomizer`. An integration test pins the header actually leaving the agent for each of our own MCP connections.
- Tokens over plain HTTP inside compose. Accepted at this layer, since TLS is `harden-cloud-deployment` scope.
- Company work needs data this change does not resolve (tenant claim, groups). D22 gives it two ports, so it adds beans rather than editing this change's code, and a personal deployment never carries company data.

## Migration Plan

1. Land the Keycloak compose service and the production realm export: roles with `USER` as the default, the app client with PKCE and direct access grants off, the password policy, the `email` mapper, the session and token lifetimes, and the confidential clients `ascend-openclaw-host` and `ascend-agent-directory`. Land the development overlay separately, carrying the seeded user, the e2e users of tenant `default` and the password-grant clients the e2e suite uses. Nothing consumes any of it yet, so this is additive.
2. Prove password sign-in end to end against that realm: an account, a password, Keycloak's own login page, an authorization code exchanged with PKCE, and a token.
3. Land the ascend-ai-agent resource server, the matrix with its coverage test, the resolved identity with its two ports, the production guard, and the identity resolved without a token with the `ADMIN` lookup.
4. Land downstream service auth in warn-only-when-unset mode (D6). With `SERVICE_AUTH_TOKEN` set in compose the services enforce, local bare runs keep working.
5. Land ascend-ai-agent outbound token attachment. This has to ship before compose sets `SERVICE_AUTH_TOKEN` for every service, or the agent starts getting 401s from its own downstream calls.

## Owner decisions of 2026-10-09

Answer 102.1: the defaults are for local personal use, and every one is a setting for a company setup: access token lifetime 1 hour (`KEYCLOAK_ACCESS_TOKEN_LIFESPAN_SECONDS` 3600), SSO session idle 12 hours (`KEYCLOAK_SSO_SESSION_IDLE_SECONDS` 43200), SSO session maximum 24 hours (`KEYCLOAK_SSO_SESSION_MAX_SECONDS` 86400), minimum password length 8 characters (`KEYCLOAK_PASSWORD_MIN_LENGTH` 8), and the Keycloak admin API client of D20 connects within 2 seconds (`APP_IDENTITY_DIRECTORY_CONNECTTIMEOUT` `2s`) and waits 5 seconds for an answer (`APP_IDENTITY_DIRECTORY_READTIMEOUT` `5s`). Tasks 1.2, 1.3, 1.13, 3.11, 9.3 and 9.8 carry the numbers. The identity cache lifetime stays derived from the access token lifetime, so its default is 3600 seconds too. Each setting has its row in the configuration reference (task 9.8).

Answer 102.3: no extra production start check for the issuer address. Compose always passes the development default of `KEYCLOAK_ISSUER_URI`, so the required placeholder of `application-production.yaml` does not stop a deployment that forgets the variable. It stays as it is: such a deployment validates against the development issuer, refuses every token (it fails closed), and the production checklist of `harden-cloud-deployment` names the variable.

Answer 100.6: every published host port is a setting `${<SERVICE>_HOST_PORT:-<today's port>}:<container port>`. The `keycloak` service of task 1.5 publishes `"${KEYCLOAK_HOST_PORT:-8180}:8080"`, and task 9.8 gives `KEYCLOAK_HOST_PORT` (8180) its row in `docs/CONFIGURATION.md`. `harden-cloud-deployment` task 1.1 later puts the bind address in front of it. Bruno, the e2e specs and the documents keep port 8180, the default.
