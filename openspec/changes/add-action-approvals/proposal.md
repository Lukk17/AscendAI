## Why

The owner wants the assistant to act on its own almost always (owner decision of 2026-10-02). Skills, subagent definitions, memories and user facts change without asking, and no normal work shows an approval prompt. A short list of actions is different, because their effect leaves the system, costs money or cannot be undone: changing the personality file, giving an integration the agent built itself a credential or letting it send anything outside the system for the first time, sending a message to another person, spending money, and deleting the owner's data outside the system. Today nothing in the agent can stop one tool call and ask the owner first. A tool is either given to the model or not, and a prompt injection in a fetched page could make the model call a sending tool with no human in the loop. The personality proposal of `add-agent-soul` waits for the owner, but that change has no way to decide it and leaves the decision to this change.

## What Changes

- A third tool mode, "requires approval", next to allowed and denied. A tool in this mode stays in the model's tool list, but a call to it never runs at once. The default list is short and configurable (kept as it is by owner decision of 2026-10-02). It is the configuration list, which ships empty, plus the tools that an `ApprovalDefaultsSource` marks. The MCP server entries of `add-mcp-tool-servers` are such a source, so an outside server that sends, pays, deletes or writes brings its gated tools with it (for example the GitHub write tools). No agent native tool and none of the own MCP servers (weather, web search, page reading, file download, transcription, OCR, memory) is on it.
- Besides whole tools, other parts of the agent can submit one action for approval through the same service. This change registers every kind the other changes need, with its category rules: `personality_change` (`add-agent-soul`, handler shipped here), `self_change` (`add-self-improvement`), `obsidian_note_write` (`add-obsidian-vault`), `coding_push` and `coding_project_cleanup` (`add-coding-agent-delegation`), and `integration_credential`, `integration_egress` and the rule-only `integration_tool_review` (`add-self-built-integrations`). Each owning change provides the handler of its kind. A timed job of the agent itself submits with the source `system`, with no user, conversation or run, and the tenant administrator decides it (owner decision 49.2 of 2026-10-03). The first such job is the free space check of `add-coding-agent-delegation`, which asks before it cleans coding projects.
- Every approval is one record in a new PostgreSQL table, created by a Flyway versioned SQL migration, and it is the only record of that approval in the system (owner answer 89.4 of 2026-10-08): a personality proposal, a credential grant, an approved host and a reviewed tool are approval requests or remembered rules here, never copies in another table. The record holds exactly what will run: the tool and its MCP server, the full arguments as canonical JSON with their SHA-256 digest, a digest of the tool's definition, and a preview the server builds itself (for the personality file, the diff). Nothing the model writes is shown as if it were the action.
- Nothing ever waits inside an HTTP request. A call from the main chat leaves one pending approval request and the chat turn ends normally, telling the user the action waits for approval. The run list keeps showing it as a run of kind `approval` through the run view port of `add-agent-subagents`, and its outcome reaches the next chat turn through the finished runs block. A call from a subagent run pauses that run in the new state `awaiting_approval`. A foreground run that pauses moves to the background, so the chat request that started it ends.
- After an approval the server runs the stored action exactly as shown, once at most. After a denial or a timeout the action never runs. The timeout is 24 hours (owner decision of 2026-10-02) and a timeout counts as a denial. When a request expires, the assistant tells the owner, through an owner notification and in the next chat turn of the conversation, so he can ask again.
- The expiry sweep is a system task of `add-shared-scheduler`, and the retention of decided requests is one entry of its one retention task (owner answer 89.7 of 2026-10-08).
- The owner decides one time, or "remember this choice" for the same tool and the same target (for example the same recipient). Remembered choices are listed and can be removed, and they never expire on their own (owner decision of 2026-10-02). Some categories can never be remembered as an allow: personality changes, self changes, spending money, deleting outside data, publishing code and cleaning coding projects. An approved credential is always remembered as the grant of exactly that credential binding, and an approved first send as the allow of that host.
- Decisions come only from a tenant `ADMIN` (owner decision of 2026-10-02), through an authenticated decision endpoint or the plugin host's relay, never from the model, never from a tool and never from text in the chat. The decision takes the deciding identity as an argument. A decision must echo the digest of the action the client showed, so the owner approves exactly what he saw.
- Approval channels: REST endpoints under `/api/v1/approvals`, the mobile app (made in `add-flutter-chat-app`), and Discord buttons through `add-openclaw-plugin-host`, whose outbox posts each pending approval with Approve and Deny buttons and whose relay decides as the linked owner. A streamed chat turn announces a new approval with the `approval_required` event.
- Every request, decision, remembered rule and execution is recorded as an audit event through `AuditEventPort` of `add-deployment-modules`, whose default writes one structured INFO log line, and is measured and logged, without the action's arguments at INFO level and never in metric tags. `add-audit-and-gdpr-compliance` (company, build group 5) registers its implementation later. This change does not wait for it.
- Tests for every rule, a Testcontainers test of the table and the at most once execution, and one new deterministic e2e spec in which the scripted model of the shared harness of `close-agent-test-gaps` calls the fake MCP server's gated `write_note` over the live MCP connection, a streamed turn announces it, the owner approves it, the fake receives the call once and the next turn carries the result (owner answers 67.1 of 2026-10-04 and 91.3 of 2026-10-08), with no container restart. The deny, remember, paused subagent and endpoint error checks are proved by the integration and unit tests and are not repeated end to end (owner answer 91.3). The scripted model and the fake MCP server start only for deterministic tests, never for AI-run e2e specs (owner answer 70.4 of 2026-10-04).

## Capabilities

### New Capabilities

- `action-approval-gate`: the "requires approval" mode and its default list, which calls and actions are gated, the approval record, how a chat turn and a run wait without holding an HTTP request, the exact and at most once execution, timeouts, remembered choices, limits, restart behaviour, and the metrics and logs of approvals.
- `action-approval-decisions`: who may decide, the REST endpoints to list, read, approve and deny approvals and to list and remove remembered choices, the digest check, the approval view shared by REST, the SSE event and the plugin host, the error codes, and the rule that no model, tool or chat text can ever decide.

### Modified Capabilities

(none. The tool policy, the run state machine, the SSE event set, the audit vocabulary and the mobile app are capabilities of changes that are not archived yet, so their changes are required edits listed in design.md and not delta specs here. `mcp-startup-resilience` keeps its rule that the filtered MCP provider is the only `ToolCallbackProvider` bean, because the gate wraps callbacks inside `ChatToolset` and registers no provider bean.)

## Impact

- New code in ascend-agent: a package `service/approval/` (approval service, the gate that wraps tool callbacks, the action handler interface with the built-in `tool_call` and `personality_change` handlers, the `ApprovalDefaultsSource` interface, canonical JSON and digest, the expiry sweep system task and the retention entry, remembered rules with `ApprovalRuleChangedEvent`, `deleteRules` and `putRule`, `ApprovalRunViewSource` and `ApprovalPersonalityProposalPort`), `controller/ApprovalController`, `config/properties/ApprovalProperties`, `model/ApprovalRequest` and `model/ApprovalRule` with their repositories, and one Flyway versioned SQL migration `V<n>__create_action_approval.sql` (`<n>` is the next free version at implementation time).
- Changed code in ascend-agent: `ChatToolset` wraps every tool whose effective mode is "requires approval", `ApprovalService` records its events through `AuditEventPort`, the gate pauses and resumes a subagent run through `pauseForApproval` and `resumeAfterDecision` of the run service, `GlobalExceptionHandler` maps the new codes, `SecurityConfig` gains the decision rules, `StartupLogConfig` reports the approval settings, and the personality proposal port of `add-agent-soul` gets its implementation here.
- Configuration: a new `app.approvals` block, and the key `app.policy.default.approval-required-tools` that `add-tenant-policy` adopts as its default. Every key with a default is a setting with an environment variable, the same default in code, a compose line on `ascend-agent` and a row in `apps/ascend-agent/docs/CONFIGURATION.md` (owner rule 98 of 2026-10-08, design D13).
- Database: two new tables, `approval_request` and `approval_rule`. The project is under development, so there is no data migration and no backfill. Owner answer 73.1 of 2026-10-06 confirms that the data in today's development stores is disposable.
- REST: `/api/v1/approvals` (list, read, approve, deny) and `/api/v1/approvals/rules` (list, remove). New `ApiErrorCode` values: `approval_not_found`, `approval_already_decided`, `approval_digest_mismatch`, `approval_forbidden`, `approval_not_rememberable` and `approval_rule_not_found`.
- No new dependency. Canonical JSON (RFC 8785) is written with the Jackson already on the classpath.
- Docs: a decision record in `apps/ascend-agent/docs/architecture/decisions/` (next free number), `apps/ascend-agent/AGENTS.md`, the module README, an approvals section in `docs/SECURITY.md`, the new metrics in `docs/OBSERVABILITY.md`, Bruno requests under `docs/api/request/AscendAI/`, and the one new e2e spec in `apps/ascend-agent/e2e/`, listed in `docs/E2E_RUN_SCENARIOS.md`.
- Backwards compatibility: with the default list and no tool configured as "requires approval", every chat and run behaves as before. `POST /api/v1/ai/prompt` keeps its request and response.
