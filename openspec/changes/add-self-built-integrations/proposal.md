## Why

The owner decided on 2026-10-02 that the assistant may build its own new tool servers and connections to outside systems when it needs one, as part of evolving itself. It may build a new tool server, test it in a sandbox and register it without asking. Giving it a password or token, or letting it send anything outside the system, needs the owner's yes once per integration. Today the assistant can delegate code work to a coding agent and can call MCP servers that the owner configured by hand, but nothing turns a need into a tested, isolated, running tool server, and nothing keeps such a server's secrets and network under the owner's control.

## What Changes

- Five tools for the main chat: `integration_build` (describe a new integration and start building it), `integration_update` (build a new version), `integration_request_credential` (ask the owner for a credential), `integration_list` (read the tenant's integrations and their state), and `integration_disable`. A build runs in the background as a run of kind `integration`, one of the run kinds `add-agent-subagents` owns. The tools and the API exist only when the deployment module `self-built-integrations` is active.
- The flow from need to running integration: the model describes the integration (purpose, the outside hosts it talks to, the credentials it needs, the tools it offers, and API notes). An OpenCode coding run of `add-coding-agent-delegation` writes an MCP server from a fixed Python template with tests, starting from a seed folder and with no network to the outside system. Then, in fresh sandbox workspaces controlled by the agent and not by the coding agent, the dependencies are installed from a hash-locked list of binary wheels, the tests run with no network at all, and a fixed contract check starts the server and compares its tool list with the declared one.
- The generated source lives in a git repository per tenant under `app.agent-home` (`tenants/<tenantId>/integrations/`), one folder per integration, one commit per version.
- The image is built by the sandbox runner from exactly the files that were tested, without any build tool and without running any code: the runner creates a container from a pinned runtime image without starting it, copies the validated archives in through the Docker Engine API, and commits it as a local image. The agent never touches the Docker socket.
- Each integration runs as one long-lived gVisor container started by the runner, with a read-only root, no capabilities, CPU, memory and process limits that protect the server, and its own internal network. Its only neighbours are its own egress proxy, which allows only the destinations the owner approved, and its own credential gateway, which adds the secret to requests for one destination. The agent reaches the server's MCP endpoint through the gateway on a separate ingress network, so the integration can never reach the agent or any other service.
- Registration: the running server becomes a new MCP server entry of `add-mcp-tool-servers` with trust `external`, found through tool search, and every tool defaults to `requires_approval` until the owner reviews it. A review is tied to the tool's definition digest, so a changed tool asks again.
- Credentials: `integration_request_credential` submits an `integration_credential` approval that names the environment variable the value goes into. Approving it remembers the grant as an allow rule of the approval service scoped to the credential's binding, and a changed binding needs a new approval (owner answer 89.4 of 2026-10-08). After approving, the owner adds the value to the runner's integration secrets file `integration-secrets.env`, which docker compose passes only to the sandbox runner, and recreates the runner (owner decision 40.1 of 2026-10-02). The value is never typed into a chat, never stored in a database, never seen by the agent, and is written by the runner only into the gateway's memory-backed folder, so the model, the coding agent, the integration container and every log never see it.
- Egress: each declared destination host is an `integration_egress` approval for that integration and host, submitted when the integration is registered. Nothing is sent before the yes. The approval is remembered by the approval service, and removing that rule removes the destination again.
- Owner management through `/api/v1/integrations`: list, read, versions, tool reviews, disable, enable, rollback to the previous version, remove, and revoke a credential grant. Updates keep the running version until the new one passes every check and its new approvals are given.
- Automatic disable after repeated failures of tool calls or of the container's health, with a WARN line, a metric, an audit event and a note to the owner.
- Running integrations are kept in line with the rows by the system task `integration-reconcile` of `add-shared-scheduler`, every minute on one agent instance. Each agent instance registers the integration MCP entries in its own memory, which stays local work.
- No limits on the number of integrations, builds, tools, destinations or credentials, and no cost or time limit per build (owner decision 40.4 of 2026-10-02). Only a few technical safety bounds stay, each named as one, because they protect the server: CPU, memory and process limits per container, one build running at a time, file, source, dependency and archive sizes, command timeouts, and the call timeout.
- Tenant rules: every integration table carries `tenant_id VARCHAR(64) NOT NULL`, written from `TenantContext.currentTenantId()` of `add-keycloak-login` (which answers `default` in the personal deployment), with no foreign key to a tenants table. A child table keeps its foreign key to its parent integration together with the tenant, added by this change's own Flyway migration. `add-tenant-isolation` (company, build group 5) adds the foreign keys to `tenants(id)` in its own migration later. The source lives under `tenants/<tenantId>/integrations/`, build reports under the object prefix `tenant/<tenantId>/`, every runner object carries the tenant, and every integration store fails closed when no tenant is bound.
- Login roles: `add-keycloak-login` lands first, so this change adds the rows of `/api/v1/integrations` to its authorization matrix in `SecurityConfig`: the read endpoints need an authenticated caller of the tenant, and every owner endpoint needs `ADMIN`.
- Audit events through the `AuditEventPort` of `add-deployment-modules` (default: one structured INFO line), usage events through its `UsageEventPort` (default: nothing), and tool policy through the `TenantToolPolicy` port of `add-agent-subagents` (default: every tool allowed). Company registers its implementations later. Erasure and export of integrations belong to `add-audit-and-gdpr-compliance`.
- Metrics, logs, traces, a startup banner block, tests with a fake coding agent that produces a fake integration against a fake outside system, and two new end-to-end specs (design D23): one deterministic Bruno spec with the fake installed under the real binary name `opencode` in the coding test image, the scripted model of the shared e2e harness of `close-agent-test-gaps` (its design D5 and task group 4) and a fake outside system, so no AI model runs (build and activation, the lifecycle being proven by integration tests, owner answer 91.3 of 2026-10-08), and one AI-run spec with real OpenCode for the Open-Meteo forecast API. The scripted model and the fake MCP server start only for deterministic tests, never for AI-run e2e specs (owner answer 70.4 of 2026-10-04).
- The project is under development, so there is no data migration and no backfill. Owner answer 73.1 of 2026-10-06 confirms that the data in today's development stores is disposable.

## Capabilities

### New Capabilities

- `integration-build`: the integration tools offered to the model, the build request and its validation, the run kind `integration` and its stages, the fixed template, the seeded coding run, the source repository per tenant, dependency install, tests and the contract check in the sandbox, image assembly from the tested files, the build safety bounds and build metrics.
- `integration-runtime`: the integration container and its safety bounds, its network with the egress proxy and the credential gateway, the ingress path for the agent, registration as an MCP server entry with tools that ask first until reviewed, health, automatic disable, and reconciliation after a restart.
- `integration-approvals`: the credential approval, how the owner sets a secret value in the runner's environment file, how it reaches the gateway, the fixed line of a credential prompt on Discord (moved here from `add-openclaw-plugin-host`), revocation, the egress approval per destination, and the rule that nothing leaves the system before the owner's yes.
- `integration-management`: the owner's REST API, integration and version states, update, rollback, disable, enable and remove, tool reviews, tenant scoping, audit events through the `AuditEventPort`, and the management metrics and logs.

### Modified Capabilities

- `production-deployment` (created by `harden-cloud-deployment`, build group 3, position 4, which is archived first): the requirements "Credentials flow from the environment with a production startup guard" and "The deployment guide covers one cloud VM per customer" gain the integration secrets file and the integration sizing, moved here from that change's task 10.6.

(Nothing else. The runner API, the coding run sources, the approval handlers, the run kinds, the tenant folder layout, the tool policy and the audit vocabulary belong to changes that are not archived yet, so their changes are required edits listed in design.md, not delta specs here. The archived spec `mcp-startup-resilience` was read and keeps every requirement: integration connections are made by the agent at run time after startup, never by `McpClientAutoConfiguration`, and the filtered provider stays the only `ToolCallbackProvider` bean.)
