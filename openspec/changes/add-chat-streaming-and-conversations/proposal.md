# Add Chat Streaming and Conversations

## Why

AscendAI's chat surface today is a single blocking call and a single eternal thread per user. `POST /api/v1/ai/prompt` (`apps/ascend-agent/src/main/java/com/lukk/ascend/ai/agent/controller/PromptController.java`) holds the HTTP connection until the full LLM answer is assembled - 10-60 s on long RAG turns - and chat memory is keyed by `conversationId == userId` (`memory/PersistentChatMemory.java`, Redis key `chat:<userId>`, Postgres `chat_history.user_id`), so every user has exactly one conversation, forever, with no way to list it, name it, start a fresh one, or delete it.

The upcoming Flutter client (mobile + web - a separate future change; no UI is specced here) needs the two API primitives every modern chat product has:

1. **Token streaming** - perceived latency drops from "whole answer" to "first token". Spring AI's `ChatClient` already exposes `.stream()` returning a `Flux`; we currently use only the blocking `.call()` path. After `upgrade-spring-boot-4` the agent runs Spring AI 2.0.1, where the stream still exists but options are builders, tools run through `ToolCallingAdvisor` and `streamToolCallResponses` is removed, so the streaming design is checked again on 2.0.1 (design D3). There is no SSE/Flux/streaming code anywhere in the agent today.
2. **Real conversations** - list past conversations, resume one, rename it, delete it. Without a conversation entity, the client cannot render a conversation drawer, and compaction/memory can never be scoped tighter than "everything this user ever said".

Doing conversations now also unblocks the parallel changes: `add-tenant-isolation` needs a conversation table to hang a tenant column on, and `add-audit-and-gdpr-compliance` needs a deletable per-conversation history unit.

## What Changes

- **New SSE streaming endpoint** `POST /api/v1/ai/prompt/stream` (multipart/form-data, same fields as `/prompt` plus optional `conversationId`) emitting `text/event-stream` with a defined event schema: `delta` (token fragments), `sources` (RAG source attachments when `attachSources=true`), `done` (terminal event carrying metadata + conversationId), `error` (terminal failure event, the RFC 7807 problem detail). Later changes add their own event names to the closed set when they land (`run_started` and `subagent_status` of `add-agent-subagents`, `approval_required` of `add-action-approvals`, owner answer 93 of 2026-10-08). Backed by `ChatClient.stream()` through the existing provider-resolution, context-assembly, prompt-cache, and history-persistence pipeline. The `sources` event carries the same `SourceFile` shape as the synchronous response, which means the mandatory presigned `downloadUrl` and `expiresAt` plus the registry `documentId` and the relative `contentPath` (`/api/v1/documents/{id}/content`), per add-document-management-api design D8.
- **One prompt pipeline on both paths.** The streaming path shares context assembly, history, prompt cache and persistence with the synchronous path. The changes of build group 4 that land later route the streaming executor through their own parts in their own tasks: `add-agent-soul` (`PromptLayout`, `ContextBudget`, `RequestProvenance`, `context_too_large`, `fileChanges` and `contextTrimmed`) and `add-self-improvement` (evidence and triggers at stream end and `request_self_review`). The turn service is callable in process with a prepared identity and attachments, which the relay of `add-openclaw-plugin-host` uses later (no new endpoint).
- **The chat stream is not resumable.** A client disconnect ends the turn. `add-agent-subagents` (build group 4) lands later and adds the rule for the runs a turn starts: a disconnect cancels only its foreground runs (`cancelledBy = parent`), and its background runs keep working and are followed with `GET /api/v1/runs/{id}/events` of that change.
- **Existing synchronous endpoint unchanged** - `POST /api/v1/ai/prompt` keeps its exact request/response shape; it gains only the optional `conversationId` form field and a `conversationId` echo inside response metadata (additive).
- **New `conversations` table** (Flyway migration): `id` (UUID), `tenant_id` (`VARCHAR(64) NOT NULL`, written from `TenantContext.currentTenantId()` of `add-keycloak-login`, `default` in the personal deployment, with no foreign key), `user_id`, `title`, `created_at`, `updated_at`. `chat_history` gains an indexed, not null `conversation_id` foreign key. The same migration empties `chat_history` first, because rows written before this change have no conversation.
- **Chat memory re-keyed by conversation id** - Redis key becomes `chat:<conversationId>` where the id is the conversation UUID; Postgres reads/writes filter on `conversation_id`. Compaction and semantic-memory extraction keep working, now scoped per conversation (extraction remains user-scoped, as memories belong to the user).
- **Auto-create and auto-title** - a prompt without `conversationId` resolves to the user's most-recent conversation (created on the fly if none exists, preserving today's one-thread behavior for legacy callers); a brand-new conversation is titled from the first prompt text.
- **Conversation management REST API** under `/api/v1/conversations`: list (paginated, most-recent-first), create, get messages (paginated), rename, delete (removes the conversation row, its Postgres history rows, and its Redis key). The agent changes of build group 4 land later and extend the delete in their own tasks: `add-action-approvals` cancels the conversation's pending approvals and deletes its `approval_request` rows, `add-agent-subagents` cancels its runs that are not final and deletes its `subagent_run` rows, `add-agent-sandbox` closes its open sandbox workspace and deletes its `sandbox_workspace` rows and their archives (owner answer 76.6 of 2026-10-08), `add-scheduled-tasks` sets `scheduled_job.origin_conversation_id` to null, and `add-openclaw-plugin-host` removes its chat platform binding through the `ON DELETE CASCADE` of `channel_conversation`.
- **No existing data is kept** (owner decision, 2026-10-02, confirmed by owner answer 73.1 of 2026-10-06): existing `chat_history` rows are deleted by the migration, nothing is copied into conversations, and old `chat:<userId>` Redis keys are never read again. This holds only until the first real customer deployment.
- **BREAKING (internal only)**: `PersistentChatMemory` callers must pass a conversation UUID instead of a raw user id. No public API contract breaks; all REST changes are additive.

## Capabilities

### New Capabilities

- `chat-streaming`: SSE token-streaming endpoint - event schema (`delta`/`sources`/`done`/`error`), one chat executor for the streaming and synchronous paths, the disconnect rule for runs, and unchanged behavior of the existing `/prompt` endpoint.
- `conversation-management`: conversation entity, auto-create/auto-title lifecycle, per-conversation chat-history keying, and the `/api/v1/conversations` CRUD + pagination API including full history deletion.

### Modified Capabilities

- `production-deployment` (created by `harden-cloud-deployment`, which lands earlier): a new requirement that the gateway streams Server-Sent Events of `POST /api/v1/ai/prompt/stream` without buffering.

- `chat-history-persistence`: the Redis TTL requirement is re-stated per conversation key - keys are `chat:<conversationId>` (conversation UUID) instead of `chat:<userId>`; TTL semantics themselves are unchanged.
- `chat-history-compaction`: the REST override-fields requirement (`compactionProvider`/`compactionModel`) now covers both `POST /api/v1/ai/prompt` and `POST /api/v1/ai/prompt/stream`; compaction scope is explicitly the conversation, not the user's lifetime history.

(`chat-history-persistence-toggle`, `prompt-caching`, and `rag-source-attachments` requirements are already stated in terms of `conversationId` or are orthogonal to conversation identity - no requirement-level change; verified against `openspec/specs/`.)

## Impact

- **New code (ascend-ai-agent)**: streaming controller method + SSE event DTOs (`controller/`, `dto/`), `ConversationController` + request/response DTOs, `Conversation` Spring Data JDBC entity + `ConversationRepository` (`CrudRepository`, paginated reads as hand-written native `@Query`) (`model/`, `repository/`), `ConversationService` (resolution, auto-title, delete cascade) in `service/`, `StreamingChatExecutor` in `service/chat/` as the one chat executor, which replaces `ChatExecutor` (owner answer 89.1 of 2026-10-08).
- **Changed code (ascend-ai-agent)**: `PromptController` (new `conversationId` field, and the blocking endpoint collects the `Flux` of `StreamingChatExecutor` into one `AiResponse`), `ChatExecutor` (removed), `AscendChatService` / `ChatHistoryService` / `PersistentChatMemory` (conversation-id keying), `CustomMetadata` (additive `conversationId`), `ChatHistoryRepository` (conversation-keyed queries), `model/ChatHistory` (new `conversationId` field), `memory/ChatHistoryCompactionService` (unchanged trigger logic, `applyToPostgres` writes both `user_id` and `conversation_id` on the summary row).
- **Database**: one new Flyway versioned SQL migration under `apps/ascend-agent/src/main/resources/db/migration/`, `V<n>__conversations.sql` (empties `chat_history`, creates the `conversations` table, adds `chat_history.conversation_id` as NOT NULL with its FK and index). `<n>` is the next free version at implementation time. No rollback script (design D6). `add-agent-subagents` (build group 4) lands later and creates `subagent_run.conversation_id` as a nullable `UUID` with its foreign key to `conversations.id` from its first migration (design D5, owner answer 27), so this change needs no second migration.
- **Dependencies**: none new - Spring MVC supports `Flux<ServerSentEvent>` return types with Reactor already on the classpath via Spring AI.
- **Configuration**: every value with a default is a setting (owner rule 98 of 2026-10-08, design D7): the page sizes of the conversation and message lists, the auto-title length and the async request timeout of the stream answer (default `300s`, owner answer 103.5 of 2026-10-09, task 5.8), each written as `${ENV:default}` in `application.yaml`, passed as `${ENV:-default}` by the `ascend-agent` service of `compose.yaml`, and listed in `apps/ascend-agent/docs/CONFIGURATION.md`.
- **Docs / API collection**: `apps/ascend-agent/AGENTS.md` API description, Bruno requests under `docs/api/request/AscendAI/ascend-agent/` for the stream endpoint and conversation CRUD.
- **Sibling changes**: `add-keycloak-login` lands before this change, so every endpoint here takes the caller from its resolved identity (never `X-User-Id`), adds its own rows to its authorization matrix (D4 of that change), and reads the tenant through its `TenantContext`. The `tenant_id` column is written from `TenantContext` with no foreign key. `add-tenant-isolation` (company, build group 5) adds the foreign key and its checks later.
- **Depends on `upgrade-spring-boot-4`**: it replaces Liquibase with Flyway in ascend-agent (owner decision, 2026-10-02), so the schema change here is written as Flyway versioned SQL migrations. It also owns the switch of every agent error body to the RFC 7807 problem detail (owner decision, 2026-10-02, its D19), so every error of the new endpoints, the pre-stream refusals and the payload of the terminal `error` event use that body, and the new codes are added to its `ApiErrorCode` enum (design D2).
- **Depends on `add-document-management-api`** (build-order): the `sources` event carries the registry `documentId` and the `/api/v1/documents/{id}/content` path from the presign-resolution amendment, so the document registry and the content endpoint from that change must be in place before this change's `sources` event is implemented. The `delta`/`done`/`error` events and the conversation model have no such dependency.
- **Extended later by the agent changes of build group 4**, each in its own tasks (moved there from task group 9 of this change by the dependency fix of 2026-10-05, because each of them lands after this change): `add-agent-subagents` (the `run_started` and `subagent_status` events, which it adds to the closed event set itself (owner answer 93 of 2026-10-08), the disconnect rule, cancelling and deleting a conversation's runs, and the foreign key from `subagent_run.conversation_id`), `add-agent-soul` (`PromptLayout`, `ContextBudget`, `RequestProvenance`, `context_too_large`, `fileChanges` and `contextTrimmed`), `add-action-approvals` (the `approval_required` event, which it adds to the closed event set itself, cancelling a conversation's pending approvals and deleting its `approval_request` rows, with the foreign key from `approval_request.conversation_id`), `add-agent-sandbox` (closing a deleted conversation's sandbox workspace and deleting its `sandbox_workspace` rows, with the foreign key from `sandbox_workspace.conversation_id`), `add-openclaw-plugin-host` (the in process turn service and the conversation binding with its cascade), `add-scheduled-tasks` (`scheduled_job.origin_conversation_id` set to null on delete) and `add-self-improvement` (evidence and triggers at stream end, `request_self_review` on the streaming path, and the conversation id as the review's conversation key). `add-usage-metering-and-quotas` (company, build group 5) adds `estimatedCostUsd` to the `done` metadata later. This change does not wait for any of them.
- **Tests**: SSE integration test (delta + done event assertions), conversation CRUD + ownership tests, Flyway migration test of the new schema, regression test that the synchronous endpoint response is byte-compatible.
