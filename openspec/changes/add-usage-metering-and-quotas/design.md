# Design - Add Usage Metering and Quotas

## Context

Every LLM call in ascend-ai-agent already funnels through one observation point: `PromptCacheStrategy.recordOutcome(userId, chatResponse)` is called by `service/chat/ChatExecutor.java` (`execute(...)`, line 97) and `service/memory/SemanticMemoryExtractor.java` (line 100), and each of the three strategy implementations (`AnthropicPromptCacheStrategy`, `OpenAiPromptCacheStrategy`, `NoopPromptCacheStrategy`) delegates to `service/cache/GenAiTokenUsageRecorder.java`, which reads `ChatResponse.getMetadata().getUsage()` and increments the aggregate `gen_ai.client.token.usage` Micrometer counter. That counter has no user/tenant tags and Prometheus retention is 72h, so it cannot back billing. The compaction path (`memory/ChatHistoryCompactionService.java`) and the embedding path call providers without passing through `recordOutcome` at all.

Provider clients are built **once at startup**: `service/provider/ChatModelResolver.initializeProviders()` (`@PostConstruct`) constructs one `OpenAiChatModel` / `AnthropicChatModel` per enabled provider from `AiProviderProperties`, with the API key baked into the `OpenAiApi` / `AnthropicApi` instance. BYOK therefore cannot be a per-request option tweak; it needs per-tenant client instances.

This change **depends on** two siblings and re-specifies neither:

- `add-keycloak-login` supplies the authenticated principal and the `USER`/`ADMIN` roles, and `add-auth-and-identity` supplies the `tenant` claim.
- `add-tenant-isolation` supplies the tenant entity/model that quota configs and provider keys reference.

A third sibling, `add-chat-streaming-and-conversations`, will make chat responses streamable; usage metadata for a streamed call is only complete when the stream finishes, which constrains where the ledger write can happen.

Infrastructure available: Postgres (Flyway-managed once `upgrade-spring-boot-4` replaces Liquibase, versioned SQL migrations under `db/migration/`), Redis (already a hard prerequisite, used for chat history), and the `add-observability` Grafana stack with provisioned dashboards under `infra/observability/grafana/dashboards/`.

## Goals / Non-Goals

**Goals:**

- One durable, queryable usage row per LLM-touching request and per metered service operation (OCR job, ingested file, transcription, web search, page read, memory operation), attributable to tenant + user, precise enough to invoice from.
- Hard token budgets (tenant/month, user/day) enforced before money is spent, with a soft-warning event ahead of cut-off.
- Request-rate limits that hold across ascend-ai-agent replicas.
- Per-tenant provider keys that never leave the server in plaintext once written, with clean fallback to the deployment's global keys.
- All enforcement and all ledger writes live in ascend-ai-agent (the gateway). Downstream Python services keep no ledger. Two of them report one extra number in a tool result (D12).

**Non-Goals:**

- Payment processing, invoicing documents, price-to-currency conversion in the API (the Grafana token-cost dashboard already handles $ via `pricing.yaml`).
- Authentication, role model, or tenant modelling (owned by the sibling changes).
- Rate limiting inside AscendMemory / ascend-web-hunter / ascend-audio-scribe themselves - they are only reachable through the gateway or trusted service calls.
- Predictive cost estimation (pre-counting prompt tokens before the provider call).

## Decisions

### D1 - One path into the ledger: every caller sends a `UsageEvent` through `UsageEventPort`, asynchronously

Owner answer 89.9 of 2026-10-08. Usage reaches the ledger through one path only. Every caller that does metered work, a model call or a service operation, builds one `UsageEvent` and hands it to `UsageEventPort.record(...)` of `add-deployment-modules`. This change registers `LedgerUsageEventPort` (D16) as the port's implementation, and it is the only class that calls `UsageLedgerRecorder` (in `service/usage/`). The three `PromptCacheStrategy` implementations stay cache-only: `recordOutcome` keeps its signature and its existing call of `GenAiTokenUsageRecorder`, and no cache strategy writes or knows a ledger row. Chat and memory extraction send their event from the caller that already holds the response (`StreamingChatExecutor` of `add-chat-streaming-and-conversations`, the one chat executor, which `POST /api/v1/ai/prompt` also runs through, owner answer 89.1, and `SemanticMemoryExtractor`), and the compaction path, the embedding path, `AscendOcrClient`, the ingestion pipeline, `SemanticMemoryClient` and the tool-callback wrapper send theirs the same way (D12). The personal deployment keeps the default `NoOpUsageEventPort`, so the callers cost nothing there. The row insert runs on a dedicated bounded executor inside `LedgerUsageEventPort`: a ledger failure logs ERROR + increments `usage.ledger.write_failed` but **never fails the user request**. Alternative considered: writing rows from inside the cache strategies - rejected by answer 89.9, because it gives the cache classes a second job (billing) and a second path next to the port. Spring AOP around `ChatModel.call` - rejected because the caller already holds the response metadata the event needs.

The fields of the ledger row come from the `UsageEvent` with no new field on the port: `requestType`, `tenantId`, `userId`, `provider`, `model`, `inputTokens` (`prompt_tokens`), `outputTokens` (`completion_tokens`), `runId`, `parentRunId` and `occurredAt` map one to one. The cached tokens travel as the quantity `cached_tokens`, and `pages`, `processing_ms`, `files`, `bytes`, `chunks` and `audio_seconds` as quantities of the same names. The conversation id travels as the attribute `conversation_id`, and `tier` and `tool` as attributes of the same names. A quantity or attribute the ledger has no column for is ignored.

### D2 - Usage context threaded explicitly, not via ThreadLocal

A caller needs tenant, user, conversation, provider, model, request type and the run ids to build its event. Each caller builds a `UsageContext` record (tenantId, userId, conversationId, provider, requestType) at the start of its work and turns it, together with the response usage metadata, into a `UsageEvent` through one small mapper, `UsageEvents`, which reads prompt, completion and cached tokens from `ChatResponse.getMetadata().getUsage()` (Anthropic `cacheReadInputTokens`, OpenAI and Gemini `PromptTokensDetails.cachedTokens`). Explicit value over `ThreadLocal`/request-scope because the compaction path runs off the request thread and the streaming sibling will complete on reactive/async threads where ThreadLocals silently vanish.

`UsageContext` also carries nullable `runId` and `parentRunId`. A row written while a run of `add-agent-subagents` works, of any request type (a model call of the run, or a metered web search, OCR job or transcription called by one of its tools), takes both ids from the `RunContext` that the agent binds on the run's own thread and removes when the run's call ends (`add-agent-subagents` D8). The caller copies them into the `UsageContext` it builds, so the recorder itself still reads no thread state. A row written outside a run has both ids empty.

**Streaming consideration:** `add-chat-streaming-and-conversations` lands before this change, and the final `ChatResponse` (with complete usage metadata) is only available at stream end; the `UsageEvent` is sent from the stream-completion callback, built from the same `UsageContext` captured at request start. The `UsageContext` design makes that a one-line move.

### D3 - Cached tokens recorded, prompt-caching spec untouched

The ledger row includes `cached_tokens`, read from the same provider metadata the cache strategies already log (`cacheReadInputTokens` for Anthropic, `PromptTokensDetails.cachedTokens` for OpenAI/Gemini). This is additive observation; no requirement in `openspec/specs/prompt-caching/spec.md` changes.

### D4 - Quota accounting: an indexed Postgres sum per gated call

Owner answer 89.9 of 2026-10-08: one store for one number. The ledger is the only record of usage, and the gate reads it directly:

- The pre-request quota gate runs one indexed aggregate per budget that is set: the tenant's tokens of the current UTC month, `SUM(prompt_tokens + completion_tokens) WHERE tenant_id = ? AND occurred_at >= <month start>`, served by the index `(tenant_id, occurred_at)`, and the user's tokens of the current UTC day, the same sum `WHERE tenant_id = ? AND user_id = ? AND occurred_at >= <day start>`, served by the index `(user_id, occurred_at)`. It rejects when a sum has already met or exceeded its budget.
- A budget that is not set is not queried. No Redis counter, no rebuild step and no second store exists, so the gate and the ledger cannot drift apart.
- Every agent instance reads the same rows, so the decision is the same on every instance (owner rule R1, CANON 26.1). A cache in front of the sum is added only if a measurement later shows the need.

Enforcement is **post-paid within one request**: the gate blocks when the budget is already exhausted, so a single request may overshoot the budget by its own size. The ledger row is written asynchronously (D1), so requests that start before the previous row is committed see the sum without it, and a burst of parallel requests can overshoot by the size of the burst. Accepted - pre-counting prompt tokens per provider tokenizer is complex and still cannot predict completion length. Alternative (reserve-then-settle two-phase accounting) rejected as disproportionate for this platform's scale. Alternative (Redis `INCRBY` counters rebuilt from Postgres) removed by answer 89.9: two stores for one number, written from an async executor, can drift.

Runs (`add-agent-subagents`, `add-scheduled-tasks`, `add-self-improvement`): the pre-request gate also runs before each model call of a run, for the run's tenant and user, not only at the HTTP entry. A refusal inside a run is not an HTTP 429: it ends the run with the failure reason `QUOTA_EXCEEDED`. So the accepted overshoot of one request becomes the overshoot of one model call. The same gate runs before each guard call of `add-self-improvement` (`self-check`). A coding run of `add-coding-agent-delegation` makes its model calls inside its workspace, so its gate runs before the run starts and at every poll (its D18).

Soft warning: when a ledger write moves a tenant or user token sum across the warning threshold (the setting `app.usage.quotas.warning-threshold`, default `0.8`, owner answer 98) of a budget that is set, emit one WARN log line and increment `usage.quota.warning` (tags: `scope=tenant|user`), once per (scope, subject, window) in the whole cluster. After `LedgerUsageEventPort` has inserted a row with tokens, it runs the same window sums as the gate for the budgets that row counts toward. When a sum has reached the threshold, it inserts one row into `usage_quota_warning` (`tenant_id`, `scope`, `subject_id`, `window_start`, `created_at`, a unique constraint `uq_usage_quota_warning` on the first four) with `INSERT ... ON CONFLICT DO NOTHING`. Only the instance whose insert added the row writes the WARN line and increments the counter, so two instances that cross the threshold at the same moment still warn once (owner rule R1, CANON 26.1). The table holds at most one row per subject and window that crossed the threshold, so it needs no retention entry. Its rows name a user, so erasure and export cover it with the ledger (D16). This replaces the Redis `SETNX` marker of the earlier plan (answer 89.9).

### D5 - Quota windows are calendar-based UTC

Tenant budget window = calendar month UTC; user budget window = calendar day UTC. `Retry-After` on a quota 429 = seconds until the window rolls over. Calendar windows are trivially explainable on an invoice; sliding windows are not. A model call inside a run counts in the calendar window in which the call happened, not in the window in which its run started.

### D6 - Rate limiting: Bucket4j with Redis (Lettuce) backend

`com.bucket4j:bucket4j_jdk17-lettuce` 8.20.0 (Lettuce integration, matching Spring Data Redis's default driver already on the classpath) provides distributed token buckets, so limits hold across replicas. After `upgrade-spring-boot-4`, Spring Boot 4.1.1 brings Lettuce 7.5.2, a major version up from 6.6.0, and the Bucket4j Lettuce module is compiled against Lettuce 6.1.8, so its compatibility must be measured again on the upgraded build (Closed Question 2). Alternatives: Resilience4j RateLimiter (in-memory only - fails the multi-replica requirement), hand-rolled Redis Lua (reinventing a maintained wheel), Spring Cloud Gateway RequestRateLimiter (would introduce a whole gateway layer).

Placement:

- Chat (`POST /api/v1/ai/prompt`) and ingestion upload (`POST /api/v1/ingestion/upload`): a `HandlerInterceptor` keyed by `{userId}` and `{tenantId}` per endpoint group, registered ahead of controller execution.
- Web-search tool invocations happen **inside** a chat turn (MCP tool callback), not on their own HTTP endpoint, so the interceptor cannot see them; the tool-callback wrapper around the ascend-web-hunter MCP tools consumes from a dedicated `web-search` bucket and surfaces a tool-level "rate limited, retry after Ns" result to the model instead of a 429 (the enclosing chat request already passed its own limit). The `web_download_file` calls of `add-file-download` consume the same `web-search` bucket as the other web-hunter tools.
- The channel message endpoint `POST /api/v1/channel-host/messages` of `add-openclaw-plugin-host` consumes the chat buckets of the linked user and tenant. A rejection is answered to the platform as `refused` with reason `rate_limited`, not as an HTTP 429 to the host.

Both a user bucket and a tenant bucket must have capacity; the stricter one wins. On rejection: `429`, `Retry-After` from Bucket4j's nanos-to-wait, and the problem detail body of D7 with code `rate_limited`. **Fail-open** when Redis is unreachable (WARN + `rate_limit.redis_unavailable` metric): availability of chat outranks limit precision, and the quota gate (D4, a Postgres sum that needs no Redis) still bounds total spend. Each bucket's capacity and refill rate are configuration values under `app.usage.rate-limit.*`, and a bucket whose capacity is not set is not created, so that endpoint group is not limited (answer 93, review item B8: no `enabled` flag).

### D7 - 429 error contract shared by quotas and rate limits

Every 429 of this change is an RFC 7807 problem detail (owner answer 24), the agent's one error body defined by `upgrade-spring-boot-4` D19 and its `agent-error-responses` spec: `Content-Type: application/problem+json`, the fields `type`, `title`, `status`, `detail`, `instance`, the snake case `code` field at the top level, and the `traceId` field (owner decision 51.3). The codes are `quota_exceeded` (type `https://ascend.ai/errors/quota-exceeded`) and `rate_limited` (type `https://ascend.ai/errors/rate-limited`), added as `ApiErrorCode` values. The extension fields at the top level of the body are `scope` (`tenant` | `user`), `retryAfterSeconds`, and for quotas `limit`, `used`, `windowEnd`. The `Retry-After` header is always set and equals `retryAfterSeconds`. Two new exceptions (`QuotaExceededException`, `RateLimitExceededException`) are handled by the one global exception handler of D19, which builds the body. The body carries no `error`, `message` or `timestamp` field.

### D8 - BYOK storage: the one encrypted secret store of `add-connector-framework`

Owner answer 89.9 of 2026-10-08: the agent has one encrypted secret store. It is the default `ConnectorCredentialStore` of `add-connector-framework` (its D24, personal, landed earlier): AES-256-GCM with a fresh nonce per write, the key from `CONNECTOR_CREDENTIALS_KEY` (32 bytes, base64, the name stays, owner answer 71), and a key version on each row so a later key rotation re-encrypts row by row. Its port, `put(tenantId, secret)`, `resolve(tenantId, reference)` and `delete(tenantId, reference)`, treats a secret as opaque characters owned by a tenant, so a provider key is a second kind of secret it holds with no change to the port, its table or its key. This change registers no store and no encryption code of its own. Mechanics:

- Table `tenant_provider_key`: tenant id, provider name, `credential_ref` (the opaque handle `ConnectorCredentialStore.put` returns), `key_last4`, timestamps, unique on (tenant, provider). The key itself is only in the store's `connector_credential` row, as ciphertext.
- An upsert puts the new key through the store, points the row at the new handle and deletes the old handle through the store. A delete removes the row and its handle. A resolve reads the handle and calls `resolve` with the caller's tenant, so a handle of another tenant is refused as not found.
- An upsert while no `CONNECTOR_CREDENTIALS_KEY` is configured is refused by the store, and the endpoint answers 503 with the shared code `unavailable`, the same rule connectors follow. A deployment that stores no provider key and no connector credential runs without the key.
- Tenant erasure, which deletes every `connector_credential` row of the tenant (`add-audit-and-gdpr-compliance` task 5.3), also removes the tenant's provider keys, and this change's store step deletes the `tenant_provider_key` rows (D16).
- The earlier envelope plan (a key per secret wrapped by `USAGE_KEK`, behind `KeyEncryptionService` with a `kek_id` column, kept "for KMS later") is removed by answer 89.9. A key management service, if one is ever wanted, becomes another implementation of the one `ConnectorCredentialStore` port, for both secret kinds at once.
- API is write-only: `PUT` upserts (request body carries the plaintext key over TLS, never logged), `GET` returns provider, `last4`, timestamps only, `DELETE` removes. All `ADMIN`-scoped under `/api/v1/admin/tenants/{tenantId}/provider-keys`, inside the one administration prefix `/api/v1/admin/` that every admin endpoint uses (owner decision, 2026-10-01). A tenant `ADMIN` whose tenant differs from `{tenantId}` gets 403.

Alternatives: a second envelope store of this change (removed by answer 89.9, two stores and two keys for one job), Postgres `pgcrypto` (puts plaintext key and passphrase into SQL text - worse), storing keys only in env per tenant (does not scale past a handful of tenants, no API), Vault-only storage (new mandatory infrastructure dependency).

### D9 - BYOK resolution: tenant-keyed client cache in `ChatModelResolver`

`ChatModelResolver.resolve(provider)` gains a tenant-aware overload, behind the provider and model gate of `add-tenant-policy` (its D1), which lands earlier and stays first. Resolution order: tenant key (if a `tenant_provider_key` row exists for (tenant, provider)) → global key from `AiProviderProperties`. Because API keys are baked into `OpenAiApi`/`AnthropicApi` at construction, tenant clients are built lazily and held in a Caffeine cache (the version catalog entry `add-tenant-policy` added) keyed `(provider, tenantId)` with a bounded size and time-based expiry: at most 200 entries (`app.usage.provider-key-cache.max-size`) and 10 minutes after the client was built (`app.usage.provider-key-cache.ttl`), owner answer 98.4. A key upsert or delete evicts the entry on every agent instance, not only on the one that served the request (owner rule R1, CANON 26.1): the service calls `pg_notify('usage_provider_key_changed', '<tenantId>:<provider>')` in the same transaction as the row change, and this change registers a `PostgresNotificationHandler` for the channel `usage_provider_key_changed` with the one `PostgresNotificationListener` of `add-keycloak-login` D20, so every instance evicts the entry and no change opens a `LISTEN` connection of its own. The handler's `onReconnect()` clears the whole tenant client cache, because notifications sent while the connection was down are lost. The time-based expiry stays as a second bound. The payload holds ids only, never a key. A deleted or replaced key is therefore not used again after the commit by any instance whose listening connection is up, and by no instance once the expiry has passed. Global clients keep today's startup construction untouched. A provider `401` with a tenant key is surfaced as a clear client error naming the tenant key (last4), not silently retried on the global key - silently billing the operator for a tenant's broken key is the exact failure this change exists to prevent.

`ProviderKeyResolver` is a port of `add-coding-agent-delegation` (its D10), whose default `DeploymentProviderKeyResolver` returns the deployment key. This change registers its per-tenant implementation, replacing that default: it returns the plain provider key of a tenant to trusted agent code in memory, the tenant's BYOK key first and the deployment key only when the caller allows it, and never through any API, log or response. Its one caller is the per-workspace credential gateway of `add-coding-agent-delegation`, which decides itself when the deployment key is allowed (`app.coding.providers.<provider>.allow-deployment-key`). The BYOK providers gain `opencode-go` and `opencode-zen`, whose deployment key is `OPENCODE_API_KEY`, named by that change. The write-only rule of D8 is unchanged: no endpoint ever returns a key.

### D10 - Usage API shape

`GET /api/v1/usage?from=&to=&groupBy=day|month|run&format=json|csv`. `USER` role: own rows only. A `USER` may pass their own id as `userId`, and a `userId` that names another user is refused with 403 `forbidden` (owner answers 75.6 of 2026-10-07 and 76.8 of 2026-10-08). `ADMIN`: whole tenant, optional `userId` filter. Response rows: period, provider, model, requestType, promptTokens, completionTokens, cachedTokens, requestCount. `groupBy=run` is an extra option (owner decision 51.4): it groups the rows of the window by `run_id` instead of by period, so each row names `runId` and `parentRunId` in place of the period, and the usage made outside any background run is one row with an empty `runId`. A caller sums a run tree itself from the `parentRunId` links. `day` and `month` work as before. CSV export is the same aggregation with `text/csv` content type - enough for invoicing without any payment logic. Backed by a Spring Data JDBC `@Query` aggregate on the ledger table with a covering index `(tenant_id, occurred_at)`.

### D11 - Observability integration

- `LedgerUsageEventPort` increments the new counter `usage.tokens{tenant,request_type,token_type}` (`token_type` is `input`, `output` or `cached`) for every event it records, so the per-tenant token series comes from the one usage path of D1 (bounded cardinality: tenants are operator-created, request types are the closed set listed in D12, which includes `sandbox`, `coding-agent` and the other types of the agent changes in D14). `GenAiTokenUsageRecorder` and its `gen_ai.client.token.usage` counter stay as they are in the cache strategies (answer 89.9: the strategies stay cache-only and gain no tenant tag), so the personal deployment's token metric is unchanged.
- New counters: `usage.ledger.write_failed`, `usage.quota.rejected{scope}`, `usage.quota.warning{scope}`, `rate_limit.rejected{scope,endpoint}`, `rate_limit.redis_unavailable`.
- One new provisioned dashboard `infra/observability/grafana/dashboards/usage-quotas.json`: tokens by tenant over time, top users, quota-consumption gauges, 429 rates.

### D12 - Metering every service: the agent records what it calls

Owner decision, 2026-10-01: metering covers everything a tenant can make the platform do, not only model calls. Every call below is made by ascend-ai-agent with the tenant and user already resolved, so the agent sends one `UsageEvent` through `UsageEventPort`, built from a `UsageContext` (D1, D2), and `LedgerUsageEventPort` writes the row. The source named in the table is the caller that sends the event. No service gets a ledger, a database or a tenant concept of its own.

| Request type | Source of the numbers | Columns filled |
|---|---|---|
| `ocr` | `AscendOcrClient`, from the terminal job record it already polls (`pages_done`, `finished_at - started_at`) | `pages`, `processing_ms`, `provider = ascend-ocr` |
| `ingestion` | the ingestion pipeline, once per ingested file, after chunking | `files = 1`, `bytes`, `chunks` (embedding tokens stay in the `embedding` rows of the same run) |
| `transcription` | the MCP tool-callback wrapper around the ascend-audio-scribe tools, from `audio_seconds` in the tool result | `audio_seconds`, `provider` = `local`, `openai` or `hf` from the tool name |
| `web-search` | the same wrapper around the ascend-web-hunter search tool, one row per call | `provider = ascend-web-hunter` |
| `web-read` | the same wrapper around the page-read tool, one row per call | `tier`, the tier that produced the content |
| `memory-search`, `memory-insert`, `memory-delete` | `SemanticMemoryClient`, one row per REST call to AscendMemory | `provider` = the embedding provider sent |
| `subagent` | every model call of a run of kind `subagent` of `add-agent-subagents` | token columns, `run_id`, `parent_run_id` |
| `sandbox` | the agent, once per destroyed workspace of `add-agent-sandbox` | `processing_ms` = time from `created_at` to `destroyed_at` of the workspace record, `run_id` and `parent_run_id` for a run workspace (empty for a chat workspace) |
| `mcp-tool` | the tool wrapper, one row per successful call of a tool of a server with `metered: true` of `add-mcp-tool-servers` | `provider` = the server id or its `metric-server-tag`, `tool` = the prefixed tool name |
| `web-download` | one row per `web_download_file` call of `add-file-download` that stored or deduplicated a file | `provider = ascend-web-hunter`, `bytes` = the size, `tier` = the `fetch_path` |
| `coding-agent` | the orchestrator of `add-coding-agent-delegation`, when a coding run ends in any state, one row per model it used | token columns (input, output, cache read), `run_id` |
| `scheduled` | every model call of a run of kind `scheduled` of `add-scheduled-tasks` | token columns, `run_id`, `parent_run_id` |
| `self-review` | every model call of a review run of `add-self-improvement` | token columns, `run_id` |
| `self-check` | every guard call of `add-self-improvement` | token columns |

The ledger table gains nullable columns `pages`, `processing_ms`, `files`, `bytes`, `chunks`, `audio_seconds` (numeric, three decimals), `tier`, `run_id` and `parent_run_id` (UUID, D14) and `tool` (D14). Token columns default to 0 for non-model rows. A row per operation means request counts are plain row counts and every quantity sums with `SUM`, so the usage API and the quota gate stay one aggregate query each. Alternative rejected: a JSON column of free measures, which cannot be summed or constrained without parsing.

Two services report one number they do not report today. ascend-audio-scribe adds `audio_seconds` (the decoded length of the input) to the success result of `transcribe_local`, `transcribe_openai` and `transcribe_hf`. ascend-web-hunter makes the page-read result name the tier that produced the content, where it does not already. Both are additive fields in the result body, so older callers ignore them.

A failed operation writes no row: an OCR job that ends failed, an ingestion that stores nothing, a tool call that returns an error, a refused or failed `web_download_file` call, a failed call of a metered MCP tool, a workspace whose create failed. The rows record work delivered, which is what an invoice can defend. The erasure job deletion of AscendMemory data (`wipeUserMemory`) is not metered, because it is the platform's legal duty and not a tenant's use.

Calls that bypass the agent are not metered, because they carry no tenant: the services' own REST and MCP endpoints called directly (ascend-ocr on 7022, ascend-audio-scribe on 7017, ascend-web-hunter on 7021, AscendMemory on 7020), for example by an operator script or an MCP client on the development stack. These ports are platform-internal. A deployment that exposes one of them to tenants must route that traffic through the agent first, and `docs/USAGE_AND_QUOTAS.md` says so.

### D13 - Budgets for the non-model costs

Two non-model costs grow with the size of the input and can be large in one call: OCR pages (CPU time in ascend-ocr) and transcription seconds (paid per minute on the OpenAI backend). Each gets an optional per-tenant monthly budget (`app.usage.quotas.ocr-pages-per-month`, `app.usage.quotas.transcription-seconds-per-month`, unset means unlimited, per-tenant overrides in `tenant_quota_config`), read the same way as D4: `SUM(pages)` of the tenant's `ocr` rows and `SUM(audio_seconds)` of its `transcription` rows of the current UTC month, served by the index `(tenant_id, occurred_at)`, with no Redis counter (answer 89.9). The OCR gate runs before `AscendOcrClient` submits a job, and the transcription gate runs in the tool-callback wrapper before the tool is called, returning a tool result that names the retry time instead of a 429, the same way the web-search bucket does (D6). Web search, page reads, ingestion and memory operations get no budget: they are bounded by the rate limits of D6 and recorded for the invoice. Embedding tokens already count against the token budget.

A quota refusal of a channel turn of `add-openclaw-plugin-host` is answered to the platform as `refused` with reason `quota_exceeded` and the retry time in the text, not as an HTTP 429 to the host.

### D14 - Request types, run ids and the agent changes

Owner sweep of 2026-10-02: the agent changes listed in the proposal add request types and columns here, each in its own "Required edits to other changes" section. This change holds all of them from its first migration, so a change that writes the rows never alters the ledger table.

- The request types of D12 are one closed set, which is also the set of `request_type` tag values (D11). A run's model call uses the request type of its kind: `subagent` for a run of kind `subagent`, `scheduled` for kind `scheduled`, `self-review` for kind `self_review`, and `coding-agent` for a coding run, so the usage view shows the assistant's own work apart from delegated subagent work. A reminder of `add-scheduled-tasks` makes no model call and records no usage.
- `run_id` and `parent_run_id` (nullable UUID) are on every ledger row, filled by D2 while a run works, with an index on `run_id`, so a run tree's usage is `SUM(...) WHERE run_id IN (tree)`.
- `tool` (nullable text) holds the prefixed tool name of an `mcp-tool` row and is empty on every other row. It is a column of the first migration, `V<n>__usage_metering.sql`, like every other column of D12 (answer 93, review item C2: the same change no longer adds it in a second migration).
- A voice note of `add-openclaw-plugin-host` that is transcribed writes a `transcription` row with `audio_seconds`, attributed to the linked user.
- None of these changes adds a dollar limit or a budget of its own here.

### D15 - Estimated cost of a chat turn in `done.metadata` (owner decision 65.4 of 2026-10-04)

The terminal `done` event of the chat stream of `add-chat-streaming-and-conversations` carries `metadata.estimatedCostUsd`: the estimated cost in US dollars of the model calls of that turn, as a decimal number. It is on by default and switched by `app.usage.cost-estimate.enabled` (default `true`), the one `enabled` flag of `app.usage.*` that stays, because owner decision 65.4 asked for it by name (answer 93 removed the other four, Migration Plan). When it is off, the field is left out.

- The price comes from `infra/pricing/pricing.yaml` through `PriceTable`, the cost meter of `add-agent-subagents` (its D12), so the dashboard, the run limits and this field read one table. The rule is the same as there: input and output tokens at their prices per 1000 tokens, cached input tokens at the full input price, and a response without usage estimated at 4 characters per token.
- The turn adds the cost of each of its own model calls, the same calls whose ledger rows carry the turn's request (chat, a compaction call it triggers, a memory extraction call it makes). The cost of a background run the turn starts is not in it, because the run outlives the turn and has its own `cost_usd` on its run view.
- A model with no price in the table makes the turn's estimate unknown: the field is left out, one WARN line names the provider and model once per model per process, and the counter `usage.cost_estimate.unpriced{provider,model}` goes up.
- The field is an estimate for the user, never a bill. The ledger stays the billing record (D1) and holds no dollar value.

### D16 - The ledger backs the company ports and joins erasure

`add-deployment-modules` owns `UsageEventPort` (`record(UsageEvent)`) with the default `NoOpUsageEventPort`, registered with `@ConditionalOnMissingBean`, and the earlier changes record their usage events through it (for example one `mcp-tool` event per successful call of a metered MCP tool of `add-mcp-tool-servers`). This change registers `LedgerUsageEventPort`, which maps a `UsageEvent` onto a ledger row through `UsageLedgerRecorder` by the field mapping of D1, so the default bean is not created and no earlier change is edited. It is the one path into the ledger: the callers this change adds (D12) send their events through the same port, and nothing else calls `UsageLedgerRecorder` (answer 89.9).

The quota gate of D4 and D14 is also registered as the implementation of `QuotaGate` of `add-deployment-modules` (its D21, ruling 13.1 of the dependency fix of 2026-10-05), replacing the default `AllowAllQuotaGate`, so every earlier change that asks the shared port before a metered action (a run of `add-agent-subagents`, a coding run, a guard call of `add-self-improvement`, an integration build through its coding run) gets the real decision with no edit. The change-local quota ports those changes once had (`RunQuotaGate`, `CodingQuotaGate`) no longer exist. A quota refusal (D4, D13, D14) also records `QUOTA_REJECTED` through `AuditEventPort` of `add-deployment-modules`, which `add-audit-and-gdpr-compliance` (earlier) stores as an audit row.

The `usage_ledger` and `usage_quota_warning` rows hold user data, so this change registers a store step in the `StoreWalker` of `add-audit-and-gdpr-compliance`: per user erasure deletes the user's rows of the tenant, per tenant erasure deletes every row of the tenant and also the tenant's `tenant_quota_config` and `tenant_provider_key` rows (the key ciphertext leaves with the tenant's `connector_credential` rows), and both exports add the ledger and warning rows as JSON. A provider key is never exported, only its provider and `last4`. `wipeUserMemory` called by erasure writes no ledger row (task 2.15). The foreign key from `usage_ledger.tenant_id`, `usage_quota_warning.tenant_id`, `tenant_quota_config.tenant_id` and `tenant_provider_key.tenant_id` to `tenants(id)` is part of this change's own migration, because `add-tenant-isolation` created `tenants` earlier.

## Risks / Trade-offs

- [A service reports a wrong number (D12)] → each reported field has a test in its own module, and the agent rejects a negative or missing `audio_seconds` by writing the row with the field empty and logging a WARN, so a bad report never fails the user request.
- [Single-request quota overshoot (D4)] → accepted and documented; budgets should be set with one-request headroom, and a burst of parallel requests can overshoot by the burst because the ledger write is asynchronous. Soft warning at 80% gives operators lead time.
- [One Postgres aggregate per gated call (D4)] → one indexed `SUM` per budget that is set, on `(tenant_id, occurred_at)` or `(user_id, occurred_at)`. A cache is added only when a measurement shows the read is a problem.
- [Redis outage weakens rate limiting (fail-open, D6)] → quota gate still bounds absolute spend, because it reads only Postgres; `rate_limit.redis_unavailable` metric alerts operators.
- [Ledger insert per chat turn adds write load] → single-row insert on an async executor, indexed narrow table; at this platform's request volume partitioning is premature. Revisit with a monthly-partition Flyway migration if row count warrants it.
- [The secret store key in an env var is weaker than a key management service] → the one `ConnectorCredentialStore` port (D8) isolates the key, so a key management service is one more implementation of that port for both secret kinds. The key version on each row allows rotation, and `harden-cloud-deployment` owns secret delivery.
- [Tenant tag on Prometheus metrics could explode cardinality if tenants become self-service] → tenants are operator-created in this platform's model; if that changes, drop the tag and rely on the ledger (Grafana Postgres datasource) instead.
- [Sibling-change coupling] → this change builds against the contracts of the changes that land before it (principal + `tenant` claim, tenant entity, the policy gate, the audit `StoreWalker`, the two company ports), in build group 5, position 6 of the owner build order of 2026-10-04.
- [Streamed responses could lose usage rows if the client disconnects mid-stream] → recorder runs in the stream completion/termination callback (both normal completion and cancellation with whatever partial usage metadata the provider delivered); noted for the streaming change to honour.

## Migration Plan

1. The one Flyway migration is purely additive (four new tables, the ledger already carrying every D12 column, `run_id`, `parent_run_id` and `tool`, D14, and the warning table of D4) - deploys ahead of code safely.
2. No `enabled` flags except `app.usage.cost-estimate.enabled` (D15, owner decision 65.4). Answer 93 (review item B8) removed `app.usage.metering.enabled`, `app.usage.quotas.enabled`, `app.usage.rate-limit.enabled` and `app.usage.byok.enabled`, because every limit stays a configuration value: a budget that is not set (platform default and tenant override) is unlimited, and a bucket whose capacity is not set is not created. Leaving every budget and capacity unset reverts to today's unlimited behavior. A tenant with no stored provider key uses the global keys, so BYOK needs no switch.
3. Rollback: unset the budgets and capacities; tables remain (no destructive rollback needed, and Flyway Community has no automatic undo anyway). BYOK rollback deletes the tenant's provider keys through the API, whose eviction (D9) moves all traffic back to global keys.
4. Ships after `upgrade-spring-boot-4`, `add-keycloak-login`, `add-deployment-modules`, `add-auth-and-identity`, `add-tenant-isolation`, `add-tenant-policy` and `add-audit-and-gdpr-compliance` are merged.
