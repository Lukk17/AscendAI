# Add Usage Metering and Quotas

## Why

AscendAI has no per-tenant or per-user accounting of what anything costs, and nothing stops one caller from burning the operator's entire provider budget. Token usage exists only as aggregate Prometheus counters with **no user or tenant dimension**: `apps/ascend-agent/src/main/java/com/lukk/ascend/ai/agent/service/cache/GenAiTokenUsageRecorder.java` emits `gen_ai.client.token.usage` tagged by `gen_ai_system` / `gen_ai_request_model` / `gen_ai_token_type` only, and `ingestion.upload.bytes` (`controller/IngestionController.java`) is equally anonymous. Prometheus data also ages out (72h retention), so it can never back an invoice. There is no rate limiting anywhere in ascend-ai-agent, AscendMemory, or ascend-web-hunter (`apps/ascend-agent/build.gradle.kts` has no Bucket4j or Resilience4j-ratelimiter dependency), and provider API keys are global per deployment (`application.yaml` - `OPENAI_API_KEY` line 195, `GEMINI_API_KEY` lines 205/255, `ASCEND_ANTHROPIC_API_KEY` line 218, `MINIMAX_API_KEY` line 229; mirrored in `compose.yaml` lines 118-121). Once `add-auth-and-identity` gives us a trustworthy identity and `add-tenant-isolation` gives us a tenant model, metering and quotas become the piece that makes multi-tenant operation financially safe and billable.

## What Changes

- **Usage ledger (Postgres).** Every LLM-touching request persists a usage row - tenant, user, conversation, provider, model, prompt / completion / cached-token counts, timestamp, and request type (`chat`, `compaction`, `memory-extraction`, `embedding`) - via a new Flyway versioned SQL migration. Usage reaches the ledger through one path (owner answer 89.9 of 2026-10-08): every caller sends a `UsageEvent` through `UsageEventPort` of `add-deployment-modules`, from `StreamingChatExecutor` of `add-chat-streaming-and-conversations`, the one chat executor (owner answer 89.1), `SemanticMemoryExtractor` (line 100), the compaction path (`memory/ChatHistoryCompactionService.java`), the embedding path and every metered service call, and this change's `LedgerUsageEventPort` writes the row. The prompt cache strategies stay cache-only.
- **Metering of every service, not only model calls (owner decision, 2026-10-01).** The same ledger also records OCR jobs (pages and processing time, read from the ascend-ocr job record the agent already polls), document ingestion (files, bytes and chunks per ingested file, with the embedding tokens in the existing `embedding` rows), audio transcription (audio seconds per provider of ascend-audio-scribe), web search and page reads of ascend-web-hunter (one row per request, with the tier that produced a page), and semantic memory operations of AscendMemory (one row per search, insert and delete). New request types: `ocr`, `ingestion`, `transcription`, `web-search`, `web-read`, `memory-search`, `memory-insert`, `memory-delete`. The agent records every row itself, because it makes every one of these calls with the tenant and user in hand. No service keeps a ledger of its own. Two services gain one reported number in a tool result: ascend-audio-scribe returns the audio length in seconds, and ascend-web-hunter returns the tier that produced a page, where it does not already. Calls that reach a service without passing through the agent carry no tenant and are not metered (design D12 lists them).
- **Request types and run ids of the agent changes (owner sweep, 2026-10-02).** The closed set of request types also holds the types that later agent changes write: `subagent` (`add-agent-subagents`), `sandbox` (`add-agent-sandbox`, the time a workspace existed), `mcp-tool` (`add-mcp-tool-servers`, one row per successful call of a tool of a server with `metered: true`), `web-download` (`add-file-download`), `coding-agent` (`add-coding-agent-delegation`), `scheduled` (`add-scheduled-tasks`), `self-review` and `self-check` (`add-self-improvement`). Every ledger row gains nullable `run_id` and `parent_run_id`, so a run tree's usage can be summed, and a nullable `tool` column for the prefixed name of a metered MCP tool. The quota gate also runs before each model call of a run, not only at the HTTP entry, and a refusal inside a run ends the run with `QUOTA_EXCEEDED` instead of an HTTP 429 (design D14).
- **Usage query API.** `GET /api/v1/usage` returns summaries grouped by day or month, or by background run as an extra option (owner decision 51.4) - tenant-wide for `ADMIN`, own usage for `USER` - with CSV and JSON export suitable for invoicing. Payment processing is an explicit **non-goal**.
- **Quotas.** Per-tenant monthly token budget and per-user daily token budget, plus per-tenant monthly budgets for OCR pages and audio transcription seconds (the two non-model costs that grow with input size, unlimited unless set), with configurable platform defaults and per-tenant overrides. Enforced **before** the provider call from an indexed Postgres sum of the ledger, with no Redis counter (owner answer 89.9); an exhausted budget returns `429` with `Retry-After` and an RFC 7807 problem detail body with code `quota_exceeded`. Crossing a soft-warning threshold (default 80%) emits a log event and a metric once per window across all agent instances, so operators can alert before hard cut-off.
- **Rate limiting.** Per-user and per-tenant request-rate limits on the chat endpoint, ingestion upload, and web-search-tool-invoking paths. Redis-backed token buckets (Bucket4j vs. Redis Lua decided in design) so limits hold across ascend-ai-agent replicas. Over-limit requests get `429` + `Retry-After` and an RFC 7807 problem detail body with code `rate_limited`. The channel message endpoint `POST /api/v1/channel-host/messages` of `add-openclaw-plugin-host` consumes the chat buckets of the linked user and tenant and is answered as `refused` with reason `rate_limited` instead of a 429, and the `web_download_file` calls of `add-file-download` consume the same `web-search` bucket as the other web-hunter tools.
- **BYOK provider credentials.** Per-tenant provider API keys stored encrypted at rest in the agent's one encrypted secret store, the `ConnectorCredentialStore` of `add-connector-framework` with `CONNECTOR_CREDENTIALS_KEY` (owner answer 89.9), and resolved at request time, falling back to the global deployment keys when a tenant has none. Keys are write-only through the API (only `last4` and metadata are ever returned); management endpoints are `ADMIN`-only. This requires per-tenant provider clients - today `ChatModelResolver` builds one client per provider at startup (`@PostConstruct initializeProviders()`), so resolution gains a tenant-keyed client cache, evicted on every agent instance when a key changes. The BYOK providers gain `opencode-go` and `opencode-zen`, and this change registers the per-tenant (BYOK) implementation of the `ProviderKeyResolver` port of `add-coding-agent-delegation`, replacing its default that returns the deployment key (`OPENCODE_API_KEY`), so the credential gateway of that change gets the tenant's key in memory only, never through any API. The provider and model gate of `add-tenant-policy`, which lands earlier, stays in front of the tenant-aware resolution.
- **Company extension ports.** This change registers a `UsageLedgerRecorder` backed implementation of `UsageEventPort` of `add-deployment-modules` (its decision "Company extension ports"), replacing the default `NoOpUsageEventPort`, so every usage event the earlier changes record through the port becomes a ledger row with no edit of those changes, and registers its quota gate as the implementation of the shared `QuotaGate` port of the same change, replacing `AllowAllQuotaGate` (ruling 13.1 of the dependency fix of 2026-10-05). Quota refusals are recorded as `QUOTA_REJECTED` through `AuditEventPort`, which `add-audit-and-gdpr-compliance` (earlier) stores as audit rows. The `usage_ledger` rows join the erasure and export jobs of `add-audit-and-gdpr-compliance` through a store step this change registers in its `StoreWalker`.
- **Its own parts of the deployment.** `add-deployment-modules` keeps metering out of the always-on core, so this change adds its own parts to the deployment when it lands: the one migration, the port implementations, the `app.usage.*` configuration and the Usage and Quotas dashboard. It adds no secret of its own.
- **Observability feed.** The ledger port emits a new counter `usage.tokens` with `tenant`, `request_type` and `token_type` tags (bounded cardinality - tenant count is small and operator-controlled), the existing `gen_ai.client.token.usage` counter stays as it is, and a Usage & Quotas Grafana dashboard joins the existing `infra/observability/grafana/dashboards/` set.

## Capabilities

### New Capabilities

- `usage-metering`: per-request usage ledger rows in Postgres for model calls and for every metered service operation (OCR, ingestion, transcription, web search and reads, memory operations, sandbox time, metered MCP tools, file downloads), the request types and run ids of the agent changes, and the `GET /api/v1/usage` summary/export API.
- `quota-enforcement`: per-tenant monthly and per-user daily token budgets, per-tenant monthly OCR page and transcription second budgets, pre-request enforcement with `429` + `Retry-After`, the same gate before each model call of a run, soft-warning threshold events.
- `rate-limiting`: Redis-backed per-user and per-tenant request-rate limits on chat, the channel message endpoint, ingestion upload, and web-search-tool-invoking paths.
- `byok-provider-keys`: per-tenant provider API keys - encrypted at rest, write-only API with `last4` display, request-time resolution with global-key fallback, `ADMIN`-only management, and the in-memory `ProviderKeyResolver` for trusted agent code.

### Modified Capabilities

(none - `openspec/specs/prompt-caching/spec.md` was reviewed for the cached-token overlap: its requirements about cache strategy resolution, structured hit/miss logging, and fallback behavior do not change. The ledger reads the same response usage metadata additively in the callers, and `recordOutcome` does not change.)

## Impact

- **ascend-ai-agent code**: new `service/usage/` package (ledger recorder, quota gate, usage query service), new `repository/` Spring Data JDBC aggregates and repositories, new `controller/UsageController.java` and `controller/admin/ProviderKeyController.java`, recorder calls in `service/ingestion/client/AscendOcrClient.java` (its `JobRecord` gains `pages_done`, `started_at`, `finished_at`), the ingestion pipeline, `service/memory/SemanticMemoryClient.java` and an MCP tool-callback wrapper for the ascend-audio-scribe and ascend-web-hunter tools, rate-limit filter/interceptor wiring, `ChatModelResolver` + `config/properties/AiProviderProperties.java` extended for tenant-key resolution. Every one of these callers sends a `UsageEvent` through `UsageEventPort`, and the three `service/cache/` strategy classes and `GenAiTokenUsageRecorder` stay unchanged.
- **Dependencies**: `apps/ascend-agent/build.gradle.kts` gains `com.bucket4j:bucket4j_jdk17-lettuce` 8.20.0 (the current Bucket4j release, Lettuce matches the Spring Data Redis driver) and Caffeine for the tenant client cache, both declared in `apps/ascend-agent/gradle/libs.versions.toml`. After `upgrade-spring-boot-4`, Spring Boot 4.1.1 brings Lettuce 7.5.2, a major version up from 6.6.0, while the Bucket4j Lettuce module is compiled against Lettuce 6.1.8, so compatibility must be measured again before the artifact is accepted (design Closed Question 2).
- **Python services**: ascend-audio-scribe adds `audio_seconds` to the success result of its three transcription tools, and ascend-web-hunter makes its page-read result name the tier that produced the content if it does not already. Both are additive fields with tests in each module, and neither service stores usage.
- **Database**: new Flyway versioned SQL migration `V<n>__usage_metering.sql` in `src/main/resources/db/migration/`, with `<n>` taken at implementation time, (usage ledger table with the `run_id`, `parent_run_id` and `tool` columns and an index on `run_id`, quota config table, tenant provider-key table holding only the secret store handle and `last4`, quota warning table, design D4, D8 and D14). Flyway finds it by location, so no master file lists it.
- **Configuration**: `application.yaml` gains default quota/rate-limit values, unset meaning unlimited, and no `enabled` flag except `app.usage.cost-estimate.enabled`; `compose.yaml` passes every setting as `${VAR:-default}` with the same default as the code, the BYOK client cache is bounded to 200 entries and 10 minutes (owner answers 98 and 98.4), and `apps/ascend-agent/docs/CONFIGURATION.md` gets a row per setting. BYOK uses `CONNECTOR_CREDENTIALS_KEY` of `add-connector-framework`.
- **Observability**: the new `usage.tokens` counter, new quota/rate-limit counters, one new provisioned Grafana dashboard under `infra/observability/grafana/dashboards/`.
- **API surface**: new `GET /api/v1/usage`, new `ADMIN` endpoints under `/api/v1/admin/tenants/{tenantId}/provider-keys` (the one administration prefix `/api/v1/admin/`, owner decision 2026-10-01); chat/ingestion/web-search paths can now return `429`.
- Build order (owner build order of 2026-10-04, which supersedes the earlier orders): build group 5 (company), position 6. It needs `upgrade-spring-boot-4` (Flyway, owner decision of 2026-10-02), `add-keycloak-login` (authenticated principal, `USER`/`ADMIN` roles), `add-deployment-modules` (`UsageEventPort` and `AuditEventPort`), `add-chat-streaming-and-conversations` (streamed responses record a ledger row at stream completion), `add-agent-subagents` (`PriceTable`), `add-coding-agent-delegation` (`ProviderKeyResolver`), `add-auth-and-identity` (the `tenant` claim), `add-tenant-isolation` (tenant model), `add-tenant-policy` (the provider and model gate and the Caffeine catalog entry) and `add-audit-and-gdpr-compliance` (the audit rows and the `StoreWalker`), all earlier. None is re-specified here. The company order of 2026-10-01, which put this change before `add-audit-and-gdpr-compliance`, `add-tenant-administration` and `add-tenant-policy`, is superseded by the owner build order of 2026-10-04.
- **Agent changes that use this change, in their build order**: `add-agent-subagents` (request type `subagent`, `run_id` and `parent_run_id`, the quota gate before each model call of a run), `add-agent-sandbox` (request type `sandbox`), `add-mcp-tool-servers` (request type `mcp-tool` and the `tool` column), `add-openclaw-plugin-host` (the channel message endpoint on the chat buckets, quota refusals as `refused`, voice note `transcription` rows), `add-file-download` and its agent part `add-download-ingestion` (request type `web-download` and the `web-search` bucket), `add-coding-agent-delegation` (request type `coding-agent`, `ProviderKeyResolver`, the providers `opencode-go` and `opencode-zen`), `add-scheduled-tasks` (request type `scheduled`) and `add-self-improvement` (request types `self-review` and `self-check`). Under the owner build order of 2026-10-04 every one of them lands before this change. This change defines every request type, column and gate from its first migration, and does the work that writes the rows or calls the gate for each of them (tasks group 9), through `UsageEventPort` where the earlier change already records a usage event and through its own hooks otherwise.
- **Docs**: `docs/` usage-and-billing page, module `AGENTS.md` touch-ups, Bruno collection additions for the new endpoints.
