## Why

The owner decided on 2026-10-02 to move both Java services, ascend-agent and ascend-weather-mcp, from Spring Boot 3.5.14 and Spring AI 1.1.5 to Spring Boot 4 and Spring AI 2, so the agent can use `org.springaicommunity:spring-ai-agent-utils` (0.12.0 on Maven Central, compiled against Spring AI 2.0.1 and Spring Framework 7.0.8). Spring AI 1.1.x cannot load that library, and Spring AI 2.0.x does not run on Spring Boot 3. Both Java services stay on one version line, so the monorepo keeps one Spring baseline.

The target versions, confirmed on 2026-10-02 against the official pages and Maven Central:

- Spring AI 2.0.1. It is the latest GA on Maven Central (`spring-ai-bom` lists 2.0.0 and 2.0.1 as releases, and 2.1.0-M1 is a milestone). The Spring AI reference documents 2.0.1 and states "Spring AI 2.0.x supports Spring Boot 4.0.x and 4.1.x".
- Spring Boot 4.1.1. It is the latest GA on Maven Central (`spring-boot-dependencies` lists 4.1.0 and 4.1.1 as releases, and 4.2.0-M1 and 4.2.0-M2 are milestones) and the version spring.io shows for the project. Spring AI 2.0.1 itself is built on the 4.1.1 line: its modules depend on Spring Framework 7.0.9 and Micrometer 1.17.1, the versions Spring Boot 4.1.1 manages.

## What Changes

- **BREAKING (build)** Spring Boot 3.5.14 to 4.1.1 and Spring AI 1.1.5 to 2.0.1 in both `gradle/libs.versions.toml` files. Spring Framework 7, Jakarta EE 11, Jackson 3, JUnit 6, Spring Security 7 and Spring Integration 7 come with it.
- Modular starters: `spring-boot-starter-web` becomes `spring-boot-starter-webmvc`, `spring-boot-starter-oauth2-client` becomes `spring-boot-starter-security-oauth2-client`, and the test side moves to the per-technology test starters. OTLP trace export moves to Spring Boot's `spring-boot-micrometer-tracing-opentelemetry` module.
- **BREAKING (database tooling)** The agent moves from Liquibase to Flyway (owner decision of 2026-10-02). Spring Boot 4.1.1 manages Liquibase 5.0.3, which is under the Functional Source License, and Flyway 12.4.0, which is under Apache 2.0. The agent depends on `spring-boot-starter-flyway` and `org.flywaydb:flyway-database-postgresql`, both at the 12.4.0 Spring Boot manages. The one Liquibase changelog (`01-initial-schema.xml` with `db.changelog-master.yaml`) becomes `db/migration/V1__initial_schema.sql` with the same two tables and index, and the same file also creates Spring Integration's JDBC tables from Spring Integration's own PostgreSQL script, with `spring.integration.jdbc.initialize-schema` set to `never`, so Flyway is the one schema owner and no start-up order test is needed (owner answer 89.11 of 2026-10-08). No existing database is carried over (owner decision of 2026-10-02, confirmed by owner answer 73.1 of 2026-10-06, `design.md` D16): the project is under development and holds no data the owner wants to keep, so a developer drops the local `ascend_ai` database and Flyway creates it from V1. One integration test proves V1 creates the expected schema.
- Qdrant server image `qdrant/qdrant:v1.13.0` to `qdrant/qdrant:v1.18.0`, together with the 1.18.0 Java client, in the agent's Testcontainers base class and in `.github/workflows/e2e.yaml` (owner decision of 2026-10-02). The owner approved the workflow file edit. It must not start a pipeline run.
- The `https://repo.spring.io/milestone` repository is removed from the agent build (owner decision of 2026-10-02). No target version is a milestone.
- **BREAKING (dependency)** `org.springframework.integration:spring-integration-aws` 3.0.10 has no Spring Integration 7 release. The project is end of life and its S3 classes now live in Spring Cloud AWS 4 (`io.awspring.cloud:spring-cloud-aws-s3`, package `io.awspring.cloud.s3.integration`). The S3 inbound pipeline moves to it.
- springdoc-openapi 2.8.17 to 3.1.1, the line built on Spring Boot 4.1.
- Jackson 3: every `com.fasterxml.jackson.databind` and `com.fasterxml.jackson.core` import moves to `tools.jackson`. `jackson-annotations` keeps its package, so the annotation-only DTOs do not change. Chat history that Jackson 2 wrote into Redis or Postgres is not kept readable. It is dropped with the database (D16).
- Provider clients: Spring AI 2 removes `OpenAiApi` and `AnthropicApi` and builds the OpenAI and Anthropic models on the vendor SDKs (`openai-java` 4.49.0, `anthropic-java` 2.52.0) with an OkHttp transport. Base URL, API key and timeout move onto the chat and embedding options. Every provider keeps its shipped defaults: OpenAI, Anthropic, Gemini (through the OpenAI client), MiniMax (through the Anthropic client at `https://api.minimax.io/anthropic`, which is already how this repository wires it) and LM Studio.
- Tool calling: Spring AI 2 removes the tool loop from `ChatModel`. Tools run through `ChatClient` and its `ToolCallingAdvisor`. The agent's tool-call tracking, which feeds `toolsUsed` in the response and the `mcp.tool.duration` metric, moves from the chat model onto that advisor.
- Options: `ChatClient` takes option builders instead of built options, so the prompt-cache strategies return builders. Prompt-cache readback moves from the removed `OpenAiApi.Usage` and `AnthropicApi.Usage` types to Spring AI's own `Usage.getCacheReadInputTokens()` and `Usage.getCacheWriteInputTokens()`.
- MCP: MCP Java SDK 2.0.0. The agent's custom MCP classes under `config/mcp` keep their design. Every Spring AI and SDK type they use still exists in 2.0.1 and is checked again by their unit and integration tests. ascend-weather-mcp gets the SDK 2.0 server-side check of tool arguments against the tool's JSON schema, which runs before the service's own input checks.
- **BREAKING (operations)** Spring Boot 4 renames the OTLP trace export properties. `management.otlp.tracing.endpoint` becomes `management.opentelemetry.tracing.export.otlp.endpoint`, so the environment variable becomes `MANAGEMENT_OPENTELEMETRY_TRACING_EXPORT_OTLP_ENDPOINT`.
- `app.ai.providers.*.requires-http1` is removed. It only switched the JDK HTTP client to HTTP/1.1, and the SDK transport that replaces that client never negotiates HTTP/2 on a plain `http://` URL.
- **BREAKING (API)** Every REST error body of the agent becomes an RFC 7807 problem detail, Spring's `ProblemDetail` with media type `application/problem+json` (owner decisions of 2026-10-02, `design.md` D19). The design follows the owner's Pharmacy service: one global exception handler that extends Spring's `ResponseEntityExceptionHandler`. Today `GlobalExceptionHandler` answers a map with `status`, `error`, `message` and `timestamp`, and the two controllers answer the `ApiError` record with `status`, `error` and `message`. After the change every error carries `type` (`https://ascend.ai/errors/<code>`, the base the Python services already use, in the format that `add-ascend-python-common` defines for every service, owner answer 70.1 of 2026-10-04), `title`, `status`, `detail`, `instance`, a stable `code` extension field and a `traceId` extension field with the id of the current trace (owner decision 51.3 of 2026-10-03, left out only when no span is current), and a request validation failure also carries an `errors` extension field with one `field` and `message` pair per rejected field. Every error the agent raises itself keeps its HTTP status, with one deliberate change: a provider 5xx that persists after the retries answers 502 `provider_error`, where today it answers 500 after about 19 minutes of retries (`design.md` D9). Spring MVC's own client errors, which answer 500 today, answer their correct status: a missing request part 400, an unknown path 404, a wrong method 405, an upload over the size limit 413, an unsupported content type 415. `ApiError` is deleted, the controllers throw one `ApiProblemException`, the 401 of the security entry point and Spring Boot's `/error` path answer the same body, and the OpenAPI description names `application/problem+json`.
- Main spec corrections (owner decision of 2026-10-02): `ingestion-correctness` says a non-vision model with an image answers 400, but the code answers 415, and `ingestion-security` asserts the message text `Unsupported MIME type`, which the code never sends. `ingestion-security` gets a MODIFIED delta that asserts the stable code `unsupported_media_type` instead of the message text. The same main spec says the multipart limits default to 25 MB per file and 30 MB per request, while `application.yaml` sets 100 MB and 110 MB. Owner answer 32 of 2026-10-02 keeps the shipped values, so a second MODIFIED block in the same delta states 100 MB per file and 110 MB per request, with the 413 answered as the problem body code `content_too_large`. `ingestion-correctness` needs its scenario "Non-vision model rejected with 400" renamed, which a MODIFIED block cannot do, so its requirement is removed and re-added with 415 and code `vision_unsupported`, the same way this change handles `mcp-startup-resilience`.
- Re-checks of work that earlier changes built against today's agent (design D21): the shared end-to-end harness of `close-agent-test-gaps` (the overlay provider entry `scripted`, the MCP connection `e2e-fake` and one scripted smoke prompt, then its provider error spec with the problem detail body, plus one new row of that same spec in which the scripted model answers 502 on every attempt and the agent gives up after the provider SDK's default retry count and answers 502 within a bounded time, owner answers 73.2 of 2026-10-06 and 90 of 2026-10-08, with no retry count setting), and the Python runtime of `add-python-runtime-upgrades` against the upgraded MCP client (owner answer 70.1 of 2026-10-04).
- Version labels: ascend-agent 0.1.3 to 0.2.0 (`fix-linux-docker-host-access` raises it from 0.1.2 to 0.1.3 earlier, owner answer 104 of 2026-10-09) and ascend-weather-mcp 0.0.4 to 0.1.0, each with a CHANGELOG entry.
- Docs: version strings in `AGENTS.md` files and READMEs, the arc42 constraints, `docs/OBSERVABILITY.md`, the MCP ADRs that name Spring AI 1.1.5, a new monorepo decision record, ADR-M011, a new agent decision record, ADR-011, for Flyway and for dropping existing data, and ADR-012 for the problem details. `apps/ascend-agent/AGENTS.md` today says Liquibase is used for all schema changes. It will say Flyway.

## Capabilities

### New Capabilities

- `agent-error-responses`: every 4xx and 5xx answer of ascend-agent is an `application/problem+json` body with `type`, `title`, `status`, `detail`, `instance`, `code` and `traceId`, plus `errors` on a request validation failure. Each error the agent raises itself keeps the HTTP status it had, Spring MVC's own client errors answer their correct 4xx status instead of 500, and the OpenAPI description names the problem body.
- `java-service-platform`: both Java services run on one supported Spring Boot and Spring AI line, and a framework upgrade keeps their external behaviour. This covers provider defaults and provider error statuses, tool-call reporting, the database schema created by versioned SQL migrations, embedding collections, the metrics and trace export the operators rely on, and how the weather server answers bad tool arguments.

### Modified Capabilities

- `mcp-startup-resilience`: the requirement "Configuration uses Spring AI's built-in deferral flag" pins its upgrade scenario to the Spring AI 1.1.x line. OpenSpec does not let a MODIFIED block drop or rename a scenario, so the requirement is removed and re-added as "Configuration uses Spring AI's built-in MCP deferral flag", with the upgrade scenario on the 2.0.x line. The flags, the auto-configuration classes, the no-fork rule and the second scenario are unchanged. `add-deployment-modules`, which lands second, carries its own delta of this capability for other requirements (the tool filter, the stale session, the banner and a new background retry), so the two deltas do not overlap.
- `prompt-caching`: the requirement "Static prefix is cached per provider via the strategy resolver" reads cached tokens from `OpenAiApi.Usage.PromptTokensDetails.cachedTokens`, a type Spring AI 2 removes. It now reads Spring AI's provider-neutral cache-read count. The per-provider decoration rules are unchanged.
- `ascend-agent-containerization`: the scenarios "Container reaches host PostgreSQL and Redis via the docker profile" and "Container reaches host PostgreSQL" say Liquibase migrations run against the host database. They now say Flyway migrations run against an empty host database or one Flyway created. The two requirements are otherwise unchanged.
- `ingestion-correctness`: the requirement "Vision-capability check for image-bearing prompts" says a non-vision model with an image answers 400, in a scenario named "Non-vision model rejected with 400". The code answers 415. OpenSpec does not let a MODIFIED block rename a scenario, so the requirement is removed and re-added as "Vision-capability check answers 415 for image-bearing prompts", with 415 and the problem body code `vision_unsupported`. The allowlist check and the vision-capable scenario are unchanged.
- `ascend-agent-test-coverage` (created by `close-agent-test-gaps`, build group 3, position 1): the requirement "Provider 429 and 502 handling is checked end to end" gains the scenario of a provider that answers 502 on every attempt, which the agent gives up on with a 502 within a bounded time (owner answer 73.2 of 2026-10-06), and its 429 scenario reads the problem body of D19 and counts three requests instead of one, because the provider SDK retries a 429 with its default of two retries and no configuration sets a retry count (`design.md` D9, measured on 2026-10-06, owner answer 90 of 2026-10-08). The existing provider error spec is updated in place, no new spec is written.
- `ingestion-security`: the requirement "MIME-type allowlist enforced on upload" asserts a body containing `Unsupported MIME type`, a text the code never sends. The scenario now asserts 415 with the stable problem body code `unsupported_media_type`. The requirement "Multipart size limits configured" names 25 MB per file and 30 MB per request, but `application.yaml` sets 100 MB and 110 MB. It now names 100 MB and 110 MB (owner answer 32), and its 413 asserts the code `content_too_large` instead of the text `Maximum upload size`.
