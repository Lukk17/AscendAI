## Goals / Non-Goals

**Goals:**

- Both Java services build, test and run on Spring Boot 4.1.1 and Spring AI 2.0.1, from one pair of version numbers each in their own catalog.
- Every behaviour listed in `specs/java-service-platform/spec.md` holds before and after, proved by a test that runs on the old code first where the behaviour already exists.
- No deprecation warning from our own code at compile time, and no `@SuppressWarnings` added to hide one.

**Non-Goals:**

- Adding `spring-ai-agent-utils` or any new agent feature. That is the next change.
- Moving Gemini to Spring AI's native Google GenAI client. It stays on the OpenAI-compatible endpoint (ADR-002).
- Adopting Spring AI's chat memory advisors or JDBC chat memory.
- Upgrading libraries the framework does not force (commonmark, PDFBox, Tika, JaCoCo, Caffeine). The surgical-change rule applies.
- Changing the Python services.

### D4: Provider clients on the vendor SDKs

Spring AI 2.0.1 removes `OpenAiApi` and `AnthropicApi`. `OpenAiChatModel.Builder` and `AnthropicChatModel.Builder` now take `options(...)`, an optional prebuilt SDK client, and `httpClientBuilderCustomizer(...)`. Base URL, API key, timeout and retry count are fields on `OpenAiChatOptions`, `AnthropicChatOptions` and `OpenAiEmbeddingOptions` (`baseUrl`, `apiKey`, `timeout`, `maxRetries`). Owner answer 90 of 2026-10-08 removed the key `max-retries`, which existed only so a test could lower the count. Owner rule 98 of 2026-10-08 brings the retry count back as an operational setting, never a test setting: every provider entry gets `max-retries` (environment variable `APP_AI_PROVIDERS_<NAME>_MAXRETRIES`), with the SDK's own default as its default, read again at implementation time in the openai-java and anthropic-sdk-java documentation (task 8.20) and 2 as read on 2026-10-06, and the resolver passes it to `maxRetries` of the options. No test, overlay or spec sets it, so every request count below is the count of that default. The SDK counts `maxRetries` as retries after the first request, so its default of 2 gives at most three requests, and it retries connection errors, 408, 409, 429 and every 5xx (measured on 2026-10-06, see D9). Task 8.6 records the count and the time on the upgraded agent. The slow provider timeout test of task 2.2 therefore runs with the SDK default too: the prompt fails with a timeout in its cause chain, the local server sees every request closed by the client before its 3 second answer, and it receives at most the SDK default of three requests. Two limits of owner answer 75.2 of 2026-10-07 change: the test no longer asserts exactly one request, and the whole prompt no longer fails in under 3 seconds, because each retry waits for its own 1 second timeout plus the SDK backoff. The count and the time are written under task 2.2 on today's code and under task 8.7 on the upgraded agent. `ChatModelResolver` and `VectorStoreConfig` move every value they pass today onto those options:

The model names keep the variables they already have (`OPENAI_MODEL` and the others). The LM Studio base URLs (`app.ai.providers.lmstudio.base-url`, `app.embedding.providers.lmstudio.base-url`) and `spring.ai.openai.base-url` are not made compose settings here: `application-docker.yaml` gives each a second value, and the requirement "Container-mode parity is delivered via the `docker` Spring profile" of `ascend-agent-containerization`, which this change keeps, makes that profile the single source of in-container topology and forbids a `${KEY}` override of those URLs in the compose `environment:` block. ### D5: The JDK HTTP client and `requires-http1` go away

Today `buildRequestFactory` builds a JDK `HttpClient` per provider, with a 10 s connect timeout, the provider's read timeout, and HTTP/1.1 when `requires-http1` is set (LM Studio hangs when the JDK client tries an HTTP/2 upgrade). The SDK clients use OkHttp. OkHttp speaks HTTP/2 only over TLS with ALPN, or with prior knowledge when told to, so it never tries an HTTP/2 upgrade on a plain `http://` URL, which is how LM Studio is reached. The property has nothing left to switch, so it is removed from `AiProviderProperties`, both YAML files and the docs, instead of being kept as a no-op.

The read timeout moves to the options `timeout`. The 10 s connect timeout is set through `httpClientBuilderCustomizer` if the SDK client builder exposes a connect timeout, from the setting `app.ai.connect-timeout-seconds` (`APP_AI_CONNECTTIMEOUTSECONDS`, default 10, today the constant `DEFAULT_CONNECT_TIMEOUT_SECONDS` of `ChatModelResolver`, owner rule 98 of 2026-10-08), and otherwise the SDK's own connect default applies, no setting is added and the docs say so. Task 8.3 decides this from the 2.0.1 API and records the answer in `apps/ascend-agent/docs/CONFIGURATION.md`.

`AppConfig.restClientBuilder` keeps forcing HTTP/1.1 on the shared `RestClient.Builder`. That builder serves the agent's own clients, not the providers, and the upgrade does not touch it beyond the package of `RestClientBuilderConfigurer`.

The equivalent of `close-agent-test-gaps` group 3 (protocol and timeout proved on the wire) is written here against the new transport, in task 2.2, because the class those tests target is deleted by this change.

### D6: The tool loop moves to `ToolCallingAdvisor`, and tool tracking moves with it

In Spring AI 2 a chat model no longer runs tools. `ChatClient` auto-registers a `ToolCallingAdvisor`, and that advisor holds the `ToolCallingManager`. A manager passed to `OpenAiChatModel.Builder.toolCallingManager(...)` is only used if the caller drives the loop by hand. So the `TrackingToolCallingManager` the resolver attaches today would silently stop recording, and `toolsUsed` would come back empty while tools still ran.

The fix: `ChatExecutor` registers `ToolCallingAdvisor.builder().toolCallingManager(trackingManager).build()` as a default advisor on the `ChatClient` it builds. `ToolCallingAdvisor` implements the `ToolAdvisor` marker, so `ChatClient` does not add a second one. `ChatModelResolver` stops passing a manager to the models. The tracking manager wraps `ToolCallingManager.builder().build()`, which carries the 2.0 defaults: 40 calls per tool and 150 calls per request, and tool resolution only from the tools attached to the request. The agent always attaches its tools explicitly, so the resolution change does not affect it. `SemanticMemoryExtractor` and `ChatHistoryCompactionService` attach no tools, so they need no advisor change. Owner rule 98 of 2026-10-08: if the 2.0.1 builder lets the two limits be set, they become the settings `app.ai.tool-calling.max-calls-per-tool` and `app.ai.tool-calling.max-calls-per-request` (`APP_AI_TOOLCALLING_MAXCALLSPERTOOL` and `APP_AI_TOOLCALLING_MAXCALLSPERREQUEST`), whose defaults are the library defaults read in task 9.2 (40 and 150 as read on 2026-10-02). If it does not, no setting is added and the docs name the library defaults.

Alternative considered: turn auto-registration off and drive the loop by hand in `ChatExecutor`. Rejected, it duplicates what the advisor does.

### D7: Options become builders

`ChatClient.ChatClientRequestSpec.options(...)` and `ChatClient.Builder.defaultOptions(...)` take a `ChatOptions.Builder` in 2.0.1, not a built `ChatOptions`. `PromptCacheStrategy.buildOptions(String model)` therefore returns `ChatOptions.Builder<?>` (or null when there is nothing to set, as today). The fallback path in `ChatExecutor` and `SemanticMemoryExtractor`, and the model override in `ChatHistoryCompactionService`, pass builders as well. Options objects are immutable in 2.0, and any change goes through `mutate()`.

`AnthropicCacheOptions` and `AnthropicCacheStrategy` move from `org.springframework.ai.anthropic.api` to `org.springframework.ai.anthropic`, with the same enum values.

### D8: Cache readback uses Spring AI's own usage fields

`AnthropicPromptCacheStrategy` reads `AnthropicApi.Usage` from `getNativeUsage()`, and `OpenAiPromptCacheStrategy` reads `OpenAiApi.Usage.PromptTokensDetails.cachedTokens()`. Both types are gone. Spring AI 2's `Usage` interface has `getCacheReadInputTokens()` and `getCacheWriteInputTokens()` (both `Long`, null when the provider does not report them), filled by the Anthropic and OpenAI models. Both strategies read those, which also removes the provider-specific casts. The metric names and tags from `add-observability` (`prompt_cache.tokens.read`, `prompt_cache.tokens.creation`, and `gen_ai.client.token.usage`, whose input series is the hit rate denominator since `add-observability` dropped `prompt_cache.tokens.total` by owner answer 93 of 2026-10-08) do not change. `isCacheConfigError` keeps its message test and is checked against the SDK's error text in task 9.5.

### D9: Provider errors keep their HTTP statuses

What the agent does today, read in the code and the Spring AI 1.1.5 sources on 2026-10-05 (dependency fix of that day, which corrected the earlier text of this decision): `ChatModelResolver` builds `OpenAiApi` and `OpenAiChatModel` (and the Anthropic pair) with no error handler and no retry template of its own, so Spring AI's defaults apply. The default error handler (`RetryUtils.DEFAULT_RESPONSE_ERROR_HANDLER`) raises `NonTransientAiException` with the message `<status> - <body>` for a 4xx answer and `TransientAiException` with the same message for every other error status. The default retry template (`RetryUtils.DEFAULT_RETRY_TEMPLATE`) retries only `TransientAiException` and `ResourceAccessException`, at most 10 attempts, with an exponential backoff of 2 seconds, multiplier 5 and at most 180 seconds. `GlobalExceptionHandler` maps only `NonTransientAiException`, by its message prefix: `429` becomes 429, every other 4xx becomes 502, and the body drops everything after the first `{`. So today:

- a provider 401 or any other 4xx except 429 answers 502 with `AI provider error: <status> -`, after one request,
- a provider 429 answers 429 with `AI provider error: 429 -`, after one request,
- a provider 5xx is retried. If a later attempt succeeds, the user gets the answer. If every attempt fails, the last `TransientAiException` reaches the catch-all handler after about 19 minutes and the agent answers 500 with `An unexpected error occurred. Check server logs for details.`, not 502.

This change keeps the first two statuses and changes the third on purpose: a provider 5xx that persists after the retries answers 502 with `provider_error` (D19), because the failure is the provider's, not the agent's. The retry count is the default of `max-retries` of D4, which equals the SDK default (owner answer 90 and owner rule 98 of 2026-10-08), and task 8.6 records the request count and the time it gives. That is a change of behaviour, listed in the CHANGELOG entry of task 11.10, and not a status that "stays as today". It is checked end to end by a new row of the existing provider error spec of `close-agent-test-gaps` (D21, task 15.4, owner answer 73.2 of 2026-10-06): the scripted model answers 502 on every attempt, and the agent answers 502 `provider_error` within 30 seconds after exactly three chat requests, the SDK default (owner answer 90 of 2026-10-08).

Retry layers after the upgrade, measured on 2026-10-06 in the current documentation through Context7:

- The SDK retries. The openai-java documentation (Context7 `/openai/openai-java`, README section "Retries" and `_autodocs/configuration.md`, also `_autodocs/api-reference/http-layer.md` on `RetryingHttpClient`) says the client retries connection errors, 408, 409, 429 and 5xx, with `maxRetries` 2 by default and a short exponential backoff, and that `maxRetries` counts the retries after the first request, so the default gives three requests in total. The anthropic-sdk-java documentation (Context7 `/anthropics/anthropic-sdk-java`, `_autodocs/errors.md` and `_autodocs/api-reference/HttpCore.md`) gives the same rule for its `RetryingHttpClient`: connection errors, 408, 409, 429 and 5xx are retried up to `maxRetries`, and 400, 401, 403, 404 and 422 are not. Both SDKs honour a `Retry-After` header and an explicit retry instruction of the server, so the scripted model's error answers send neither (task 15.1).
- Spring AI's own retry does not wrap these calls. In the Spring AI 2.0.0 API documentation (Context7 `/websites/spring_io_spring-ai_2_0_0`, pages `OpenAiChatModel.Builder`, `AnthropicChatModel.Builder` and the `OpenAiEmbeddingModel` constructors in `index-all.html`) neither chat model builder has a `retryTemplate` method and no `OpenAiEmbeddingModel` constructor takes a `RetryTemplate`. The retry count reaches the SDK client only as `maxRetries` of the options (`AbstractOpenAiOptions.AbstractBuilder.maxRetries`, `AnthropicChatOptions.getMaxRetries`, passed to `OpenAiSetup.setupSyncClient` and `AnthropicSetup.setupSyncClient`). `spring.ai.retry` (`SpringAiRetryProperties`) still exists in 2.0.0, but only the models that still take a `RetryTemplate`, such as Ollama (`OllamaChatModel.Builder.retryTemplate`), DeepSeek, Mistral AI and ElevenLabs, read it, through the `retryTemplate` and `responseErrorHandler` beans of `SpringAiRetryAutoConfiguration` (page `class-use/SpringAiRetryProperties.html`, rechecked through Context7 on 2026-10-07). The agent sets no `spring.ai.retry` property and builds no `RetryTemplate` (read in `apps/ascend-agent/src/main` on 2026-10-06), so nothing has to be switched off: the SDK is the one retry layer for the OpenAI and Anthropic providers.
- The agent's own retry in `ChatExecutor` runs only when `AnthropicPromptCacheStrategy.isCacheConfigError` matches the error text (task 9.5). The scripted model's 429 and 502 bodies hold no cache text, so it never adds a request to the counts below.

So after the upgrade a provider answer of 429 is retried too, which today's agent does not do. With the SDK default of 2 retries, which every provider uses because `max-retries` defaults to it and no test or overlay sets it (owner answer 90 and owner rule 98 of 2026-10-08), the counts in the scripted model's request log are exact: a 429 on every attempt gives three requests and then HTTP 429 `provider_rate_limited`, a 502 on every attempt gives three requests and then HTTP 502 `provider_error`, a 502 followed by a normal answer gives two requests and then 200, and a 401 gives one request and then 502. Task 8.6 records the count and the time on the upgraded agent.

With the vendor SDKs a provider failure may surface as the SDK's own exception type (for example `com.anthropic.errors.UnauthorizedException`) instead of a `NonTransientAiException` with a status prefix. `NonTransientAiException` still exists in `spring-ai-retry` 2.0.1, but the wrapping is not documented. Task 2.3 first writes the tests that pin today's statuses and bodies on the 1.1.5 code: a 401 and a 429 from a local fake provider, and a 500 that is followed by a success, which proves the retry. A 500 on every attempt is not pinned on the old code, because it takes about 19 minutes. Task 8.6 then makes the handler produce the same answers on 2.0.1, mapping whatever type the SDK throws, and adds the changed case: a 500 on every attempt answers 502 `provider_error`. The status and the message of the 429 case stay, but its request count does not: the SDK retries a 429, so the one-request assertion of task 2.3 becomes the count the SDK default gives, which task 8.6 records. The spec requirement is the statuses, not the exception type.

### D10: Jackson 3

Boot 4.1.1 auto-configures a Jackson 3 `JsonMapper` (`tools.jackson.databind.json.JsonMapper`, a subclass of `tools.jackson.databind.ObjectMapper`). ### D16: No data to preserve

The owner decided on 2026-10-02 that the project is under development and holds no data anyone needs to keep, and owner answer 73.1 of 2026-10-06 confirms that the data in today's development database, Redis, Qdrant, object storage and AscendMemory is disposable. RFC 9457 replaced RFC 7807 and keeps the same fields, and Spring Framework 7 documents its `ProblemDetail` against RFC 9457, so both names describe the same body here.

Owner answer 70.1 of 2026-10-04: the problem format is defined by `add-ascend-python-common` (build group 2, position 1 of the owner build order of 2026-10-04), which lands before this change: RFC 7807 problem details with the top level extension fields `code` and `traceId`, the type base `https://ascend.ai/errors/`, `title` as the HTTP reason phrase, `instance` as the request path, the platform codes for the framework errors and the fixed detail of the internal error. This decision makes the agent follow that format. The points below were written to the same format before the order changed, and task 15.3 compares them with what the library defines when this change is applied. Where they differ, the library's format wins and this decision and the agent are changed to it, never the library.

Where sky and Pharmacy differ, this change follows Pharmacy, because it is the more complete of the two: it has exactly one advice for every error (what the owner asked for), a validation shape that keeps every message of a field, a project type on every error, the 401 and 403 bodies written by the same writer as the rest, and an architecture test for the single advice. sky splits the work over a shared advice, an advice per service and a fallback resolver, which a library shared by several services needs and one service does not, and its `field-errors` object keeps only one message per field. Two things are taken from sky because Pharmacy lacks them: the `ApiCommonErrorResponses` annotation that documents the problem body, and the precedence test that throws `MaxUploadSizeExceededException` from a mocked service and asserts that a 500 body names neither the exception type nor its message.

The decision:

1. One `@RestControllerAdvice`, `exception/GlobalExceptionHandler.java`, extends `ResponseEntityExceptionHandler`, as in Pharmacy. It keeps its own `@ExceptionHandler` methods for the agent's exceptions and its catch-all for `Exception`. The base class declares each Spring MVC exception by its type, and Spring picks the closest match, so a framework exception reaches the base class handler and never the catch-all. No other class of the agent is annotated `@ControllerAdvice` or `@RestControllerAdvice`.
2. One enum, `exception/ApiErrorCode.java`, is the single source of truth for each error class: its `code`, its HTTP status and its type URI. The type URI is `https://ascend.ai/errors/<code with _ replaced by ->`, the same base `https://ascend.ai/errors` that ascend-audio-scribe, AscendMemory and ascend-web-hunter already use in their problem bodies. Two codes reuse the sibling slugs exactly, `validation` and `internal`, so a client that switches on `type` sees the same class across services. Pharmacy's `urn:pharmacy:problem:` form and sky's `about:blank` are not taken, because this platform already has its type base. The `code` extension field stays, although neither reference project has one: the sibling services and the active changes that already use problem bodies switch on a stable `code`.
3. One factory method builds every body: `ProblemDetail.forStatusAndDetail(status, detail)`, then `type` from the enum, `title` left as Spring sets it (the HTTP reason phrase, so the old handler `error` value moves to `title` unchanged), `instance` set to the request path, and two extension properties: `code`, set to the enum's code, and `traceId`, the trace id of the current trace (owner decision 51.3 of 2026-10-03, `add-observability` D12). The old `timestamp` field is dropped. The request time is already in the log line and the trace of the request.
   - `traceId` is the 32 character lower case hex id that Micrometer's `Tracer` gives for the current span (`tracer.currentSpan().context().traceId()`). The agent already depends on `micrometer-tracing-bridge-otel` (D2), so a `Tracer` bean exists, and `add-observability` exports the trace to Tempo under the same id. Spring Boot propagates W3C trace context by default, so a request that arrives with a `traceparent` header continues that caller's trace and its error body names that trace.
   - The trace exists even when the span is not sampled, so the id is always the real one. When no span is current, which happens only outside an HTTP request, the field is left out. It is never set to an empty or invented value.
   - The factory is the only place that sets it, and the writer of point 8 and the error controller of point 9 build their bodies with the factory, so the 401 body and the `/error` body carry it too. That a span is current on each of those paths (the advice, the security entry point and the `/error` dispatch) is not assumed: tasks 8.10 and 8.13 assert a `traceId` on each path, and a path that has none is fixed by running it inside the request's observation, never by a body without the field.
4. Spring MVC's own errors answer their correct status. `handleExceptionInternal` is overridden as in Pharmacy: it builds the body with the factory when Spring passes none, and it sets `type`, `instance` and `code` on a body Spring built. The detail of a framework 4xx is Spring's own description (for example `Required part 'prompt' is not present.`), because that is what the caller can act on. The detail of a framework 5xx is the fixed text of `internal`. The codes:
   - 400 for a missing request part or parameter, an unreadable body or a value of the wrong type: `bad_request`.
   - 400 for a bean validation failure (`MethodArgumentNotValidException`, `HandlerMethodValidationException`): `validation`, with the `errors` field of point 5.
   - 404 for a path no controller maps (`NoResourceFoundException`): `not_found`.
   - 405 (`HttpRequestMethodNotSupportedException`): `method_not_allowed`, with the `Allow` header the base class sets.
   - 406 (`HttpMediaTypeNotAcceptableException`): `not_acceptable`.
   - 413 for an upload over `spring.servlet.multipart.max-file-size` or `max-request-size` (`MaxUploadSizeExceededException`): `content_too_large`. Spring Framework 7 names this status `CONTENT_TOO_LARGE` after RFC 9110 and deprecates `PAYLOAD_TOO_LARGE`, so the code takes the new name. Spring's detail names the maximum upload size, so the 413 of the main spec `ingestion-security` is answered with a detail that names the limit, and its corrected scenario asserts the code `content_too_large` (D20).
   - 415 for a request body type a mapping does not consume (`HttpMediaTypeNotSupportedException`): `unsupported_media_type`, the same code the upload refusal uses, because it is the same class of error.
   - Any other status the base class answers (for example 503 for an async request timeout): `http_error`.
5. A bean validation failure carries the extension field `errors`: a JSON array with one object per rejected constraint, each with `field` (the field or parameter name) and `message` (the constraint's message), sorted by `field`. This is Pharmacy's name and shape. sky's `field-errors`, an object from field to message, is not taken, because it keeps only one message per field. `errors` appears only on a `validation` body from bean validation. An `IllegalArgumentException` answered with `validation` carries no `errors`. The agent has no `@Valid` parameter today, so this path is proved by a unit test that builds both exceptions directly, and `add-agent-skills`, `add-agent-subagents` and `add-agent-sandbox` are its first real callers (D14). Pharmacy also maps `jakarta.validation.ConstraintViolationException` raised below the web layer. The agent has no `@Validated` service and does not declare `spring-boot-starter-validation`, so that mapping is not written here. The change that adds the validation starter also maps `ConstraintViolationException` to the same `validation` body with `errors`, and D14 hands that rule to the three changes above.
6. The catch-all answers 500 with code `internal` and a fixed detail, and the body never carries the exception message, its class name or a package name, as sky's precedence test asserts.
7. The controllers stop building error bodies. They throw one new exception, `exception/ApiProblemException.java`, carrying an `ApiErrorCode` and the detail text, and `GlobalExceptionHandler` maps it. `dto/ApiError.java` and its test `dto/ApiErrorTest.java` are deleted, and the controller methods return their success body type instead of `ResponseEntity<?>`. The four codes the controllers send today keep their values, so a client that read the old `error` field of those paths finds the same value in `code`.
8. One writer, `exception/ProblemDetailWriter.java` (Pharmacy's `ProblemDetailWriter`), writes a problem body to a servlet response for the places outside the advice. With security enabled, the 401 is answered by an `AuthenticationEntryPoint` in `SecurityConfig` that uses it (code `unauthorized`) and keeps the `WWW-Authenticate: Basic` header the default entry point sends. No access denied handler is added: the agent's filter chain has one role and only requires `authenticated()`, so Spring Security never answers 403 there. Pharmacy has one because it has role rules.
9. Errors that still reach Spring Boot's `/error` path (raised in a servlet filter, or sent with `sendError` by the container) are rendered through the same writer by one `ErrorController` of the agent's own in place of Spring Boot's default one, with code `http_error` and the status the container set. Neither reference project has this, and the owner asked for RFC 7807 on every error. Its Spring Boot 4.1.1 package is checked at compile time in task 8.13 and not assumed here.
10. `application.yaml` sets `spring.mvc.problemdetails.enabled: true`, as sky and Pharmacy do. Spring Boot registers its own problem details advice only when no `ResponseEntityExceptionHandler` bean exists, so with the agent's handler the setting adds no second advice. Task 8.10 reads that condition in the 4.1.1 jar and records it.
11. Extension fields are rendered at the top level of the JSON body, not under a `properties` object. Spring Framework registers its `ProblemDetailJacksonMixin` for that. The upgrade moves the agent to Jackson 3 (D10), so a test proves the flat `code`, `traceId` and `errors` fields on the 4.1.1 stack (task 8.10). If they are not flat, the fix is registering that mixin on the message converter's mapper, documented in `apps/ascend-agent/docs/CONFIGURATION.md`, not a hand-written serializer.
12. Both controllers declare `produces = "application/json"` on their class `@RequestMapping`. Whether Spring Framework 7.0.9 still answers `application/problem+json` for an advice `ProblemDetail` under that declaration is not assumed. A MockMvc test asserts the exact `Content-Type` header on each path (task 8.10). If the header comes back as `application/json`, both class mappings list `application/problem+json` next to `application/json`.

Not taken from Pharmacy, and why: the `correlationId` extension field, because the agent has no correlation id, and owner decision 51.3 puts the trace id into every body as `traceId` instead (point 3, `add-observability` D12). A trace id already names one request across every service, so no second request id is added. The ArchUnit test, because the agent has no ArchUnit dependency and one grep in task 8.10 checks the single advice. The `@ResponseStatus` annotation on each exception, because the status already lives in `ApiErrorCode`, one table instead of one annotation per class.
