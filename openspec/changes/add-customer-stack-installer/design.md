# Design - Add Customer Stack Installer

## Context

This change is build group 5, position 8 of the owner build order of 2026-10-04. By then every web-hunter, base and personal change and the other company changes have landed, so the pieces of a customer stack exist: the main `compose.yaml` with a gateway on 80 and 443, Keycloak on its own host name, the admin API, and a manual guide. `add-deployment-modules` splits the stack into deployment modules: one catalog at `apps/ascend-agent/src/main/resources/modules/catalog.json`, `COMPOSE_PROFILES` as the one switch, and the presets `personal`, `company-docs` and `core`. The core is always on and never switchable (owner answer 52 of 2026-10-03): chat, document search, memory, the sandbox, monitoring and the prerequisites. A customer may buy only some of the switchable modules, or none beyond the core, which already searches documents. Nothing strings these pieces into a repeatable install. The four data stores are external prerequisites that `compose.yaml` does not define, and the server must pull released images instead of building from source.

Owner decision 65.5 of 2026-10-04: there is no guide or code for a cloud provider. The installer targets any Linux server with Docker, and the deployment target is not chosen now. The operator brings the server, its DNS names and its firewall, and the installer checks them before it changes anything.

## Goals / Non-Goals

Goals:

- One command per phase: choose the modules, check the server, start data stores, bootstrap `.env`, pull and start the stack, provision the first tenant, verify.
- The core is always installed, with its secrets, the sandbox host setup and monitoring. Of the switchable modules only the chosen ones are installed: no secret, GPU or model cache for a module the customer did not choose.
- No hand-typed generated secret and no development default in production.
- A broken install fails visibly.

Non-Goals:

- A shared multi-tenant control plane or an onboarding web page.
- Application code changes.
- Choosing a cloud provider, a DNS provider or a managed object store, and any guide or infrastructure code for one (owner decision 65.5 of 2026-10-04, D0). Creating the server, its DNS records and its firewall is the operator's work before the install.
- Several copies of a service. The installer starts one container of each service on one server (owner answer 98.6). Company plans several copies later in `plan-scaled-deployment` (build group 5, a Kubernetes Helm chart with a Horizontal Pod Autoscaler, owner answer 99.1), and this change does not wait for it.

## Decisions

### D0 - Any Linux server with Docker, no provider (owner decision 65.5 of 2026-10-04)

The installer targets any Linux server with Docker Engine and Docker Compose 2.20 or later. No cloud provider, DNS provider or managed object store is chosen, now or by the implementer, and no Terraform or other provider code and no provider guide is written. The deployment target is chosen later, outside this change. The object store of the data-store stack is the S3-compatible container of `deploy/datastores/compose.yaml` by default, and the operator may give the address and keys of an S3-compatible store he already runs instead (D2).

### D1 - Server prerequisites the operator brings, checked before the install

`deploy/README.md` lists what the operator prepares before the install: a Linux server (x86_64) with Docker Engine, Docker Compose 2.20 or later and `sudo`, enough memory for the core and the chosen modules (the sizes of `docs/MODULES.md` of `add-deployment-modules`), a disk for the data-store volumes, DNS records for `ASCEND_DOMAIN` and the Keycloak host name that point at the server, and a firewall that opens 80 and 443 to everyone and 22 only to the operator. The installer runs on that server and checks, before the module question, in this order: the operating system is Linux, `docker info` answers, `docker compose version` is 2.20 or later, and `sudo` works. After the module question and before the stack starts it checks that both DNS names resolve to an address of this server and that ports 80 and 443 are free on it. A failed check stops the install and names the check. The installer never changes the firewall or DNS.

### D2 - Data stores come from a separate stack

`compose.yaml` keeps no data store (owner rule). On the server the installer runs `deploy/datastores/compose.yaml`, project name `ascend-datastores`, with Postgres (databases `ascend_ai` and `keycloak`), Redis with a password, Qdrant with an API key, and the S3-compatible store unless the operator gave an existing one (D0). Each service publishes its port on `127.0.0.1` only, for the operator's own use on the server, on a host port read from a setting whose default is the port the local prerequisite stack uses (owner answer 98, task 3.1), and stores data on named volumes on the server's disk. The application stack reaches them by container name on a network that both projects share, never through `host.docker.internal` (`close-agent-test-gaps` D8, rule 1). The earlier plan, to reach them through `host.docker.internal` like the local-dev stack, does not work on the Linux server this installer targets: there `host.docker.internal` (with `extra_hosts: "host.docker.internal:host-gateway"`) resolves to the host's address on the default bridge network, and a port published on `127.0.0.1` only does not answer on that address. Owner answer 82.6 of 2026-10-08 sets the values. The shared Docker network is `ascend-data`: `deploy/datastores/compose.yaml` declares it with `name: ascend-data`, so starting the data-store stack creates it. The data store containers carry the fixed names `ascend-postgres`, `ascend-redis`, `ascend-qdrant` and `ascend-object-storage` (`container_name`) and join `ascend-data`. The application services join it through a compose override file that the installer writes on the server: `compose.override.yaml` next to `compose.yaml`, which declares `ascend-data` as an `external` network and adds it, next to `default`, to the `networks` of every application service that uses a data store. Docker Compose reads `compose.override.yaml` by itself when no `-f` flag is given and merges it into `compose.yaml` (checked in the Docker documentation, Context7 `/docker/docs`, `content/manuals/compose/how-tos/multiple-compose-files/merge.md`, on 2026-10-08), so the rule that the application stack starts only with `docker compose` against the main `compose.yaml` and no `-f` flag holds. A service that names `networks` loses the implicit `default` network unless it lists it, so the override lists both. The connection settings the installer writes into `.env` name those containers and their container ports. `compose.override.yaml` is listed in the root `.gitignore`, so it never reaches the repository, and local development has no such file and keeps reaching its data stores through `host.docker.internal`. When the operator gave an existing S3-compatible store, this file runs without the object store service and `.env` points at that address. This is a prerequisite stack, not a second application project, so the single entry point rule for the application stack holds.

### D3 - Images from the registry

`release.yaml` publishes `lukk17/ascend-ai-<service>` and `ghcr.io/lukk17/ascend-ai-<service>`. The six app `image:` lines in the compose files become `${ASCEND_IMAGE_REGISTRY:-}ascend-ai-<service>:${<SERVICE>_IMAGE_TAG:-latest}`, for example `${ASCEND_IMAGE_REGISTRY:-}ascend-ai-ascend-agent:${ASCEND_AGENT_IMAGE_TAG:-latest}`. Unset, the names equal today's local build names, so local `docker compose up --build` is unchanged. The installer sets `ASCEND_IMAGE_REGISTRY=ghcr.io/lukk17/` and each tag to the released `v<version>`, runs `docker compose pull` for the released services of the chosen modules, then `docker compose up -d --no-build` for them. It names only services of the chosen modules, because a service named on the command line starts even when its profile is not in `COMPOSE_PROFILES`. The core services are always pulled and started, whatever the module question chose. `container-metrics-exporter` is not released and is built on the server from the repo checkout in every install, because monitoring is core.

### D4 - Bootstrap: generate secrets, ask for inputs

`deploy/bootstrap.sh` and `deploy/bootstrap.ps1` read `.env.example` and sort every variable into one of three lists kept at the top of each script, one list per class, which a test checks against `.env.example` so a new variable cannot be missed. Each variable in the three lists carries the module it belongs to (`core-chat` for the variables of the core, which every deployment needs), and a variable of a switchable module that the module question (D4a) did not choose is neither generated nor asked:

- Generated: every password, secret key and API key the stack owns (Postgres, Redis, Qdrant, object store keys, ascend-ocr result store keys, `GRAFANA_ADMIN_PASSWORD`, `SEARXNG_SECRET` at 48 characters, `VNC_PASSWORD`, `SERVICE_AUTH_TOKEN` of `add-keycloak-login`, `CONNECTOR_CREDENTIALS_KEY` of `add-connector-framework`, which also encrypts the BYOK provider keys of `add-usage-metering-and-quotas` (owner answer 89.9), Keycloak admin password, the audit pseudonym pepper of `add-audit-and-gdpr-compliance`, the Keycloak admin client secret of `add-tenant-administration`). Values come from the system random source (`openssl rand` or `[System.Security.Cryptography.RandomNumberGenerator]`). `VNC_PASSWORD` belongs to `web-search`. `SEARXNG_SECRET` also belongs to `web-search` but is always generated, because its compose `:?` guard needs it in every deployment (`add-deployment-modules` D11, owner answer 41.2). The secrets of the core belong to `core-chat` and are always generated: the datastore credentials that document search and memory use, `GRAFANA_ADMIN_PASSWORD` of monitoring, and `SANDBOX_RUNNER_TOKEN` of the sandbox (at least 32 characters, `add-agent-sandbox`), the last two guarded with `:?` in compose.
- Customer inputs: LLM provider keys (`OPENAI_API_KEY`, `ASCEND_ANTHROPIC_API_KEY`, `GEMINI_API_KEY`, `MINIMAX_API_KEY`), `HF_TOKEN`, the realm SMTP settings of `add-tenant-administration`, connector credentials, secrets of outside MCP servers (`add-mcp-tool-servers`), `ASCEND_DOMAIN`, the Keycloak host name. Read from a hidden prompt or from an inputs file in `.env` format named with `--inputs <file>`, which the operator keeps with mode 600 and deletes after the install, never from the shell environment (owner answer 85.1). Connector credentials and outside MCP server secrets are never generated. At least one LLM provider key is required, because a customer server has no LM Studio. `MEM0_DEFAULT_PROVIDER` is set to the provider of the first key given.
- Fixed production values: `EXPOSE_BIND=127.0.0.1`, `SPRING_PROFILES_ACTIVE=docker,production`, both public object store endpoints equal to the private address, `ALLOWED_PRIVATE_HOSTS` set to the object store host only (the name `MCP_ALLOWED_HOSTS` was renamed to `ALLOWED_PRIVATE_HOSTS` by `add-ascend-python-common`, owner answer 68 of 2026-10-04), image registry and tags, `COMPOSE_PROFILES` from the module question, and, when `coding` is chosen, `app.coding.providers.opencode-go.allow-deployment-key` false (`add-coding-agent-delegation` D10: an OpenCode Go subscription is personal use, so only the owner's personal deployment may use the deployment key).

The script writes `.env` with mode 600, refuses to overwrite an existing `.env` without `--rotate`, and aborts before writing when any required value is blank or equals a development default.

### D4a - Module question, before any secret is asked

The installer asks which modules to install before it asks for or generates any secret, as `add-deployment-modules` D18 designs it:

1. Read the module catalog from the checkout (`apps/ascend-agent/src/main/resources/modules/catalog.json`, with `ConvertFrom-Json` in PowerShell and `jq` in Bash).
2. Print what the core holds and that it is always installed. Ask: `personal`, `company-docs`, `core` or `custom`. For `custom`, show each switchable module with its title and description and ask yes or no. A core part or a companion is never offered as a module.
3. Add every missing `requires` module and print which ones were added and why.
4. Write `COMPOSE_PROFILES`. Always generate the secrets of the core and `SEARXNG_SECRET`, `GRAFANA_ADMIN_PASSWORD` and `SANDBOX_RUNNER_TOKEN`, whose compose guards need them in every deployment, and ask only for the secrets of the chosen switchable modules (D4). Ask for companions (`redis`, `captcha-intervention`, `clamav`) only when their module is chosen, with no as the default answer, so no install turns on the virus scanner `clamav` unless the operator asks for it (owner answer 51.2).
5. Always set up the sandbox host (D5a).
6. When `audio` is chosen, detect whether the server has an NVIDIA GPU and choose the transcription backend from that (D5).
7. The smoke test compares `GET /api/v1/modules` with the chosen list (D7).

Before the question the installer checks that `docker compose version` reports 2.20 or later, because the agent's `depends_on` entries use `required: false`, which older versions refuse. The image `ascend-ai-obsidian-sync:local` of `add-obsidian-vault` is never built, pulled or shipped by the installer or its published artifacts, because the sync client's licence is `UNLICENSED`. A customer who chooses `obsidian` builds it on their own machine with their own Obsidian account, as that change documents.

### D5 - Audio backend: GPU when present, OpenAI when not

Only when the module question (D4a) chose `audio`. The installer checks for the NVIDIA container runtime (`docker info --format '{{json .Runtimes}}'` lists `nvidia`).

- With the runtime: the local faster-whisper backend works. `HF_CACHE_ROOT` stays the `hf-cache` named volume from `harden-cloud-deployment`, and before the stack starts the installer runs the ascend-audio-scribe image once with the volume mounted and downloads the configured Whisper model, so the first request is not a download.
- Without the runtime: the OpenAI backend is the default (owner decision 65.5 of 2026-10-04). The installer sets `AUDIO_GPU_COUNT=0`, so ascend-audio-scribe starts with no GPU reservation, and `AUDIO_TOOLS_EXCLUDE=health,transcribe_local`, so the `ascend-audio-scribe` entry of `add-mcp-tool-servers` never offers the local tool and the model uses `transcribe_openai`. `OPENAI_API_KEY` becomes a required customer input, and no Whisper model is downloaded. The local backend is not an error on such a server, it is simply not offered.

`compose.yaml` reads the GPU reservation count from `${AUDIO_GPU_COUNT:-1}` instead of a fixed value, and the agent's `ascend-audio-scribe` entry reads its exclude list from `${AUDIO_TOOLS_EXCLUDE:health}`. Both keep today's behaviour when unset. The `ascend-agent` service passes `- AUDIO_TOOLS_EXCLUDE=${AUDIO_TOOLS_EXCLUDE:-health}`, and neither variable gets a `.env.example` line, because each has a default (owner answer 98). The installer writes both into `.env` as fixed production values. Task 5.1 measures that Docker Compose 2.20 or later accepts a count of 0 and starts the container with no GPU. If it does not, the implementer stops and asks the owner before choosing another way, and never adds a second compose file.

Without `audio` the runtime check and the model cache are skipped.

### D5a - Sandbox host, in every install

The sandbox runner of `add-agent-sandbox` is core and runs in every deployment, so every install prepares its host before the stack starts, whatever the module question chose: install `runsc` (from the gVisor apt repository on Debian and Ubuntu, from the gVisor release binaries with their published checksums on any other Linux), run `sudo runsc install`, reload Docker, confirm with `docker info` that `runsc` is listed and that the default runtime is still `runc`, run `docker run --rm --runtime=runsc hello-world`, and write the group id of the Docker socket on the host to `DOCKER_SOCKET_GID` in `.env`. The commands are the ones `add-agent-sandbox` task 7.5 writes into the cloud VM section of `docs/DEPLOYMENT.md` (`harden-cloud-deployment` D11). The installer never sets `runsc` as the engine's default runtime. A failed step stops the install and names the step. The coding project area partition of `add-coding-agent-delegation` is prepared only when `coding` is chosen.

### D6 - First tenant through the product API

The realm is imported by Keycloak itself at start (`--import-realm`, from `add-keycloak-login`). The installer waits for the Keycloak health endpoint, gets a `PLATFORM_ADMIN` token the way `add-tenant-administration` documents for the platform operator, calls `POST /api/v1/admin/tenants`, then creates the tenant's first `ADMIN` user through the user endpoint that change defines. The implementer reads `openspec/specs/` (or the change folder if not archived) of `add-tenant-administration` for the exact request bodies.

### D7 - Smoke test is a hard gate

`deploy/smoke-test.sh` and `.ps1` check, in order: gateway TLS certificate valid for `ASCEND_DOMAIN`, `docker compose ps` shows `ascend-agent` healthy (its healthcheck on the internal management port `9918`, which the gateway never routes), `GET https://<ASCEND_DOMAIN>/actuator/health` answers 404, Keycloak's discovery document answers on its own host name, a token for the seeded admin is issued, one authenticated `POST /api/v1/ai/prompt` returns 200, `GET /api/v1/modules` lists `core-chat` and exactly the switchable modules the module question chose (D4a), Grafana answers its health endpoint on loopback, the sandbox runner reports ready, and an external port scan from the operator machine shows only 80 and 443. The script exits non-zero naming the first failed check.

### D8 - One application entry point

The installer starts the application stack only with `docker compose` against the main `compose.yaml`, no `-f` flag. The data-store stack is the one other project, as in D2.

## Risks / Trade-offs

- A server without a GPU sends audio to OpenAI. Accepted by owner decision 65.5 of 2026-10-04: the OpenAI backend is the default there, and the customer's own OpenAI key is required for it (D5).
- The operator may bring a wrong DNS record or a closed port. The checks of D1 stop the install before anything starts, and the smoke test of D7 scans the open ports from outside.
- The core always costs its memory and its secrets, also for a customer who would not use the sandbox or monitoring. Accepted by owner answer 52 of 2026-10-03, and `docs/MODULES.md` of `add-deployment-modules` states the memory of the core so the server is sized for it.
- Generated `.env` on the server holds every secret. Mode 600, never committed, rotation documented.
- The bootstrap variable lists can drift from `.env.example`. A test compares them.
