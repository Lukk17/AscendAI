## Why

The owner decided on 2026-10-02 that when he asks the assistant to build an app or to change code, the assistant must not write the code itself. It must hand the work to an existing coding agent that is good at it and report back what was done. By owner decision 36.1 that coding agent is OpenCode only, running on an OpenCode subscription such as OpenCode Go where possible instead of a per-token API key, with the provider kept configurable so an API key or a local LM Studio also works. By owner decision 36.3 the code lives in project folders on one shared disk area that many runs and projects use, and a project's folder is never deleted while its work is not done or not committed and pushed. The agent has no way to do any of this today. Its sandbox of `add-agent-sandbox` runs short commands in a small memory-backed workspace with no secrets, which is too small and too short for a coding agent that clones a repository, installs packages, builds and tests for up to an hour, and talks to a model provider and a git host.

## What Changes

- A tool `delegate_coding` for the main chat. Input: a GitHub repository and an optional base branch, a new empty project, or an existing coding project to continue, the task text, an optional provider and model, an optional cost budget and time budget, and an optional test command. It starts a background run of the run kind `coding` and returns the run id at once. The run's status, progress, cost and result are followed through the run API of `add-agent-subagents`, and the conversation is told when it ends.
- Coding projects: every repository or new project the owner works on is a coding project with its own folder on one shared coding project area on the host (a named volume `ascend-coding-area`, in production bound to a host folder on its own file system), laid out as `tenants/<tenantId>/projects/<projectId>/`. Many projects and runs share the space. Each coding workspace is a gVisor container that mounts exactly one project folder at `/workspace` through Docker's volume subpath mount, so it never sees another project. The agent tracks each project's state: `in_progress`, `done` (work exists that is not pushed) or `pushed`.
- Cleanup only with the owner's yes: nothing in this change deletes a project folder on its own. A system task of `add-shared-scheduler` checks the free space of the area every 15 minutes. Below 10 percent free it asks the owner, through an approval of `add-action-approvals`, which pushed projects to clean, and it warns him through the approval channels and an owner notification of `add-shared-scheduler`. The owner can also ask to clean projects of his own choice, and an unpushed project is cleaned only when he approves exactly that.
- A trusted internal entry point, never a tool, starts a coding run from a seed folder for `add-self-built-integrations`: the seed is the base commit, the run has only the model route, its egress allow-list comes from its caller, and the project can never be published.
- Secrets never enter the workspace. Each coding workspace gets a small credential gateway container of its own, beside its egress proxy. OpenCode talks plain HTTP to the gateway for the model API and for git. The gateway adds the model API key and the git token and forwards to the real host over TLS. The keys live only in that gateway container's memory-backed file system, are written there by the runner and never logged, and the workspace cannot read them.
- Model providers, configurable per deployment and per run: `opencode-go` (the OpenCode Go subscription, 10 US dollars a month, the default where it is configured), `opencode-zen` (OpenCode's pay per token gateway), the agent's own providers with an API key (`anthropic`, `openai`, `gemini`, `minimax`), and `lmstudio` (local). The subscription key is the owner's own and is used only in the personal deployment. The key of a run comes from `ProviderKeyResolver`, a port this change owns, whose default returns the deployment key (`OPENCODE_API_KEY` for the OpenCode providers) when the deployment allows that provider to use it. `add-usage-metering-and-quotas` (company) registers the per tenant key implementation later, so a tenant of a multi-tenant deployment then uses its own key. The provider and model of a run pass `ModelAccessPolicy`, the shared port of `add-deployment-modules`, whose default allows every provider the deployment has enabled, and `add-tenant-policy` (company) registers the tenant allow-lists later. The owner accepted OpenCode Go with its terms risk in answer 44 of 2026-10-02, and a pay-per-token provider stays configurable as the fallback.
- Network of a coding workspace: only the gateway (model provider and the one repository) and package registries through the egress proxy's host allow list. Never the Docker socket, never the agent, never another internal service.
- Git: a GitHub App owned by the owner. The agent mints a GitHub installation token for each step, limited to the one repository and to the least permission: read for the clone, write only for an approved push, pull request write only for an approved pull request. Each token expires after one hour and is never stored.
- Results of a run: OpenCode's summary, the diff against the run's start commit, the commit list, the test command's output and exit code, the token use and cost, and a git bundle of the run's commits. They are stored in the object store bucket `coding-output` under `tenant/<tenantId>/coding/<runId>/` and served by `GET /api/v1/coding-runs/{id}/result`, `/diff` and `/bundle`. The project folder stays.
- Publishing: a project's work branch is pushed to the remote only after the owner approves it through `add-action-approvals`, through the tool `coding_publish` or `POST /api/v1/coding-projects/{id}/publish`. The branch name is made by the server under a fixed prefix and can never be the default branch. A later publish of the same project only fast-forwards that branch. A pull request is opened only when the approval said so. Nothing in this change can merge.
- Limits: time and cost per run from configuration and from the tool input, never above the configured maxima, enforced three times: by OpenCode's own step limit, by the agent reading the streamed usage, and by a hard deadline that kills the process and destroys the workspace. A run also stops when the area falls below 5 percent free. Coding runs at once default to 1.
- Module: this change is the switchable module `coding` of `add-deployment-modules`. It requires no other module, because the sandbox it runs on is core and always on (owner decision of 2026-10-03). There is no `app.coding.enabled` flag. With the module off the tools, routes and system tasks do not exist.
- Audit: the events `CODING_RUN_STARTED`, `CODING_RUN_PUBLISHED` and `CODING_PROJECT_CLEANED` are recorded through `AuditEventPort` of `add-deployment-modules`. Erasure and export of coding projects, runs, results and project folders are added by `add-audit-and-gdpr-compliance` (company) later, through the project archive endpoint the runner of `add-agent-sandbox` already has.
- Tenant rules: `coding_project` and `coding_run` carry `tenant_id VARCHAR(64) NOT NULL`, written from `TenantContext.currentTenantId()` of `add-keycloak-login` (`default` in the personal deployment), with no foreign key to `tenants(id)`: `add-tenant-isolation` (company) adds those foreign keys in its own migration later. Project folders live under `tenants/<tenantId>/projects/`, results under the object prefix `tenant/<tenantId>/`, every query and every runner call carries the tenant, a coding run thread and each approval handler bind the row's tenant with `TenantContext.runAs`, and every coding store fails closed when no tenant is bound.
- Images: one pinned workspace image `ascend-sandbox-coding`, built in this repository from the base image of `add-agent-sandbox`, with OpenCode preinstalled at a pinned version and its update checks, sharing and model list download switched off, on top of the base image of `add-agent-sandbox`.
- Usage events of the coding run's model cost (request type `coding-agent`) through `UsageEventPort` of `add-deployment-modules`, a quota check through the shared port `QuotaGate` of `add-deployment-modules`, whose default allows every call, metrics, logs, a startup banner block, tests with a fake OpenCode installed under the real binary name in a test image (no test-only setting in the agent or the runner, answer 90 of 2026-10-08), and two new end-to-end specs (design D23): a deterministic Bruno spec with the fake OpenCode and the scripted model of the shared harness of `close-agent-test-gaps` on new projects (no AI model, no GitHub account), and an AI-run spec with real OpenCode on a dedicated private test repository, which also proves the publish path (the separate deterministic publish spec is dropped by answer 91.3 of 2026-10-08). The scripted model of the harness starts only for the deterministic spec, never for the AI-run spec, which runs against the agent with the shipped profile (owner answer 70.4 of 2026-10-04).
- The project is under development, so there is no data migration and no backfill. Owner answer 73.1 of 2026-10-06 confirms that the data in today's development stores is disposable.

## Capabilities

### New Capabilities

- `coding-delegation`: the `delegate_coding` and `coding_projects` tools, the internal entry point for seed runs, their input and validation, when they are offered, the coding run kind and its lifecycle, limits and cancel, progress in the run status, reporting back to the conversation, the result endpoints, and the agent side metrics and logs.
- `coding-agent-execution`: the coding workspace image and profile, how OpenCode is started headless and non-interactive, provider choice and the subscription, the network of a coding workspace, the credential gateway, secrets handling, the GitHub tokens for the clone, collecting the result, metering, and the cost and time enforcement inside a run.
- `coding-result-publication`: the `coding_publish` tool and endpoint, the push and pull request approval, branch rules, the push workspace, and the rules that nothing merges and nothing reaches the default branch.
- `sandbox-disk-workspaces`: the shared coding project area, project folders and their isolation, project state tracking, the free space check, and cleanup only after the owner's approval.

### Modified Capabilities

- `production-deployment` (created by `harden-cloud-deployment`, which is archived first): the credentials list gains the coding secrets, and the deployment guide gains the coding host step (moved here by the dependency fix of 2026-10-05).

Otherwise, the run state machine, the runner API, the approval categories, the usage ledger request types and the tool policy belong to changes that are not archived yet, so their changes are required edits listed in design.md, not delta specs here. `ascend-agent-containerization` already requires `.env.example` to list every variable `compose.yaml` uses.
