## Build order

This change depends on `upgrade-spring-boot-4`, which moves ascend-agent to Spring Boot 4 and Spring AI 2. It cannot start before that change is applied, because the library it reuses, `org.springaicommunity:spring-ai-agent-utils` 0.12.0, is built against Spring AI 2.0.1 and declares Spring AI 2.0 or later as a requirement. Every task in this change is blocked until `upgrade-spring-boot-4` is green.

Build order (owner build order of 2026-10-04, which supersedes the earlier orders): build group 4 (personal), position 1. It needs `close-agent-test-gaps` (the e2e suite its specs join), `upgrade-spring-boot-4`, `add-keycloak-login` (the authorization matrix and `TenantContext.currentTenantId()`) and `add-deployment-modules` (the `skills` module of its catalog and the company extension port `AuditEventPort`), which all land earlier in build group 3. `add-agent-subagents`, `add-agent-sandbox`, `add-agent-soul`, `add-action-approvals`, `add-mcp-tool-servers`, `add-openclaw-plugin-host`, `add-download-ingestion`, `add-self-improvement` and `add-self-built-integrations` plug into the pieces this change creates, each in its own tasks.

Self-improvement, meaning the agent deciding on its own when a lesson is worth a new skill, is `add-self-improvement` (build group 4, position 13). This change provides the mechanism that change uses, and the hooks that change asks for (design D3, D6, D8, D9 and D14).

## Why

The agent has no way to carry reusable know-how between conversations. Every procedure the owner wants it to follow must be pasted into a prompt again, and anything the agent learns is lost when the conversation ends. Claude Code, OpenCode, Kilo Code, Hermes and OpenClaw all solve this with skills: folders holding a `SKILL.md` file in the agentskills.io format, whose name and description tell the model when a skill applies and whose body is loaded only when the model asks for it. The repository already holds 62 such skills in `.agents/skills/`, and a maintained Spring AI library (`spring-ai-agent-utils`, Apache 2.0) already implements the tool that serves them. What is missing is the part around it: loading from several folders safely, reloading while the agent runs, a single validated and undoable way to write a skill, and a way to find the right skill without paying for the whole list in every request. Listing all 62 names and descriptions costs 28,234 characters in every request, measured in the library's own format.

## What Changes

- ascend-agent loads skills at startup from an ordered list of folders set in configuration. The repository's own `.agents/skills` folder is one of them and loads without changes. The read-only folders come first and the one writable folder must be last. The writable folder is the agent home root, shared with `add-agent-subagents`: each tenant has the folder `tenants/<tenantId>/` under it, and the tenant's skills live in `tenants/<tenantId>/skills/`, which is the tenant's own git repository for skills.
- When two read-only folders hold a skill with the same name, the folder listed first wins. The other copy is skipped and logged.
- A malformed skill (bad front matter, a name that does not match its folder, too large, not UTF-8, unreadable) is skipped and logged with the reason. It never blocks startup, and a missing or unreadable folder never blocks startup either. A skill that loaded and then becomes invalid keeps its last good version and a WARN line names the file, the same rule `add-agent-subagents` uses.
- Skills are not all listed in every request. Their names and descriptions are indexed in the Qdrant vector store the RAG pipeline already uses, through the existing Qdrant client and embedding models, and the model finds the skills that fit the task with a new `skill_search` tool (a query, a type of `skill` or `subagent`, a configurable top N and score threshold). The index is one capability index shared with the subagent definitions of `add-agent-subagents` and the MCP tools of `add-mcp-tool-servers`, with a type field `skill`, `subagent` or `tool`.
- The index follows the skill folders: it is rebuilt at startup and on the reload endpoint and updated on every add, change and delete the watcher, the rescan or a write reports. Entries are tenant scoped, every search is limited to what the request's tenant and tenant policy allow, and a search falls back to a plain text match when the embedding provider is down or the index is not ready.
- The skills reach the model through one tool named `Skill`, reused from `spring-ai-agent-utils` 0.12.0. Its description lists only a small configurable always-listed set (empty by default) and points at `skill_search`, and it loads any skill the request is allowed by name. This cuts the skill text in every request from 28,234 characters to 726, measured before `skill_search` gained its `type` parameter, whose length task 5.8 measures.
- A companion tool lets the model read a text file inside a skill folder (for example `references/REFERENCE.md`), limited to that folder and to a size limit. Scripts inside skill folders are never run.
- A folder watcher reloads the skill list when a skill is added, changed or deleted while the agent runs, within a quiet period of under one second. A periodic rescan covers file systems that do not deliver change events, and `POST /api/v1/skills/reload` forces a reload.
- The loader, the snapshot, the watcher, the write path, the git store and the REST controller are one catalog with a validator per type, shared with the subagent definitions of `add-agent-subagents`, which adds its type to it (owner decision 89.5 of 2026-10-08). The URL paths `/api/v1/skills/**` and `/api/v1/subagents/definitions/**` stay as routes onto the one controller.
- Several agent instances share one agent home root: writes take a Postgres advisory lock per tenant and type, and a write or reload on one instance reaches every other instance through a Postgres notification, with the rescan as fallback (owner decision 87 of 2026-10-08).
- A chat request keeps the skill list it started with until it finishes. A reload only affects requests that start after it.
- One validated write path is the only way to change a skill folder that belongs to a tenant. Three callers use it:
  - a tool the agent calls to create a new skill or update a skill it wrote earlier,
  - the same tool when the owner pastes a skill in chat and asks the agent to save it,
  - REST endpoints under `/api/v1/skills` for the owner: create or replace, read, list, delete, history and revert.
- Every accepted write is validated first and then committed to the git repository of the caller's tenant skills folder. Every commit records its origin (agent, owner through REST or a skill the owner pasted in chat, or an edit made outside the agent). Any change can be undone with the revert endpoint, which writes a new commit and never rewrites history. A skill the agent writes goes live at once, without an approval step.
- Skills in the read-only folders, including `.agents/skills`, are global. Skills written by the agent or an owner belong to the caller's tenant, each tenant skills folder `tenants/<tenantId>/skills/` is its own git repository, and a personal deployment runs as tenant `default`, read from `TenantContext.currentTenantId()` of `add-keycloak-login`. Which global skills and which tools a tenant is offered is decided by two small ports this change owns, `GlobalSkillPolicy` and `TenantToolPolicy`, whose defaults read a deny list from this change's configuration (`app.tool-policy.denied-tools` and `app.tool-policy.denied-global-skills`, both empty by default), so the personal deployment offers every global skill and every tool until the owner lists one. `add-tenant-policy` (company, build group 5) registers its implementation later. This change does not wait for it. Every skill write and reload is published as an audit event through `AuditEventPort` of `add-deployment-modules`, whose default writes one structured log line. `add-audit-and-gdpr-compliance` (company, build group 5) registers its implementation later and adds tenant erasure and export of skills.
- No one, neither the agent nor the owner, can write a skill with the name of a shipped skill from a read-only folder. The write path refuses it with a clear error naming the folder that holds the name. The agent can never overwrite a skill the owner wrote, and every agent write is recorded as coming from an untrusted source together with the chat request id and the tools that ran earlier in the same request. Git and the index never hold a user id, so a user's erasure needs no history rewrite.
- Names are checked against the agentskills.io rules before any path is built, so path traversal is impossible. Every size and count limit, every folder path, the watcher timings, the search settings and the git author live in configuration under `app.skills`.
- The whole feature is the module `skills` of the module catalog of `add-deployment-modules`: it is on when `skills` is in `ASCEND_MODULES` (from `COMPOSE_PROFILES`), and its beans carry `@ConditionalOnModule("skills")`. There is no `app.skills.enabled` flag. The capability index, `ChatToolset`, `AgentNativeTool`, `TenantToolPolicy` and `app.agent-home` belong to `core-chat` and exist with the module off.
- `ChatToolset` is the one place where every tool of a request is assembled and governed: it drops tools of modules the tenant lacks, applies the tenant tool policy through the `TenantToolPolicy` port, applies an optional per-request narrowing list (peer bot turns of `add-openclaw-plugin-host`), wraps self-write tools in the `SelfChangeGate` of `add-self-improvement` and wraps every tool that needs approval in the gate of `add-action-approvals`, and returns the tools in two parts, always and deferred, for `add-mcp-tool-servers`.
- New metrics and log lines cover loading, skipped skills, last good versions, reloads, searches, index syncs, writes and skill use.

## Capabilities

### New Capabilities

- `agent-skill-catalog`: loading skills from the configured folders, precedence between folders, skipping malformed skills, the last good version, live reload through the watcher, the rescan and the reload endpoint, the per-request snapshot, the `Skill` tool with its always-listed set, the `skill_search` tool, the skill file read tool, and the related metrics and logs.
- `agent-skill-authoring`: the single validated write path, the shipped name rule, git history and revert, origin recording, the agent write tool, the owner REST endpoints, write protection rules, path and size safety, and the related metrics and logs.
- `agent-capability-index`: the capability index in the existing Qdrant shared by skills and subagent definitions, its collections and embedding providers, how it stays in step with the catalogs, tenant and policy filtering of search results, the text match fallback, and the related metrics and logs. Tenant erasure of index entries is written by `add-audit-and-gdpr-compliance` (company, build group 5), which owns erasure and export for every store (ruling 13.3 of the dependency fix of 2026-10-05).

### Modified Capabilities

(none. The skill tools are not a `ToolCallbackProvider` bean, so the `mcp-startup-resilience` rule that the filtered MCP provider is the only such bean still holds.)

## Impact

- Dependency: `upgrade-spring-boot-4` (Spring Boot 4, Spring AI 2) must be applied first.
- Dependency for the error body: `upgrade-spring-boot-4` owns the switch of every agent error body to an RFC 7807 problem detail (owner decision of 2026-10-02) and the deletion of `ApiError`. This change only uses that body for the errors of `/api/v1/skills`.
- Sibling changes: `add-agent-subagents`, which lands right after this change, needs the same two libraries, a skill lookup by name, one composition point for agent native tools, the tool policy port and a way to find definitions. This change provides the lookup, the composition point (`ChatToolset` and `AgentNativeTool`) with the tool context keys `request_id`, `tenant_id` (from `TenantContext.currentTenantId()` of `add-keycloak-login`) and `embedding_provider`, the `TenantToolPolicy` port, a generic git backed folder component (`VersionedFolder`) and the capability index with `CapabilitySource`, `CapabilityIndexSync` and `skill_search`, which the sibling reuses, so the changes never add a second way of doing the same thing. `add-agent-sandbox` registers its sandbox tools through the same composition point.
- New dependencies in `apps/ascend-agent/gradle/libs.versions.toml` and `build.gradle.kts`: `org.springaicommunity:spring-ai-agent-utils:0.12.0` (Apache 2.0, pulls `spring-ai-agent-utils-common` and `flexmark-html2md-converter` at compile scope) and `org.eclipse.jgit:org.eclipse.jgit:7.8.0.202609011348-r` (Eclipse Distribution License 1.0). The index uses the Spring AI Qdrant store and the Qdrant client already on the classpath.
- New code in ascend-agent: a `catalog` package under `service/` for the one catalog of every type (loader, snapshot holder, watcher, change notifier, write path and the `CatalogType` interface), a `skills` package under `service/` for the skill type, its validator and tools, a `capability` package under `service/` for the index, its sync and its search, a `SkillProperties` class in `config/properties/`, and a `CatalogController` in `controller/`.
- Changed code in ascend-agent: `StreamingChatExecutor` of `add-chat-streaming-and-conversations`, the one chat executor (owner decision 89.1 of 2026-10-08), takes its tool list once per request from the new `ChatToolset`, which adds the skill tools of the request's snapshot next to the MCP tools, and puts `request_id`, `tenant_id`, the request's `embedding_provider` and `user_message` into the tool context. `service/chat/AscendChatService.java` passes the embedding provider it already resolves to it. `config/VectorStoreConfig.java` exposes the per-provider embedding models it already builds as one bean, from which both the RAG stores and the capability index stores are built. `service/provider/ToolCallTracker.java` gains a read of the tools seen so far that does not clear them, `config/StartupLogConfig.java` reports skill folders, counts and the index, `exception/GlobalExceptionHandler.java` maps the new write errors to the RFC 7807 problem detail that `upgrade-spring-boot-4` defines (design D10), with each write reason as its `code`, and `config/SecurityConfig.java` gains the `ADMIN` rows of this change for the owner write endpoints in the authorization matrix of `add-keycloak-login` (its D4), whose realm role `ADMIN` the owner's Keycloak account holds.
- Configuration: a new `app.skills` block in `application.yaml`, a new `app.tool-policy` block with the two deny lists `denied-tools` and `denied-global-skills` (empty by default), the agent home root `app.agent-home` that the writable skill folder and the subagent definitions of `add-agent-subagents` both use, two new collections `ascendai-capabilities-768` and `ascendai-capabilities-1536` in `app.vectorstore.collections`, and container paths in `application-docker.yaml`.
- Database: no schema change in this change. Schema changes in the agent use Flyway (owner decision, `upgrade-spring-boot-4` switches the tool), which applies to the `tenant_policy` table of `add-tenant-policy`. The global skill names of tenant `default` are not seeded by a migration: skills are files on disk, so they are seeded at agent startup after the first global catalog load (design D16).
- Compose: the `ascend-agent` service mounts `./.agents/skills` read-only and the named volume `agent-home` at `/app/agent-home`, the agent home root that holds the tenant folders and that `add-agent-subagents` reuses for its definitions and `add-agent-soul` for its files. The index lives in the existing Qdrant prerequisite.
- New REST surface: `/api/v1/skills` (list, get, put, delete, history, revert, reload), acting on the caller's tenant. Every endpoint needs an authenticated caller, and the owner write endpoints (put, delete, revert, reload) need the `ADMIN` role (owner decision of 2026-10-02, the same decision `add-agent-subagents` applies to its definition endpoints). `add-keycloak-login` lands before this change (split of 2026-10-04, owner rule of 2026-10-04), so this change adds these rules as its own rows in that change's authorization matrix (its D4).
