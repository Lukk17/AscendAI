## Why

AscendAI has no real authentication. `AscendAgent/src/main/java/com/lukk/ascend/ai/agent/config/SecurityConfig.java` ships with `app.security.enabled=false` (permitAll on every request); flipping the flag only buys a single in-memory HTTP Basic user whose defaults are `admin`/`admin` (`config/properties/SecurityProperties.java`, `application.yaml` lines 68-74), with CSRF disabled. Worse, user identity, the key for chat history, RAG scoping, and semantic memory, is a client-supplied `X-User-Id` header (`controller/PromptController.java` lines 86-88) falling back to `app.user.default-id=user1`. Anyone who can reach port 9917 can read or write any user's conversation and memories by typing a header.

The downstream services are fully open: AscendMemory (:7020), ascend-audio-scribe (:7017), ascend-web-hunter (:7021), ascend-ocr (:7022), and ascend-weather-mcp (:9998) accept unauthenticated REST and MCP calls, including AscendMemory's destructive `POST /api/v1/memory/wipe` and `DELETE /api/v1/memory`. And the sibling changes now in flight (`add-tenant-isolation`, `add-usage-metering-and-quotas`, `add-audit-and-gdpr-compliance`) all presuppose a trustworthy identity; none of them can be built on a spoofable header. The Javadoc in `SecurityConfig` already names the destination, "swap for OAuth2 resource-server, JWT, or Keycloak", and `spring-boot-starter-oauth2-client` plus `spring-boot-starter-security` are already on the classpath (`build.gradle.kts` lines 46, 76). This change is that swap.

There is a second reason this has to land first. `docs/architecture/permission-aware-retrieval.md` settles how AscendAI decides which chunks a person may read, and its ownership table assigns six pieces of that mechanism to this change. This version delivers two of them: the principal identifier format with its typed factory, and group membership resolution. Four are deferred with the directory work they belong to, and are listed as such in `design.md`: the directory object id carried alongside the token subject, the Redis principal-set cache and its time to live, the cross-provider identity link with reused-address detection, and the administrator API that corrects a link. Without the two that land, `add-tenant-isolation` has a filter it cannot populate and `add-document-connectors` writes access lists nothing can be matched against.

The platform decision has been taken. Keycloak, self-hosted, is the identity layer in production and not a development convenience with a real provider assumed behind it later. The normal shape of the product is a Keycloak account with a password. A person types their password into Keycloak's own login page, the application receives an authorization code, and the application never sees the password. Groups are Keycloak realm groups. An administrator creates them, puts people in them, and a protocol mapper puts them into the access token. Nothing is imported from a customer's Microsoft or Google directory in this version.

Corporate single sign-on remains available as optional configuration. A customer's own identity provider is brokered inside the one realm through the generic OpenID Connect provider or SAML, and a person who arrives that way still lands in the Keycloak groups an administrator assigned to them. Brokering changes where a person authenticates. It does not change where their groups come from. Nothing on the password path depends on a brokered provider existing.

That simplification has one consequence that has to be stated rather than softened. A document synced from SharePoint or Google Drive carries that source's own group identifiers in its access list, and a Keycloak group name will never match one. Per-document permissions therefore work for documents uploaded directly into the product, where an administrator assigns Keycloak groups, and match nothing at all for documents synced from a customer's own storage. For this version a connector-synced document is visible to everyone in the company, which is what `add-document-connectors` said before it was amended to capture source access lists. It is recorded in `design.md` as a named limitation, together with what would have to be built to lift it.

Running Keycloak is a standing operational commitment, and the risk list says so.

## What Changes

- AscendAgent becomes an OAuth2 resource server. JWT validation against a configurable `issuer-uri`. That issuer is the platform's own Keycloak realm `ascend-ai`, added as a docker-compose service with a checked-in realm export, and it is the same single issuer for every customer. The export provisions a public client for the future Flutter app (authorization code with PKCE, direct access grants off), realm roles `USER` and `ADMIN`, realm groups and the protocol mappers the claims contract needs, a password policy, and the realm session and token lifetimes that bound how stale a group membership can be. Validating a different issuer's tokens directly remains possible as an escape hatch and is not the customer story.
- Password sign-in is the default and the path everything else is built on. A person has a Keycloak account, types their password on Keycloak's own login page, and the application receives an authorization code. The application never handles the password. The direct access grant, in which the application collects the password itself and posts it to Keycloak, stays disabled on the customer-facing client. It is a different mechanism with a different security boundary, and enabling password sign-in does not mean enabling it.
- Groups live in Keycloak and nowhere else. An administrator creates realm groups, puts people in them, and a group protocol mapper puts the group names into the access token. Group membership is read from that claim. No directory is called, and no group data is imported from any upstream provider.
- Identity brokering is optional configuration for a customer who wants corporate sign-on. One brokered identity provider per customer inside the one realm, configured through the generic OpenID Connect provider pointed at the customer's discovery document or through SAML, never code. The brokered provider's alias is the customer's identifier and it stamps the `tenant` value onto everyone who arrives through it. A person who arrives through it is a realm user like any other, and their groups are the Keycloak groups an administrator assigned. No group claim, and no other attribute carrying authorization meaning, is imported across the broker in this version.
- BREAKING: `X-User-Id` header trust is removed. User identity is derived from validated token claims (`sub`, `preferred_username`), and a `tenant` claim is defined and propagated but not yet enforced, reserved for the sibling `add-tenant-isolation` change. `app.user.default-id` survives only in dev mode.
- Role model. `USER` may chat (`POST /api/v1/ai/prompt`) and upload documents (`POST /api/v1/ingestion/upload`); `ADMIN` additionally may trigger ingestion runs (`POST /api/v1/ingestion/run`) and any future admin endpoints. Roles map from Keycloak realm roles to Spring authorities. `USER` is the realm default role. `ADMIN` is assigned deliberately and never by a mapper reading a customer's claim.
- Dev-mode escape hatch. A `dev` profile keeps today's permitAll and default-user behaviour for local single-user work and the Bruno collection. The docker-compose posture defaults to secured.
- Service-to-service authentication. Every Python service (AscendMemory, ascend-audio-scribe, ascend-web-hunter, ascend-ocr) and ascend-weather-mcp requires a bearer token on both REST and MCP surfaces, a static service token injected via env var as the baseline (design discusses OAuth2 client-credentials as the upgrade path). AscendAgent attaches the token on all outbound calls: the `SemanticMemoryClient` RestClient, the ingestion clients that call ascend-ocr, and the Spring AI MCP client connections.
- Swagger UI and actuator exposure rules under the secured posture: health and prometheus stay reachable for infra, OpenAPI docs stay readable, everything else authenticated.
- The old `app.security.*` HTTP Basic block and in-memory user are removed (superseded, not deprecated, nothing external depends on them).
- A principal set on every request. A typed factory produces `namespace:type:id` principals from the caller's Keycloak groups, the set is assembled once during authentication, is immutable for the life of the request, and is capped at 256. A caller over the cap gets an error rather than a truncated set, because a truncated set denies people access they actually have and looks exactly like a retrieval bug.
- The dev profile synthesises a usable principal set rather than an empty one, so a developer running locally against a seeded corpus actually retrieves documents instead of concluding search is broken.
- Two roles stay two roles, and roles are not principals. Roles gate endpoints, principals gate documents, and an `ADMIN` token widens the endpoint matrix while widening retrieval by nothing at all.
- A named limitation, recorded rather than worked around. No principal this version can mint matches a directory group identifier, so an access list naming one matches nobody. Connector-synced documents are company-visible for this version, and lifting that is a later change whose analysis is preserved in the deferred section of `design.md`.

## Capabilities

### New Capabilities

- `agent-authentication`: AscendAgent validates JWTs as an OAuth2 resource server; endpoint authorization matrix (USER/ADMIN roles, public infra endpoints, Swagger/actuator rules); dev-profile fallback.
- `user-identity`: user identity resolved from validated token claims (`sub` / `preferred_username` / reserved `tenant`), `X-User-Id` header no longer trusted, group identifiers and the principal set carried on the resolved identity.
- `service-authentication`: bearer-token enforcement on the REST and MCP surfaces of all five downstream services, plus AscendAgent attaching the token on every outbound call.
- `identity-provider`: Keycloak as the platform's identity layer, one realm and one issuer for every customer, password sign-in through Keycloak's own login page as the default, provisioned by a checked-in realm export whose contents are a contract (roles, realm groups, PKCE client with direct access grants off, protocol mappers, password policy, session and token lifetimes), with the development seed kept in a separate overlay.
- `identity-brokering`: optional corporate single sign-on, one brokered identity provider per customer inside that realm, configured through the generic OpenID Connect provider or SAML; how a person is matched to their customer's provider at sign-in; the tenant stamp; and the rule that a brokered person's authorization comes from Keycloak groups rather than from anything the upstream token asserted.
- `principal-resolution`: the `namespace:type:id` principal format and its typed factory, group membership resolved from the Keycloak group claim, the immutable capped principal set the search filter is later composed from, and the stated fact that a directory group identifier matches nothing in this version.

### Modified Capabilities

- `semantic-memory-client`: outbound requests to AscendMemory gain a mandatory `Authorization: Bearer` header carrying the service token.

(`ingestion-security` was reviewed and left unchanged. Its requirements cover upload hygiene (filename sanitization, MIME allowlist, size limits), not authentication posture. The authorization matrix for ingestion endpoints lives in `agent-authentication` to keep one source of truth.)

## Impact

- AscendAgent (permission-aware retrieval groundwork): new principal factory and value type; a membership resolver reading the Keycloak group claim; `app.identity.*` configuration binding claim names and the principal cap.
- AscendAgent: `SecurityConfig.java` rewritten (resource server plus role rules, HTTP Basic path deleted); `SecurityProperties.java` replaced; `PromptController.java` and `IngestionController.java` switch from header/param identity to the authenticated principal; new outbound token propagation on `SemanticMemoryClient`, ingestion clients, and MCP client config; `build.gradle.kts` swaps `oauth2-client` for `oauth2-resource-server`; `application.yaml` and `application-docker.yaml` gain issuer-uri and service-token config, lose the `app.security.user` block.
- Python services (AscendMemory, ascend-audio-scribe, ascend-web-hunter, ascend-ocr): one shared-pattern FastAPI auth dependency per service checking the bearer token on REST routes, plus the equivalent check on the FastMCP surface; new `SERVICE_AUTH_TOKEN` env var.
- ascend-weather-mcp: a Spring filter enforcing the same bearer token.
- docker-compose.yaml: new `keycloak` service and realm import volume; `SERVICE_AUTH_TOKEN` and issuer env wiring for all services. The realm import splits into a production export and a development overlay, so the seeded human user and the direct-access-grant client the e2e suite needs never reach a production deployment.
- Operations: an administrator runbook in `docs/SECURITY.md` covering account creation, the password policy, realm group creation and membership, and how a group becomes a principal. Plus an optional brokering runbook for a customer who wants corporate sign-on, and the standing cost of running Keycloak: a database, certificates, backups with a tested restore, and an upgrade habit that a roughly monthly patch cadence with no long-term support release makes non-optional.
- `docs/architecture/`: `permission-aware-retrieval.md` and `ADR-M007` describe a membership order and an ownership table that this version only partly delivers. Both need an amendment naming what this version does and what it defers. That edit is a task in this change rather than something it performs, because those files sit outside the change folder.
- e2e / Bruno: the collection at `docs/api/request/AscendAI/` needs a token-acquisition step or must run against the dev profile, called out in tasks.
- Docs: root `AGENTS.md`, per-module `AGENTS.md` files, and a new `docs/SECURITY.md` (auth setup, token flow, IdP swap recipe).
- Blocks: `add-tenant-isolation` cannot compose an access-list predicate without the principal set, and `add-document-connectors` cannot write access lists without the principal format. The tasks those two changes wait on are marked in `tasks.md`.
- Contradicts, pending the owner's decision: `add-document-connectors` captures per-item access lists naming `entra:group:*` principals. Nothing in this version can mint or match one. That change is not edited here, and the conflict is reported rather than resolved.
- Depends on / enables: defines the `tenant` claim consumed by `add-tenant-isolation`; provides the identity primitive assumed by `add-usage-metering-and-quotas` and `add-audit-and-gdpr-compliance`. Network-level TLS stays with `harden-cloud-deployment`.
