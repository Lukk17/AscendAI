- Latest releases on PyPI on 2026-10-03: `opentelemetry-sdk` and `opentelemetry-exporter-otlp` 1.45.0, the instrumentation packages 0.66b0, `slowapi` 0.1.10, `python-json-logger` 4.2.0, `colorlog` 6.12.0, `prometheus-client` 0.26.0, `prometheus-fastapi-instrumentator` 8.1.0, `pydantic-settings` 2.15.0, `fastapi` 0.142.2, `uvicorn` 0.54.0, `fastmcp` 4.0.10, `mcp` 2.3.0.

## Goals / Non-Goals

Goals:

- One source of truth for every concern listed in the proposal, with each service keeping only what is its own.
- One error rule on every Python REST error, RFC 7807 problem details with `code` and `traceId` and the type base `https://ascend.ai/errors/`, defined by this library (owner answer 70.1 of 2026-10-04). The agent follows the same format later in `upgrade-spring-boot-4` D19, so a client then sees one error contract across all six services.
- Each service migrated alone and green before the next starts.

Non-Goals:

- No shared library for the Java services. ascend-weather-mcp is a demo service (owner answer 56).
- No framework upgrade. FastAPI, uvicorn, Starlette, FastMCP, mcp and pydantic stay at the versions the four services already share. Moving `fastapi`, `uvicorn`, `fastmcp` and `mcp` to FastAPI 0.142, uvicorn 0.54, FastMCP 4 and the MCP SDK 2 is the separate change `add-python-runtime-upgrades` (build group 2, position 2 of the owner build order of 2026-10-04), which lands right after this one and also adds `starlette` and `httpx2` to the library's version set (owner answer 60.6 of 2026-10-03, open question 7 closed).
- No change to any success body, any business rule or any job, memory, transcription or crawl behaviour.
- No new authentication. `add-keycloak-login` adds it later, inside the library (its section 4, Required edits).

### D1: Location and layout

The library lives in `libs/ascend-python-common/`. `apps/` holds deployables only: every folder there has a Dockerfile, a CI matrix entry, a release and a `CHANGELOG.md` that the release workflow reads, and a library has none of that. `packages/` is the JavaScript convention and `apps/ascend-python-common` would make the CI and release workflows treat it as an image. Distribution name `ascend-python-common`, import package `ascend_python_common`, so it never collides with each service's own top level package `src`.

```text
libs/ascend-python-common/
  pyproject.toml          version, pinned dependencies, its own tooling sections
  README.md
  CHANGELOG.md
  tooling/ruff.toml       the shared ruff rule set every service extends
  src/ascend_python_common/
    __init__.py           __all__ and __version__
    app.py                ServiceDefinition, create_service_app, the MCP path route
    settings.py           ServiceSettings, McpFetchSettings, CsvTuple, LogLevel
    log_config.py         configure_logging, formatters, filters
    request_context.py    correlation id and MCP session digest (pure ASGI), the FastMCP log context middleware
    tracing.py            tracer provider builder, the span processor that drops the MCP session id, current trace id (worker tracing and context carry stay in ascend-ocr, owner decision 93 of 2026-10-08)
    errors/
      codes.py            ProblemCode and the platform codes
      problem.py          the one problem body builder
      registry.py         ErrorRegistry (exception type to code and detail)
      handlers.py         REST handler registration
      mcp.py              FastMCP middleware that maps registered exceptions to tool errors
      refusals.py         refusal logging and the error counter
    readiness.py          probe types, the aggregator, /health and /ready
    rate_limit.py         the limiter, REST wiring, FastMCP tool call limiting
    security_headers.py   pure ASGI response headers
    startup_banner.py     the banner frame and printing rules, D20
    uri_guard.py          the URI fetch guard (SSRF check, address pinning, redirect checks, file:// jail), D21
    uri_guard_aiohttp.py  the pinned resolver and the guarded GET for aiohttp, installed with the fetch extra, D21
    tooling.py            the conformance check every service's test suite calls
  tests/
```

The layout follows `python-patterns`: `src/` layout, absolute imports, `__all__` in `__init__.py`. The library module is named `log_config.py`, not `logging.py`, so no reader confuses it with the standard library module.

### D2: Where pip gets the library (packaging)

The dependency line is the same in every option: `ascend-python-common==<version>` in `[project] dependencies` of each service. The options differ only in where pip finds that version.

| | (a) Monorepo folder | (b) Pinned git URL | (c) Private package index |
|---|---|---|---|
| Local venv | `pip install -e ../../libs/ascend-python-common`, then `pip install -e .[dev]` in the service. A library edit is live at once | Needs the tag pushed first, or an editable override, which gives two sources | Needs a publish first, or an editable override |
| Docker | Compose `additional_contexts: ascend-python-common: ./libs/ascend-python-common` per service, `COPY --from=ascend-python-common . /opt/ascend-python-common` and `pip install /opt/ascend-python-common` before `pip install .`. Each service keeps its own build context. `release.yaml` adds `build-contexts:` to `docker/build-push-action`. A plain `docker build` in a service folder needs `--build-context ascend-python-common=../../libs/ascend-python-common` | Network access to GitHub during the build. The repository is public today, so no credentials are needed now. If it becomes private, every build needs a token as a build secret | Network access and a token for the index in every build |
| One pull request changes library and service | Yes, CI tests both from the same commit | No. The tag must exist before the service build can resolve it, so a library change and its use are two steps | No, publish then use |
| Release work | None beyond the version in `pyproject.toml` | Tag per library version, pushed before each build | Publish job and index account |
| Standalone web-hunter bundle | Unaffected: `deploy-standalone/compose.yaml` pulls `lukk17/ascend-ai-ascend-web-hunter:v0.0.3`, which already contains whatever library its image was built with | Unaffected for the same reason | Unaffected for the same reason |
| Weakness | The name is not on PyPI. An install that runs `pip install .` in a service before the library is installed asks PyPI for `ascend-python-common`, and anyone could publish that name (dependency confusion) | Each build depends on GitHub being reachable. Tag discipline | GitHub Packages has no Python registry, so this means PyPI (public), or a hosted index such as AWS CodeArtifact, Gemfury or a self-hosted devpi, each with its own account and cost |

Decision (owner answer of 2026-10-03, open question 2 closed): option (a). The library is installed from `libs/ascend-python-common`, editable (`pip install -e`) in every local virtual environment, and in Docker from the named build context `ascend-python-common` that Compose `additional_contexts` and the release workflow's `build-contexts` provide. It keeps one pull request atomic across library and services, needs no network or credentials beyond PyPI for the other dependencies, and adds no release step. Nothing is published to a package index, and the name is not registered on PyPI. The dependency confusion risk is handled by install order alone: every documented install, the CI job and every Dockerfile install the library from the folder before the service, so pip finds the pinned version already installed and never asks an index for it. The one gap left is a person who runs a service's `pip install` before the library's, and the Risks section keeps it.

### D3: Versioning of the library

- Semantic versioning in `libs/ascend-python-common/pyproject.toml`, starting at `0.1.0`, with a `CHANGELOG.md` in the format of the services' own changelogs.
- Each service pins the exact version (`==`). With option (a), pip refuses the install when the folder holds another version, so a forgotten pin bump fails at once instead of building against an unexpected library.
- A library change that changes the behaviour of a service bumps the library version and, in the same commit, the pin in all four services plus a new top entry in each affected service's `CHANGELOG.md`, because `ci.yaml`'s `verify-changelog` and `release.yaml` read the service changelog. Inside one OpenSpec change, that entry is the one named version of the change (D25).
- While the version is `0.x`, a breaking change bumps the minor number. `1.0.0` is cut once all four services are migrated (task 8.1).

### D5: Errors

The body is defined here, built in one place (owner answer 70.1 of 2026-10-04). `upgrade-spring-boot-4` D19 later gives the agent the same body.

- `ProblemCode` is a frozen dataclass: `code`, `status`. Its type URI is `https://ascend.ai/errors/` plus the code in lower case with `_` replaced by `-`, so ascend-ocr's `QUEUE_FULL` gets `https://ascend.ai/errors/queue-full`.
- The platform codes, the values `upgrade-spring-boot-4` D19 later uses for the same cases in the agent: `validation` (400), `bad_request` (400), `unauthorized` (401), `not_found` (404), `method_not_allowed` (405), `not_acceptable` (406), `content_too_large` (413), `unsupported_media_type` (415), `rate_limited` (429), `http_error` (any other framework status), `internal` (500).
- `unauthorized` is the answer to a missing or refused service token. This change only defines the code and its problem body (a fixed detail that names no token and no caller, and a `WWW-Authenticate: Bearer` header). The bearer token check that raises it is added to the library later by `add-keycloak-login` (its tasks 4.1 and 4.2, moved there from `add-auth-and-identity` on 2026-10-04), which uses this code on REST and `unauthorized: ` on MCP, the same code `upgrade-spring-boot-4` D19 later gives the agent's own 401.
- `problem_response(request, code, detail, headers=None, extensions=None)` is the only builder. It sets `type`, `title` (the HTTP reason phrase, `http.HTTPStatus(status).phrase`, as Spring does for the agent), `status`, `detail`, `instance` (the request path), `code` and `traceId`, and the media type `application/problem+json`. `traceId` comes from `tracing.current_trace_id()` (D10). `extensions` adds further members at the top level of the body, and an extension never replaces one of the seven standard members.
- Detail rule for 5xx answers. Only the internal code (the catch-all for an exception no entry is registered for, `internal` or a service's own internal code such as ascend-ocr's `INTERNAL_ERROR`) gets the fixed detail `An unexpected error occurred. Check server logs for details.`, the text `upgrade-spring-boot-4` D19 later uses for the agent. Every other 5xx keeps the detail its registry entry builds, because it reports another service or an upstream and the caller needs to know what failed: a 502, 503 or 504 entry, and the named upstream codes (ascend-ocr's `DOWNLOAD_FAILED`, `extraction_failed` of `enhance-web-search-extraction-and-tiers`, `download_failed` and `download_timeout` of `add-file-download`). That detail still never names an internal host, an internal path, an exception class, a traceback or the user info of a URI. The registry refuses at start-up an entry for the internal code whose detail rule is not the fixed text.
- `ErrorRegistry` maps a service exception type to a `ProblemCode`, a detail rule (the exception message, or a fixed text), optional response headers (ascend-ocr's `Retry-After` on `QUEUE_FULL`) and optional extension members read from the exception (ascend-web-hunter's `vnc_url` on `human_intervention_required`). Each service builds one registry in its own `src/api/exception_handlers.py`, which keeps its exception classes and codes and nothing else. A service can name its own internal code: ascend-ocr keeps `INTERNAL_ERROR`, the other three use `internal`.
- `install_error_handlers(app, registry)` registers: every registry entry, the framework's `HTTPException` (status to platform code), FastAPI's `RequestValidationError` (400 `validation` with `errors`), slowapi's `RateLimitExceeded` (429 `rate_limited` with `Retry-After`), and the catch-all `Exception` (500).
- `errors` on a validation failure is a list of `{"field", "message"}` sorted by `field`, `field` being the error location joined with `.` after dropping the first element (`body`, `query`, `path`, `form`, `header`). `upgrade-spring-boot-4` D19 point 5 later sets the same rule for the agent. It moves every service from 422 to 400 (BREAKING in the proposal).
- Refusal logging, taken from ascend-ocr: a registered code with a 4xx status, a platform 4xx and the upstream codes a service marks as expected (ascend-ocr's `DOWNLOAD_FAILED`) are logged as one WARNING `Refused with <code>: <detail>` without a traceback. A 5xx that is not marked expected is logged at ERROR with the traceback. Both increment `ascend_service_errors_total{code, surface, operation}`. `operation` is the route template on REST (for example `/v1/ocr/jobs/{job_id}`, never the raw path, so an identifier in the path never becomes a label value) and the tool name on MCP (for example `ocr_submit`), so refusals of different tools or routes that share a code can be told apart. A request that matches no route (the problem 404 and 405 of D12) is counted with `operation` `unmatched`, which keeps the label values bounded by the routes and tools a service has. The metric replaces `ascendocr_ocr_errors_total{error_code, surface}`. No dashboard or alert in `infra/observability` reads the old name (`git grep -n errors_total -- infra` found nothing on 2026-10-03), and ascend-ocr's arc42 page 08 is updated.
- MCP: `McpRefusalMiddleware`, a FastMCP middleware on `on_call_tool`, maps every registry exception to `ToolError(f"{code}: {detail}")` with FastMCP's own log line lowered to DEBUG, logs and counts it with `surface="mcp"`, and maps any other exception to the internal code with the fixed detail. This is ascend-ocr's `_mcp_error_codes` context manager, moved from a per-tool `with` block to one middleware. ascend-audio-scribe and ascend-memory drop their `{"status": "error"}` result objects (BREAKING). ascend-web-hunter's MCP `human_intervention_required`, `novnc_busy` and `session_expired` result objects are successful tool results, not errors, and stay as they are.
- The codes the three RFC 7807 services already send keep their `type` and gain `code`: `validation`, `internal`, `file_too_large`, `upstream_provider` (ascend-audio-scribe), `external_service_unavailable`, `blocklist_refresh_invalid`, `blocklist_refresh_throttled` (ascend-web-hunter).
- ascend-web-hunter's 428 and 409 REST answers (owner answer 60.2 of 2026-10-03). Today they are not problem bodies: `exception_handlers.py` builds `{"status": "human_intervention_required", "intervention_type", "vnc_url", "message"}` for the 428 and `{"status": "novnc_busy", "message", "holder_url", "holder_profile"}` with `Retry-After` for the 409, and its comment names ADR-003 as the reason. The old `status` word moves to `code`, `message` becomes `detail`, and `status` becomes the HTTP status number as in every problem body. Every extension member keeps its name, type and meaning. Both are expected 4xx refusals, so they are logged as one WARNING and counted like any other code, and the service's own `HUMAN_INTERVENTION_TOTAL` and `NOVNC_FLOW_BUSY_TOTAL` keep counting as today. ### D9: Rate limiting

- One slowapi `Limiter` per service, keyed by the caller's address (`get_remote_address`), with the storage the service names in `ServiceDefinition.rate_limit_storage_uri`: in memory by default (the library's own tests and sample app), and Redis in all four services, each through its `REDIS_URL` (answer 94.3 of 2026-10-08), because several containers of each service run (owner decision 87 of 2026-10-08, the cross-instance paragraph below). REST: slowapi's ASGI middleware applies `RATE_LIMIT_DEFAULT` to every route, `/health`, `/ready` and `/metrics` are exempt, and the MCP path is skipped (it is limited per tool call). A service marks its stricter routes with `@limiter.limit(settings.<NAMED_LIMIT>)`. `headers_enabled=True` gives `Retry-After` and the `X-RateLimit-*` headers. The 429 body is the problem body with code `rate_limited` (D5), in place of slowapi's own `{"error": ...}` body that ascend-ocr answers today.
- MCP: `McpRateLimitMiddleware`, a FastMCP middleware on `on_call_tool`, hits the same limiter storage with the same key (the address of the HTTP request that carried the call) and the limit the service maps to that tool name, `RATE_LIMIT_DEFAULT` when unmapped. Over the limit it raises `ToolError("rate_limited: ...")`, logged and counted like any refusal. `tools/list` and the session handshake are not limited. FastMCP's own `SlidingWindowRateLimitingMiddleware` is not used, because it keeps its own windows, so a caller could spend the same budget twice, once on REST and once on MCP.
- Every caller inside the platform reaches a service from one address (the ascend-agent container), so a per-address limit is in effect a limit on the whole agent. The limits are flood protection only, not a throughput cap, so they sit well above any load the agent makes. The defaults below are the owner's (answer 60.4 of 2026-10-03, open question 5 closed). Each one is a setting the service reads from its environment and its `.env` file (D6), with the value below as its code default:

| Service | `RATE_LIMIT_DEFAULT` | Stricter named limits |
|---|---|---|
| ascend-ocr | `600/minute` (was `60/minute`) | `RATE_LIMIT_OCR=60/minute` (was `20/minute`) on `POST /v1/ocr/jobs` and now also `ocr_submit`. Its queue holds at most 8 documents (`OCR_JOB_QUEUE_MAX_DOCUMENTS`) and refuses more with `QUEUE_FULL` anyway, so this limit only stops a flood of submissions |
| ascend-memory | `6000/minute` | none. The agent searches and inserts on every chat turn |
| ascend-web-hunter | `1200/minute` | none |
| ascend-audio-scribe | `600/minute` | `RATE_LIMIT_TRANSCRIBE=60/minute` on the four transcription routes and the transcription tools |

- Where the values come from. Only ascend-ocr had rate limit settings before this change (`60/minute` and `20/minute`), and nobody measured them. The other three services had no limit, and the values this design proposed for them before answer 60.4 were unmeasured guesses. The defaults above are owner values, not measurements either. Owner decision 91.3 of 2026-10-08 removed the load test of task 7.2 that was to measure each service's capacity and set the final defaults, because the limits are flood protection and not a throughput cap, so the owner values stay the defaults. A deployment that needs other values sets them in the service's environment.
- Several containers of one service (owner decision 87 of 2026-10-08, rule R1). The owner runs several containers of the same service at once, several ascend-web-hunter containers among them. A limit kept in each container's memory then gives a caller one budget per container. So the limiter storage is a setting of the service definition, `rate_limit_storage_uri`, a storage URI of the `limits` package with the default `memory://`, and Redis is the one mechanism for state shared between containers of a Python service. ascend-web-hunter passes its existing `REDIS_URL`, so every container of it draws a caller's REST and MCP calls from one budget in the Redis it already uses, the bundled Redis of `deploy-standalone/` included, and no new setting is added (task 4.15). slowapi's in-memory fallback is on, so a Redis that cannot be reached never refuses traffic: each container then limits on its own until Redis answers again, and the fallback is logged at WARNING (task 1.18). ascend-memory, ascend-audio-scribe and ascend-ocr do the same (answer 94.3 of 2026-10-08): each gets the setting `REDIS_URL` in its own `ServiceSettings` subclass, with the same default as ascend-web-hunter (`redis://127.0.0.1:6379/0`, for a native run), and passes it as `rate_limit_storage_uri`. In `compose.yaml` each of the three services reads `REDIS_URL=${REDIS_URL:-redis://host.docker.internal:6379/0}`, the line and default ascend-web-hunter has in `compose.ascend-web-hunter.yaml`, so all four reach the shared Redis prerequisite through the one `REDIS_URL` of the root `.env` (tasks 2.13, 3.15, 5.8 and 2.9). Each service keeps its limiter keys under its own prefix: the library passes the service's name (`ServiceDefinition.name`, for example `ascend-memory`) to slowapi's `key_prefix`, and `McpRateLimitMiddleware` builds its keys with the same prefix, so REST and MCP still draw from one budget and two services never share or overwrite a window. `redis==8.0.0`, the version ascend-web-hunter pins today, moves into the library's pins (D4), because all four services now need the Redis client of the `limits` storage, and ascend-web-hunter drops its own pin.
- `compose.yaml` today pins ascend-ocr's old values (`RATE_LIMIT_DEFAULT=60/minute` and `RATE_LIMIT_OCR=20/minute`). Those two literal lines are replaced. By owner rule 98 of 2026-10-08 (D26), every compose service passes each of its rate limit settings in the form `${VAR:-default}` with the code default above: `RATE_LIMIT_DEFAULT=${MEMORY_RATE_LIMIT_DEFAULT:-6000/minute}` on `ascend-memory`, `RATE_LIMIT_DEFAULT=${AUDIO_SCRIBE_RATE_LIMIT_DEFAULT:-600/minute}` and `RATE_LIMIT_TRANSCRIBE=${RATE_LIMIT_TRANSCRIBE:-60/minute}` on `ascend-audio-scribe`, `RATE_LIMIT_DEFAULT=${WEB_HUNTER_RATE_LIMIT_DEFAULT:-1200/minute}` on `ascend-web-hunter` (in `compose.ascend-web-hunter.yaml` and in `deploy-standalone/compose.yaml`), and `RATE_LIMIT_DEFAULT=${OCR_RATE_LIMIT_DEFAULT:-600/minute}` and `RATE_LIMIT_OCR=${RATE_LIMIT_OCR:-60/minute}` on `ascend-ocr`. The interpolation name of `RATE_LIMIT_DEFAULT` carries the service, because the four defaults differ and one root `.env` line must never change all four at once (the reason of D23). A deployment overrides a limit through that variable in the `.env` next to the compose file.

- ascend-web-hunter's main spec forbids per-caller limits today. The requirement is removed and added again so it forbids only outbound self-throttling per domain (spec delta `web-search-antibot-evasion`).

### D10: Tracing

- Every service always installs an SDK `TracerProvider` with resource `service.name` set to the service name. When `OTEL_EXPORTER_OTLP_ENDPOINT` is set, it has an OTLP gRPC exporter to that endpoint and the sampler `ParentBased(ALWAYS_ON)`. When the endpoint is unset or empty, it has no exporter and the sampler `ParentBased(ALWAYS_OFF)` (owner decision 89.14 of 2026-10-08: export whenever the endpoint is set, no custom `OTEL_ENABLED`). The SDK still creates a real trace id for an unsampled span, so every request has a trace id in both cases, and a `traceparent` from the caller is continued. OpenTelemetry's standard `OTEL_SDK_DISABLED=true` is left to the SDK: it then hands out no-op tracers, so no span exists, nothing is exported and a problem body leaves `traceId` out, the case "no trace is current" of D5. This is the switch tests and operators use to turn tracing off.
- MCP session id on spans (owner decision 93 of 2026-10-08, review item C10): one span processor drops the attribute `mcp.session.id`, which FastMCP sets on its spans, from every span at span start, so no exported span carries an MCP session id, raw or as a digest. It replaces ascend-ocr's exporter wrapper `McpSessionDigestSpanExporter`, which rewrote the raw id to its digest. The library turns on no capture of the `mcp-session-id` HTTP header, so no other span attribute holds it. What is lost is grouping spans by MCP session in Tempo. Log lines keep the session digest (D8). The trace exists even when it is not sampled, and the field is left out only when no span is current. `upgrade-spring-boot-4` D19 point 3 later sets the same rule for the agent.
- The server span is started by OpenTelemetry's ASGI middleware placed just inside the correlation id middleware, around the whole Starlette stack, instead of `FastAPIInstrumentor().instrument()`. The reason: Starlette runs the catch-all `Exception` handler in `ServerErrorMiddleware`, outside every user middleware, so a span started by an instrumentation that sits in the user middleware has already ended when the 500 body is built, and the 500 would have no `traceId`. Task 1.10 proves a `traceId` on a 500 body.
- `current_trace_id()` returns the 32 character lower case hex id of the current span when its context is valid, otherwise `None`.
- ascend-ocr's worker process tracing (`configure_worker_tracing`) and its context carry helpers (`inject_trace_context`, `extract_trace_context`) stay in ascend-ocr's `src/observability/tracing.py`, because ascend-ocr is their only caller (owner decision 93 of 2026-10-08, review item C7, which replaces the first plan to move them into the library, task 1.17). The worker builds its tracer provider with the library's public builder, so the export rule above exists once. ascend-ocr installs the aiohttp client instrumentation itself, in its own lifespan.

### D11: Health, readiness and metrics

- `/health`: 200 and `{"status": "ok", "service": <name>, "version": <version>}`, never touching a dependency. ascend-memory keeps its own `/health/legacy` route.
- `/ready`: a service passes named probes (`async def probe() -> ProbeResult`, or a sync function the aggregator runs in a thread). `ProbeResult` holds `status` (`ok`, `skipped`, `degraded`, `error`) and optional safe details. The aggregator runs all probes at once with a budget of `READINESS_PROBE_TIMEOUT_SECONDS` each (default 3 seconds, the web-hunter and memory value, a setting by owner rule 98 of 2026-10-08, D6 and D26), turns a timeout or an exception into `error` with a WARNING log line and no exception text in the body, and answers 200 `ready` when every probe is `ok` or `skipped`, else 503 `not-ready`. Body: `{"status", "service", "version", "checks"}`.
- The status word for a 503 is `not-ready` (ascend-ocr's word). ascend-web-hunter, ascend-memory and ascend-audio-scribe answered `degraded`, which reads as "still serving" next to a 503. `degraded` stays as the status of one check, for example an open circuit breaker.
- ascend-ocr's `/ready` moves from 200 in both states to 200 or 503, and its fields move under `checks`: `engine` (`warm`), `worker_pool` (`accepting_work`), `jobs` (`queued`, `running`, always `ok`, because busy stays ready, its ADR-004). Its ADR-004 gets an amendment. `.github/workflows/e2e.yaml` waits with `curl -fsS http://localhost:7022/ready | grep -q '"status":"ready"'`, which still works: `-f` makes a 503 a failed attempt and the loop tries again.
- `/metrics`: `prometheus-fastapi-instrumentator` with `should_group_status_codes=False` and `excluded_handlers=["/metrics", "/health", "/ready"]`, the setting three services already use. ascend-ocr changes from grouped status codes. The instrumentator keeps honouring `PROMETHEUS_MULTIPROC_DIR`, which ascend-ocr's worker metrics rely on.

### D12: App factory and the MCP attachment

`create_service_app(definition: ServiceDefinition) -> FastAPI`. `ServiceDefinition` is a frozen dataclass: `name`, `distribution` (for the version through `importlib.metadata`), `settings`, `mcp` (the FastMCP server), `routers`, `error_registry`, `probes`, `lifespan` (the service's own async context manager, optional), `tool_rate_limits`, `rate_limit_storage_uri` (D9, default `memory://`) and `startup_banner` (the service's function that returns its own banner content lines, D20). It has no `extra_middleware` and no `extra_instrumentors` field (owner decision 93 of 2026-10-08, review item C7): each had one caller, so ascend-audio-scribe adds its `ForceJSONUTF8Middleware` to the app the factory returns, and ascend-ocr installs its aiohttp instrumentation in its own lifespan.

The factory, in this order: configures logging, builds the tracer provider, builds the MCP app with `mcp.http_app(path="/mcp", stateless_http=True)` and adds the FastMCP middlewares (request log context, rate limit, refusal mapping), creates the FastAPI app with the service name as title and the version, installs the security headers, rate limiting, error handlers, the service's routers, `/health`, `/ready`, `/metrics`, and attaches the MCP app. The lifespan enters the MCP app's lifespan, then the service's own lifespan, then logs the startup banner, then yields. The outer stack is correlation id, then the OpenTelemetry ASGI middleware, then Starlette's own stack.

Stateless HTTP mode (answer 94.2 of 2026-10-08). Several containers of each Python service run at once, so any container must be able to answer any MCP request. FastMCP's documentation (Context7 `/websites/gofastmcp`, `https://gofastmcp.com/llms-full.txt`, "Production Deployment > Horizontal Scaling", read on 2026-10-08) says that by default the Streamable HTTP transport keeps each session in the memory of the instance that created it, so a request routed to another instance fails, that sticky sessions do not work reliably because most MCP clients do not forward `Set-Cookie`, and that stateless mode, enabled with `mcp.http_app(stateless_http=True)` (or `mcp.run(transport="http", stateless_http=True)`, or the environment variable `FASTMCP_STATELESS_HTTP=true`), "creates a fresh transport context" for each request, "eliminating the need for session affinity entirely". The installed FastMCP 3.3.1 has the same parameter (`fastmcp/server/mixins/transport.py`, `http_app(..., stateless_http=...)`, read on 2026-10-08), and in stateless mode `fastmcp/server/http.py` serves only `POST` and `DELETE` on the MCP path, so there is no standing `GET` stream. The library passes `stateless_http=True` in code, never through the environment variable, so no service can drift from it. Consequence: no tool may rely on a message the server sends to the client between requests (no elicitation, sampling or roots request and no notification on a standing stream). A tool answers within its own call. No tool of the four services sends such a message today (`git grep` for `ctx.elicit`, `ctx.sample`, `report_progress` and `ctx.log` over `apps/*/src` returned nothing on 2026-10-08). The MCP session digest of D8 then stays for a client that still sends an `mcp-session-id` header, and the framework creates no session of its own.

The MCP app is attached by a small route class whose `matches` answers a full match only for the paths `/mcp` and `/mcp/` and passes the scope on unchanged. Today every service mounts the MCP app at `/`, which sends every unmatched path and every wrong method to the MCP app's plain text 404 (measured on ascend-ocr: `GET /nonexistent` and `DELETE /health` both answer `404 text/plain`). With the route class, FastAPI's router answers those with the problem 404 and 405 of D5, while the MCP endpoint stays inside FastAPI's middleware, so it is still traced, counted and rate checked as today.

Each service's `src/main.py` shrinks to building its `ServiceDefinition` and `app = create_service_app(...)`, plus its own lifespan hooks (ascend-ocr's worker pool and job runner, ascend-memory's warm-up task, ascend-audio-scribe's cleanup loop, ascend-web-hunter's browser pool and client shutdown). The `if __name__ == "__main__"` blocks call `uvicorn.run("src.main:app", host=settings.API_HOST, port=settings.API_PORT)` with no `log_config`.

### D13: Ports, and whether MCP gets its own port

The owner asked that ascend-audio-scribe have both an MCP port and an API port, and asked for one rule for all four services.

Facts: uvicorn serves one app on one host and port per `Server`, and the `uvicorn` command line starts one server. FastMCP's own runner starts one server too. Two ports from one process therefore means two `uvicorn.Server` objects started with `asyncio.gather` from `python -m src.main`. Both servers install signal handlers, uvicorn restores and re-raises a captured signal when a server stops, so a stop signal reaches both, but this is not a documented uvicorn use. The `--reload` workflow in every service's `AGENTS.md` runs through the `uvicorn` command line and would serve only one port.

Decision (owner answer 58 of 2026-10-03, open question 1 closed): option A.

Option A, chosen: the MCP endpoint stays at `/mcp` on `API_PORT` in all four services. One server, one port, one lifespan, `--reload` keeps working, no Dockerfile `CMD` changes, no new ports in compose, the agent's MCP connection URLs and the Bruno collection stay as they are. ascend-audio-scribe's `MCP_HOST` and `MCP_PORT` are renamed to `API_HOST` and `API_PORT` (owner defect 6), which also makes the `API_PORT=7017` its Dockerfile sets today take effect. No `MCP_PORT` setting exists. `API_PORT` is defined once, in the library's `ServiceSettings` base (D6), and each service subclass only sets its default.

Option B, rejected by the owner: every service serves MCP on its own port. The settings base adds `MCP_PORT` (1 to 65535, must differ from `API_PORT`). `create_service_app` returns two apps, the library adds `serve(definition)` that runs both servers in one loop, every Dockerfile `CMD` becomes `python -m src.main`, every compose file publishes a second port, the agent's `spring.ai.mcp.client.streamable-http.connections` URLs, the Bruno environments and every e2e spec that calls an MCP tool change, and ascend-ocr's MCP session digest binds by port instead of by path. Gain: the MCP surface can be published on a different network from REST, and REST and MCP get their own middleware stacks. The owner chose option A, so none of option B is built.

The tasks are written for option A.

### D21: The URI fetch guard

Three services carry their own copy of one rule: a URI a caller names may be fetched only when it leads to a public address. ascend-ocr (`src/api/mcp/mcp_server.py`: `_fetch_file`, `_download_http`, `_validate_host`, `_is_blocked`, `_validate_jailed_path`, `_is_within`) and ascend-audio-scribe (`src/adapters/download_service.py`: `_validate_http_target`, `_resolve_to_ips`, `_is_safe_ip`, `_resolve_file_uri`) check the URIs an MCP caller names. ascend-web-hunter (`src/validator/url_validator.py`: `is_safe_external_url`, `_is_safe_host`, `_is_public_address`, `_is_ip_literal`, `_resolve_public_addresses`, `PinnedHost`, `pin_safe_host`) checks the URLs a REST or MCP caller asks it to read, and its curl_cffi tier (`src/reader/strategies/curl_cffi_fetcher.py`, `fetch_with_curl_cffi` and `_pin_session_to`) follows redirects by hand and checks and pins every hop (its ADR-012). Owner answer 60.5 of 2026-10-03 (open question 6, closed) moves the guard into the library's `uri_guard.py`. Owner answers 63.1 and 63.2 of 2026-10-04 add the redirect check and the third copy. The download itself stays in each service: aiohttp in ascend-ocr (read into memory) and ascend-audio-scribe (streamed to a temp file), curl_cffi in ascend-web-hunter, each with its own size cap and body handling.

What each copy checks today (read in the source on 2026-10-04):

| Rule | ascend-ocr | ascend-audio-scribe | ascend-web-hunter |
| --- | --- | --- | --- |
| Schemes | `http`, `https`, `file` | `http`, `https`, `file` | `http`, `https` |
| User info in an HTTP URI refused | yes | no | no |
| No host name refused | yes | yes | yes |
| A URI that does not parse, or an invalid port, refused | no | no | yes |
| A host on the allow list (today `MCP_ALLOWED_HOSTS`, renamed `ALLOWED_PRIVATE_HOSTS` by D22) skips the address check | yes | yes | no such setting |
| Every resolved address must be public (not private, loopback, link-local, multicast, reserved or unspecified) | yes | yes | yes |
| A lookup that fails, or answers no address, refused | fails only | yes | yes |
| A lookup answer that is not an IP address refused, not raised | no, it raises | yes | yes |
| Lookup with the URI's port (or the scheme's default port) | no | no | yes |
| Lookup off the event loop | yes | no | no |
| Connection pinned to the checked addresses, so a second lookup cannot answer differently | no | no | yes, in the curl_cffi tier (`CURLOPT_RESOLVE`) |
| Redirects | not followed (`allow_redirects=False`), a 3xx answers `DOWNLOAD_FAILED` | followed by aiohttp's default (up to 10) after the first check only, so no hop is checked | followed by hand in the curl_cffi tier, each `Location` resolved against the hop that returned it, checked and pinned, at most 10 hops |
| `file://` jail by real path | yes | yes | no `file` |

The library's guard is the union of these rules, so no service loses a refusal it has today:

- `FetchPolicy`, a frozen dataclass: `allowed_hosts` (a tuple, may be empty), `file_root` (an absolute path or none) and `max_redirect_hops` (0 means redirects are not followed). `MAX_REDIRECT_HOPS = 10`, ascend-web-hunter's value today and aiohttp's default, is the code default of the setting `FETCH_MAX_REDIRECT_HOPS` that gives `max_redirect_hops` its value in every service (owner rule 98 of 2026-10-08, D6 and D26: `10` in ascend-audio-scribe and ascend-web-hunter, `0` in ascend-ocr). ascend-ocr and ascend-audio-scribe build the policy with `McpFetchSettings.fetch_policy()` (D6). ascend-web-hunter builds it with no file root, with `max_redirect_hops` from its own `FETCH_MAX_REDIRECT_HOPS` and with `allowed_hosts` from its own setting `ALLOWED_PRIVATE_HOSTS`, read with the library's `CsvTuple` type, the same name and parsing as `McpFetchSettings` without that mixin's file root and timeout, and empty by default (owner answer 67.3 of 2026-10-04).
- `check_fetch_uri(uri, policy)` is async and answers a `FetchTarget`: for HTTP the URL, the host, the port and the checked addresses, and for `file://` the resolved local path inside the jail. It refuses with the library exception `UnsafeUriError` and a detail that names no internal path, no user info and no resolved address:
  - every scheme other than `http`, `https` and `file` (bare paths, `ftp://`, `data:`, Windows drive paths),
  - a URI that does not parse, or whose port is not a valid port number,
  - an HTTP URI with user info in it, or with no host name,
  - an HTTP host that is not on `allowed_hosts` and whose lookup fails, answers no address, answers a value that is not an IP address, or answers any address that is private, loopback, link-local, multicast, reserved or unspecified. The lookup uses the URI's port, or 80 and 443 by scheme, and runs without blocking the event loop. Every answered address is checked,
  - a `file://` URI when `file_root` is unset, and a `file://` path whose real path (symbolic links resolved) is outside the real path of `file_root`.
- Address pinning (ascend-web-hunter's ADR-012 rule, now in the library): the connection goes only to the addresses `check_fetch_uri` checked, never to the answer of a second lookup. So a name that answers a public address to the check and a private one to the connection (DNS rebinding) cannot reach the private address. A host that is an IP literal needs no pin. A host on `allowed_hosts` is not pinned and resolves as today. ascend-web-hunter's curl_cffi hop builds its `CURLOPT_RESOLVE` entries from the target, as `PinnedHost.curl_resolve_entries` does today. The two aiohttp services use `PinnedResolver` of `uri_guard_aiohttp.py`: an aiohttp resolver that answers a pinned host with its checked addresses only, set for the current hop through a context variable, installed once on the service's `TCPConnector` with `use_dns_cache=False`, so no cached answer goes around it.
- Redirects (owner answer 63.1): `follow_guarded_redirects(target, policy, send_hop)` is the one redirect loop. `send_hop` is the service's transport function: it sends one request to the target with automatic redirects off, connected to the target's pinned addresses, and returns the answer with its status and its `Location` header. On 301, 302, 303, 307 or 308 with a `Location`, the loop resolves the `Location` against the URL of the hop that returned it (RFC 9110 section 10.2.2), runs `check_fetch_uri` on the result with the same policy, where only `http` and `https` are accepted, so a redirect never reaches a `file://` path, and sends the next hop pinned to the new answer. A hop the guard refuses raises `UnsafeUriError`, and no request is sent to it. A hop to a host on `allowed_hosts` passes, as a first request to it does. When `max_redirect_hops` hops are used up, or when it is 0, the loop hands the last answer back unchanged, so each service treats it as it treats any answer that is not 200 today. `uri_guard_aiohttp.guarded_get(session, uri, policy)` is the loop with an aiohttp `send_hop`, used by ascend-ocr and ascend-audio-scribe.
- What each service gains:
  - ascend-ocr: `max_redirect_hops` 0, so a 3xx answer stays `DOWNLOAD_FAILED`, as today. It gains address pinning, the refusal of a lookup with no address or with an answer that is not an IP address, the port check and the lookup with the URI's port.
  - ascend-audio-scribe (owner answer 63.1): `max_redirect_hops` 10. `_fetch_http_streaming` calls `guarded_get` in place of `session.get(uri)`, so a public URL that redirects to a private address is refused before the private address gets any request. It gains the redirect check, user info refusal, the lookup off the event loop, address pinning and the port check.
  - ascend-web-hunter (owner answer 63.2): `max_redirect_hops` 10. `is_safe_external_url`, `pin_safe_host` and their helpers leave `url_validator.py`. The REST endpoints and MCP tools that check a URL today (three places in `src/api/rest/rest_endpoints.py`, four in `src/api/mcp/mcp_server.py`) call `check_fetch_uri`, and `fetch_with_curl_cffi` uses `follow_guarded_redirects` with a curl_cffi `send_hop` that sets `CURLOPT_RESOLVE` from the target. `URLValidator` and the `url_validator` singleton apply the ad blocklist, not the address rule, and stay in `url_validator.py`. ascend-web-hunter gains user info refusal and the lookup off the event loop. It also reads `ALLOWED_PRIVATE_HOSTS`, empty by default, and no production file sets it (owner answer 67.3 of 2026-10-04): the guard's own allow list is the only way its end-to-end suite reaches the local fake site of `add-web-search-scraping-e2e` (its D12), through the value `e2e-fake-site` that only the start command of a sweep sets, in its own shell, never a file or value of the service configuration (owner decision 90 of 2026-10-08, D23), so no test-only exception enters the guard's code. A test proves the production settings allow nothing (tasks 4.8 and 4.14).

## Risks / Trade-offs

- [Four services change their error, readiness and MCP refusal contracts at once] → Each migration starts with tests that pin today's success behaviour, the new error behaviour is asserted per code, and the services move one at a time. The only in-repo consumer of an error body is `AscendOcrClient`, which reads only `code`.
- [Dependency confusion: the package name is free on PyPI and is not registered (owner answer of 2026-10-03)] → Install order everywhere (library first from its folder), so pip finds the pinned version installed and never asks an index. A person who runs a service's install before the library's could still pull a foreign package of that name. Every service README and `AGENTS.md` puts the library install first, and `python -m pip show ascend-python-common` naming the folder as its location is part of each service's install check (tasks 2.2, 3.2, 4.2, 5.2).
- [A library change breaks a service that CI does not rebuild] → `ci.yaml`'s path filter runs all four Python services and the library job whenever `libs/ascend-python-common/**` changes.
- [mypy strict and the wider ruff set on ascend-ocr and the removed ignores on three services produce many findings] → Each is fixed in code in that service's group, in a commit separate from the behaviour change, so review sees formatting and typing apart from behaviour.
- [`filterwarnings = ["error"]` turns third-party deprecation warnings into failures in three services] → A narrow ignore naming the third-party module is allowed only when the library has no fix, as ascend-ocr's rule says.
- [The always-on tracer provider adds work to every request when `OTEL_EXPORTER_OTLP_ENDPOINT` is unset] → Unsampled spans are non-recording, the cost is generating ids and context propagation. Measured in task 1.6 against the sample app before and after, and reported.
- [Rate limits that sit below the agent's peak would refuse platform traffic] → The limits are flood protection set well above the agent's load (owner answer 60.4), each is a setting, `ascend_service_errors_total{code="rate_limited"}` shows any refusal, and a deployment that needs other values sets them in the service's environment (the load test of task 7.2 was removed by owner decision 91.3 of 2026-10-08).
- [Several containers of one service share one caller budget only through Redis (owner decision 87 of 2026-10-08)] → ascend-web-hunter keeps its limiter windows in its existing Redis. When Redis cannot be reached, slowapi's in-memory fallback limits each container on its own and logs it at WARNING, so traffic is never refused because of Redis. The three services without Redis keep in-memory windows until they run as several containers (D9).
- [FastMCP keeps each MCP session in the memory of the container that created it by default (owner decision 87 of 2026-10-08)] → Settled by answer 94.2 of 2026-10-08: every service runs FastMCP in stateless HTTP mode (D12, task 1.19), so any container answers any MCP request. The cost is that no tool can push a message to the client between requests, which no tool does today.
- [One shared URI guard changes what three services accept] → Each service gains only the refusals another copy already had, plus the redirect check of owner answer 63.1 (D21 table). ascend-audio-scribe now refuses user info in an HTTP URI and a redirect to a private address. ascend-web-hunter now refuses a URL with user info, such as `https://user:pass@site.example/`, which it reads today. ascend-ocr now refuses a name whose lookup answers no address. ascend-ocr and ascend-audio-scribe keep their codes. ascend-web-hunter keeps its 400 status and gains the code `unsafe_uri`.
- [Pinning in aiohttp depends on how its connector resolves names] → `PinnedResolver` is installed with `use_dns_cache=False`, and task 1.13 reads the installed aiohttp 3.13.5 source to confirm that every new connection asks the resolver, with a test that a second lookup answering a private address is never used.
- [Editing `ci.yaml` and `release.yaml`] → They are edited, not created. Nothing is pushed, so no run starts. The owner pushes when he chooses.
- [Option A keeps MCP and REST on one port] → No separate network exposure for MCP. The owner accepted this (answer 58 of 2026-10-03).
- [ascend-web-hunter's 428 and 409 change shape] → A caller that reads `status` as a word or `message` breaks. No ascend-agent code reads either REST body (D5), the MCP status objects do not change, and the Bruno requests and e2e specs that read them move to `code` and `detail` in task 4.11.

## Migration Plan

1. Library (group 1), green on its own gates.
2. ascend-memory, ascend-audio-scribe, ascend-web-hunter, ascend-ocr, in that order, each green and its container checked before the next.
