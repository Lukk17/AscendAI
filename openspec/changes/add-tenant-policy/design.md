# Design - add-tenant-policy

## Context

Provider and model are resolved per request in `ChatModelResolver`, which asks the `ModelAccessPolicy` port of `add-deployment-modules` before it builds a client and which `add-usage-metering-and-quotas` (build group 5, position 6, after this change) later extends to a tenant-aware `resolve(provider, tenantId)` with a Caffeine cache for BYOK clients. MCP tools reach the chat call through one `@Primary` `ToolCallbackProvider`, `apps/ascend-agent/src/main/java/com/lukk/ascend/ai/agent/config/mcp/FilteredToolCallbackProvider.java`, which `service/chat/ChatExecutor.java` injects today and which `StreamingChatExecutor`, the one chat executor of `add-chat-streaming-and-conversations` (answer 89.1), injects once that change lands. Its `getToolCallbacks()` reads `config/mcp/McpToolCallbackCache.java` (`getOrList(...)`), which caches the tools of the connected MCP clients for the whole deployment. Nothing in it knows the tenant. Neither resolution point consults any per-tenant policy, so provider choice and tool availability are effectively deployment-wide.

The changes that land before this one change the tool path:

- `add-agent-skills` adds `ChatToolset` (its D3), the one place that composes the tool list of a chat request and of a subagent run of `add-agent-subagents`: the filtered MCP callbacks plus the callbacks of every `AgentNativeTool` bean. Its fixed steps are 1 module filter (`add-deployment-modules` D10, through the `ModuleAccess` port), 2 tenant tool policy (the `TenantToolPolicy` port of `add-agent-skills` D16, whose default allows every tool and which this change implements), 3 per-request narrowing list (`add-openclaw-plugin-host`), 4 self-change gate (`add-self-improvement`), 5 approval gate (`add-action-approvals` D4) and 6 always and deferred (`add-mcp-tool-servers`). It also adds the skill catalog with global skills and tenant skills, and the `GlobalSkillPolicy` port (D16) whose default offers every global skill.
- `add-mcp-tool-servers` names every MCP tool `<prefix>_<name>` and keeps its server id on each callback (its D4).
- `add-action-approvals` reads the mode of a tool, `allowed`, `requires_approval` or `denied`, through its `ToolModeResolver` interface (its D1), whose default, registered with `@ConditionalOnMissingBean`, reads the deployment default `app.policy.default.approval-required-tools` only.
- `add-deployment-modules` asks the `ModuleAccess` port for a tenant's granted modules (its D9). Its default bean `AllActiveModuleAccess` grants every active module until this change.

Two concrete risks follow. First, the sovereignty claim is unenforceable: a user on a local-only customer can still route a prompt (with its RAG context) to a cloud provider. Second, MCP tools are an exfiltration channel: a poisoned RAG document can steer the model to call the web-search tool with tenant data in the query, sending private content to an external engine inside one turn.

## Goals / Non-Goals

**Goals:**

- Per-tenant enforcement of which providers and models may be used, at the existing resolution point, before any provider call.
- Per-tenant enforcement of which tools, MCP and agent native, the model may call, by filtering the tool set it is given, and of which of those need an approval first.
- Per-tenant module grants and a per-tenant skill allow-list.
- A tenant-admin policy API that can only narrow within a deployment default, never widen.
- Make local-only ("data never leaves our infrastructure") a hard, testable guarantee.

**Non-Goals:**

- Content-inspection of tool arguments (a heuristic arms race); allow-listing the tool set is the robust control and the one we ship.
- Quota / rate enforcement (owned by `add-usage-metering-and-quotas`).
- Prompt-level DLP or output filtering.
- Any UI.

## Decisions

### D1 - Enforce provider/model policy through `ModelAccessPolicy`, before the client is built

The provider/model gate is this change's implementation of the `ModelAccessPolicy` port of `add-deployment-modules` (its D21 "Company extension ports", ruling 13.1 of the dependency fix of 2026-10-05). Its default `ConfiguredModelAccessPolicy` allows every provider the deployment has enabled, and `ChatModelResolver` asks the port before it builds a client, so this change edits no class of an earlier change (the earlier plan to edit `ChatModelResolver` directly is replaced by the ruling). The implementation reads the tenant from `TenantContext.currentTenantId()` of `add-keycloak-login` and checks the requested `(provider, model)` against the tenant's allow-list through `TenantPolicyService`. `add-usage-metering-and-quotas`, which lands after this change, extends `ChatModelResolver` with tenant-keyed BYOK clients behind the same port. A violation throws a policy exception surfaced as HTTP 403 before any client is built or any token is spent. The body is the RFC 7807 problem detail that `upgrade-spring-boot-4` defines for every agent error (its D19, owner decision of 2026-10-02): `application/problem+json` with `type`, `title`, `status`, `detail` (naming the denied provider or model), `instance` and a top-level `code`, `provider_denied` or `model_denied`, two values this change adds to its `ApiErrorCode` enum (types `https://ascend.ai/errors/provider-denied` and `https://ascend.ai/errors/model-denied`). This change adds no error body of its own. Asking the port at resolution (not at the controller) covers chat, embedding, memory-extraction, and compaction paths uniformly, since they all resolve through the same component.

A coding run of `add-coding-agent-delegation` does not resolve through `ChatModelResolver`, because OpenCode calls its provider itself. That change asks the same `ModelAccessPolicy` port before a coding run starts (its D10, no coding-specific port), so this one implementation also checks coding runs, with `opencode-go` and `opencode-zen` as provider names. There is no coding agent choice to check, because OpenCode is the only one.

### D2 - Enforce tool policy by filtering the tool set given to the model

This change registers its implementation of the `TenantToolPolicy` port of `add-agent-skills` (its D16), replacing the default `ConfiguredTenantToolPolicy`, which denies only the tools of `app.tool-policy.denied-tools` (empty by default, ruling 13.2). The implementation is a thin adapter of the one decision service of D9: a tool is allowed when its mode is not `denied`. A tool on `app.tool-policy.denied-tools` stays denied for every tenant, because that setting is the deployment part of the one deny list (D9), the same narrow-only rule as D3, so an owner who set the list before this change landed keeps it. `ChatToolset` applies the port in step 2 to every tool it composes, the MCP callbacks that `FilteredToolCallbackProvider` returns from the deployment-wide `McpToolCallbackCache` included, so neither class is edited. The cache stays tenant-agnostic, because discovery does not depend on the tenant, and the port is asked on every composition, so a policy update or a tool change both take effect on the next request. The implementation reads the effective tool allow-list of the tenant in `TenantContext.currentTenantId()` of `add-keycloak-login` through `TenantPolicyService`, and a call with no resolved tenant allows no tool (fail closed, matching `add-tenant-isolation`). The allow-list names tools by the prefixed name `<prefix>_<name>` that `add-mcp-tool-servers` produces (its D4), so the names an admin sets are the names the model sees. A disallowed tool is simply absent from the tools the model can see. This is strictly stronger than intercepting tool calls after the fact: a tool the model was never given cannot be invoked, so the RAG-injection exfiltration path for egress tools is closed by construction, not by detection.

The same allow-list governs every agent native tool, because the port is applied where the chat tool list is composed: `ChatToolset` of `add-agent-skills` (its D3). Before it applies the allow-list, the same pass drops every tool whose module is not effective for the tenant through `ModuleAccess` (D6), which is step 1 of `ChatToolset`, and the allow-list is step 2. `ChatToolset` runs once per chat request and once per subagent run, so `Task`, `TaskOutput`, `subagent_definition_write`, the sandbox tools `shell`, `file_read` and `file_write` and every other agent native tool are governed by the same list as the MCP tools. `skill_search` has no entry of its own: it is offered when `Skill` or the `Task` tool of `add-agent-subagents` is offered. A policy denial of an agent native tool, a skill tool included, records the same audit event through `AuditEventPort` as any other restricted request.

Entries of the allow-list:

- A tool name. It allows that one tool.
- `server:<id>`. It allows every exposed tool of the MCP server entry with that id (`add-mcp-tool-servers`), matched on the server id each callback keeps.
- `integrations:own`. It allows every tool of the tenant's own integrations of `add-self-built-integrations`, the tools of its tenant-scoped server entries, so a tenant decides once whether self-built tools may be offered at all. The per tool mode of such a tool still comes from its review.

The one deny list of D9 sits next to the allow-list. A tool on it is `denied` whatever the allow-list says, so a deny entry removes one tool from an allowed server.

Work that uses the allow-list outside one chat request:

- Subagent definitions of `add-agent-subagents`, agent-written or saved by the owner, are validated against the tenant's allow-list at write time (a REST save that names a tool outside it answers 403 with `code` `tool_not_allowed` of that change, owner answer 76.7 of 2026-10-08), and a run re-checks it at start in `ToolPermission`, both through the `TenantToolPolicy` port, so a policy narrowed after a definition was written still binds the run.
- A tenant policy that removes a tool does not change the stored jobs of `add-scheduled-tasks`. The tool is dropped at the next firing, because a firing's run composes its tools through `ChatToolset` like every run.

### D3 - Deployment default policy, tenant may only narrow

A deployment-level default policy (`app.policy.default.*`) sets the maximum allowed providers and tools. A tenant's stored policy can only be a subset of the default; an update attempting to allow a provider or tool outside the default is rejected. This lets a security-forward operator ship local-only, no-egress-tools defaults and have tenants opt into more only within bounds the operator permits. A tenant with no stored policy inherits the default, except the tools D8 marks off for a new tenant, which stay off until a tenant `ADMIN` stores a policy that lists them, and the skill allow-list, which starts empty (D7).

The narrow-only rule covers every list of the policy:

- Tool allow-list: a tenant entry is inside the default when the default holds the same entry, or, for one tool name, when the default holds that tool or the `server:<id>` of its server. `integrations:own` is allowed for a tenant only when the default lists it.
- Approval-required list: the deployment default is `app.policy.default.approval-required-tools` (empty by default) plus the tools a registered `ApprovalDefaultsSource` of `add-action-approvals` marks. The effective list is the union of the default and the tenant's own list, so a tenant can add tools and can never remove one the default lists (D5).
- Deny list: a tenant's deny list only removes tools and global skills, so any entry is inside the default. The effective deny list is the union of the deployment part and the tenant's own entries (D9).
- Module grants: the deployment default is `app.policy.default.modules` (default: every active switchable module). An update naming an inactive or unknown module, an always-on module, or a set not closed under `requires`, is refused with 400 (D6).

### D4 - One policy store, and a cache that is safe with several agent instances

Policy is a `tenant_policy` row per tenant (provider allow-list, per-provider model allow-list, tool allow-list, approval-required list, the one deny list of D9, module grants and skill allow-list, JSONB columns), a Spring Data JDBC aggregate. The deployment default `app.policy.default.*` is read at startup into the same `TenantPolicy` shape, so a stored row and the default are one model in one store: the table for a tenant that has a row, the default as the fallback for one that has none (owner answer 89.8 of 2026-10-08).

`TenantPolicyService` reads the effective policy through a Caffeine cache keyed by tenant, so the resolution path stays a cache read, not a database hit per request. Several agent instances run at once (owner answer 87, rule R1), and a stale policy is a defect, so the cache follows the one cache mechanism of the platform: every entry has a bounded time to live (`app.policy.cache.ttl`, environment variable `APP_POLICY_CACHE_TTL`, default 5 minutes) and the cache a bounded size (`app.policy.cache.max-size`, environment variable `APP_POLICY_CACHE_MAXSIZE`, default 1000 entries, owner answer 98.4 of 2026-10-08), and an update reaches every instance through shared invalidation. The update writes the row and, in the same transaction, calls `pg_notify('tenant_policy_changed', <tenantId>)`. Postgres delivers it only when the transaction commits. This change opens no `LISTEN` connection of its own: it registers a `PostgresNotificationHandler` for the channel `tenant_policy_changed` on the one `PostgresNotificationListener` of `add-keycloak-login` D20, which holds one listening connection per agent instance. The handler evicts that tenant's entry when the notice arrives, on every instance, the one that wrote included. Its `onReconnect()` clears the whole policy cache, because a notice sent while the connection was down is lost, and the time to live bounds any entry that is missed in another way. The payload is the tenant id only. The startup seed of tenant `default` below sends the same notice. This change adds the Caffeine entry to the version catalog when it is missing, and `add-usage-metering-and-quotas` later reuses the entry and the shape for its BYOK client cache.

The Flyway migration seeds the row of tenant `default`, the tenant the personal deployment runs as (`add-tenant-isolation`): its tool allow-list holds every tool D8 marks on for the personal deployment, so a personal deployment behaves as it did before the policy existed.

The global skills of tenant `default` are not seeded by the migration, because skills are files on disk and a migration cannot know which global skills exist when it runs (`add-agent-skills` D16). They are seeded at agent startup instead. After the first load of the global catalog at each startup, a seed step reads `SkillCatalog.globalSkillNames()` and adds to the skill allow-list of tenant `default` every name it has never added before. The row records the names the seed already added, in a JSONB column `seeded_global_skills`. A name is added only when it is not in that record, and it is then written to both lists in one transaction. So a global skill shipped later reaches tenant `default` at the next startup, and a name a tenant `ADMIN` removed from the skill allow-list stays removed, because it is still in the record. The seed touches only tenant `default` and never removes a name.

### D5 - A third tool mode, read through `ToolModeResolver`

The mode of a tool is `allowed`, `requires_approval` or `denied` (`add-action-approvals` D1). This change owns all three:

- `denied`: the tool's module is not effective for the tenant, the tool is not on the allow-list, or it is on the deny list.
- `requires_approval`: the tool is on the allow-list and on the effective approval-required list (D3). It is given to the model, and its calls go through the approval gate of `add-action-approvals`, which wraps it in step 5 of `ChatToolset`.
- `allowed`: every other tool on the allow-list.

This change registers its implementation of the `ToolModeResolver` port of `add-action-approvals`, backed by `TenantPolicyService`, so the gate reads the mode through it, and that change's default `ConfigToolModeResolver`, registered with `@ConditionalOnMissingBean`, is then not created. No class of `add-action-approvals` is edited. The key `app.policy.default.approval-required-tools` keeps its name, so the configuration of a deployment does not change when this change lands.

### D6 - Module grants per tenant through `ModuleAccess`

Module grants cover only the switchable modules (owner decision of 2026-10-03): `ocr`, `audio`, `web-search`, `web-download`, `weather`, `obsidian`, `channels`, `openclaw-apps`, `coding`, `self-built-integrations`, `subagents`, `skills`, `self-improvement` and `scheduler`. The always-on parts, `core-chat`, `observability` (monitoring), `rag`, `memory`, `sandbox` and the prerequisites, are never granted, never listed in `app.policy.default.modules` and never denied to a tenant: `ModuleAccess` reports them for every tenant, so their routes never answer `module_denied` and their tools never drop out in step 1 of `ChatToolset`. A policy update or a default that names one of them is refused with 400 and code `validation`. A tenant can still turn off single tools of an always-on module as tools, for example the shell tools `shell`, `file_read` and `file_write` of `sandbox`, through the tool allow-list and the deny list (D2, D8).

The policy holds a list of granted module names, narrowed against `app.policy.default.modules` (D3). This change registers its implementation of the `ModuleAccess` port of `add-deployment-modules` (its D9), backed by `TenantPolicyService`, replacing the default `AllActiveModuleAccess`: `grantedModules(TenantId)` returns the tenant's effective grants. `ModuleState.effectiveFor(tenant)` of that change still computes `active ∩ granted ∩ deployment default`, so no implementation can widen. A grant set must be closed under `requires`, and an update that breaks it is refused with 400.

A switchable module the tenant lacks hides its tools in the same pass as the tool policy (D2), and its routes answer 403 with the code `module_denied` that `add-deployment-modules` adds (its D8). A per tenant switch of a feature, such as `self-improvement`, is this module grant, not a flag of its own.

### D7 - A skill allow-list of global skill names

The policy holds a skill allow-list of global skill names (`add-agent-skills` D16). A global skill is offered to a tenant only when its name is on the list. A new tenant starts with an empty list, and the seed of tenant `default` holds every global skill (D4). A tenant's own skills are always offered to that tenant when `Skill` is allowed, because the tenant wrote them. The list is applied through this change's implementation of the `GlobalSkillPolicy` port of `add-agent-skills` (its D16), a thin adapter of the one decision service of D9, replacing the default `ConfiguredGlobalSkillPolicy` (which hides only the skills of `app.tool-policy.denied-global-skills`, a setting that is now the deployment part of the one deny list, so a skill it names stays hidden), when `add-agent-skills` assembles the per-request catalog, so `skill_search` never returns a skill the policy hides, and a policy change reaches the next request with no reload and no reindex.

### D9 - One decision service with one deny list behind the five plug-in points (owner answer 89.8 of 2026-10-08)

`TenantPolicyService` is the one service that decides every tenant policy question: whether a provider and model may be used (D1), the mode of a tool, `allowed`, `requires_approval` or `denied` (D2 and D5), the effective module grants (D6), and whether a global skill is offered (D7). It reads the one policy store of D4 and applies one deny list.

The five plug-in points of the earlier changes stay, as owner rule R2 requires, because a deployment without this change keeps their defaults and behaves as before: `ModelAccessPolicy` and `ModuleAccess` of `add-deployment-modules`, `TenantToolPolicy` and `GlobalSkillPolicy` of `add-agent-skills`, and `ToolModeResolver` of `add-action-approvals`. The implementation this change registers on each is a thin adapter: it turns the port's call into one question to `TenantPolicyService` and holds no rule, no list, no setting and no cache of its own. `TenantToolPolicy` answers "allowed" exactly when `ToolModeResolver` answers a mode other than `denied`, because both ask the same method. So two ports can never disagree about one tool, a fix to a rule is made in one place, and a test asserts that each adapter depends on nothing but `TenantPolicyService` and `TenantContext`.

The one deny list holds tool names and global skill entries written `skill:<name>`. Its deployment part is read from the two settings that `add-agent-skills` already ships, `app.tool-policy.denied-tools` (each value a tool name) and `app.tool-policy.denied-global-skills` (each value read as `skill:<name>`), so a deployment that set them before this change keeps them, and no third deny setting is added. A tenant row holds the tenant's own entries in the same form. The effective deny list is the union of both parts, and an entry on it is denied whatever an allow-list says. This replaces the earlier text in which the `TenantToolPolicy` and `GlobalSkillPolicy` implementations each honoured their own deployment setting next to a separate tenant deny list of tool names.

## Risks / Trade-offs

- [A future tool that is both useful and egress-capable] → the allow-list is per tool, so a new egress tool ships default-off and a tenant opts in explicitly; no blanket on/off. The new tools of the changes that land around this one are listed with their state for a new tenant in D8.
- [`server:<id>` allows a tool the tenant did not expect when the server adds one] → the deny list removes single tools from an allowed server, and a tenant that wants a fixed set lists tool names instead.
- [A policy narrowed after a subagent definition was written] → the run re-checks the allow-list at start (D2), so the definition cannot widen the run.
- [Model selection bypass via a raw base-URL provider] → the gate is on the resolved provider key; any request resolves to one of the known provider keys, and an unknown provider already fails resolution.
- [Policy cache staleness after an update] → the update sends a Postgres `NOTIFY` that every agent instance answers by evicting the tenant's entry, an instance that lost its listening connection clears its whole cache when it is back, and the bounded time to live caps any miss (D4), so the next request on any instance sees the new policy with no restart.
- [Over-blocking breaks a legitimate flow] → policy-denied requests record an event through `AuditEventPort` and return a clear error naming the denied provider/model/tool, so an admin can see and adjust.
