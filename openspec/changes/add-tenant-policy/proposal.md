## Why

AscendAI's sovereignty pitch is "your data stays on your infrastructure - pick a local model and nothing leaves your GPU." Today that is a convention, not a control. Provider and model are chosen per request by whoever sends the prompt (`provider` / `model` form fields resolved in `ChatModelResolver`), so any user can route a prompt - and the RAG context stapled to it - to OpenAI or Anthropic even if the customer's policy is local-only. `add-usage-metering-and-quotas`, which lands after this change, adds per-tenant BYOK keys but does not constrain which providers a tenant may use either.

The same gap exists for tools. MCP tools (web search, weather, and future tools) are exposed to the model globally. A poisoned RAG document can instruct the model to call the web-search tool with sensitive tenant content embedded in the query string - a prompt-injection exfiltration channel that sends private data to an external search engine, entirely within a single chat turn. Nothing lets a tenant say "my users may not use web search" or "only local providers."

This change adds a per-tenant policy surface that makes both enforceable: which providers and models a tenant's requests may use, and which MCP tools its model may call. Allow-listing tools is also the robust mitigation for the injection-exfiltration channel - a tool the model is never given cannot be called.

The changes that land before this one add more to govern. `add-agent-skills` adds agent native tools next to the MCP tools, all composed in one place, `ChatToolset`, and global skills. `add-agent-subagents`, `add-agent-sandbox` and `add-agent-soul` add tools that act inside the system. `add-action-approvals` adds a third tool mode between allowed and denied. `add-deployment-modules` adds modules that a tenant can be granted or not. `add-mcp-tool-servers` gives every MCP tool a server prefix and adds outside servers. The policy of this change covers all of them in one place.

## What Changes

- **Per-tenant provider and model allow-list**: a policy per tenant naming the permitted providers (subset of `lmstudio`, `openai`, `gemini`, `anthropic`, `minimax`, plus `opencode-go` and `opencode-zen` for the coding runs of `add-coding-agent-delegation`) and, optionally, permitted models per provider. A chat or embedding request selecting a provider or model outside the tenant's allow-list SHALL be rejected with a clear error before any provider call. This change registers its implementation of the `ModelAccessPolicy` port of `add-deployment-modules` (its D21 "Company extension ports", ruling 13.1 of the dependency fix of 2026-10-05), replacing the default `ConfiguredModelAccessPolicy` that allows every provider the deployment has enabled. `ChatModelResolver` and the coding runs of `add-coding-agent-delegation` already ask that port, so no class of an earlier change is edited. The tenant comes from `TenantContext.currentTenantId()` of `add-keycloak-login`. A local-only policy (`lmstudio` alone) makes "data never leaves our infrastructure" enforceable.
- **Per-tenant tool allow-list**: a policy naming the tools a tenant's model may call. This change registers its implementation of the `TenantToolPolicy` port of `add-agent-skills` (its D16), replacing the default `ConfiguredTenantToolPolicy` that denies only the tools of `app.tool-policy.denied-tools`, and `ChatToolset` of `add-agent-skills` applies the port in step 2 to every tool, MCP and agent native, of a chat request or a subagent run, so a disallowed tool is never exposed to the model and cannot be invoked - closing the RAG-injection exfiltration channel for egress tools like web search. Tool names are the prefixed names of `add-mcp-tool-servers`. An entry `server:<id>` allows every exposed tool of that server, the entry `integrations:own` allows every tool of the tenant's own integrations (`add-self-built-integrations`), and a deny list of tool names removes tools from an allowed server.
- **A third tool mode** (`add-action-approvals`): next to the allow-list, a tenant policy holds an approval-required list. A tool on both is `requires_approval`: it is given to the model and its calls go through the approval gate of `add-action-approvals`. A tool not on the allow-list stays `denied`. The deployment default `app.policy.default.approval-required-tools` stays as `add-action-approvals` defines it, and this change registers its implementation of the `ToolModeResolver` port of that change (its D1), replacing the default that reads the deployment configuration only.
- **Module grants per tenant** (`add-deployment-modules`): the policy gains a list of module names, with the deployment default `app.policy.default.modules` (every active switchable module). A grant covers only the switchable modules (owner decision of 2026-10-03): `ocr`, `audio`, `web-search`, `web-download`, `weather`, `obsidian`, `channels`, `openclaw-apps`, `coding`, `self-built-integrations`, `subagents`, `skills`, `self-improvement` and `scheduler`. The always-on parts, `core-chat`, `observability` (monitoring), `rag`, `memory`, `sandbox` and the prerequisites, are never in a grant or in the default and cannot be denied to a tenant. The shell tools of `sandbox` (`shell`, `file_read`, `file_write`) can still be turned off per tenant as tools, through the tool allow-list and the deny list. This change registers its implementation of the `ModuleAccess` port of `add-deployment-modules` (its D9), replacing the default `AllActiveModuleAccess`, so a switchable module the tenant lacks hides its tools and answers its routes with 403 `module_denied`.
- **Skill allow-list** (`add-agent-skills`): the policy names the global skills a tenant is offered, through this change's implementation of the `GlobalSkillPolicy` port of `add-agent-skills` (its D16), replacing the default `ConfiguredGlobalSkillPolicy` that hides only the skills of `app.tool-policy.denied-global-skills`. A tenant's own skills are always offered when `Skill` is allowed.
- **New tools ship off for a new tenant**: the tools of the changes that land around this one are governed by the allow-list, and each one's starting state for a new tenant and its place in the default policy of the personal deployment are listed in one table (design D8). The Flyway migration seeds the tools of tenant `default`, the tenant the personal deployment runs as. Its global skills are seeded at agent startup from `SkillCatalog.globalSkillNames()` of `add-agent-skills` (its D16), and the seed records the names it already added, so a newly shipped global skill reaches tenant `default` and a skill an `ADMIN` removed stays removed.
- **Policy management API** under `/api/v1/admin/policy`, restricted to tenant `ADMIN`, scoped to the caller's tenant: get and update the tenant's provider/model, tool, approval-required, deny, module and skill lists. A deployment-level default policy applies to tenants with no explicit policy; a tenant admin may only narrow within the deployment default, never widen beyond it.
- **Default-deny option**: the deployment default policy is configurable; a security-forward deployment can default to local-only providers and no egress tools, with tenants opting in.
- **Its own parts of the deployment**: `add-deployment-modules` keeps tenant policy out of the always-on core, so this change adds its own parts to the deployment when it lands: the `tenant_policy` table, the policy beans that replace the port defaults, and the `app.policy.default.*` configuration. A deployment without this change keeps the five defaults of the ports `ModelAccessPolicy`, `TenantToolPolicy`, `ToolModeResolver`, `ModuleAccess` and `GlobalSkillPolicy` and behaves as before.
- **One decision service, one deny list, one store** (owner answer 89.8 of 2026-10-08): `TenantPolicyService` is the one service that decides every policy question, the `tenant_policy` table with the deployment default `app.policy.default.*` as its fallback is the one policy store, and the policy has one deny list. The five ports above stay as the places the policy plugs into (owner rule R2), and the implementation this change registers on each is a thin adapter that asks `TenantPolicyService` and holds no rule of its own. The deny list holds tool names and global skill entries `skill:<name>`, and its deployment part is read from the two existing settings `app.tool-policy.denied-tools` and `app.tool-policy.denied-global-skills` of `add-agent-skills`, so no third deny setting exists.
- **Audit events**: policy changes and policy-denied requests are recorded through `AuditEventPort` of `add-deployment-modules`, whose default writes one structured log line. `add-audit-and-gdpr-compliance` lands later and registers its `AuditRecorder` backed implementation, which stores them as `ADMIN_OPERATION` rows.

## Capabilities

### New Capabilities

- `provider-model-policy`: per-tenant allow-list of providers and models enforced at resolution; requests outside the allow-list rejected before any provider call; deployment default with narrow-only tenant overrides.
- `tool-policy`: per-tenant tool allow-list for MCP and agent native tools enforced at tool-callback assembly and in `ChatToolset`, so disallowed tools are never exposed to the model. It also covers `server:<id>` and `integrations:own` entries and the deny list, the `requires_approval` mode, module grants with 403 `module_denied`, the skill allow-list, new tools off for a new tenant and the seed of tenant `default`, the ADMIN policy API, and the injection-exfiltration mitigation this provides for egress tools.

### Modified Capabilities

(none as spec deltas - provider resolution (`ChatModelResolver` with its `ModelAccessPolicy` port, which `add-usage-metering-and-quotas` later makes tenant-aware for BYOK keys) and MCP tool wiring are defined in sibling/existing code, not in an archived `openspec/specs/` capability this change can modify. The enforcement requirements live in this change's two new capabilities; the resolver and tool-assembly hook points are named in the tasks for coordination.)
