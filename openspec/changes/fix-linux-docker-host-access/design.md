## Context

See proposal.md, Why. The stack runs today on Docker Desktop for Windows. Docker Desktop resolves `host.docker.internal` in every container, accepts Windows host paths in volume sources and creates `/var/run/docker.sock` as `root:root` with mode 660. Docker Engine for Linux does none of this: the name resolves only through the special value `host-gateway` (`extra_hosts` in compose, `--add-host` on `docker run`), a Windows path is not a host path, and the socket belongs to the group `docker`.

Docker facts used here, checked through Context7 (`/docker/docs`) on 2026-10-08:

- `content/manuals/compose/how-tos/networking.md`: `extra_hosts` with `host-gateway` maps a name to the host. On Linux it resolves to the host's address on the default bridge network. Docker Desktop provides `host.docker.internal` by itself.
- `data/cli/engine/docker_container_run.yaml`: `--add-host` supports the special value `host-gateway`.
- `content/manuals/engine/release-notes/20.10.md`, release 20.10.0: "Support host.docker.internal in dockerd on Linux" (moby/moby#40007). So `host-gateway` needs Docker Engine 20.10 or newer.
- `content/manuals/engine/install/linux-postinstall.md`: the daemon creates its Unix socket accessible by members of the `docker` group.
- `content/reference/compose-file/services.md`: `group_add` adds the container user to further groups, by name or by number. A name is looked up inside the container, so the host's `docker` group is added by its number.

One consequence on Linux: a call through `host.docker.internal` arrives at the host's bridge address, not at `127.0.0.1`. A host service that listens on `127.0.0.1` only, or a port that a container publishes on `127.0.0.1` only, is not reached that way, and a host firewall can drop the call.

The rule (owner answer 81.3 of 2026-10-08, recorded for groups 3 to 5 in `close-agent-test-gaps` D8, and owner answer 83 of 2026-10-08 for the existing setup):

1. Container to container: the container name or the compose service name on the shared network.
2. Host to container: `127.0.0.1` and a published port.
3. Container to host: `host.docker.internal` only together with `extra_hosts: "host.docker.internal:host-gateway"` on that compose service, `--add-host=host.docker.internal:host-gateway` on a `docker run`, or `ExtraHosts` with the same value through the Docker Engine API. Needs Docker Engine 20.10 or newer.
4. Inside a container, `localhost` and `127.0.0.1` mean that container itself.
5. A `docker run` that calls no other service needs none of this.

### D10: Published host ports are settings (owner answer 100.6 of 2026-10-09)

Every host port a compose file publishes is a setting in the form `${<SERVICE>_HOST_PORT:-<today's port>}:<container port>`, so an operator moves a host port with one `.env` line when it clashes with another program, and the container port, which the other containers, healthchecks and scrape jobs name, stays fixed. The change that first owns a compose service in build groups 1 and 2 carries its port: `add-observability` (`PROMETHEUS_HOST_PORT`, `GRAFANA_HOST_PORT`, `AGENT_HOST_PORT`, `WEATHER_MCP_HOST_PORT`) and `add-ascend-python-common` (`MEMORY_HOST_PORT`, `AUDIO_SCRIBE_HOST_PORT`, `OCR_HOST_PORT`, `WEB_HUNTER_HOST_PORT`). This change carries the four services no other change of the two groups touches (section 10):

| Service | Compose file | Line | Setting | Default |
| --- | --- | --- | --- | --- |
| `docling-serve` | `compose.yaml` | `"${DOCLING_SERVE_HOST_PORT:-5001}:5001"` | `DOCLING_SERVE_HOST_PORT` | `5001` |
