## Why

The owner wants the assistant to find files on the web and hand them to him: electronics schematics, datasheets, PDFs, images and archives (owner request of 2026-10-02). Today ascend-web-hunter can search (`web_search`) and read a page as text (`web_read`), but it has no way to fetch a file as bytes, keep it, and give the owner a link. A binary file read through `web_read` is either refused by content validation or turned into garbage text, and the agent has nowhere to put the result. The fetch tiers, the stored sessions, the SSRF guard with connect-time pinning (ADR-012) and the human captcha help through NoVNC already exist, so a download feature should reuse them instead of starting a second fetch stack.

## What Changes

- A new MCP tool `web_download_file` and REST endpoint `POST /api/v2/web/downloads` in ascend-web-hunter. Input: `url`, optional `expected_type`, optional `file_name`, optional `profile`. The file is streamed to a temporary file with a hard size limit, never held in memory as a whole.
- The SSRF guard and connect-time pinning run on the first URL and on every redirect hop, through the library guard of `add-ascend-python-common` (`check_fetch_uri` and `follow_guarded_redirects`, owner answer 63.2) with a curl_cffi `send_hop`, the same one the read path uses, so both paths use one implementation.
- The content type is decided by sniffing the first bytes of the body against an allow list of file families (`pdf`, `image`, `archive`, `text`, `office`). The server's `Content-Type` header is only a hint. Executables, scripts, HTML pages and macro-enabled office files are always refused.
- Reuse of the tier ladder when a plain request is blocked: a stored session is replayed (including one imported by `add-web-session-import`), then a browser tier of `enhance-web-search-tier-ladder` passes the wall and the download is retried with the fresh session, then a browser-native download, and as the last step the same NoVNC human help `web_read` returns today.
- Storage in object storage through the S3 client that `enhance-web-search-crawl-at-scale` adds to ascend-web-hunter, never a second client. Keys live under `tenant/<tenantId>/downloads/<sha256>/`, with a metadata record holding the source URL (no query string, no fragment, no user info), the time, the size and the SHA-256.
- Deduplication by SHA-256 inside one tenant, never across tenants.
- A presigned download link that lasts at most 24 hours, plus the companion operations to get a fresh link, list downloads and delete one: MCP tools `web_download_get`, `web_download_list` and `web_download_delete`, and the matching REST endpoints.
- Downloaded files are temporary: each one is deleted automatically 24 hours after its last download, and downloading the same file again starts the 24 hours again (owner decision of 2026-10-02, answer 47.2). The deletion runs inside ascend-web-hunter itself, as a background sweep every 15 minutes over every tenant that has downloads (owner instruction of 2026-10-04: no agent system task). With several ascend-web-hunter instances one Redis lock lets one instance sweep per round. There is no endpoint that forces the deletion (owner decision 90 of 2026-10-08).
- When the assistant needs a file for longer, it keeps it: the MCP tool `web_download_keep` (REST `POST /api/v2/web/downloads/{download_id}/keep`) copies the file server side to the persistent folder `tenant/<tenantId>/files/` in object storage, where it stays until it is deleted, with `web_download_kept_get`, `web_download_kept_list` and `web_download_kept_delete` and their REST twins under `/api/v2/web/downloads/kept`. The other persistent place is the knowledge base, through `knowledge_add_download` of the agent change `add-download-ingestion`. Design D7 lists the three locations.
- An optional malware scan through ClamAV in its own container. No virus scanner runs by default anywhere (owner decision 51.2 of 2026-10-03): the scan mode defaults to `off` and ClamAV stays off in every preset and every deployment, production included, until an operator turns it on. ClamAV is the companion `clamav` of the module `web-download` in the development stack only. The standalone web-search bundle has no compose profiles and leaves it out, which its README lists as an intended difference.
- The module switch is `ASCEND_MODULES`, the list of `COMPOSE_PROFILES` in `.env`: ascend-web-hunter reads it and registers the download tools and routes only when `web-download` is in it. This change passes `ASCEND_MODULES=${COMPOSE_PROFILES:-}` to ascend-web-hunter in the development compose file itself, the line `add-deployment-modules` D2 asks every change that needs the list to add, so the switch works before that change lands. No flag of this change's own switches the feature. `add-deployment-modules` (build group 3, position 6) lands later and adds `web-download` to its module catalog, its validation and its presets. The agent side (the module marking of the `web_download_*` tools on the agent's `ascend-web-hunter` server entry, and `@ConditionalOnModule("web-download")` on the agent parts) is `add-download-ingestion` (build group 4).
- Opt-in ingestion is the agent change `add-download-ingestion` (split out on 2026-10-04): the agent native tool `knowledge_add_download` and the REST endpoint `POST /api/v1/documents/from-download` copy one download or kept file into the tenant's knowledge base on request. This change gives that agent change what it reads: `GET /api/v2/web/downloads/{id}` and `GET /api/v2/web/downloads/kept/{id}` carry `storage.bucket` and `storage.key` for the internal caller. ascend-web-hunter never calls the agent.
- A download budget of 10 GB per tenant per calendar month (owner answer 45 of 2026-10-02), configurable, with the month boundary in `Europe/Warsaw`, counted in bytes stored by downloads. A download that would pass it is refused with a problem body and the code `download_budget_exceeded`.
- Limits (size, total time, concurrent downloads), metrics, and log lines that never carry a full URL: logs name the host and a short digest of the URL only.
- RFC 7807 problem bodies with the type base `https://ascend.ai/errors/`, a `code` and a `traceId`, as `add-ascend-python-common` defines them for every Python service (owner answer 70.1 of 2026-10-04). The agent follows the same format later in `upgrade-spring-boot-4` D19.
- Tests with an in-memory fake transport on the test side, with no seam or allowed test host in the service (owner decision 90 of 2026-10-08), inside web-hunter's 100 percent branch coverage gate, Bruno requests and documentation. End-to-end (owner request of 2026-10-04, trimmed by owner decision 91.3 of 2026-10-08): one deterministic web-hunter spec against the shared e2e fake site of `add-web-search-scraping-e2e`, a public datasheet row in the real-world spec 7 and a human download part in spec 11, each listed in `docs/E2E_RUN_SCENARIOS.md`. The agent specs are `add-download-ingestion`'s.
- The project is under development, so there is no data migration. Owner answer 73.1 of 2026-10-06 confirms that the data in today's development stores is disposable.

## Capabilities

### New Capabilities

- `web-search-file-download`: the download operation, its input, the SSRF and pinning rules, streaming with a size limit, type sniffing and the allow list, reuse of sessions and tiers, human help, the optional scan, limits, the monthly download budget per tenant, errors, metrics and logs.
- `web-search-download-storage`: object keys under the tenant prefix, the metadata record, deduplication, presigned links, the get, list and delete operations, the automatic deletion 24 hours after the last download by a sweep inside ascend-web-hunter, and keeping a file in the persistent folder.

### Modified Capabilities

(none. `web-search-fetch-correctness` keeps every requirement: the download path follows them through the shared redirect helper, and the requirement texts already cover every in-process fetch.)

## Dependencies and Build Order

Build order (owner build order of 2026-10-04, which supersedes the earlier orders, among them the web-hunter order of 2026-10-01): build group 2 (web-hunter), position 10. `scale-web-hunter-across-containers` (position 11, owner answer 96 of 2026-10-08) lands after it and is the last of the group, and runs ascend-web-hunter as several containers on the retention lock of this change. On 2026-10-04 the agent parts moved to the personal change `add-download-ingestion` (build group 4, position 8), so this change is web-hunter only and depends on no agent change, no base change of group 3 and no company change: nothing personal, web-hunter or base may depend on company work (owner rule of 2026-10-04).

It needs the changes before it in group 2: `add-ascend-python-common` (position 1: its problem builder, error registry and refusal handling for the D13 codes, the guarded redirect loop and the `ServiceSettings` base that the web-hunter settings extend), `add-python-runtime-upgrades` (position 2: FastMCP 4 for the tools and their tests), `open-several-novnc-windows-at-once` and `detect-challenge-walls-in-any-language` (positions 3 and 4: the human help windows and `ChallengeDetector.assess`), `enhance-web-search-tier-ladder` (position 5: the patched browser tiers and the tier memory), `enhance-web-search-extraction-and-tiers` (position 6: the shared byte fetcher, required edit), `add-web-session-import` (position 8: an imported session is replayed) and `enhance-web-search-crawl-at-scale` (position 9: the shared S3 client, required edit). Its e2e specs use the shared e2e fake site of `add-web-search-scraping-e2e` (build group 1). Every download without a tenant from the caller belongs to tenant `default`, and a caller that names one before tenant isolation exists sends `X-Ascend-Tenant: default`, so no tenant change is needed. The retention runs inside ascend-web-hunter, so no scheduler change is needed. Later changes plug in and are not waited for: `add-deployment-modules` (build group 3) adds the module `web-download` to its catalog and presets, `add-keycloak-login` (build group 3) closes the routes behind its service token, `add-mcp-tool-servers` and `add-download-ingestion` (build group 4) give the agent its side, and the company changes `add-tenant-isolation`, `add-usage-metering-and-quotas` and `add-audit-and-gdpr-compliance` (build group 5) register their implementations later. The required edits to other changes are listed in design.md.
