## Why

The agent needs a shell and file tools to do real work, such as running a script, checking out code or converting a file. Subagent runs need them, and by owner decision of 2026-10-02 (answer 21.6) the main chat needs them too. Running those tools inside the agent's own process or container would let a bad command, a prompt injection or a downloaded piece of malware read the agent's provider keys and database passwords, reach every internal service and other tenants' data, and damage the host. The owner decided on 2026-10-02 that every such workspace is its own throwaway container, created and destroyed by a separate small service, never by the agent through the Docker socket.

## What Changes

- New service `ascend-sandbox-runner` (Java 21, Spring Boot 4.1, port 9940, never published on the host), with no compose profile, so it runs in every deployment (owner decision of 2026-10-03: the sandbox is core, always on and never switchable). It is the only service that talks to the Docker Engine API for sandboxes. It offers a small internal REST API: create a workspace, run a command with a timeout, read a file, write a file, copy a folder out as a tar archive, list and destroy workspaces. Every call carries a bearer token and the tenant id.
- Isolation: every workspace is one container started with the gVisor `runsc` runtime (Apache 2.0, a user space kernel that needs no hardware virtualization, so it runs on a Hetzner or Contabo virtual server). The container runs as a non-root user with every Linux capability dropped, `no-new-privileges`, a read-only root file system, a size-limited `/workspace`, CPU, memory, process count and time limits from configuration, no published ports, no mounts from the host except one project folder for a profile marked `project-backed`, and no secrets.
- Only workspace containers run under gVisor (owner decision 21.6). Ascend's own services, the runner, the egress proxies and every other compose service run on the engine's default runtime.
- Network policy: off by default (`network_mode: none`). A workspace may get an allow list of host names. It then sits on its own internal network whose only other member is a per-workspace egress proxy (Stripe Smokescreen, MIT licence) that allows only the listed host names and refuses every private, loopback and link-local address.
- Coding project area for `add-coding-agent-delegation`: a profile marked `project-backed` mounts exactly one project folder of one shared named volume `ascend-coding-area` at `/workspace` through Docker's volume subpath mount, instead of the tmpfs. In production the volume is bound to a host folder on a separate partition at `/srv/ascend/coding` (`CODING_AREA_HOST_PATH`, owner answer 44 of 2026-10-02). Five endpoints create, measure, delete and archive project folders through a short-lived helper container that runs no project code. The archive serves the user and tenant export. A deployment without a `project-backed` profile needs no area.
- Credential gateway: a workspace or service that needs authenticated calls gets one small nginx gateway container of its own beside its egress proxy. The runner writes each secret into the gateway's memory-backed folder through standard input, and the workspace never sees it.
- Integration images and services for `add-self-built-integrations`: images assembled by the engine from tested archives without running any code, and long-lived integration services with their own network, proxy and gateway, reconciled to the requested state and adopted after a runner restart. Their secrets come only from the optional file `integration-secrets.env` next to `compose.yaml` (owner answer 46.2 of 2026-10-02).
- The egress proxy image also has an open mode (`ALLOWED_HOSTS=*`) for `add-mcp-tool-servers`, which keeps the private address refusal. The runner itself never uses it.
- Cleanup: every container and network carries labels with the tenant, workspace, owner and expiry time. A reaper inside the runner removes everything past its expiry, at startup and on a schedule, so a crash of the agent or the runner leaves nothing behind for longer than one reaper interval after expiry. The reaper stays in the runner because the runner has no database and must clean up even while the agent is down. The agent side jobs are the chat workspace idle sweep, a system task of `add-shared-scheduler` that also closes the records of workspaces the runner already expired, and two retention entries of its one shared retention task (owner answers 89.7 and 93 of 2026-10-08).
- Images: workspaces start only from named image profiles listed in the runner configuration, pinned by digest and pulled when the runner starts. The agent can never pass an image name. A base profile image is built in this repository, scanned, and rebuilt on a schedule.
- Development on Docker Desktop for Windows: Docker Desktop has no supported way to add `runsc` (docker/desktop-feedback issue 364). The runner therefore allows the plain `runc` runtime only outside the `production` profile, logs a WARN banner and tags its metrics with the runtime, and refuses to start under the `production` profile unless `runsc` is registered in the engine.
- Agent side: a `SandboxClient` port with an HTTP adapter, and three tools `shell`, `file_read` and `file_write`, which exist in every deployment and are offered only when the `TenantToolPolicy` port of `add-agent-skills` allows them. Its default allows them unless the owner lists them in `app.tool-policy.denied-tools`, and the tenant policy that `add-tenant-policy` registers later can switch the three tools off for one tenant.
  - A subagent run gets one workspace for its whole life, created on its first sandbox tool call and destroyed when the run reaches a final state. Files under `/workspace/out` are copied out and stored under `tenant/<tenantId>/sandbox-output/<runId>.tar.gz` in the `sandbox-output` bucket.
  - The main chat gets one workspace per conversation, created on the first sandbox tool call of that conversation and kept between turns. It is closed after 30 minutes without a sandbox tool call, shortly before its runner expiry of 2 hours, when the tenant's limit of open chat workspaces needs room, or when the conversation no longer exists. Before an idle, expiry or room close, files under `/workspace/out` are stored under `tenant/<tenantId>/sandbox-output/chat/<workspaceId>.tar.gz`.
- Agent table `sandbox_workspace` for audit and per tenant limits, created by a Flyway versioned SQL migration.
- Logs, metrics and traces on both sides, following `add-observability` naming, including a runner metric of sandbox time in seconds. Command text is logged only at DEBUG.
- Errors of the runner API are RFC 7807 problem details with the same fields and rules as the agent's error body of `upgrade-spring-boot-4` (its D19): `type` (`https://ascend.ai/errors/` followed by the code with dashes), `title`, `status`, `detail`, `instance`, a top-level snake case `code`, and `errors` on a validation failure.
- Tests: unit tests, Testcontainers integration tests of the runner against a real engine, an escape attempt suite (Docker socket, capabilities, mounts, network, DNS, other tenants, private addresses, resource exhaustion, path traversal), contract tests between the agent client and the runner, and one new deterministic end-to-end spec of the agent on the scripted model of the shared harness, which forces the shell and file tool calls, listed in `docs/E2E_RUN_SCENARIOS.md`. No runner suite and no probe container, because the runner integration tests and the contract tests prove the runner API (owner answer 91.3 of 2026-10-08).

## Capabilities

### New Capabilities

- `agent-sandbox-runner`: the runner service, its REST API and authentication, the container isolation settings and runtime rule, resource and time limits, the network policy and egress proxy, tenant separation, image profiles and updates, project-backed workspaces and the coding project area, the credential gateway, integration images and services with their secrets, orphan cleanup, and the runner's logs and metrics.
- `agent-sandbox-tools`: the agent's sandbox client, the `shell`, `file_read` and `file_write` tools, when they are offered, one workspace per run and one per conversation and their lifecycles, copying results out, the `sandbox_workspace` table, and the agent side logs and metrics.

### Modified Capabilities

- `production-deployment` (created by `harden-cloud-deployment`, build group 3, position 4): `ascend-sandbox-runner` becomes the one service allowed to mount the Docker socket for sandbox work, publishes no port, `SANDBOX_RUNNER_TOKEN` joins the `${VAR:?message}` guards of every deployment, and the cloud VM guide gains the gVisor host steps (moved here from `harden-cloud-deployment` in the dependency fix of 2026-10-05).

`ascend-agent-containerization` already requires `.env.example` to list every variable `compose.yaml` uses, so the new runner token is covered by that requirement as it stands. The agent's container, port and profile do not change.

- New module `apps/ascend-sandbox-runner/` with its own Gradle build, Dockerfile, `AGENTS.md`, README and tests. The root `AGENTS.md` module and compose tables and `.claude/CLAUDE.md` gain it.
- New images and files under `infra/sandbox/`: the base workspace image, the Smokescreen egress proxy image and the nginx credential gateway image (`credential-gateway/`), all built from pinned sources, and the host setup script of the coding project area (`coding-area/setup-coding-area.sh`).
- `compose.yaml`: service `ascend-sandbox-runner` with no `profiles` key, on the stack's default network, with the Docker socket mount and no published port, the optional `env_file` `integration-secrets.env`, one new network `sandbox-egress` used only by egress proxies and gateways, and one new network `integrations-ingress` (`internal: true`) that the agent joins and the runner attaches integration gateways to. `.env.example` gains `SANDBOX_RUNNER_TOKEN`, `DOCKER_SOCKET_GID` and `CODING_AREA_HOST_PATH`, and `integration-secrets.env.example` documents the integration secret variables. `.gitignore` gains `integration-secrets.env`.
- Module catalog (`add-deployment-modules`): no entry, because the sandbox is core (owner decision of 2026-10-03). `SANDBOX_RUNNER_TOKEN` is a required secret of every deployment, guarded in compose with `${SANDBOX_RUNNER_TOKEN:?...}` like `SEARXNG_SECRET`, and generated by the installer.
- ascend-agent: `service/sandbox/` (client port and adapter, workspace service, three tools, results copy), `config/properties/SandboxProperties`, `model/SandboxWorkspace` and its repository, one Flyway versioned SQL migration in `src/main/resources/db/migration/`, `application.yaml` keys under `app.sandbox`, no bean marked with `@ConditionalOnModule` and every new class in the `core-chat` list of `ModuleMarkingCoverageTest`, and three system tasks of the shared scheduler, registered in every deployment.
- New dependencies: `com.github.docker-java:docker-java-core` and `docker-java-transport-httpclient5` in the runner, and `org.apache.commons:commons-compress` for the archive checks of integration images (all Apache 2.0, versions looked up and pinned at implementation time). No new dependency in the agent beyond what Spring Boot already ships.
- Host requirement for production: Docker Engine 26.0 or later on Linux (for the volume subpath mount) with `runsc` registered as a runtime (`runsc install`), and, when the module `coding` is used, the coding project area on its own partition. Documented in `docs/DEPLOYMENT.md`.
- Docs: a monorepo ADR for the isolation choice, `docs/architecture/` updates for the new service, `docs/OBSERVABILITY.md` for the new metrics, `docs/SECURITY.md` for the credential gateway and the project isolation, the module README and AGENTS.md files, and the rows of every new setting in `docs/CONFIGURATION.md` (runner, egress proxy, credential gateway) and `apps/ascend-agent/docs/CONFIGURATION.md` (agent), each added in the same commit as its setting (owner rule 98 of 2026-10-08, design D18).
- Backwards compatibility: from this change on the runner and the three tools exist in every deployment, and `.env` must hold `SANDBOX_RUNNER_TOKEN` before the next `docker compose up`. A tenant whose tool policy does not allow a sandbox tool is not offered it, and a definition that lists such a tool behaves as `add-agent-subagents` already specifies for a missing tool. Chat without sandbox tool calls does not change.
