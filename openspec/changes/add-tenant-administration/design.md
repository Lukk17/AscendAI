# Design - add-tenant-administration

## Context

Two sibling changes lay the groundwork this one builds on. `add-keycloak-login` makes ascend-ai-agent an OAuth2 resource server against Keycloak (realm `ascend-ai`, roles `USER` / `ADMIN`, a PKCE public client for Flutter), and `add-auth-and-identity` adds a `tenant` claim copied from the Keycloak user attribute `tenant` by a protocol mapper, `default` when the attribute is absent. `add-tenant-isolation` adds the `tenants` table, the slug format `[a-z0-9-]{1,64}`, and the `default` tenant row, and every tenant-scoped store reads the tenant through the fail-closed `TenantContext.currentTenantId()` of `add-keycloak-login`. Neither creates tenants or users at runtime, and nothing sets the `tenant` attribute on a directly invited user. Build order: build group 5, position 4 of the owner build order of 2026-10-04, after `add-auth-and-identity`, `add-tenant-isolation` and `add-tenant-policy` and every personal change. `add-audit-and-gdpr-compliance` lands after this change (the company order of 2026-10-01 that put it before is superseded by the owner build order of 2026-10-04), so this change records its events through `AuditEventPort` of `add-deployment-modules`, and that change adds tenant delete (D5), per-user erasure on user removal, and the `PLATFORM_ADMIN` audit query (D6) on top of this change.

The go-to-market is single-tenant-per-customer dedicated stacks first, multi-tenant later. The API must serve both: a `PLATFORM_ADMIN` who manages tenants (rare on a dedicated stack, central under multi-tenancy) and a tenant `ADMIN` who manages their own users (the common case on every stack).

## Goals / Non-Goals

**Goals:**

- Runtime tenant lifecycle (create / suspend / resume) behind a platform-operator role, with delete added later by `add-audit-and-gdpr-compliance` (D5).
- Runtime user management (invite / roles / enable-disable / remove) behind tenant admin, scoped to the caller's tenant.
- Set the Keycloak `tenant` user attribute on every invited user so their token carries the right `tenant` claim, and send the invitation email through the realm SMTP settings.
- Fail-closed suspension: a suspended tenant cannot use any data-plane operation.

**Non-Goals:**

- Data isolation enforcement (owned by `add-tenant-isolation`), quotas / BYOK (owned by `add-usage-metering-and-quotas`), per-tenant provider/tool policy (owned by `add-tenant-policy`).
- Self-service tenant signup / billing-driven provisioning (no public signup; tenants are operator-created).
- SSO / external IdP federation beyond the issuer-uri swap the auth change already allows.
- Any UI (Flutter client is a separate change).

## Decisions

### D1 - The Keycloak user attribute `tenant` is the one source of the `tenant` claim

`add-auth-and-identity` already decides where the claim comes from: a protocol mapper in the realm export copies the user attribute `tenant` into the `tenant` access-token claim, a realm user with no attribute gets `default`, and a brokered provider's hardcoded-attribute mapper stamps the attribute for every user who arrives through it (`add-auth-and-identity` D3b and D15). This change uses that same attribute and adds no second path.

- Invite sets the attribute. `UserManagementService` creates the Keycloak user with `attributes.tenant = [<caller's tenant>]`, where the tenant comes from the inviting admin's resolved tenant context, never from the request path or body.
- The attribute is admin-only. The realm export's user profile declares `tenant` with `view` and `edit` permission for `admin` only, so a user cannot change their own tenant through the account console or a self-service API. A brokered user's attribute is written by the provider's hardcoded-attribute mapper, which an end user cannot influence either.
- No tenant groups. A Keycloak group per tenant would be emitted by the D9 group mapper of `add-auth-and-identity` into the group claim, and every group in that claim becomes a `local:group:<name>` retrieval principal. A `/tenants/acme` group would therefore widen what a user can retrieve and would be a second, competing source of the tenant value. Tenant membership is the attribute, and groups stay purely for retrieval breadth as auth defines them.
- Moving a user to another tenant is an attribute change through the Admin API by a `PLATFORM_ADMIN`, followed by the user's next token. It is not part of the tenant `ADMIN` surface.

Alternative considered: a group per tenant with a group attribute and a group-membership mapper. Rejected for the two reasons above: it conflicts with auth's broker mapper, which stamps a user attribute, and it leaks a group into retrieval principals.

### D2 - `PLATFORM_ADMIN` is a new realm role, additive to the export

Tenant lifecycle is a cross-tenant privilege, so it cannot be the tenant-scoped `ADMIN`. A new realm role `PLATFORM_ADMIN` gates `/api/v1/admin/tenants`. On a dedicated single-tenant stack it is held by the operator; under multi-tenancy it is the control-plane role. Tenant `ADMIN` (already defined by `add-keycloak-login`) gates `/api/v1/admin/users` and is always constrained to the caller's own tenant server-side, never a path/body-supplied tenant.

### D3 - ascend-ai-agent talks to Keycloak through the Admin REST API with a service account

Provisioning (create group, create user, assign role, trigger invite email) happens through Keycloak's Admin REST API. ascend-ai-agent authenticates with a dedicated confidential client using client-credentials (service account with the `manage-users` and `view-users` realm-management roles, nothing more, because no client is created and the retrieval groups of D7 are covered by `manage-users`). The secret follows the deployment secret conventions from `harden-cloud-deployment`.

- Invitation flow: create the user with the `tenant` attribute, then trigger Keycloak's `execute-actions-email` with `UPDATE_PASSWORD` and `VERIFY_EMAIL` so Keycloak sends the set-password email. ascend-ai-agent never handles the password.
- SMTP: `execute-actions-email` fails without a realm mail server. The realm export gains an `smtpServer` block (host, port, from address, `auth`, `starttls`, user, password) whose values are placeholders the Keycloak import resolves from the environment, so no mail secret is committed. Development points it at the local test mail server Mailpit, a `mailpit` compose service on SMTP port 1025 with STARTTLS and login turned on (owner answer 106 of 2026-10-09), production at the operator's relay. The variables are `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD` and `SMTP_FROM`, plus `SMTP_AUTH` and `SMTP_STARTTLS` for the `auth` and `starttls` fields (owner rule 98 of 2026-10-08), both with the default `true` (owner answer 103.5 of 2026-10-09), and the admin client of D3 reads `KEYCLOAK_ADMIN_CLIENT_ID` and `KEYCLOAK_ADMIN_CLIENT_SECRET` (owner answer 75.5 of 2026-10-07). The secrets among them, `KEYCLOAK_ADMIN_CLIENT_SECRET`, `SMTP_USERNAME` and `SMTP_PASSWORD`, are listed in the root `.env.example` with no value and their values live only in env files, never in a committed file. The others have defaults and get no `.env.example` line (owner rule 98 of 2026-10-08, see Settings below).
- Address: the Admin API address is derived from `KEYCLOAK_ISSUER_URI`, the one issuer variable of every service (owner answer 98.3 of 2026-10-08, default `http://keycloak:8080/realms/ascend-ai`). The part before `/realms/` is the Keycloak server address and the path segment after it is the realm, so the client calls `<server>/admin/realms/<realm>/...` and no second Keycloak address setting exists. The token endpoint of the client credentials grant is the issuer's own `<issuer>/protocol/openid-connect/token`.
- Settings (owner rule 98 of 2026-10-08): `KEYCLOAK_ADMIN_CLIENT_ID` is not a secret, so the agent reads it as `${KEYCLOAK_ADMIN_CLIENT_ID:ascend-agent-admin}` with `ascend-agent-admin`, the id task 1.2 gives the service-account client in the realm export, as its default, and the compose service passes `${KEYCLOAK_ADMIN_CLIENT_ID:-ascend-agent-admin}`. `KEYCLOAK_ADMIN_CLIENT_SECRET` is a secret: no default, its guard stays (startup fails with a clear message when it is missing), and its value lives only in `.env`. The `RestClient` of `KeycloakAdminClient` has an explicit connect timeout `app.keycloak.admin.connect-timeout` (`APP_KEYCLOAK_ADMIN_CONNECTTIMEOUT`) and read timeout `app.keycloak.admin.read-timeout` (`APP_KEYCLOAK_ADMIN_READTIMEOUT`), each with the same default in `application.yaml`, in the properties record and in the compose line: `2s` to connect and `5s` to read (owner answer 106 of 2026-10-09).

### D4 - Tenant status lives in Postgres; suspension is enforced at tenant-context resolution

The `tenants` table (from `add-tenant-isolation`) gains a `status` column (`ACTIVE` / `SUSPENDED`). Suspension is enforced right after the tenant is resolved: a request filter of this change, placed after the authentication of `add-keycloak-login`, reads `TenantContext.currentTenantId()` and answers 403 when that tenant is `SUSPENDED`. This is one enforcement point covering every data-plane operation (chat, ingest, RAG, memory), rather than scattering checks per endpoint, and no class of an earlier change is edited.

Suspension uses this one mechanism and nothing else (owner answer 89.16 of 2026-10-08). Suspend and resume change only the `status` of the `tenants` row. They disable and enable no Keycloak user. The earlier plan also disabled every Keycloak user of the tenant on suspend and enabled them all again on resume, which re-enabled a user that a tenant `ADMIN` had disabled one by one before the suspend. With the status as the only mechanism, resume cannot touch a per-user disable: that is the Keycloak `enabled` flag, and only the user management of D3 and task 5.1 changes it. A user of a suspended tenant can still sign in to Keycloak and obtain a token, and every request with that token, or with one issued before the suspend, is refused with 403 by the filter, so a suspended tenant cannot use the data plane with any token.

The filter reads the status through a cache, because it runs on every request. Several agent instances run at once (owner answer 87, rule R1), and a stale status is a defect, so the cache follows the one cache mechanism of the platform, the same one as the policy cache of `add-tenant-policy` D4: every entry has a bounded time to live (`app.tenant.status-cache.ttl`, environment variable `APP_TENANT_STATUSCACHE_TTL`, default 30 seconds) and the cache a bounded size (`app.tenant.status-cache.max-size`, environment variable `APP_TENANT_STATUSCACHE_MAXSIZE`, default 1000 entries, owner answer 98.4 of 2026-10-08), and suspend and resume call `pg_notify('tenant_status_changed', <tenantId>)` in the transaction that changes the row. This change opens no `LISTEN` connection of its own: it registers a `PostgresNotificationHandler` for that channel on the one `PostgresNotificationListener` of `add-keycloak-login` D20, which evicts the tenant's entry on every agent instance when the notice arrives, and whose `onReconnect()` clears the whole status cache, because a notice sent while the connection was down is lost. The payload is the tenant id only. A suspend therefore reaches every instance at once, and the time to live bounds any entry that is missed in another way.

### D5 - Delete is erase-then-deprovision, and it lands with erasure

Deleting a tenant is destructive and ordered: (1) suspend, (2) run the per-tenant erasure job to zero residue, (3) disable the Keycloak users whose `tenant` attribute equals the tenant id and clear their personal attributes, never deleting them (owner decision, 2026-10-01, the same rule erasure follows), (4) remove the `tenants` row, each step an `ADMIN_OPERATION` event. Step 2 needs the `ErasureOrchestrator` of `add-audit-and-gdpr-compliance`, which lands after this change under the owner build order of 2026-10-04, so the delete endpoint and its order are built in that change (its D10), on top of the suspend operation and the `KeycloakAdminClient` of this change. This change ships no delete operation, so a tenant can never be removed with its data left behind.

### D6 - `PLATFORM_ADMIN` reads the audit log across tenants, added by the audit change

The audit log and its query `GET /api/v1/audit` belong to `add-audit-and-gdpr-compliance`, which lands after this change and therefore knows `PLATFORM_ADMIN` from its first day. That change gives a caller holding `PLATFORM_ADMIN` every tenant's rows with an optional `tenant` filter, and keeps a tenant `ADMIN` on their own tenant whatever `tenant` value they pass (its D8). This change only adds the role.

### D7 - Retrieval groups of a tenant, company-only (owner decision 65.3 of 2026-10-04)

A tenant `ADMIN` creates, lists, renames and deletes the retrieval groups of his tenant and manages their members, through `/api/v1/admin/groups`. This is company-only work, built after the personal version (task group 7), and it is the group source for `PUT /api/v1/documents/{id}/access` of this change (D8).

- A retrieval group is a Keycloak realm group named `<tenantId>.<name>`, created through the Keycloak Admin API. The D9 group mapper of `add-auth-and-identity` emits that name into the token, so a member holds `local:group:<tenantId>.<name>`. The tenant prefix keeps two tenants with a group of the same name apart, and it is the one tenant marker of a group: the group carries no `tenant` group attribute (owner answer 93 of 2026-10-08, review item C10). `<name>` follows the character set of `add-auth-and-identity` D8 and is at most 51 characters, so the principal `local:group:<tenantId>.<name>` stays within the 128-character cap of that D8 with a tenant id of 64 characters.
- Endpoints: `POST /api/v1/admin/groups` (201 with `Location`), `GET /api/v1/admin/groups` (paginated), `GET /api/v1/admin/groups/{name}`, `DELETE /api/v1/admin/groups/{name}`, `GET /api/v1/admin/groups/{name}/members`, `PUT /api/v1/admin/groups/{name}/members/{userId}` and `DELETE /api/v1/admin/groups/{name}/members/{userId}`. The tenant is the caller's, never from the path or body. A group or user of another tenant answers 404. A group name that already exists answers 409.
- Deleting a group that a document's access list still names is refused with 409 `access_group_in_use`, so no document silently becomes invisible.
- The service account of D3 keeps `manage-users` and `view-users`. In Keycloak `manage-users` also covers creating groups and changing group membership, and task 7.1 confirms that against the pinned version.
- A membership change reaches retrieval at the member's next token, the staleness bound of `add-auth-and-identity` D18.
- Each operation is recorded as an `ADMIN_OPERATION` event through `AuditEventPort`.

This sits beside the "no tenant groups" rule of D1: a retrieval group widens what its members find, which is what it is for, and it never carries the tenant value of a user, which stays the attribute.

### D8 - Document access groups on direct uploads (owner decision 65.3 of 2026-10-04)

A tenant `ADMIN` narrows who may find a directly uploaded document with `PUT /api/v1/documents/{id}/access`. Moved here from `add-document-management-api` D15 by the dependency fix of 2026-10-05. It needs the `ADMIN` role and the `local:group:*` principal of `add-auth-and-identity` D8, the `acl`, `acl_source` and `acl_version` chunk fields and the tenant filter of `add-tenant-isolation`, and the retrieval groups of this change's D7. It plugs into `add-document-management-api` through its core port `ChunkPayloadContributor` (its D15) and edits no class of that change.

- Body: `{"everyone": <boolean>, "groups": ["<group name>", ...]}`. `everyone` true writes `tenant:everyone:{tenantId}`. Each group name is a retrieval group of the caller's tenant (D7) and is minted through the principal factory of `add-auth-and-identity` D8 into `local:group:<tenantId>.<name>`. The tenant is the caller's, from `TenantContext.currentTenantId()` of `add-keycloak-login`, never from the path or body.
- The new access list is stored on the `documents` row of `add-document-management-api` in a new column `access_list TEXT[]` that this change adds in its own Flyway migration, and written onto every chunk of the document in every RAG collection through Qdrant's set payload by filter on the document's `source` and `tenant_id`: `acl` becomes the new list, `acl_source` becomes `admin-assignment` and `acl_version` becomes the hash of the new list, computed by the access-list helper of `add-tenant-isolation` (its task 3.2). This change registers a `ChunkPayloadContributor` that reads `access_list` from the registry row, so a later reindex or bucket scan of `add-document-management-api` keeps the narrowed list. A row with no `access_list` keeps the default of `add-tenant-isolation`, `tenant:everyone:{tenantId}`.
- Refusals, as the problem details of `upgrade-spring-boot-4` D19: 400 `validation` when `everyone` is false and `groups` is empty, because such a document would be found by nobody (deny by default of `add-tenant-isolation`), and for a group name outside the D8 character set. 404 `not_found` for an unknown document or one of another tenant, and 400 `unknown_access_group` (a new value of `ApiErrorCode`) for a group that does not exist in the tenant. 409 `document_state_conflict` while the document is `DELETING`. 403 for a caller without `ADMIN`.
- Only documents with `source_type` `upload` or `web-download` take a narrowed list. A connector document gets its list from its connector (`add-document-connectors`) and is refused with 409 `document_access_managed_by_connector`, a new value of `ApiErrorCode`.
- `GET /api/v1/documents/{id}` returns `access: {everyone, groups}`, added by this change to the detail view of `add-document-management-api`. Each change is recorded through `AuditEventPort` of `add-deployment-modules` (its D21) as `DOCUMENT_ACCESS_CHANGED` with the document id and the old and new lists (listed in `add-audit-and-gdpr-compliance` D3, edit made there on 2026-10-04).

### D9 - User management routes

The user management API of task 5.2 lives under `/api/v1/admin/users`, tenant `ADMIN` only, with the tenant always the caller's (D2). Disabling and enabling an account are two routes of their own (owner answer 98.10 of 2026-10-08):

- `POST /api/v1/admin/users/{userId}/disable` sets the Keycloak `enabled` flag of that user to false.
- `POST /api/v1/admin/users/{userId}/enable` sets it to true.

`{userId}` is the Keycloak user id. Both answer 200, like the suspend and resume routes of task 3.3, and both record one `ADMIN_OPERATION` event through `AuditEventPort`. A user whose `tenant` attribute is not the caller's tenant answers 403 and is not changed (spec `user-management`). These two routes are the only place the `enabled` flag of a user changes, which is what keeps a per-user disable in place across a suspend and a resume (D4).

## Risks / Trade-offs

- [Keycloak Admin API coupling] → the Admin client is isolated behind `KeycloakAdminClient` so an IdP swap replaces one class; the REST surface stays IdP-agnostic.
- [Suspended tenant with a still-valid token, or a new one] → the Postgres status check at context resolution refuses every request of the tenant whatever its token, and the notice of D4 reaches every agent instance at once. Keycloak still issues tokens to the tenant's users, which carry nothing they can use.
- [Partial invite failure (Keycloak user created, email not sent)] → invite is idempotent by email within the tenant: a retry finds the existing user and triggers the email again. Tenant create touches Postgres only, so it needs no saga.
- [PLATFORM_ADMIN on a single-tenant stack is heavy] → acceptable; on a dedicated stack the operator holds it and rarely uses it, and it is the exact primitive multi-tenancy needs later.
