## Why

`add-tenant-isolation` creates the `tenants` table and enforces the `tenant` claim, `add-keycloak-login` ships Keycloak with realm roles `USER` / `ADMIN`, and `add-auth-and-identity` adds the `tenant` claim. But nothing creates a tenant at runtime, invites a user, assigns a role, or sets the Keycloak user attribute that the realm's `tenant` protocol mapper turns into the `tenant` claim. Today a tenant exists only because a default-tenant migration inserted one row, and a user exists only if someone edited Keycloak by hand. That is not a product: onboarding a customer, adding a colleague, promoting someone to admin, or offboarding all require manual database and Keycloak surgery.

This change is the control plane. Under the single-tenant-per-customer go-to-market it is what lets a customer admin invite their colleagues and manage roles without operator involvement. Under later multi-tenancy it is what lets one operator create and suspend tenants across a shared deployment. It is deliberately scoped to lifecycle and membership: it does not touch data isolation (owned by `add-tenant-isolation`), quotas (owned by `add-usage-metering-and-quotas`), or per-tenant provider policy (owned by `add-tenant-policy`).

## What Changes

- **Tenant lifecycle API** under `/api/v1/admin/tenants`, restricted to a new platform-operator role `PLATFORM_ADMIN` (a realm role added to the realm export of `add-keycloak-login`): create, list, get and suspend/resume a tenant. Delete is added by `add-audit-and-gdpr-compliance`, which owns erasure and lands later. Tenant ids remain the constrained slug (`[a-z0-9-]{1,64}`) defined by `add-tenant-isolation`.
- Keycloak side of a tenant: one source of truth for the `tenant` claim, the Keycloak user attribute `tenant`. `add-auth-and-identity` already ships the protocol mapper that copies that attribute into the `tenant` claim, and for a brokered customer its hardcoded-attribute mapper stamps the same attribute. This change sets the attribute on every user it invites, server-side from the inviting admin's tenant, and makes the attribute admin-only in the realm's user profile so a user can never edit it in the account console. No `/tenants/...` Keycloak group is created, so no tenant group reaches the group claim and no `local:group:*` retrieval principal is minted for a tenant. Creating a tenant is a `tenants` row only. Deleting a tenant needs the per-tenant erasure job, which `add-audit-and-gdpr-compliance` owns and which lands after this change, so the delete operation (erase, then disable, never delete, the Keycloak users whose `tenant` attribute equals the tenant id, then remove the row) is added by that change on top of this change's lifecycle service (moved there in the dependency fix of 2026-10-05).
- **User management API** under `/api/v1/admin/users`, restricted to tenant `ADMIN` and always scoped to the caller's own tenant: invite a user (creates the Keycloak user with the `tenant` attribute set to the caller's tenant and triggers Keycloak's built-in set-password email, which needs the realm SMTP settings this change adds to the realm export), list users, assign or revoke the `ADMIN` / `USER` role, disable and enable an account through `POST /api/v1/admin/users/{userId}/disable` and `POST /api/v1/admin/users/{userId}/enable` (owner answer 98.10 of 2026-10-08), and remove a user, which disables the Keycloak account and never deletes it. The option to hand off to per-user erasure is added by `add-audit-and-gdpr-compliance`, which lands later.
- **Suspend semantics, fail-closed**: a suspended tenant's users are refused right after authentication - `TenantContext` of `add-keycloak-login` already fails closed on an unresolved tenant; this change adds a request filter of its own, "resolved but suspended → 403", so a suspended customer cannot chat, ingest, or read, while their data is retained until an explicit delete. The tenant status is the one suspension mechanism: suspend and resume disable and enable no Keycloak user, so a user an administrator disabled one by one stays disabled after resume (owner answer 89.16 of 2026-10-08), and the status cache reaches every agent instance through a Postgres `NOTIFY` (owner answer 87). No class of an earlier change is edited.
- **Audit events**: every administration operation is recorded as an `ADMIN_OPERATION` event through `AuditEventPort` of `add-deployment-modules`, whose default writes one structured log line. `add-audit-and-gdpr-compliance` lands later and registers its `AuditRecorder` backed implementation, which stores them as audit rows.
- **Its own parts of the deployment**: `add-deployment-modules` keeps company parts out of the always-on core, so this change adds its own parts to the deployment when it lands: the `tenants.status` migration, the admin controllers and the suspension filter, the Keycloak admin client configuration, the realm SMTP settings and the local test mail server Mailpit of the development stack, its image pinned by version and digest (owner answer 106 of 2026-10-09).
- **Document access groups** (moved here from `add-document-management-api` D15 and task group 8 in the dependency fix of 2026-10-05): `PUT /api/v1/documents/{id}/access`, a new `access_list` column on the `documents` table added by this change's own migration, and a `ChunkPayloadContributor` registered on the port of `add-document-management-api`, so a reindex keeps the narrowed list (design D8, task group 9).
- **Keycloak Admin client**: ascend-ai-agent gains a Keycloak Admin REST client authenticated by a service-account (client-credentials) so it can create groups/users, assign roles, and trigger invitation emails. This is the one new outbound trust relationship; its client secret follows the deployment's secret conventions.

## Capabilities

### New Capabilities

- `tenant-administration`: platform-operator tenant lifecycle API (create/list/get/suspend/resume) and fail-closed suspension. Tenant delete with its erase-then-deprovision order and the cross-tenant audit query for `PLATFORM_ADMIN` are requirements of `add-audit-and-gdpr-compliance`, which lands later.
- `retrieval-groups`: company-only, built after the personal version (owner decision 65.3 of 2026-10-04): a tenant `ADMIN` creates, lists and deletes the retrieval groups of his tenant and manages their members under `/api/v1/admin/groups`, through the Keycloak Admin API (design D7).
- `document-access-groups`: company-only (owner decision 65.3 of 2026-10-04, moved here from `add-document-management-api` in the dependency fix of 2026-10-05): a tenant `ADMIN` narrows who finds a directly uploaded document with `PUT /api/v1/documents/{id}/access`, using the retrieval groups of this change, through the `ChunkPayloadContributor` port of `add-document-management-api` (design D8).
- `user-management`: tenant-admin user lifecycle API (invite/list/role-assignment/enable-disable/remove) scoped to the caller's tenant, backed by Keycloak user provisioning with the admin-only `tenant` attribute and invitation emails over the realm SMTP settings.

### Modified Capabilities

(none as spec deltas - `agent-authentication` and `tenant-isolation` are defined only in their sibling changes, which are not yet archived, so their base specs are not in `openspec/specs/` to modify. The additive rules those capabilities need - the `PLATFORM_ADMIN` role and authorization matrix for the admin endpoints, and the suspended-tenant fail-closed 403 at tenant-context resolution - are stated as ADDED requirements in this change's `tenant-administration` capability, and the realm-export and resolver edits are coordinated into `add-keycloak-login` (the realm export and its authorization matrix, where this change adds its own rows), `add-auth-and-identity` and `add-tenant-isolation` via the tasks. When those changes archive first, the enforcement point is theirs; this change references it.)

## Impact

- Build order (owner build order of 2026-10-04, which supersedes the earlier orders): build group 5 (company), position 4. It needs `upgrade-spring-boot-4` (Flyway, owner decision of 2026-10-02), `add-keycloak-login` (Keycloak, roles, resource-server posture, `TenantContext`), `add-deployment-modules` (`AuditEventPort`), `add-document-management-api` (the `documents` registry and its `ChunkPayloadContributor` port, its D15, which the access route of this change plugs into), `add-auth-and-identity` (the `tenant` attribute mapper) and `add-tenant-isolation` (the `tenants` table and the slug format). All of them land earlier. `add-audit-and-gdpr-compliance` lands after it and adds tenant delete, per-user erasure on user removal, the `PLATFORM_ADMIN` audit query and the stored audit rows of this change's events. The company order of 2026-10-01, which put `add-audit-and-gdpr-compliance` before this change, is superseded by the owner build order of 2026-10-04.
- **ascend-ai-agent (new code)**: `controller/admin/TenantAdminController.java`, `controller/admin/UserAdminController.java`; `service/admin/` package (tenant lifecycle service, user management service); `service/identity/KeycloakAdminClient.java` (Admin REST client); DTOs under `dto/`; Spring Data JDBC touch-points on the `tenants` aggregate from `add-tenant-isolation` (add a `status` column, `ACTIVE` / `SUSPENDED`, via a Flyway versioned SQL migration `V<n>__tenant_status.sql` under `src/main/resources/db/migration/`, with `<n>` taken at implementation time).
- Keycloak realm export (an `add-keycloak-login` artifact, with the company additions of `add-auth-and-identity`): add the `PLATFORM_ADMIN` role, the user-profile rule that makes the `tenant` attribute admin-only, the realm `smtpServer` block for invitation email (values supplied at import from the deployment's secrets), and a service-account client for the Admin API. The `tenant` claim mapper itself is already in the export and is not changed.
- Config: the Keycloak Admin API address and realm are derived from `KEYCLOAK_ISSUER_URI` (owner answer 98.3 of 2026-10-08), the admin-client id and secret are `KEYCLOAK_ADMIN_CLIENT_ID` and `KEYCLOAK_ADMIN_CLIENT_SECRET`, the admin client id defaults to `ascend-agent-admin`, the admin client timeouts are `app.keycloak.admin.connect-timeout` (`2s`) and `app.keycloak.admin.read-timeout` (`5s`) (owner answer 106 of 2026-10-09), the tenant status cache is `app.tenant.status-cache.ttl` (30 seconds) and `app.tenant.status-cache.max-size` (1000, owner answer 98.4), and the SMTP host, port, user, password and sender for the realm are `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD` and `SMTP_FROM` (owner answer 75.5 of 2026-10-07), with `SMTP_AUTH` and `SMTP_STARTTLS` for the `auth` and `starttls` fields of the realm mail server (owner rule 98 of 2026-10-08), both `true` by default (owner answer 103.5 of 2026-10-09). The development defaults point at the test mail server Mailpit on SMTP port 1025 with STARTTLS and login, `SMTP_HOST` `mailpit`, `SMTP_PORT` `1025` and the development sender `noreply@ascend.local`, which is never a production default (owner answer 106 of 2026-10-09). Every value with a default is a setting passed by compose as `${VAR:-default}` with the same default in code (owner rule 98 of 2026-10-08). The secrets `KEYCLOAK_ADMIN_CLIENT_SECRET`, `SMTP_USERNAME` and `SMTP_PASSWORD` have no default, follow the secret conventions of `harden-cloud-deployment`, are listed in `.env.example` and live only in env files.
- **Docs**: `docs/SECURITY.md` (from `add-keycloak-login`) gains a tenant/user administration section; `AGENTS.md` endpoint notes; Bruno requests for the admin API.
- Tests: invite → Keycloak user with `tenant` attribute and `USER` role asserted, and the user's token carries `tenant` and no tenant group (Keycloak Testcontainer); invitation email captured by Mailpit; suspended-tenant request returns 403; tenant-admin cannot manage another tenant's users; PLATFORM_ADMIN required for tenant lifecycle; one `AuditEventPort` event per administration operation.
