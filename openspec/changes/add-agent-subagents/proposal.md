## Why

The agent answers every prompt in one model loop with one tool list. A task that needs a focused helper, such as "research these three companies and compare them", runs in the same context window, with the same tools and the same model as everything else, and it blocks the HTTP request until the last tool call returns. There is no way to hand a piece of work to a narrower helper with fewer tools and a cheaper model, no way to let that work run in the background, and no way to see or stop it.

The owner wants the Claude Code subagent model inside AscendAI: helpers defined as `.claude/agents/*.md` files with `name`, `description`, `tools`, `model` and `skills` front matter, started by the main agent through a `Task` tool, nested up to a configured depth, running in the background with a visible status, a cost and a cancel button. The status must be ready for a later Discord bot and the Flutter mobile app.

`org.springaicommunity:spring-ai-agent-utils` 0.12.0 (Apache 2.0) already ships the Claude Code style pieces: the `TaskCall` tool input, the `SubagentDefinition`, `SubagentResolver`, `SubagentExecutor` and `SubagentType` SPI, `ClaudeSubagentDefinition`, `ClaudeSubagentResolver`, `TaskOutputTool` and a `TaskRepository`. The owner decided on 2026-10-02 to reuse that code and write only what is missing. What is missing is real: definitions are resolved once and never reloaded, there is no depth limit and no nesting, background tasks live only in memory and cannot really be stopped, nothing counts tokens or cost, the per-call model override is ignored, `permissionMode` is not supported, and the default subagent tool set includes a shell and file system tools that run inside the agent's own process, which must never happen here. The owner decided on 2026-10-02 that subagents may use a shell and files only inside the isolated sandbox of `add-agent-sandbox`.

## What Changes

- Subagent definitions:
  - Claude Code style Markdown files with YAML front matter (`name`, `description`, `tools`, `disallowedTools`, `model`, `skills`), kept per tenant in `tenants/<tenantId>/.claude/agents/` under the agent home root `app.agent-home` of `add-agent-skills`, each tenant definitions folder its own git repository. It is the same tenant folder layout as skills, whose tenant skills live next to it in `tenants/<tenantId>/skills/` as a separate repository. A personal deployment uses the tenant `default`. The root lives on the named Docker volume `agent-home` of `add-agent-skills`, not in the image and not in the repository's own `.claude/agents/` (that folder holds the developer agents).
  - Loaded at startup, kept current by the one catalog watcher of `add-agent-skills` that picks up added, changed and deleted files while the agent runs, with its rescan for file systems that deliver no events, a Postgres notification that brings in a write made on another agent instance (owner answer 87), and `POST /api/v1/subagents/definitions/reload` as the backup.
  - One validated write path, the one catalog write path of `add-agent-skills`, used by three sources: a REST endpoint, a definition the owner pastes in chat, and a definition the agent writes itself. The path validates, writes the file into the folder (so the watcher loads it) and commits it to git with the source and author recorded, so every change can be undone. REST companions: list, read, delete, history and revert.
  - Agent-written definitions get extra rules: they may only name tools the writing conversation already has, they cannot overwrite an owner definition, they can never grant the write tool, and they carry `origin: agent` stamped by the server. They are live as soon as they are written, with no approval step, and the owner can revert them through the git history. The one exception, set by `add-self-improvement` (owner answer 38.1): a chat write in a request whose request provenance of `add-agent-soul` is not `clean` waits for one tap of the owner's approval. The write tool takes an optional reason, and the regression guard of `add-self-improvement` can revert an agent definition with origin `guard`, which no tool can write.
  - Every loaded definition is registered in the shared capability index of `add-agent-skills` with the type `subagent`, kept in step on every reload, write and delete by that change's `CapabilityIndexSync`. The main agent finds subagents with the `skill_search` tool and type `subagent`, so the `Task` tool description does not list every definition in every request.
- Subagent execution:
  - A `Task` tool and a `TaskOutput` tool offered to the main chat and, below the depth limit, to subagents. `Task` keeps the library's `TaskCall` input (`description`, `prompt`, `subagent_type`, `model`, `run_in_background`).
  - Nesting up to `app.subagents.limits.max-depth` (default 3). The `Task` tool is not offered at the last level and refuses a call that claims a deeper level.
  - Tool permission per definition: a subagent gets the tools its definition names, minus `disallowedTools`, never more than its parent has, and never a tool the tenant's tool policy does not allow.
  - Sandbox tools: a definition may list the tools `shell`, `file_read` and `file_write` of `add-agent-sandbox`. They are offered once that change (build group 4, position 3) adds them and the `TenantToolPolicy` port of `add-agent-skills` allows them, and they always run in the run's own throwaway sandbox container, never in the agent's process. By owner answer 21.6 of 2026-10-02 the main chat gets the same three tools, and each conversation uses its own sandbox workspace. No shell or file tool that runs inside the agent is ever offered.
  - The per-call model override and the definition's `model` are honoured, resolved through the existing `ChatModelResolver` and checked against a configured allowlist. The aliases `opus`, `sonnet` and `haiku` resolve to the latest model of that family, set in configuration.
  - Every limit is configuration: depth, runs at once, runs waiting, cost per run in US dollars, tokens per run, and time per run. A child's cost, token and time budget is never larger than what its parent has left. The defaults, accepted by the owner on 2026-10-02, are 4 runs at once, 16 waiting, 1.00 US dollar and 200000 tokens per run, 10 minutes per run, 30 days retention, and at most 100 definitions of up to 32 KiB each.
  - Cost is counted from the token usage of every model call, priced from the one price table the token cost dashboard already uses. Every model call of a run is also published as a usage event through `UsageEventPort` of `add-deployment-modules` with its run id, its parent run id and the request type of the run's kind (`subagent`, `scheduled` or `self-review`, design D12), and `QuotaGate` of `add-deployment-modules` is asked before each of them. Their defaults record nothing and allow every call. `add-usage-metering-and-quotas` (company, build group 5) registers its ledger and quota implementations later.
- Run status:
  - Every run, background or not, is a tenant-keyed row in a new PostgreSQL table created by a Flyway versioned SQL migration: kind (`subagent`, `coding`, `scheduled`, `self_review`, `integration`), state (`waiting`, `running`, `awaiting_approval`, `done`, `failed`, `cancelled`), parent run, parent conversation, depth, definition and its git version, model, tokens, cost so far, last step, limits, result and failure reason. This change owns the table and the behaviour of kind `subagent`. The later changes named in the build order add the behaviour of the other kinds without changing the table.
  - A run waiting for an owner approval of `add-action-approvals` holds no worker slot and its time limit is paused, through the two methods `pauseForApproval` and `resumeAfterDecision` that that change calls. Every kind takes its slots from one slot pool with a limit per run kind, `RunSlots`, whose counts live in Postgres so the limits hold across agent instances (owner answers 87 and 89.7). Kinds `coding`, `integration` and `self_review` register pools of their own, and the `integration` pool has a safety bound on running builds and no bound on waiting builds (owner decision 40.4).
  - A main chat tool call that waits for the owner is a row of `approval_request` of `add-action-approvals`, the one record of an approval, not a run row (owner answer 89.4). The new port `RunViewSource` lets that change show it in the run list, the read, the cancel, the event stream and the finished runs block with kind `approval`. A run of kind `self_review` has no cost limit (owner answer 38.3), and its cost is still counted.
  - `GET /api/v1/runs`, `GET /api/v1/runs/{id}` and `POST /api/v1/runs/{id}/cancel`. Cancel reaches the running thread and every descendant.
  - Background runs outlive the chat request that started them. `GET /api/v1/runs/{id}/events` streams `subagent_status` events and can be resubscribed with `Last-Event-ID`. A streamed chat turn announces a run with `run_started` and follows it with `subagent_status` while the stream is open, two event names this change adds to the chat stream. The event stream and the streamed turn read run changes from Postgres through a notification with a poll fallback, so a run on another agent instance reaches them (owner answer 87).
  - A stable JSON run view and an application event on every state change, so a Discord bot or the mobile app can show and follow runs later without touching run code.
  - On agent restart, runs that were waiting, running or paused for approval are closed as `failed` with reason `AGENT_RESTARTED`, never resumed, because their tools may already have had side effects. A main chat approval is a row of `approval_request` of `add-action-approvals`, not a run row, so it survives a restart there, and the run list shows it through the port `RunViewSource`. The periodic sweep is a system task of the shared scheduler of `add-shared-scheduler`, and run retention is an entry of its one shared retention task.
  - Finished runs the main conversation has not seen yet are listed in the next chat turn's dynamic system block, so the model can report them.
- Metrics, logs and traces for definitions and runs, following the naming and cardinality rules of `add-observability`.
- The subagent definitions, their registry, the definition API and the tools `Task`, `TaskOutput` and `subagent_definition_write` are the module `subagents` of the catalog of `add-deployment-modules`, which requires `skills`. They are on when `subagents` is in `ASCEND_MODULES` (from `COMPOSE_PROFILES`), and there is no `app.subagents.enabled` flag. The run table, the run service, the run loop, `/api/v1/runs` and the run sweeps are `core-chat` (owner decision of 2026-10-02), because runs of other kinds, such as approvals, use them in every deployment.

## Capabilities

### New Capabilities

- `subagent-definitions`: the definition format, the definition folder and its git history, loading at startup, the folder watcher, the reload endpoint, the single validated write path for REST, chat and agent sources, the REST definition endpoints, the security rules for agent-written definitions, and the registration of definitions in the shared capability index.
- `subagent-execution`: the `Task` and `TaskOutput` tools, finding subagents through `skill_search`, nesting with a depth limit, tool permission per definition, sandbox tools, model selection with the aliases and the model allowlist, the concurrency, cost, token and time limits, and cost accounting from token usage.
- `subagent-run-status`: the persisted run record and its state machine, the run REST API with list and cancel, following a run after its chat request ended (event stream and resubscribe), the run view and change event for later Discord and mobile clients, restart behaviour, reporting finished runs back to the conversation, and the metrics and logs of runs.

### Modified Capabilities

- `observability-stack` (created by `add-observability`, build group 1): the price table path becomes `infra/pricing/pricing.yaml` in the Token Cost dashboard and the pricing requirement, and the agent reads the same file for run cost (moved from `add-observability` task 14.3 in the dependency fix of 2026-10-05).

(Otherwise none. `mcp-startup-resilience` requires the filtered MCP provider to be the only `ToolCallbackProvider` bean. This change keeps that true: the subagent tools are added to the chat tool list without registering a second `ToolCallbackProvider` bean. `prompt-caching` was reviewed too: subagent model calls go through the same `PromptCacheStrategy` and its requirements do not change.)
