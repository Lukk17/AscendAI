## Context

See proposal.md for why. This section holds only the current state that shapes the approach.

- The chat path is `PromptController` to `AscendChatService.prompt(...)` to `ChatExecutor.execute(...)`. `ChatExecutor` builds a new `ChatClient` per call with `defaultToolCallbacks(toolCallbackProvider.getToolCallbacks())`, passes `toolContext(Map.of("user_id", userId))`, applies the provider's `PromptCacheStrategy`, and lets Spring AI run the tool loop inside `.call()`.
- MCP tools reach the model only through `FilteredToolCallbackProvider` (`config/mcp/`), which lists tools of `CONNECTED` clients, sanitises names to `^[a-zA-Z0-9_-]+$`, renames collisions and caches the listing (`McpToolCallbackCache`, ADR-010). The `mcp-startup-resilience` spec requires it to be the only `ToolCallbackProvider` bean.
- `ChatModelResolver` builds one `ChatModel` per enabled provider at startup. After `upgrade-spring-boot-4` (its D6) a chat model no longer runs tools: `ChatExecutor` registers `ToolCallingAdvisor.builder().toolCallingManager(trackingManager).build()` on the `ChatClient` it builds, the `TrackingToolCallingManager` inside that advisor records tool names in the thread local `ToolCallTracker`, and `ChatModelResolver` passes no manager to the models.
- Token usage is recorded by `GenAiTokenUsageRecorder` from every `PromptCacheStrategy.recordOutcome(...)`. Prices exist only in `infra/observability/grafana/dashboards/pricing.yaml`, per provider, in dollars per 1000 input and output tokens.
- Persistence is Spring Data JDBC (`@Table`, no JPA) on PostgreSQL. Schema changes use Liquibase today (only `01-initial-schema.xml` exists), and `upgrade-spring-boot-4` replaces it with Flyway 12.4.0 (its design D15 to D17): versioned SQL migrations `V<n>__<description>.sql` in `apps/ascend-agent/src/main/resources/db/migration/`, after its `V1__initial_schema.sql`. This change writes its schema as one such Flyway migration only.
- The conversation key today is the user id (`PersistentChatMemory`, Redis `chat:<userId>`). `add-chat-streaming-and-conversations` (build group 3, position 9) lands before this change and turns it into a conversation UUID with its `conversations` table.
- Security is the Keycloak login of `add-keycloak-login`, which lands before this change (build group 3, right after `upgrade-spring-boot-4`, split of 2026-10-04, owner rule of 2026-10-04): an OAuth2 resource server with the roles `USER` and `ADMIN`, one authorization matrix that each later change extends with its own rows (its D4), and `TenantContext.currentTenantId()` answering the tenant `default`, with `TenantContext.runAs(tenantId, action)` for code that runs on another thread (its D3 and task 3.9). `add-tenant-isolation` (company, build group 5) later brings several tenants, and `add-tenant-policy` (company, build group 5) later registers a per-tenant tool allow-list as the implementation of the `TenantToolPolicy` port of `add-agent-skills`.
- `add-usage-metering-and-quotas` (company, build group 5) plans a usage ledger with one row per model call and metered operation, a quota gate that blocks when a calendar month (tenant) or calendar day (user) budget is already used up, and accepts that one request may overshoot by its own size (its design D4 and D5). It plugs in later through `UsageEventPort` of `add-deployment-modules` and `QuotaGate` of `add-deployment-modules` (D12).
- `add-chat-streaming-and-conversations` (build group 3, position 9, lands earlier) adds a streamed chat endpoint with a closed set of SSE events (`delta`, `sources`, `done`, `error`) and ends the turn when the client disconnects (its design D2 and Risks).
- The runtime image is `eclipse-temurin:21-jre-alpine` with no `git` binary.

### What the library gives, read from its source

The source of `spring-ai-community/spring-ai-agent-utils` at the 0.12.0 release commit (`de8c937`, the later `HEAD` only bumps versions) was read for this design. Beyond the facts the owner listed, it shows:

- `BackgroundTask` does have `cancel(boolean)`, but it calls `CompletableFuture.cancel`, which never interrupts the running supplier, and `getStatus()` then reports the task as `Failed: ...`. So in effect there is still no cancel.
- `TaskTool.Builder.build()` always adds four built-in classpath definitions (`general-purpose`, `Explore`, `Plan`, `Bash`) when the `CLAUDE` kind is registered, and its description template is private and written for Claude Code (it tells the model to prefer `Read` and `Glob`, tools this agent does not have).
- `ClaudeSubagentType.Builder.build()` gives every subagent `ShellTools`, `FileSystemTools`, `GrepTool`, `GlobTool`, `TodoWriteTool` and `SmartWebFetchTool` by default, plus Brave search when `BRAVE_API_KEY` is set. These run inside the agent's own process. A shell and file access inside the agent container must never be offered. Shell and file work is allowed only through the sandbox tools of `add-agent-sandbox` (D9a).
- `ClaudeSubagentResolver` parses front matter with the library's `MarkdownParser`, which reads one `key: value` per line. A YAML list (`tools:` followed by `- a` lines) or a multi line value is lost or garbled, and `ClaudeSubagentDefinition.getName()` throws a `NullPointerException` when `name` is missing.
- `ClaudeSubagentExecutor.execute(...)` returns `.call().content()`, so the token usage of the response is dropped, and it ignores `TaskCall.resume` as well as `TaskCall.model`. Its alias table maps `opus`, `sonnet` and `haiku` to fixed model ids.
- `TaskTool.TaskFunction` is a `Function<TaskCall, String>`, so a tool call carries no `ToolContext` and an executor cannot know its caller, its depth or its conversation.
- `DefaultTaskRepository` keeps every task in a map forever, with no eviction and no persistence.

## Goals / Non-Goals

**Goals:**

- Use the library's interfaces and data types, with our own runner, loader and `Task` tool (owner decision of 2026-10-02), and write only the parts the gaps above force us to write, each one as an implementation of a library interface or a small class next to it, never a fork or a copy of library code.
- Keep the MCP tool filtering contract of `mcp-startup-resilience` exactly as it is.
- Make every limit a configuration value with a safe default.
- Make a run's state, cost and last step readable at any time from the database, so status survives a restart and a second agent instance can answer for it.

**Non-Goals:**

- Resuming a run after a restart, and the `resume` parameter of `TaskCall`. Both need the run's full message history persisted and replayed, and a replay can repeat tool side effects.
- A Discord bot or a mobile screen for runs. This change makes the view, the event and the run event stream ready for them.
- Per-tenant limit values. Limits are deployment wide in this change. Per-tenant values belong with `add-tenant-policy`.
- Currency on invoices. Cost per run in dollars is a limit and a display value, the usage ledger stays the billing record.
- Remote subagents over A2A (`spring-ai-agent-utils-a2a`). The SPI allows them later as another `SubagentType`.
- Proposing anything upstream to `spring-ai-agent-utils` (owner decision of 2026-10-02).
- The sandbox itself: its container, its isolation and its tools belong to `add-agent-sandbox`. This change only lets a definition name those tools and passes them through the same permission rules as every other tool.
- The capability index itself, `CapabilitySource`, `CapabilityIndexSync` and the `skill_search` tool: all belong to `add-agent-skills`. This change only makes its definition registry a `CapabilitySource` of type `subagent`.

## Decisions

### D1: Reuse map

| Library piece | Use | Why |
| :--- | :--- | :--- |
| `TaskCall` | Reused as the `Task` tool input type | Same contract as Claude Code, keeps definitions portable |
| `TaskOutputTool.TaskOutputCall` | Reused as the `TaskOutput` tool input type | Same contract |
| `SubagentDefinition`, `SubagentResolver`, `SubagentExecutor`, `SubagentReference`, `SubagentType` | Implemented and used as the seams | This is the SPI the owner asked to extend |
| `ClaudeSubagentDefinition` | Reused as the loaded definition object | It already exposes `tools()`, `disallowedTools()`, `skills()`, `getModel()`, `permissionMode()`, `getContent()` |
| `ClaudeSubagentReferences.fromRootDirectory` | Reused to list the files, filtered to exclude `.git/` | It already walks the folder and builds references |
| `ClaudeSubagentResolver` | Not used. `YamlSubagentResolver implements SubagentResolver` (kind `CLAUDE`) parses with SnakeYAML, which Spring Boot already ships, normalises list values to the comma joined form `ClaudeSubagentDefinition` expects, and builds a `ClaudeSubagentDefinition` | `MarkdownParser` loses YAML lists and multi line values |
| `ClaudeSubagentExecutor`, `ClaudeSubagentType` | Not used. `AscendSubagentExecutor implements SubagentExecutor` (kind `CLAUDE`), wrapped in a plain `new SubagentType(resolver, executor)` | Dangerous default tools, model override ignored, usage dropped, no cancel or limit checkpoints |
| `TaskTool`, `TaskTool.TaskFunction`, `TaskTool.Builder` | Not used. `SubagentTaskTool` is a `BiFunction<TaskCall, ToolContext, String>` built into a `FunctionToolCallback` named `Task` | Resolves once, injects built-ins, no `ToolContext`, Claude Code specific description that lists every subagent in every request (D6a) |
| `TaskOutputFunction`, `TaskRepository`, `DefaultTaskRepository`, `BackgroundTask` | Not used. `SubagentTaskOutputTool` reads the run table | The in-memory repository loses runs on restart, cannot scope by conversation and cannot report `waiting` or `cancelled` |

The alternative of forking the library was rejected by the owner. The alternative of using `TaskTool.builder()` and rebuilding the whole `ToolCallback` on every reload was rejected because it still injects the four built-ins with the dangerous tools behind them and still gives the executor no caller context.

An ADR in `apps/ascend-agent/docs/architecture/decisions/` (the next free number at implementation time, after the records of `upgrade-spring-boot-4` and `add-agent-skills`, never a number fixed now, named `ADR-NNN-subagents-through-the-library-spi.md`) records this table and its reasons. Nothing is proposed upstream to the library.

### D2: Tools reach the chat without a second `ToolCallbackProvider` bean

`ChatToolset` and `AgentNativeTool` are owned by `add-agent-skills` (its design D3), which lands before this change. `ChatToolset` returns the tools for one chat turn or one run: the filtered MCP callbacks from the existing `ToolCallbackProvider`, plus the callbacks of every `AgentNativeTool` bean. This change adds no composition point of its own. It registers one `AgentNativeTool` bean that returns `Task`, `TaskOutput` and, for the main chat and for a run of kind `self_review` only (D9), `subagent_definition_write`. The `mcp-startup-resilience` scenario "only one `ToolCallbackProvider` bean" stays true.

Tool context: `add-agent-skills` owns the keys `user_id`, `request_id`, `tenant_id` and `embedding_provider` (its D3). This change adds `conversation_id`, `subagent_run_id` (absent for the main chat), `subagent_depth` (0 for the main chat), `subagent_run_kind` (absent for the main chat, else the run's kind of D13), `scheduled_job_id` (only for a run of kind `scheduled`, asked for by `add-scheduled-tasks`). The key `user_message` that the paste rule of D6 reads is owned by `add-agent-skills` (its D3 and D8), because since answer 93 of 2026-10-08 one paste rule serves both catalog types. A run's own tool context carries the caller's `user_id`, `request_id`, `tenant_id`, `embedding_provider` and `conversation_id` unchanged, plus its own `subagent_run_id`, `subagent_depth` and `subagent_run_kind`, so `skill_search`, the skill tools and the sandbox tools work inside a run as they do in the main chat, and an `AgentNativeTool` bean can tell the main chat and each kind of run apart. A run that has no caller (kinds `scheduled`, `self_review` and `integration`) gets the tenant, user and conversation its starter gives, and `conversation_id` is absent when there is none. `add-agent-soul` (build group 4, position 4) later adds its key `request_provenance` (its D15) to the tool context in its own task: a run started by `Task` gets a holder of its own that starts at the caller's current value and is raised by the run's own tool calls, and a run with no caller starts at the value its starter gives. A `self_review` run starts at the review's recorded provenance and its own tool calls do not change it (`add-agent-soul` D15).

Sandbox tools and the tool context (owner answer 21.6 of 2026-10-02): the sandbox tools `shell`, `file_read` and `file_write` of `add-agent-sandbox` are offered to the main chat as well as to runs. Each conversation uses its own sandbox workspace, found by `tenant_id` and `conversation_id` when the context holds no `subagent_run_id`, and each run uses its own workspace, found by `subagent_run_id` (D9a).

Module (owner decision of 2026-10-02): this change is split between `core-chat` and the module `subagents` of the catalog of `add-deployment-modules`, which requires `skills` (its D3).

- Module `subagents`, with `@ConditionalOnModule("subagents")`: the subagent definitions and everything that serves only them (the type `subagent` of the one catalog of `add-agent-skills` D24, `SubagentCatalogType`, with the routes `/api/v1/subagents/definitions` of that change's `CatalogController`, `subagent_definition_write`, `YamlSubagentResolver`, `SubagentDefinitionValidator` and `SubagentDefinitionStore`, the type's use of `VersionedFolder`), their registry `SubagentRegistry`, the tools `Task` and `TaskOutput`, and `AscendSubagentExecutor`, the thin adapter of the library SPI that turns a definition into a run (D8). With the module off none of them is a bean, `/api/v1/subagents/definitions` answers 404, and no chat request is offered `Task`, `TaskOutput` or `subagent_definition_write`. A tenant whose policy does not grant `subagents` gets none of these tools (the module filter of `ChatToolset`, `add-agent-skills` D3 step 1) and 403 with code `module_denied` on `/api/v1/subagents/definitions` (`add-deployment-modules` D8).
- `core-chat`, with no marking: the run table and its migration (D13), `SubagentRunService` with the port `ScheduledRunStarter` (D14a), `RunController` under `/api/v1/runs` with its event stream (D17), the run loop `RunLoop` (D8), `RunSlots`, `RunBudget`, `PriceTable`, `SubagentModelResolver`, `ToolPermission`, `SubagentProperties` (the limits, models and price file that runs of every kind read, D10 to D12), the finished runs block (D16), the run metrics (D19), the system task `run-orphan-sweep` and the retention entry `subagent-run` (D14). These serve runs of every kind, and the main chat approvals that `add-action-approvals` shows in the run list through `RunViewSource` belong to `core-chat` too, so `/api/v1/runs` exists in every deployment, whatever modules are active. With `subagents` off it lists the runs of the other kinds only.

There is no `app.subagents.enabled` flag. The run table is the same in every deployment, as every schema is (`add-deployment-modules` D15). Because the `core-chat` part holds no library type, the library `spring-ai-agent-utils` is used only by the classes of the module `subagents`.

Tenant tool policy: `ChatToolset` of `add-agent-skills` applies its `TenantToolPolicy` port to every MCP tool and every agent native tool (its D3 step 2 and D16), so `Task`, `TaskOutput` and `subagent_definition_write` are governed by the same port. `ToolPermission` (D9) asks the same port again when a run starts. Its default `ConfiguredTenantToolPolicy` denies only the tools listed in `app.tool-policy.denied-tools` of `add-agent-skills` (empty by default), so the personal deployment offers all three until the owner lists one. `add-tenant-policy` (company, build group 5) registers its allow-list implementation later, where the three tools ship off for a new tenant. This change does not wait for it. The tenant comes from `TenantContext.currentTenantId()` of `add-keycloak-login`, which this change uses and does not duplicate. Because a run works on its own thread, `SubagentRunService` captures the caller's tenant on the request thread and runs the whole run inside `TenantContext.runAs(tenantId, action)` of `add-keycloak-login`, with the security principal bound the same way and cleared at the end, so every MCP tool listing and every policy check inside the run sees the right tenant. A run with no tenant to bind fails with `INTERNAL_ERROR` before any model call.

### D3: Definition registry, snapshot and last good version

`SubagentRegistry` is the part of the one catalog snapshot of `add-agent-skills` (its `CatalogSnapshot` in `CatalogHolder`, D24, answer 89.5 of 2026-10-08) for the type `subagent`, an immutable `DefinitionSnapshot`: a map from name to the loaded `ClaudeSubagentDefinition`, its origin, its version (the git blob id of the file) and its source file, plus a list of per file results (`loaded`, `invalid`, `conflict` with messages). A reload reads every file, validates each, and builds a new snapshot. For a file that fails, the previous snapshot's entry of the same name stays, and one WARN line names the file, the kept version and the first validation message. An agent instance that holds no previous entry in memory (it started after the broken edit, or restarted) takes the last good version from git: the newest commit touching the file whose content passes validation, so every agent instance serves the same version (answer 87). Two files with the same `name` are both marked `conflict` and the previous entry of that name stays. The swap is one `set`. A chat turn or a run reads the snapshot once when it starts and keeps that object, so a reload never changes a run in the middle.

`SubagentDefinitionValidator` holds every rule of the `subagent-definitions` spec in one place, and the catalog loader and the catalog write path of `add-agent-skills` both call it as the validator of the type `subagent`. Agent-written rules (D7) are a second validator step that only the write path calls with origin `agent`.

### D4: Folder, volume, atomic writes and git history

- Folder: `app.subagents.definitions.root`, default `${app.agent-home}`, the agent home root of `add-agent-skills` (its D7 and D11: `/app/agent-home` in the container and `${user.home}/.ascend-agent` for `bootRun`), so skills and definitions always share one root. Each tenant's definitions live in `tenants/<tenantId>/.claude/agents/` below it. The tenant folder `tenants/<tenantId>/` is the same one that holds the tenant's skills in `skills/`, which `add-agent-skills` keeps as its own repository. This change never reads or writes `skills/`. Tenant ids are slugs (`[a-z0-9-]{1,64}`, the tenant slug rule that the write path of `add-agent-skills` checks, its D6), so they are safe as path segments, and the write path checks the slug again before building a path. `compose.yaml` already mounts the named volume `agent-home` of `add-agent-skills` at `/app/agent-home`, and the Dockerfile of that change creates the folder owned by `app`, so this change adds no volume. `SubagentRegistry` holds one snapshot per tenant. A named volume and not a bind mount, because file events from a Windows host bind mount often do not reach the container, and because the definitions are runtime data, not source.
- Git: this change has no git code of its own. It reuses `VersionedFolder`, the generic JGit component that `add-agent-skills` owns and creates (its design D13 and task 6.1): open or initialise a repository, commit with given trailers, commit uncommitted changes as external, history for a path, read a path at a commit. The JGit entry in the version catalog comes from `add-agent-skills` too (its task 1.1). `SubagentDefinitionStore` is the thin subagent-specific user of it, the same way `SkillRepository` is for skills. Layout, matching `add-agent-skills`: one git repository per tenant definitions folder, `tenants/<tenantId>/.claude/agents/`, never one repository at the root or at the tenant folder `tenants/<tenantId>/`, so it never nests with the tenant's `skills/` repository. The reason is the same as in that change: tenant erasure deletes the tenant definitions folder, and with it the tenant's whole history of definitions, with no history rewrite and without touching any other tenant. At startup `SubagentDefinitionStore` opens or initialises the repository of the `default` tenant and of every tenant definitions folder it finds, through `VersionedFolder`, and creates the folder and repository of any other tenant on that tenant's first write. It commits as the catalog's configured author, `app.skills.git.author-name` and `app.skills.git.author-email` of `add-agent-skills` (defaults `ascend-agent` and `ascend-agent@localhost`, answer 98), and commits any file found uncommitted with source `startup`, so hand edits on the volume are recorded too. Commit message: first line `<action> <name>`, then `source: ...`, `origin: ...`, `request: ...` (the chat request id of `add-agent-skills`, when there is one) and `run: ...` (when there is one) trailers. The write path also writes, when its caller gives them, the trailers `reason: ...` (the optional `reason` argument of `subagent_definition_write`, D6), `self-change: ...` (the change id of `add-self-improvement`) and `provenance: retrieved|untrusted` (the request provenance of a self-written change that is not `clean`, `add-self-improvement` D7), all three asked for by `add-self-improvement`. Every trailer value is written as one line, with each line break replaced by a space, so a value can never add a trailer of its own, the rule `add-agent-skills` D6 uses. The origin is `owner`, `agent` or `guard`. `guard` marks a revert made by the regression guard of `add-self-improvement` through this write path, and no tool can ever write it. No user id and no conversation id is written into git (today the conversation id is the user id), because git history cannot be edited when a user asks for erasure. History reads use `git log -- <name>.md` in the tenant's repository. Revert reads the blob at the commit and sends it through the write path.
- Shipped read-only definitions: this change ships none. If read-only definitions are shipped later, they stay global, outside every tenant repository, and the write path never writes them, as for shipped skills in `add-agent-skills`.
- Atomic write: write to `<name>.md.tmp-<uuid>` in the same folder, `fsync`, then `Files.move` with `ATOMIC_MOVE` and `REPLACE_EXISTING`. Before writing, the resolved real path of the target must be inside the real path of the folder, and an existing target must not be a symbolic link. The file name comes only from the validated `name`. The loader ignores files ending in `.tmp-*` and files under `.git/`.
- Writes, reverts, deletes and the commit of hand edits run in the one catalog write path `CatalogWriteService` of `add-agent-skills` (its D6 and D24), in one Postgres transaction under the transaction advisory lock keyed by the type `subagent` and the tenant, so they run one at a time across every agent instance and two instances never commit in one repository at once (answer 87). The write path validates, writes, commits, then triggers a reload itself, sends the `catalog_changed` notification so every other instance reloads that tenant too, and returns the reload's result for that name. The watcher event that follows finds nothing new. This keeps the call synchronous and still makes the folder the single source of truth.

### D5: Folder watcher

The definitions folders are watched by the one catalog watcher `CatalogWatcher` of `add-agent-skills` (its D5 and D24), with which this change registers its type, and this change adds no watcher of its own (answer 89.5 of 2026-10-08). It watches `tenants/`, every tenant folder and every tenant's `.claude/` and `.claude/agents/` folder (the JDK watch is not recursive), registers each of them when it appears, and ignores every other entry of a tenant folder, such as `skills/` of the type `skill`, `soul/` and `users/` of `add-agent-soul` or `integrations/` of `add-self-built-integrations`. After the quiet period `app.skills.watch.quiet-period` (500 milliseconds by default) it reloads the definitions of the tenant whose folder changed (a full reload of that tenant, which is simpler than per file updates while the folder is small). An `OVERFLOW` event triggers a full reload too. The catalog's fingerprint rescan (`app.skills.watch.rescan-interval`) covers volumes that deliver no file events, the `catalog_changed` notification of `add-agent-skills` D24 brings in a write or reload made on another agent instance (answer 87), and the reload endpoint stays. This replaces the 300 millisecond debounce and the owner decision of 2026-10-02 that no polling fallback is added: by answer 89.5 one watcher with one rescan serves both types. If the watch service cannot be registered (some file systems do not support it), the agent logs one WARN at startup naming the folder, the rescan interval and the reload endpoint, and keeps running.

### D6: Write sources, one path, and how a chat paste is told apart

- REST: the one `CatalogController` of `add-agent-skills` (its D24), on the route `/api/v1/subagents/definitions`, calls the catalog write path `CatalogWriteService` with source `rest` and origin `owner`.
- Guard: the regression guard of `add-self-improvement` reverts a definition by calling `CatalogWriteService` directly with source `agent` and origin `guard`. No tool can write origin `guard`.
- Chat: the main chat gets the tool `subagent_definition_write` (input: `content`, optional `action` of `upsert` or `delete`, optional `reason` of at most `app.skills.limits.max-reason-chars` characters of `add-agent-skills` (default 300, answer 98), written into the `reason` trailer of D4 and asked for by `add-self-improvement`. A longer `reason` is refused as text with no commit). `StreamingChatExecutor` of `add-chat-streaming-and-conversations` puts the current user message text into the tool context under `user_message`, a key of `add-agent-skills` (its D3). The check below is the one paste rule of the catalog, the same for skills (`add-agent-skills` D8, answer 93 of 2026-10-08): if the submitted content, with line endings normalised to `\n` and outer blank lines trimmed, appears in full in the user message, the source is `chat` and the origin `owner`. Otherwise the source is `agent` and the origin `agent`. A model cannot pass the check by copying content the user did not paste, because the check is against the user's own message text, not against anything the model says.
- Agent: the same tool, when the check above fails.

Delete through chat follows the same rule: a delete is owner only when the user message names the definition and asks for deletion, which cannot be checked reliably, so every chat delete is treated as agent. An agent may replace or delete only definitions whose origin is `agent` or `guard` (the rule `add-self-improvement` asks for, the same as for skills in `add-agent-skills` D8).

### D6a: Finding subagents through the shared capability index

While search is turned on (`app.skills.search.enabled`, the default), the `Task` tool description does not list the loaded subagents. With up to 100 definitions per tenant, a full list in every request would cost tokens on every turn and grow the tool list part of the prompt. Instead every loaded definition is an entry in the shared capability index that `add-agent-skills` owns in the vector store (its D18 to D21), with `type` `subagent`, and the model finds subagents with that change's `skill_search` tool and `type` `subagent`. The `Task` description tells the model to search with type `subagent` first and then call `Task` with the name it found.

- `SubagentRegistry` implements `CapabilitySource` of `add-agent-skills` (its D18) for type `subagent`. For one chat request or run it gives the definitions of the tenant snapshot that request or run started with (D3), with name, description and entry key. After every reload of a tenant (startup, watcher, endpoint, write) it reports the new snapshot of that tenant scope to `CapabilityIndexSync` (its D20), with the reload's trigger. This change adds no index code of its own: the entry format (its D18: type, name, scope `tenant`, tenant, entry key, source, embedding provider, content hash), the full rebuild at startup and on the reload endpoint, the incremental update on watcher and write reloads, the pending entries and their retry, the text match fallback and the log lines are all that change's.
- A definition that keeps its last good version (D3) stays in the snapshot with its last good name and description, so the index keeps its last good entry.
- The index is used only to find a subagent. `Task` always resolves the name in the turn's own snapshot (D3), so an index entry that is a moment behind a reload can never start a definition that is no longer loaded, and an unknown name is refused as before.
- An index update that fails (the vector store is down, the embedding call fails) leaves the affected entries pending, as `add-agent-skills` D20 describes. It never blocks loading, `Task` by name keeps working, and `skill_search` finds pending definitions through its text match.
- Index entries are keyed by tenant, so `skill_search` of one tenant never returns a subagent of another (the filter is the index's own tenant field and the allowed keys of `add-agent-skills` D19).
- A run finds deeper subagents the same way, when its computed tools (D9) include `skill_search`.
- When `app.skills.search.enabled` is false, `add-agent-skills` does not offer `skill_search`, and the `Task` description lists the name and description of every definition in the tenant snapshot the chat turn or run started with (D3), in name order and with markup characters escaped. This is the same fallback `add-agent-skills` uses for skills, where the `Skill` description then lists every skill of the request (its D19). With search off, the `Task` description therefore changes when the tenant's definitions change, so the provider prompt cache entry is renewed after a definition change, as it is for the `Skill` description. The same snapshot always gives the same description bytes.

### D7: Rules for agent-written definitions

Enforced in the write path, from the `subagent-definitions` spec: explicit `tools` required, every tool must be in the writing conversation's current tool list (taken from the tool context of the call), never the write tool, model on the allowlist, never replace or delete a definition whose origin is `owner`, `origin: agent` stamped by the server. There is no setting of this change that turns agent writes off (answer 89.17 of 2026-10-08): listing `subagent_definition_write` in `app.tool-policy.denied-tools` of `add-agent-skills` is the one switch, and it removes the tool with its paste path. The owner then saves definitions through REST.

The subset rule in a self review (asked for by `add-self-improvement`): a run of kind `self_review` writes for a request it did not take part in, and its own fixed tool set says nothing about what that request could do. So in such a run the "tool list of the writing conversation" is the list of tools the reviewed request had, which `add-self-improvement` stores in the review's evidence (its D3) and passes to the write path. The rule itself does not change: an agent-written definition can never name a tool the reviewed request did not have.

Agent-written definitions are live as soon as they are written, with no approval step (owner decision of 2026-10-02), with one exception. A write through `subagent_definition_write` in a chat request whose `RequestProvenance` (`add-agent-soul` D15) is not `clean` waits for one tap of the owner's approval, as an approval request of kind `self_change` of `add-action-approvals` (owner answer 38.1, `app.self-improvement.provenance.chat-write-untrusted` default `stage`). The `SelfChangeGate` of `add-self-improvement`, which wraps the tool in `ChatToolset` (`add-agent-skills` D3 step 4), makes that decision before the write path is called, and an approved change goes through this write path with its `If-Match` stale check. The write path itself does not change for it, and before `add-self-improvement` is applied every agent write is live at once. Why live writes are acceptable: an agent-written definition can never do more than the conversation that wrote it could already do directly, every write is a git commit the owner can revert, and the limits of D10 still bind every run.

The real threat is prompt injection: a web page fetched by a tool tells the model to write a definition whose body tells future runs to leak data through a tool. The subset rule stops it from gaining new tools, the write tool is never offered to subagents (so a run cannot write definitions), and the WARN log line plus the write counter with source `agent` make it visible. It is not fully prevented, and the risk section says so.

### D8: Executor with its own tool loop

The loop lives in `RunLoop`, a `core-chat` class with no library type in it, because runs of every kind that call a model use it (D2). `AscendSubagentExecutor.execute(TaskCall, SubagentDefinition)`, in the module `subagents`, only builds the system instructions of a definition (below) and hands them with the prompt to `RunLoop`. A run of another kind is handed to `RunLoop` by `SubagentRunService` with the instructions its owning change provides.

`AscendSubagentExecutor.execute(TaskCall, SubagentDefinition)` is called with a `RunContext` held by the run's own thread (the SPI method has no context parameter, so `SubagentRunService` binds the `RunContext` in a `ThreadLocal` on the run's own thread before the call and removes it in a `finally` block. `ScopedValue` would fit better but is a preview API in Java 21, the version this module runs today). The `RunContext` holds the run's id, kind, depth, tool set, budget counters, cancel flag, the run's `RequestProvenance` holder (D6) and one optional field for the sandbox workspace id, which only the workspace service of `add-agent-sandbox` reads and writes.

`RunLoop` builds the chat request itself and runs Spring AI's user controlled tool execution: options with `internalToolExecutionEnabled(false)`, call the model, record usage, check the checkpoints, execute the tool calls through the same `TrackingToolCallingManager` that the `ToolCallingAdvisor` of `StreamingChatExecutor` holds (`upgrade-spring-boot-4` D6, answer 89.1), wrapping `ToolCallingManager.builder().build()` with its 2.0 defaults, so `ToolCallTracker` and the `mcp.tool.duration` metric keep working. The run's own loop calls the manager directly and registers no advisor, because with internal tool execution off there is no advisor loop to drive, append the tool results, and loop. `add-mcp-tool-servers` (build group 4, position 6) later adds, in its own task, a call of its `DeferredToolSelection` (its D5) before each model call, with the always part and the deferred part of the run's computed tool set (D9) and the run's messages so far, and the loop then offers the model what it returns: the always part, the tool search tool when the deferred part is not empty, and the deferred tools found by earlier searches of the run. A deferred tool that the run's definition names is put in the always part, so it is offered from the run's first model call. In this change there is no deferred part and the loop offers the computed tool set as it is. `RunLoop` keeps the step before each model call in one method, so that change plugs in without changing the loop. Checkpoints before every model call and before every tool call:

1. cancel requested,
2. deadline passed,
3. tree cost or tree tokens at or over the limit (the cost part is skipped for a run with no cost limit, D10),
4. the tool name is in the run's computed tool set (D9).

Every model call goes through the provider's `PromptCacheStrategy` (`buildOptions` and `recordOutcome`), so subagent spend shows in `gen_ai.client.token.usage` and prompt caching applies. `recordOutcome` is also the point where `RunLoop` publishes the call's usage event through `UsageEventPort` (D12), so one hook feeds the metric, the usage event and the run's own counters. Before each model call `RunLoop` calls `QuotaGate.check(QuotaRequest)` of `add-deployment-modules` for the run's tenant and user, and a refusal ends the run with `QUOTA_EXCEEDED`. The default `AllowAllQuotaGate` allows every call (D12). `maxTokens` of each call is the smaller of the provider default and the tokens the run has left. The last step is updated after every model call (`model: <first 200 characters of the assistant text or "tool calls: a, b">`) and after every tool call (`tool: <name> ok|error`).

System instructions are the definition body, then the preloaded skills from the `add-agent-skills` registry, then a short fixed footer that tells the model it is a subagent, its depth, and that its final message is returned to its caller. A run of kind `scheduled` has no definition and gets, instead of the body, the fixed footer that `add-scheduled-tasks` provides. The other kinds of D13 get the instructions their owning change provides.

`add-agent-soul` (build group 4, position 4) lands after this change and builds the run prompt itself (its task 7.3). From then on a run's system instructions go through its `PromptLayout`: three system messages, the tenant's personality block first, the global prompt second, and the definition body (or the kind's instructions), preloaded skills and footer in the dynamic block, with the personality reminder at the start of the run's first user message and no user facts. Until then a run sends the instructions above as they are. The run's budget then follows the context budget of that change with the run's provider.

Why our own loop and not an advisor around `.call()`: with internal tool execution, the whole loop is one `.call()`, so no code of ours runs between steps. Cancel, cost and time could then only act after the last step. The user controlled loop is documented Spring AI API, not a workaround. The exact option and class names are checked against the Spring AI 2.0 documentation when `upgrade-spring-boot-4` has landed.

### D9: Depth and tool permission

Computed once when a run starts, from the tool context of the `Task` call:

- `depth = caller depth + 1`, refused when over `app.subagents.limits.max-depth`.
- `tools = (definition.tools or caller tools) - disallowedTools`, then kept only where the caller has the tool, then kept only where the tenant tool policy allows it (D2), then minus `Task` and `TaskOutput` at the maximum depth, then minus the tools that are never offered to a run: `subagent_definition_write` here, `personality_propose` and `user_facts_update` of `add-agent-soul`, and the four scheduling tools of `add-scheduled-tasks`, plus `owner_notify` outside runs of kind `scheduled`.
- The result keeps the always and deferred parts that `ChatToolset` gave the caller (`add-agent-skills` D3 step 6). A tool the definition names explicitly is moved to the always part (D8).

The computation from definition and caller applies to runs of kind `subagent` only (asked for by `add-self-improvement`). A run of another kind of D13 has no definition, and most kinds no caller, so its starting tool set is given by the change that owns the kind (for example the stored tool names of a scheduled job, or the fixed set of a `self_review` run of `add-self-improvement`). It is then kept only where the tenant tool policy allows it and loses the never-offered tools above, with one documented exception: the fixed set of a run of kind `self_review` may hold `subagent_definition_write` (create only in a review, `add-self-improvement` D5), `user_facts_update` and `personality_propose` (proposal only, `add-agent-soul` D8), and they are kept. No other kind of run is ever offered any of those three tools.

The caller's tool set is stored on its `RunContext` (and for the main chat, computed by `ChatToolset` for that turn). Tool names in definitions are the names the model sees: the prefixed MCP names of `add-mcp-tool-servers` (`<prefix>_<name>`, for example `weather_current` or `web_session_status`, its D3), which may name a tool of the deferred part, plus `Task`, `TaskOutput`, the skill tool names of `add-agent-skills` (`Skill`, `skill_search`, `skill_read_file` and `skill_write`) and the sandbox tool names of `add-agent-sandbox`, `shell`, `file_read` and `file_write` (D9a), which the main chat has too, so a run started by the main chat can get them by the subset rule. Claude Code names such as `Read` or `Bash` match nothing here and are dropped with a WARN, which is the honest result.

### D9a: Sandbox tools

By owner decision of 2026-10-02, a subagent may get shell and file system tools, but only inside an isolated sandbox: a throwaway container per run, separated from the agent and from the host, so malware or a bad command cannot reach either. By owner answer 21.6 of 2026-10-02 the main chat gets the same tools, with one sandbox workspace per conversation. The sandbox is the separate change `add-agent-sandbox` (build group 4, position 3, right after this change), shared with `add-coding-agent-delegation`. That change wires its tools into runs in its own tasks, and this change does not wait for it.

- A definition may list the three sandbox tools by the names `add-agent-sandbox` gives them: `shell`, `file_read` and `file_write`. The validator accepts these names like any other tool name, and the WARN line for a tool that is not available uses the same names.
- Sandbox tools reach the tool list the same way as every other agent native tool, through `ChatToolset` and `AgentNativeTool` of `add-agent-skills`. `add-agent-sandbox` provides them as the beans `ShellTool`, `FileReadTool` and `FileWriteTool`. By owner answer 21.6 of 2026-10-02 the main chat gets them too, and each conversation uses its own sandbox workspace: with no `subagent_run_id` in the tool context the tools act in the workspace of the context's `tenant_id` and `conversation_id`, and with one they act in that run's own workspace. Inside a run they pass the same rules as every other tool (D9): the definition names them, the caller has them, and the tenant policy allows them. In the main chat they pass the module filter and the `TenantToolPolicy` port of `ChatToolset`, whose default allows them.
- Before `add-agent-sandbox` is applied, no sandbox tool exists. A definition that names one still loads, and the name is dropped with a WARN at run start like any other tool that is not available.
- A sandbox tool call never runs in the agent's process. The tool passes the call, the run id (or, in the main chat, the conversation id) and the tenant to the sandbox runner through the `SandboxClient` port of `add-agent-sandbox` (create, run, read, write, archive, destroy, with the `HttpSandboxClient` adapter), and the command runs in that run's or that conversation's own workspace container. A run's workspace id is kept in the optional field of the run's `RunContext` (D8). A conversation's workspace, its lifetime and its removal belong to `add-agent-sandbox`. The container's start, its isolation and its removal belong to `add-agent-sandbox`. This change gives it the run id and publishes `SubagentRunChangedEvent` on every final state, so the sandbox can remove the run's container when the run is `done`, `failed` or `cancelled`, also after a restart sweep (D14).
- The library's in-process `ShellTools`, `FileSystemTools`, `GrepTool` and `GlobTool` are never created. The wiring test of task 6.6 keeps asserting that no tool callback backed by one of them, and no callback named `Bash`, `Shell`, `Read`, `Write`, `Edit`, `Glob`, `Grep` or `WebFetch` that is not a sandbox tool of `add-agent-sandbox`, can be offered to a run, with or without `add-agent-sandbox`. In short: no in-process shell or file tool is ever offered.

Slots (answer 89.7 of 2026-10-08, safe with several agent instances by answer 87): `RunSlots` is the one slot pool of the platform. It keeps one pool per pool name. Each pool has a running limit and a waiting bound, which is a number, `0` (start now or refuse) or unbounded. The change that owns a run kind registers its pool with one `RunPoolRegistration` bean: the pool name, the kinds that use it, the running limit and the waiting bound, both read from that change's own properties. This change registers the pool `subagent` for the kinds `subagent` and `scheduled`, with `max-running` and `max-waiting` above. No change keeps a slot pool, semaphore or slot counter of its own.

The counts live in Postgres, in the `subagent_run` rows, so they hold across every agent instance. A run holds a slot while its row is `running` with `holds_slot` true (D13). A foreground run started by another run of the same pool works in its caller's slot, because the caller only waits for it, so its row has `holds_slot` false. A run in `waiting` or `awaiting_approval` holds none. Each run works on its own virtual thread on the instance that accepted it. Every queue and start step runs in one transaction under the pool's transaction advisory lock (`pg_advisory_xact_lock` on a key derived from the pool name):

- Queue: a background run counts the pool's `waiting` rows, is refused when they reach the waiting bound, and otherwise inserts its row as `waiting`. A refused call creates no row.
- Start: while the pool's rows with `holds_slot` true are below the running limit, an instance moves the oldest `waiting` row of the pool (by `created_at`, then `id`) to `running` with `holds_slot` true, but only when that row is its own (`owner_instance`), so arrival order holds across the cluster and each run starts on the instance that holds its thread. When the oldest row belongs to another instance, that instance starts it.
- Start now: a foreground run started by the main chat, and every acquire of a pool whose waiting bound is `0`, inserts its row directly as `running` when a slot is free and is refused at once otherwise, so an HTTP request never hangs on a full pool.
- Wake: a run that leaves `running` (a final state or `awaiting_approval`) sends `pg_notify('run_slot_freed', '<pool name>')` in the same transaction. `RunSlots` is a `PostgresNotificationHandler` of the one `PostgresNotificationListener` of `add-keycloak-login` D20 for the channel `run_slot_freed`, and opens no connection of its own: every instance with a waiting run of that pool tries a start when it hears it. A poll every `heartbeat-interval` is the fallback, and `onReconnect()` tries a start for every pool. A slot held by a run of a dead instance is freed when the orphan sweep (D14) closes that run, which sends the same notification.

The other pools are registered by the change that owns the kind, in its own task: kind `coding` uses the pool `coding` of `add-coding-agent-delegation` (`app.coding.limits.max-running`, default 1, and `max-waiting`, default 4), kind `integration` the pool `integration` of `add-self-built-integrations` (its safety bound `max-running-builds`, default 1, and no waiting bound, so builds wait in arrival order with no count limit, owner decision 40.4), and kind `self_review` the pool `self_review` of `add-self-improvement` (`review.max-concurrent`, default 1, waiting bound `0`, so a review that finds no slot ends `skipped`). A coding run or a build holds a disk and gigabytes of memory for a long time and must not starve subagents. The execution of an approved main chat action of `add-action-approvals` is one tool call and takes no run slot (its D7). The limits of D10 stay the pool `subagent`'s.

Waiting for approval (asked for by `add-action-approvals`): a run in state `awaiting_approval` holds no worker slot and its deadline watchdog is paused, so waiting time never counts against `max-duration-per-run`. `SubagentRunService` offers two methods for this, built and tested here with a stub caller: `pauseForApproval(runId, approvalId)` moves the run from `running` to `awaiting_approval` with a conditional update, stores `approval_id`, releases the run's slot, pauses its watchdog and applies the foreground detach of D14a, and `resumeAfterDecision(runId)` takes a slot again in arrival order like a waiting run, moves the run back to `running`, clears `approval_id` and resumes the watchdog. `add-action-approvals` calls them from its gate, on the run's own thread. The paused run keeps its heartbeat, because its conversation lives only in its thread's memory. Both methods are conditional updates on the run row, and the approval decision reaches a paused run on another instance through the shared `approval_request` row, which the waiting thread of `add-action-approvals` reads at every heartbeat interval (its D6), never through an in-process signal alone (answer 87).

Budgets: a child's limits are `min(configured, parent remaining)`, computed at start from the parent's in-memory `RunContext` counters. Every model call's usage is added to the run's and every ancestor's `AtomicLong` counters and, in one statement, to their rows (`UPDATE subagent_run SET input_tokens = input_tokens + ?, output_tokens = output_tokens + ?, cost_usd = cost_usd + ? WHERE id = ANY(?)`), so concurrent children never lose an update. A deadline watchdog (one local scheduled task per run, on the run's own instance) interrupts the run's thread at its deadline, and is paused while the run is `awaiting_approval`.

### D12: Cost meter, the usage ledger and the one price table

Two records, one source of usage. Every model call of a run is published as one `UsageEvent` through `UsageEventPort.record` of `add-deployment-modules` (its decision "Company extension ports") with `run_id` and `parent_run_id` and a request type that follows the run's kind: `subagent` for kind `subagent`, `scheduled` for kind `scheduled` and `self-review` for kind `self_review`. The default `NoOpUsageEventPort` records nothing. `add-usage-metering-and-quotas` (company, build group 5) registers its ledger-backed implementation later, which turns each event into a ledger row of its D14, the billing record. A coding run makes its model calls inside its workspace, so the orchestrator of `add-coding-agent-delegation` publishes one `coding-agent` usage event per model it used when the run ends. Runs of kind `integration` make no model call of their own and publish no model usage event (the coding child of an integration build publishes its own `coding-agent` events). The mapping lives in one place, on the `SubagentRunKind` enum, where each kind holds its ledger request type or none, and `RunLoop` reads it from the run's kind, so no call site names a request type. Every metered operation called by a run's tools (web search, OCR, transcription) carries the same two ids because the run binds them in the run context that a usage event reads. The run's own counters (`input_tokens`, `output_tokens`, `cost_usd` on `subagent_run`) are the fast running total that the limits read before each child call, updated from the same `recordOutcome` call. They are never summed from the ledger at check time, because that would be a database aggregate per model call. Usage for a run can be checked against the published events, and task 4.7 does exactly that in a test with a capturing port. The quota gate before each model call is the shared port `QuotaGate` of `add-deployment-modules` (its decision "Company extension ports", ruling 13.1 of 2026-10-05), called with a `QuotaRequest` for the run's tenant and user, whose default `AllowAllQuotaGate` allows every call. This change adds no quota port of its own. `add-usage-metering-and-quotas` registers its quota implementation later, and a refusal ends the run with `QUOTA_EXCEEDED`.

Order of landing (owner decision of 2026-10-02, kept by the owner build order of 2026-10-04): this change lands long before `add-usage-metering-and-quotas`, which is company work in build group 5. Until that change registers its implementations, no usage event is stored and no quota refuses a call, and the run counters, the cost meter and the per-run limits of D10 work alone. The ledger rows and the quota implementation arrive with that change, in its own tasks (dependency fix of 2026-10-05). Nothing in this change waits for it.

The per-run budget is checked before each model call and before a child is started. ### D14: Restart, crash and shutdown

Each process gets a random `owner_instance` id at startup. A running or waiting run renews `heartbeat_at` every `heartbeat-interval` (waiting runs too, so a crash while queued is found, and a paused run of kind `subagent` in `awaiting_approval` too, because its conversation lives only in its thread's memory). A sweep moves every `waiting`, `running` or `awaiting_approval` row whose `heartbeat_at` is older than `heartbeat-stale-intervals` intervals (default 3, D10) to `failed` with `AGENT_RESTARTED`, and publishes `SubagentRunChangedEvent` for every run it closes, so listeners such as the workspace cleanup of `add-agent-sandbox` see those runs end too. A main chat approval waiting for the owner is not a run row (owner answer 89.4 of 2026-10-08), so the sweep needs no exception. When the sweep closes a paused run, the `SubagentRunChangedEvent` it publishes is how `add-action-approvals` cancels that run's pending approval, and the sweep's update sends the `run_slot_freed` notification of D10. Rows of a live second instance keep fresh heartbeats and are left alone.

Where the sweeps run (asked for by `add-shared-scheduler`, which owns the engine): the periodic sweep is the system task `run-orphan-sweep` on the shared scheduler of `add-shared-scheduler`, which runs each system task on exactly one agent instance, with the default `app.scheduler.system-tasks.run-orphan-sweep.cron` `*/5 * * * *` and `.time-zone` `UTC`, both settings with the environment variables of D10 under the contract of `add-shared-scheduler` D2, because it repeats every five minutes and must not skip or repeat a firing at a clock change. Run retention (the retention requirement of the `subagent-run-status` spec) is the entry `subagent-run` of the one shared retention task `record-retention` of `add-shared-scheduler` (its D15, owner answer 89.7 of 2026-10-08), registered as a `RetentionEntry` bean: table `subagent_run`, time column `finished_at`, age `app.subagents.limits.retention` (30 days), and a condition written in code that selects the root of a run tree whose every run is final and finished longer ago than that age, the rest of the tree going with its root. `add-coding-agent-delegation` and `add-agent-sandbox` hook their own cleanup onto this entry with `RetentionCleanup` beans. This change adds no retention task of its own and no `run-retention` task name. The sweep and the entry are `core-chat` and are registered by this change in every deployment, whatever modules are active, because the table exists in every deployment and holds runs of kinds that other modules own. The sweep also still runs once at startup before the agent reports ready, as a local startup action. The per run heartbeat and the deadline watchdog stay local on the run's own instance, because they prove one instance alive. On graceful shutdown (`SmartLifecycle.stop`, before the datasource closes), the service refuses new runs, cancels every run it owns, waits up to `shutdown-wait` (default 10 seconds, D10) for their threads, and writes `AGENT_SHUTDOWN` on whatever is still not final.

Why not resume: the run's message history is not stored, and replaying the prompt would repeat tool calls that may have written data, sent searches or spent money. Same choice as ascend-ocr's `SERVICE_RESTARTED`.

### D14a: Runs of other kinds and pausing a foreground tree

Starting a run with no `Task` call: `SubagentRunService` implements the port `ScheduledRunStarter.start(ScheduledRunRequest)` that `add-scheduled-tasks` asks for. It inserts the run row of kind `scheduled` in the caller's transaction, starts the run's thread after commit through the same slots and waiting queue as other background runs (D10), binds the tenant and the identity given in the request, applies the cost and token limits given in the request and the run deadline `max-duration-per-run`, and refuses with a reason when the waiting queue is full. The kinds `self_review`, `coding` and `integration` are started by trusted code of their owning change through the same run service, each with its own pool (D10). No tool can start a run of those kinds.

Pausing a foreground tree (asked for by `add-action-approvals`): when a run pauses in `awaiting_approval` (through `pauseForApproval`, D10) and its tree's root is a foreground run that the main chat waits for in a `Task` call, the root becomes a background run and that `Task` call returns at once with the run id and a note that the run waits for approval. The chat request then ends, and the disconnect rule of D17 (cancel foreground runs) no longer applies to that tree. A foreground run started by another run is not moved to the background, because only a thread waits for it, not an HTTP request.

### D15: Cancel

`POST .../cancel` sets `cancel_requested_at` on the run and on every descendant that is not final, in one transaction, then, for runs owned by this process, sets the cancel flag on their `RunContext` and interrupts their threads. For runs owned by another instance, that instance sees `cancel_requested_at` at its next heartbeat and does the same, so the shared row is the cancel signal and the heartbeat is its poll (answer 87, CANON 26.1). The run's thread stops at the next checkpoint or when the interrupt breaks a blocking call, and writes `cancelled`. An HTTP model call already in flight may finish before the interrupt is noticed. Its usage is still counted, and the time limit bounds the wait.

### D16: Reporting finished runs to the conversation

`ChatContextAssembler.buildSystemMessages` gains one call that selects final runs of the conversation with `reported_at IS NULL`, renders the block from the `subagent-run-status` spec into the dynamic suffix, and sets `reported_at` in the same transaction. The static prefix is untouched, which keeps the `prompt-caching` contract.

The block lists every kind the same way, with one line per run, and adds what the owning change asks for: a main chat approval of `add-action-approvals` names the tool, the outcome and the start of the result (it comes from `RunViewSource.takeUnreported`, see below), a run of kind `coding` names the coding agent, the outcome, the start of the result and the result endpoint of `add-coding-agent-delegation`, and a run of kind `integration` names the integration and the outcome, and lists an automatic disable once. A run of kind `self_review` is never listed, and a run without a conversation (some runs of kind `scheduled`) is skipped, because no conversation waits for it.

The block also asks every registered `RunViewSource` (D17) for its finished items of the conversation that were not reported yet (`takeUnreported(tenantId, conversationId)`), in the same transaction that sets `reported_at` on the run rows, and lists them the same way, newest last. With no source registered the block lists run rows only.

Once `add-agent-soul` (build group 4, position 4, after this change) is applied, the block is one section of its dynamic block, after the conversation summary, and its context budget trims it after the summary. A request whose dynamic block holds this block with at least one run result gets the source `finished_run_result` of its D15, so its request provenance is `untrusted` (owner decision 49.3 of 2026-10-03), because a run result can carry a web page, a file or a tool output.

### D17: REST, view, event and following a run

The definition endpoints under `/api/v1/subagents/definitions` are routes of the one `CatalogController` of `add-agent-skills` for the type `subagent` (its D24, answer 89.5 of 2026-10-08), and `RunController` serves `/api/v1/runs`. Runs get the shorter, kind neutral path because a client following a run should not need to know it is a subagent run, and later kinds of background work can share it. Errors are the RFC 7807 problem detail that `upgrade-spring-boot-4` defines for every agent error (its D19, owner decision of 2026-10-02) and builds in `GlobalExceptionHandler` with one factory method: `type` (`https://ascend.ai/errors/` followed by the code with every `_` replaced by `-`), `title` (the HTTP reason phrase), `status`, `detail`, `instance` (the request path) and a top-level `code`, a stable snake case value of the endpoint's closed set, added to its `ApiErrorCode` enum. Every definition refusal that is a validation refusal answers 400 with code `validation` and the `errors` field of its D19 point 5 and of its `agent-error-responses` spec, one `field` and `message` object per validation message, sorted by `field`. That covers every rule of `SubagentDefinitionValidator` and the agent-written rules (D7): a missing or wrong front matter key, a name that breaks the pattern or differs from the path, an empty body, `permissionMode`, a token with an API key prefix, a model off the allowlist, content that is not UTF-8, and a revert whose content fails validation. `field` is the front matter key, `name`, `body` or `content`, and `message` is the validator's message, which names the rule that failed (for example `description is required`). The specific reasons are not codes: no `ApiErrorCode` value is added for them, and they appear only inside each `errors` message and in the text the write tool returns to the model. The shared codes that `add-agent-skills` owns (`conflict` for a stale `If-Match`, `unavailable`), the code `forbidden` of `add-keycloak-login` (owner answer 76.9 of 2026-10-08) and the codes of `upgrade-spring-boot-4` (`validation`, `not_found`, `content_too_large` for a body over `max-size`) are reused and never added a second time. This change adds one code of its own, `tool_not_allowed` (403, type `https://ascend.ai/errors/tool-not-allowed`, owner answer 76.7 of 2026-10-08): the write path refuses, from every source, a definition whose `tools` names a tool that the `TenantToolPolicy` port of `add-agent-skills` does not allow for the caller's tenant, the port `ToolPermission` asks again when a run starts. The check runs after validation and before anything is written. Through `PUT` and revert the refusal answers 403 with this code and a `detail` that names the refused tools, and through `subagent_definition_write` it is the tool text naming them. It is not a validation refusal, so it is not in `errors`. `add-tenant-policy` (company, build group 5) reuses the code for its allow-list later. The run view is one record, `SubagentRunView`, used by both controllers and by the event `SubagentRunChangedEvent`, which is published with `ApplicationEventPublisher` and delivered after commit (`@TransactionalEventListener(phase = AFTER_COMMIT)` on consumers), so a listener never sees a state the database does not have. Cursor pagination encodes `(created_at, id)` as an opaque base64 cursor.

`RunViewSource` (a new port of this change, no default bean) lets a later change show work in the run API that is not a row of this table. Its methods: `page(RunQuery)` returns at most `limit` views of the caller's scope after the cursor key, newest first, with the same filters as the table query (`kind` included), `find(tenantId, id)` returns one view, `cancel(tenantId, id, identity)` cancels the item, and `takeUnreported(tenantId, conversationId)` returns the finished items of a conversation not yet reported and marks them reported in the caller's transaction. The list asks the run repository and every source for at most `limit` views after the cursor, merges them newest first by `(created_at, id)` and keeps the first `limit`, so the opaque cursor stays one `(created_at, id)` pair. The read, cancel and event stream of an id the table does not hold ask the sources in turn. A `SubagentRunChangedEvent` published for a source view wakes the event stream the same way as the event of a table run, so a client following it on another instance sees it (CANON 26.1). `add-action-approvals` (build group 4, position 5) registers the only source, for its main chat approvals, which carry kind `approval`, `approvalId` equal to their id, and the states and failure reasons of its D5. This change builds and tests the merge with a stub source and does not wait for it. The run view keeps `approvalId` (from `approval_id` for a paused run, from the source for a main chat approval).
 The run view carries `kind`, `approvalId` and `scheduledJobId` from its first version, and `GET /api/v1/runs` takes a repeatable `kind` filter.

Background runs outlive the request because they work on their own virtual threads, started by `SubagentRunService`, never on the request thread. `GET /api/v1/runs/{id}/events` uses the same SSE mechanism as `add-chat-streaming-and-conversations` D3 (`Flux<ServerSentEvent<String>>` on Spring MVC, Reactor is already on the classpath): it sends the current view as `subagent_status` with the row's `version` as the SSE id, then pushes each `SubagentRunChangedEvent` for that run, and completes after a final state. A run owned by another agent instance produces no local event, so every committed change of a run row also sends `pg_notify('run_changed', '<run id>')` in its transaction (answer 87). `RunChangeRelay` is a `PostgresNotificationHandler` of the one `PostgresNotificationListener` of `add-keycloak-login` D20 for the channel `run_changed`: it reads the row and hands the view to the open streams of that run on its own instance, never to the in-process `SubagentRunChangedEvent` listeners, so a cleanup listener never runs twice. The stream also reads the row every `app.subagents.runs.events-poll-interval` (default 2 seconds, D10) as the fallback and sends it when `version` grew, and `onReconnect()` makes every open stream read its row. On reconnect with `Last-Event-ID`, the current view is sent only if its `version` is greater. `Cache-Control: no-store` and `X-Accel-Buffering: no` as in that change.

On the streamed chat turn of `add-chat-streaming-and-conversations`, the turn follows the runs it started and writes `run_started` (first event of a run) and `subagent_status` (each later change) into the stream until its own terminal event. The turn reads the events of the runs it started from the same shared source that feeds `GET /api/v1/runs/{id}/events` (the run rows in Postgres, with the `run_changed` notification and the poll fallback), not only from the in-process `SubagentRunChangedEvent`, so a run that executes on another agent instance still reaches the chat stream of the instance that holds the client connection (owner answer 87, rule R1). Its disconnect handler cancels the turn's foreground runs with `cancelledBy = parent` and leaves its background runs alone. `add-chat-streaming-and-conversations` lands before this change, so this change writes the two events and the disconnect rule on that change's streamed turn itself (task 7.4). This change adds the event names `run_started` (`{"run": <run view>}`, 0..n, non-terminal, one per run the turn starts) and `subagent_status` (`{"run": <run view>}`, 0..n, non-terminal, one per later change of such a run) to the closed event set of the chat stream of `add-chat-streaming-and-conversations` D2, with their rows in that table's documentation (`apps/ascend-agent/AGENTS.md`), their OpenAPI entries on `POST /api/v1/ai/prompt/stream`, and their serialization tests (owner answer 93 of 2026-10-08). Deleting a conversation also cancels and deletes its runs, which this change adds to that change's conversation delete (task 7.7).

## Risks / Trade-offs

- [Prompt injection writes a harmful agent definition] → subset rule, no write tool for subagents, limits on every run, WARN log and write counter for every agent write, git revert. Not fully prevented. The owner can switch agent writes off.
- [A parent waits in `TaskOutput` while holding a slot, and its background children wait for slots] → `TaskOutput` waits at most `task-output-max-wait` (default 600 seconds), every run has a time limit, and `max-running` is configurable. It can stall, it cannot deadlock forever.
- [An in-flight model call ignores the interrupt] → it finishes, its usage is counted, the time limit bounds it, and the cost limit can be passed by at most that one call, which is itself capped by `maxTokens` of the remaining budget.
- [Spring AI 2.0 renames the user controlled tool loop API] → `RunLoop` is the only class that uses it, and task 6.1 checks the API against current documentation first.
- [File events do not arrive on some volumes] → named volume by default, WARN at startup when the watch fails, the catalog rescan of `add-agent-skills` D5, reload endpoint.
- [Two agent instances write definitions at once] → the catalog write path takes a Postgres advisory lock per tenant and type, and the `catalog_changed` notification brings the write to every other instance, with the rescan as fallback (answer 87, `add-agent-skills` D24).
- [Several agent instances share the slot pools] → the slot counts live in the run rows in Postgres, every queue and start step runs under one advisory lock per pool, and a freed slot wakes the other instances through `run_slot_freed`, with a poll as fallback (D10).
- [The price table is per provider, not per model] → cost of a cheap model on an expensive provider is overestimated. That errs on the safe side for limits. Per model prices can be added to the same file later without changing this design.
- [Runs store prompts and results] → retention deletes them, and `add-audit-and-gdpr-compliance` includes `subagent_run` in user erasure (see "Required edits to other changes").
- [The capability index is a moment behind the definitions folder, or the vector store is down] → `Task` resolves names only in the turn's snapshot, a failed sync leaves entries pending, logged, counted and retried by `CapabilityIndexSync` of `add-agent-skills`, the text match of `skill_search` still finds pending definitions, and a subagent whose name the model already knows still starts.
- [A subagent or the main chat with a shell] → sandbox tools run only in the run's or the conversation's own throwaway container of `add-agent-sandbox`, are off until the tenant policy allows them, and the wiring test asserts no in-process shell or file tool exists.
- [A run forgets its tenant on its own thread] → `SubagentRunService` runs every run inside `TenantContext.runAs` of `add-keycloak-login` before any other step, and an architecture test asserts every run entry point goes through it. A run with no resolved tenant fails with `INTERNAL_ERROR` rather than running as no tenant.
