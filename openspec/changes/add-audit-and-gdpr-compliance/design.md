## Goals / Non-Goals

**Goals:**

- One append-only audit trail for security-relevant events, queryable by admins.
- One-call, provable, asynchronous erasure of everything a user (or tenant) owns across every store that holds subject data.
- Zero prompt/document content in logs under the docker/production posture, with a convention all seven services follow.
- Bounded retention for the two unbounded Postgres surfaces (chat history, audit log).

**Non-Goals:**

- Authentication, roles, token validation (`add-keycloak-login`).
- Tenant claim propagation and per-tenant data scoping (`add-tenant-isolation`).
- Single-conversation delete (`add-chat-streaming-and-conversations`) and single-document delete (`add-document-management-api`) - erasure here is the everything-for-a-user path only.
- Usage-ledger schema and quota logic (`add-usage-metering-and-quotas`).
- Consent management, data-processing agreements, cookie banners - legal-document territory, out of scope.
- Cryptographic erasure / envelope encryption of stores (a future hardening; physical deletion suffices for the stores we run).

## Decisions

### D1 - Audit events via Spring application events, not inline writes

`AuditRecorder.record(AuditEvent)` publishes a Spring `ApplicationEvent`; an `@Async` listener persists the row. The same recorder backs `AuditEventPort` of `add-deployment-modules` (D11), so an event recorded through the port by any earlier change takes this path. Rationale: the business operation must never block on or fail because of audit persistence (a chat request that 500s because the audit insert timed out is worse than a missed audit row). A failed audit write logs at ERROR and increments a Micrometer counter (`audit.write.failed`) so the observability stack alerts on systemic loss. Alternative considered: synchronous same-transaction insert (strongest guarantee, but couples chat latency to a second Postgres write and fails closed); rejected for the request path, but erasure-job lifecycle events use synchronous writes since they are already async background work where the stronger guarantee is free.

### D2 - Append-only enforced in the database, not just the code

A Flyway migration creates `audit_log` and a Postgres trigger that raises an exception on `UPDATE` or `DELETE` - except deletes issued by the retention job's dedicated path (implemented as the trigger allowing deletes where `occurred_at` is older than a session-set retention boundary, via `set_config`). Rationale: "append-only because the repository has no update method" is not a compliance argument; a DB-level guard is. Alternative: separate Postgres role with only INSERT/SELECT grants - cleaner in principle, but the app runs as a single DB user today and introducing role separation is a `harden-cloud-deployment` concern; the trigger works with the current single-user setup and survives role changes later.

### D3 - Audit schema

`audit_log(id BIGSERIAL PK, occurred_at TIMESTAMPTZ NOT NULL, actor VARCHAR NOT NULL, tenant VARCHAR NULL, action VARCHAR NOT NULL, resource_type VARCHAR NULL, resource_id VARCHAR NULL, outcome VARCHAR NOT NULL, source_ip VARCHAR NULL, details JSONB NULL)` with indexes on `(occurred_at)`, `(actor, occurred_at)`, `(action, occurred_at)`. `action` is a closed enum-backed set: `AUTH_TOKEN_REJECTED`, `CHAT_PROMPT`, `DOCUMENT_UPLOADED`, `DOCUMENT_DELETED`, `DOCUMENT_PRESIGN_ISSUED`, `INGESTION_RUN`, `MEMORY_WIPED`, `ERASURE_REQUESTED`, `ERASURE_COMPLETED`, `EXPORT_REQUESTED`, `EXPORT_COMPLETED`, `ADMIN_OPERATION`, `QUOTA_REJECTED`, plus the actions of the agent changes below. `details` carries action-specific payload - for `CHAT_PROMPT` that is `{"prompt_length": N, "prompt_sha256": "..."}`, never the body.

Every action uses one naming style, the style this change used before the owner sweep of 2026-10-02: upper case words joined by underscores, the subject first and then the event in the past tense (`DOCUMENT_UPLOADED`, `ERASURE_REQUESTED`), with the outcome column telling whether the event succeeded or was refused. ### D4 - Erasure is a persisted state machine, not a fire-and-forget task

One job table serves erasure, export and tenant delete (owner answer 93, review item C8): `data_job(id UUID PK, kind ERASURE|EXPORT|TENANT_DELETE, subject_type USER|TENANT, subject_id, tenant_id, requested_by, status PENDING|RUNNING|COMPLETED|FAILED|PARTIAL, store_outcomes JSONB (one entry per store step with its outcome and its deleted or exported count), archive_location (nullable, set only for `EXPORT`), requested_at, completed_at, failure_detail)`, with a named check constraint `ck_data_job_kind` on `kind` and an index `idx_data_job_subject` on `(tenant_id, subject_id, kind)`. The three kinds share the `StoreWalker` (task 5.3a) and the status machine, so they share one table. `FAILED` and `PARTIAL` are erasure outcomes. An export ends `COMPLETED` or `FAILED`.

Several agent instances (owner rule R1, CANON 26.1): the endpoint writes the `data_job` row and schedules one execution `data-job/<jobId>` on the shared scheduler of `add-shared-scheduler` in the same transaction, and the instance that picks the execution runs the walk. So exactly one instance runs a job, and a job whose instance dies is picked up again by the scheduler's dead execution rule and re-run from the start, which is safe because every step is a delete-if-exists or a read. No job runs on an in-process executor of the instance that received the request. The orchestrator walks the stores in a fixed order: Postgres rows, Redis keys, the user facts folder, Floci `knowledge-base` objects, `ocr-results` objects, Qdrant points (both collections), AscendMemory wipe (every configured embedding provider), the stores of the agent changes through the steps this change writes for them (D9), and last the Keycloak user record through the Keycloak Admin REST API, recording per-store outcome. The rows of `subagent_run` (`add-agent-subagents`), `approval_request` (`add-action-approvals`) and `sandbox_workspace` (`add-agent-sandbox`) reference `conversations(id)` by a foreign key with no delete action (owner answer 76.6 of 2026-10-08), so the steps of those three stores run before the user's `conversations` rows are deleted. The Keycloak step disables the account and never deletes it (owner decision, 2026-10-01). It sets `enabled` to false, ends every active session of the account, and clears its personal attributes (first name, last name, email and every custom attribute except `tenant`), so the account can no longer sign in and holds no personal data. The disabled record keeps its id, so the pseudonymized audit rows and the erasure job keep pointing at a record that exists. The Admin REST client used by this step never issues a `DELETE` on a user. A store failure marks the job `PARTIAL` (not rolled back: erasure of four stores is strictly better than zero) and the job is re-runnable idempotently; every step is a delete-if-exists. Rationale for Postgres-persisted jobs over an in-memory `@Async` future: an erasure request is a legal act - it must survive a restart and be reportable ("job X completed at T with counts") months later. `DELETE /api/v1/users/{userId}/data` returns `202 Accepted` with the job id; `GET /api/v1/users/{userId}/data/erasure/{jobId}` returns status. Authorization: the authenticated principal must equal `userId`, or hold the tenant `ADMIN` role in the same tenant as `userId` (self-service Article 17 without a support ticket). A tenant `ADMIN` naming a user of another tenant gets 403. `PLATFORM_ADMIN` of `add-tenant-administration`, which lands before this change, erases a whole tenant through tenant delete (D10), not through this endpoint. A tenant `ADMIN` erases the whole data of their own tenant while keeping the tenant through `DELETE /api/v1/admin/tenants/{tenantId}/data` (kept, answer 93 does not cut it).

### D5 - Audit rows survive erasure, pseudonymized

GDPR Article 17(3)(b) permits retaining data needed for legal obligations; an audit trail that evaporates on erasure is useless. Decision: erasure rewrites `actor` (and `resource_id` where it is the userId) in the subject's audit rows to `HMAC-SHA256(userId, server-side pepper)` truncated to 16 hex chars, prefixed `pseudo:`. The pepper lives in configuration, read from the environment variable `AUDIT_PSEUDONYM_PEPPER` (owner answer 75.5 of 2026-10-07) whose value is kept only in env files, never in the database - without it the pseudonym is irreversible; with it, a lawful re-identification (e.g. a court order) remains possible. This rewrite is the **one sanctioned mutation** of audit rows and goes through the same trigger-gated path as retention deletes. Alternative considered: deleting the subject's audit rows outright - rejected, it destroys the evidence that the erasure itself happened.

### D6 - Prompt redaction at the source, levels fixed in the docker profile

Three layers: a) `PromptController` logs `promptLength` + `promptSha256` instead of the body (the hash lets support correlate a user-reported prompt with logs without storing content); b) `application-docker.yaml` gains a `logging.level` block pinning `org.springframework.ai: INFO` and `com.lukk.ascend.ai.agent: INFO` (also fixing the stale `com.lukk.ai.agent` logger name in base `application.yaml`); c) a redaction convention in `docs/COMPLIANCE.md`: user-supplied content (prompts, documents, transcripts, memory text, scraped pages, OCR output) is never a log argument - log lengths, counts, hashes, ids. The convention covers seven services: the six existing ones and `ascend-openclaw-host` of `add-openclaw-plugin-host`, whose containers of both roles share one log format. The Python services and the channel host are swept against this convention (AscendMemory's REST layer spot-checked clean already; apps/ascend-audio-scribe/apps/ascend-web-hunter/ascend-ocr and `ascend-openclaw-host` to verify). DEBUG for AI packages remains available in the local dev profile - redaction is a posture of the shipped profiles, not a removal of debuggability.

### D7 - Retention as a system task of the shared scheduler, not a cron container

The retention job is the system task `retention` of `add-shared-scheduler`, with its cron from `app.scheduler.system-tasks.retention.*` (default `0 3 * * *` in `Europe/Warsaw`). It is run by exactly one agent instance through the shared scheduler, also when more than one agent replica runs, which is the replica-safe requirement in `data-retention`. It deletes `chat_history` rows older than `app.retention.chat-history` and audit rows older than `app.retention.audit-log` (default `730d` in every deployment), batched deletes of `app.retention.batch-size` rows to bound lock time (answer 98). `app.retention.chat-history` takes a duration or the keep-forever value `forever`. When it is not set, its default follows the active module list of `add-deployment-modules` (read from `ModuleState`): `forever` when the list equals the `personal` preset, and `180d` for the company presets `core` and `company-docs` and for any other list. A value that is set always wins. With `forever` the job deletes no `chat_history` row. In the same run the job also deletes every conversation that has no `chat_history` row left and whose `updated_at` is older than `app.retention.empty-conversation-grace` (default `24h`, so a conversation the user has just created and not yet used is kept). It removes such a conversation through the conversation delete path of `add-chat-streaming-and-conversations` (D5 there), so its pending approvals, runs, scheduled job links and chat platform binding are handled the same way as a delete by the user, and it deletes empty conversations also when chat history is kept forever. Owner decision 65.1 of 2026-10-04. It deletes no user facts: `add-agent-soul` drops the `user_instructions` table, and the user facts that replace it are a profile kept until the user deletes them, not chat history. The cleanup of produced export archives is the system task `export-archive-cleanup`. Rationale: the agent already owns the schema and its Flyway migrations; a separate cron container would duplicate datasource config for one query, and a lock of its own would duplicate what the shared scheduler already guarantees. Retention values are `@ConfigurationProperties`-bound and documented in the retention matrix in `docs/COMPLIANCE.md` alongside the already-bounded Redis/Loki/Prometheus/Tempo windows and the bounds the agent changes set: notifications 30 days (`add-shared-scheduler`), final scheduled jobs 30 days (`add-scheduled-tasks`), `self_review` 90 days and `self_change` 365 days deleted by the system task `self-improvement-retention` of `add-self-improvement` (not by `retention`), temporary downloads 24 hours after the last download, deleted by the retention sweep inside ascend-web-hunter (`add-file-download` D7 and task 6.9, no agent system task since the owner instruction of 2026-10-04), with kept files until deleted, and crawl results 7 days, with the crawl job records, crawl progress and recrawl state on the same bound, `CRAWL_JOB_RETENTION_SECONDS` of `enhance-web-search-crawl-at-scale` (default 604800, its D3 and D12).

### D8 - Audit query API shape

`GET /api/v1/audit?actor=&action=&outcome=&from=&to=&page=&size=` - tenant `ADMIN` (role from `add-keycloak-login`), always filtered to the caller's tenant, or `PLATFORM_ADMIN` of `add-tenant-administration`, which sees every tenant's rows and may pass an optional `tenant` filter (moved here from that change's D6, because the audit log is this change's and lands after it). A tenant `ADMIN` passing `tenant` is still filtered to their own tenant. default sort `occurred_at DESC`, page size capped at the setting `app.audit.query.max-page-size` (default 200, answer 98), returns a standard page envelope. Filters map 1:1 to the indexed columns; no free-text search over `details` (that is what Grafana/Loki is for operationally; the API is the compliance surface).

### D10 - Tenant delete is erase-then-deprovision (moved here from `add-tenant-administration` D5)

Deleting a tenant needs erasure, and erasure is this change, which lands after `add-tenant-administration` under the owner build order of 2026-10-04. So this change adds `DELETE /api/v1/admin/tenants/{tenantId}` for `PLATFORM_ADMIN` to the tenant controller of `add-tenant-administration`. The order is fixed: (1) suspend the tenant through the lifecycle service of `add-tenant-administration`, (2) run the per-tenant erasure walk of D4 to zero residue through `ErasureOrchestrator`, (3) disable the Keycloak users whose `tenant` attribute equals the tenant id and clear their personal attributes through `KeycloakAdminClient` of `add-tenant-administration`, never deleting them (owner decision, 2026-10-01), (4) remove the `tenants` row. Each step is an `ADMIN_OPERATION` row. The endpoint writes one `data_job` row of kind `TENANT_DELETE` and its `data-job/<jobId>` execution (D4), so the four steps run on one instance and survive a restart. When the erasure walk ends `PARTIAL` or `FAILED`, the job stops before step 3, leaves the users and the row, and its status names the failed steps. The answer is 202 with the job id.

User removal of `add-tenant-administration` gains the option to chain the per-user erasure job of D4 (moved here from its task 5.1), and the removal still disables the Keycloak account and never deletes it.

### D12 - The crawl tenant erase and export calls in ascend-web-hunter (moved here from `enhance-web-search-crawl-at-scale` D11)

Owner answer 57 of 2026-10-03, owner answer 70.3 of 2026-10-04. Tenant erasure and tenant export of this change reach one tenant's crawl data (results, job records, crawl progress and recrawl state) through two internal calls that this change adds to ascend-web-hunter, built on the crawl key layout of `enhance-web-search-crawl-at-scale` (its D3, D5, D6, D8 and D12). This is the same way `add-file-download` gives the agent (its agent part, `add-download-ingestion`) its own internal calls for downloads. The agent never lists or deletes an object in `CRAWL_RESULT_S3_BUCKET` with a storage client of its own, so the key layout and the storage credentials stay inside ascend-web-hunter, also on a standalone web-hunter host. The calls live in a new module `src/crawl/tenant_data.py` and on the crawl router `src/api/rest/crawl_endpoints.py` of `enhance-web-search-crawl-at-scale`.

| Method | Path | Answer |
| :-- | :-- | :-- |
| DELETE | `/api/v1/crawl/data` | Internal. 200 with `{"jobs_cancelled": <count>, "jobs_deleted": <count>, "objects_deleted": <count>, "recrawl_scopes_deleted": <count>}`, also when the tenant has no crawl data |
| GET | `/api/v1/crawl/data/export` | Internal. 200 with one gzip tar archive streamed as `application/gzip` |

Tenant: both calls take the tenant only from the header `X-Ascend-Tenant`, which the agent fills with the tenant of its erasure or export job and sends together with the service token of `add-keycloak-login`. Unlike the job calls they never fall back to the tenant `default`: a call without the header, or with a value outside `[a-z0-9-]{1,64}`, is refused with 400 `invalid_tenant` (the code `enhance-web-search-crawl-at-scale` already registers), so a missing header never erases or exports the default tenant. Neither call is offered as an MCP tool, so a model can never erase or export crawl data. Objects and keys of another tenant are never listed, read or deleted.

Erase runs these steps in this order:

1. Every job of the tenant in state `waiting` or `running` moves to `cancelled`, exactly as `DELETE /api/v1/crawl/jobs/{job_id}` does, which also removes the job from the shared set `crawl_runnable` of `enhance-web-search-crawl-at-scale` D15 and stops the workers of that job on every ascend-web-hunter instance (owner rule R1).
2. The call waits until the in-flight counters (`enhance-web-search-crawl-at-scale` D5) of those jobs read zero, so no worker writes a new object after the delete. It waits at most `CRAWL_ERASE_DRAIN_SECONDS` (default 120). When a counter is still above zero then, it answers 503 `crawl_erase_busy` with `Retry-After` set from `CRAWL_ERASE_RETRY_AFTER_SECONDS` (answer 98, default not decided) and has deleted nothing yet, and the agent repeats the call.
3. Every object under `tenant/<tenantId>/` followed by `CRAWL_RESULT_S3_PREFIX` in `CRAWL_RESULT_S3_BUCKET` is listed by that prefix with a continuation token and deleted.
4. Every Redis key that matches `crawl_*:{tenantId}:*` is deleted: the frontier keys of every job of the tenant and the keys `crawl_claims:{tenantId}:{job_id}`, `crawl_next_fetch:{tenantId}:{job_id}:{domain}` and `crawl_pages:{tenantId}:{job_id}` of `enhance-web-search-crawl-at-scale` D15.
5. The recrawl state of the tenant (every scope hash of `enhance-web-search-crawl-at-scale` D6) is deleted.
6. Last, every job record of the tenant is deleted, so a call that fails half way still finds the jobs on its next run.

Each step is a delete-if-exists, so a repeated call finishes a half-done one, and a call after a complete one answers zero for every count.

Export writes one gzip tar archive with this layout:

- `jobs/<job_id>/job.json`: the job record (request, state, counts and times) of every job of the tenant still retained, in any state.
- `jobs/<job_id>/pages.ndjson` and `jobs/<job_id>/pages/<sha256 of URL>.md` (or `.json`): the result objects, read one at a time from the object store.
- `jobs/<job_id>/frontier.json`: for a job that still has frontier keys, its queued URLs per domain and its seen URLs.
- `recrawl/<scope>.ndjson`: one line per URL with the URL, content hash, `ETag`, `Last-Modified` and result key.
- `manifest.json`, the last entry: the tenant, the export time, and per job its id, state, counts and the archive paths of its files.

A running job is exported as it is at that moment and is not cancelled. The archive is written to the response while each object is read, so neither the service nor the agent holds the whole archive in memory. When the object store or Redis cannot be reached before the answer starts, the call answers 503 `storage_unavailable`. When a read fails after the answer has started, the stream stops without the closing tar blocks, so the agent sees a broken archive and fails that step instead of keeping an archive that only looks complete.

No call works on one user. A crawl job holds its tenant and no user id (`enhance-web-search-crawl-at-scale` D8), so deleting or exporting one user touches no crawl data.

Error codes (moved from the D9 rows of `enhance-web-search-crawl-at-scale`, registered by this change in ascend-web-hunter's `ErrorRegistry` in `src/api/exception_handlers.py`, built by the `ascend-python-common` problem builder, with `Retry-After` as a response header of the `crawl_erase_busy` entry, and both kept as codes whose detail says what failed):

| Code | Status | When |
| :--- | :--- | :--- |
| `crawl_erase_busy` | 503 | Erase, a worker of a cancelled job is still writing after `CRAWL_ERASE_DRAIN_SECONDS`, with `Retry-After` |
| `storage_unavailable` | 503 | Erase or export, the object store or Redis cannot be reached before the answer starts |

## Risks / Trade-offs

- [Async audit writes can drop events on crash] → acceptable for request-path events (metric + alert on `audit.write.failed`); erasure lifecycle events write synchronously, so the legally significant records are not exposed to this window.
- [Erasure completeness depends on tenant-isolation's ownership metadata] → `add-tenant-isolation` lands before this change, so objects and points carry the tenant; the erasure spec requires per-user deletion of *attributed* data and the tenant-wide job covers shared data.
- [Prompt SHA-256 of low-entropy prompts is guessable] → the hash is a correlation id, not a secrecy mechanism; a short prompt's hash confirms a guess an attacker already has. Documented as such; no salting (salting would break the correlate-user-report-to-log use case).
- [Retention delete vs. append-only trigger conflict] → the trigger's retention escape hatch (session-scoped config) is a sharp edge; covered by a dedicated integration test proving ad-hoc DELETEs fail and the retention path succeeds.
- [Usage-ledger coordination] → `add-usage-metering-and-quotas` lands after this change and adds its own store step to the `StoreWalker`; the schema-drift test of task 7.2 enumerates user-keyed tables via `information_schema`, so it fails in that change's build if its step is missing.
- [Pepper loss makes pseudonyms permanently irreversible] → acceptable (privacy-safe failure mode); pepper handling documented with the platform's existing secret conventions.
