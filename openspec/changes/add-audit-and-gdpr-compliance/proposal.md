## Why

AscendAI cannot be sold to EU companies in its current shape. Three compliance gaps, all verified in code:

1. **No audit trail.** There is no record of who did what, anywhere in the codebase - no audit table, no audit service, nothing an auditor or an incident responder could query. A GDPR Article 30 processing record and any SOC-2-adjacent sales conversation both start with "show me the audit log", and today the answer is `docker logs`.
2. **Customer content leaks into logs.** `apps/ascend-agent/src/main/java/com/lukk/ascend/ai/agent/controller/PromptController.java` lines 90-97 log the **full prompt body** plus userId at INFO on every request. `application.yaml` lines 397-404 set `org.springframework.ai` to DEBUG, so Spring AI's request/response logging (prompt, document context, model output) also hits stdout - and the observability stack ships all stdout to Loki via Vector, giving prompt content a 2160h searchable afterlife in a log store (the default `LOKI_RETENTION_PERIOD` of `add-observability`). (Side finding: the `com.lukk.ai.agent: DEBUG` entry names a logger that doesn't match the actual package `com.lukk.ascend.ai.agent` - it is a stale no-op.)
3. **The right to erasure (GDPR Article 17) is unimplementable.** AscendMemory has a per-user wipe (`POST /api/v1/memory/wipe`) and `SemanticMemoryClient` exposes it, but nothing deletes a user's chat history (Redis `chat:{conversationId}` keys and Postgres `chat_history`), `user_instructions` rows, ingested documents (the Floci `knowledge-base` bucket), or their Qdrant vectors (`ascendai-768` / `ascendai-1536`). A data-subject request today means several manual store-by-store operations with no proof of completion. Retention is equally absent: Postgres rows live forever (the `chat-history-persistence` spec explicitly defers "a separate retention policy" that was never built).

## What Changes

- **Audit log (new).** An append-only Postgres `audit_log` table (Flyway migration) recording actor, tenant, action, resource, outcome, source IP, and timestamp for security-relevant events: token rejections at the resource server, chat requests (prompt **length and SHA-256 hash**, never the body), document upload / delete / presigned-URL issuance, ingestion runs, memory wipes, erasure jobs, admin operations, and quota rejections (the action `QUOTA_REJECTED` is in the vocabulary here, and `add-usage-metering-and-quotas`, which lands after this change, records it through `AuditEventPort`). Events are written through a service-layer `AuditRecorder` (Spring application events, async listener), never via log lines. This change registers an `AuditRecorder` backed implementation of `AuditEventPort` of `add-deployment-modules` (its decision "Company extension ports"), replacing the default `LogAuditEventPort`, so every event the earlier changes and the earlier company changes already record through the port becomes an audit row with no edit of those changes. Queryable through ADMIN-only `GET /api/v1/audit` with filters and pagination. Every action uses one naming style, upper case words joined by underscores with the event in the past tense, the style this change used before the owner sweep of 2026-10-02, and actions that agent changes wrote in lower case with dots are converted to it. The agent changes record their own actions through `AuditEventPort`, and this change adds them to the closed vocabulary, each with details that never hold content: `SKILL_CREATED`, `SKILL_UPDATED`, `SKILL_DELETED`, `SKILL_REVERTED` and `SKILL_RELOADED` (`add-agent-skills`); `SUBAGENT_DEFINITION_WRITTEN`, `SUBAGENT_DEFINITION_DELETED`, `SUBAGENT_DEFINITION_REVERTED`, `SUBAGENT_DEFINITION_RELOADED` and `SUBAGENT_RUN_CANCELLED` (`add-agent-subagents`); `PERSONALITY_REPLACED`, `PERSONALITY_REVERTED`, `PERSONALITY_PROPOSED`, `PERSONALITY_APPROVED`, `PERSONALITY_REJECTED`, `PERSONALITY_EXPIRED`, `USER_FACTS_UPDATED`, `USER_FACTS_REPLACED`, `USER_FACTS_DELETED` and `USER_FACTS_REVERTED` (`add-agent-soul`); `APPROVAL_REQUESTED`, `APPROVAL_DECIDED`, `APPROVAL_RULE_CHANGED` and `APPROVED_ACTION_EXECUTED` (`add-action-approvals`); `OBSIDIAN_NOTE_WRITTEN` (`add-obsidian-vault`); `CHANNEL_PAIRING_CREATED`, `CHANNEL_LINK_CREATED`, `CHANNEL_LINK_REMOVED`, `CHANNEL_PAIRING_REDEEM_FAILED` and `CHANNEL_MESSAGE_REFUSED` (`add-openclaw-plugin-host`); `CODING_RUN_STARTED`, `CODING_RUN_PUBLISHED` and `CODING_PROJECT_CLEANED` (`add-coding-agent-delegation`); `SCHEDULED_JOB_CREATED`, `SCHEDULED_JOB_UPDATED`, `SCHEDULED_JOB_CANCELLED`, `SCHEDULED_JOB_TRIGGERED` and `SCHEDULED_JOB_FIRED` (`add-scheduled-tasks`); `SELF_IMPROVEMENT_REVIEWED`, `SELF_IMPROVEMENT_CHANGED`, `SELF_IMPROVEMENT_STAGED`, `SELF_IMPROVEMENT_GUARD_REVERTED`, `SELF_IMPROVEMENT_FROZEN`, `SELF_IMPROVEMENT_UNDONE` and `SELF_IMPROVEMENT_CASE_WRITTEN` (`add-self-improvement`); and `INTEGRATION_BUILD_STARTED`, `INTEGRATION_BUILD_FINISHED`, `INTEGRATION_REGISTERED`, `INTEGRATION_ACTIVATED`, `INTEGRATION_DISABLED`, `INTEGRATION_ENABLED`, `INTEGRATION_ROLLED_BACK`, `INTEGRATION_REMOVED`, `INTEGRATION_TOOL_REVIEWED` and `INTEGRATION_CREDENTIAL_REVOKED` (`add-self-built-integrations`).
- **User and tenant erasure (new).** `DELETE /api/v1/users/{userId}/data` (self, or a tenant `ADMIN` of the same tenant) starts an asynchronous erasure job spanning every store that holds subject data: Postgres (`chat_history` and the subject's `conversations` rows; `add-usage-metering-and-quotas` lands after this change and adds its `usage_ledger` rows as a store step of its own), the Redis keys `chat:{tenantId}:{conversationId}` for each of the subject's conversations, the subject's user facts folder `<root>/tenants/<tenantId>/users/<userKey>/` of `add-agent-soul` (which replaces the dropped `user_instructions` table and its Redis key), the subject's objects under `tenant/{tenantId}/` in the Floci `knowledge-base` bucket, the results of the subject's OCR jobs in the ascend-ocr `ocr-results` bucket (the jobs the agent recorded for the tenant), Qdrant points in both collections, AscendMemory memories under the tenant-qualified id `{tenantId}:{userId}` across configured embedding providers, and the subject's Keycloak user record, which is disabled and stripped of its personal attributes, never deleted (owner decision, 2026-10-01). The per-tenant variant additionally covers tenant-shared tables that are not attributed to a single user - the tenant-scoped `documents` / `document_index_state` / `ingestion_runs` registry from `add-document-management-api` and the connector configuration, sync-run and stored credential tables from `add-connector-framework`. The agent changes add their stores to both jobs, listed under "Stores of the agent changes" below. Job status is queryable; completion emits an audit event with per-store deletion counts. Audit rows survive erasure with the actor pseudonymized (design decides the mechanism).
- **Data export / portability (new).** A per-user `POST /api/v1/users/{userId}/data/export` (self, or a tenant `ADMIN` of the same tenant) and per-tenant `POST /api/v1/admin/tenants/{tenantId}/data/export` (tenant `ADMIN` of that tenant) start an asynchronous export job that assembles the subject's data - chat history and conversations, the user facts file `USER.md` at its newest commit, ingested documents from the Floci `knowledge-base` bucket, OCR results from the `ocr-results` bucket, AscendMemory memories, and the subject's Keycloak user record (profile fields, roles, groups) - into one downloadable gzip tar archive in its own bucket `data-exports`, with one folder per store step and a manifest at its root (owner answer 98.5), satisfying GDPR Article 20 portability and clean customer offboarding ("give us our data, then erase it"). Reuses the erasure job machinery and store-walker inventory so export and erasure never drift on which stores hold subject data.
- **Stores of the agent changes.** Every agent change lands before this one under the owner build order of 2026-10-04, so every store below exists when this change lands. This change writes the erasure and export step of each store, lists them in design D9, and the orchestrators call them. Per user erasure: the user facts folder (`SoulTenantStore`), `subagent_run` rows, `sandbox_workspace` rows and their output archives (open workspaces destroyed first), `approval_request` rows with `created_by` of the user's `approval_rule` rows set to null, `owner_notification` and `owner_notification_delivery` rows (`OwnerNotificationErasure`), `channel_link`, `channel_pairing` and `channel_outbox` rows with one `purge` row per removed link, `coding_project` and `coding_run` rows with their `coding-output` objects and the project folders the user created (runs stopped first), `scheduled_job` rows with their firings and `scheduler_execution` rows (`ScheduledJobErasure`), `self_review` rows with the memory text and reason of the user's `self_change` rows cleared, and `created_by` of the user's integrations set to null. Per user export: `USER.md` at its newest commit, `subagent_run` rows, approval requests, notifications, channel links and conversation bindings, `coding_project` and `coding_run` rows with their `coding-output` objects and one archive of each project folder the user created (through the archive call of the sandbox runner), scheduled jobs and firings, `sandbox_workspace` rows with their output archives, `self_review` and `self_change` rows, and the integrations whose `created_by` is the user, never a secret value. Per tenant erasure: the skills folder `tenants/<tenantId>/skills/` and every capability index entry of the tenant (`SkillTenantStore`), the definitions folder `tenants/<tenantId>/.claude/agents/` (`SubagentDefinitionStore`), the `soul/` and `users/` folders, every `subagent_run`, `sandbox_workspace`, `approval_request`, `approval_rule`, channel, notification, `scheduled_job`, coding and self-improvement row of the tenant, the `sandbox-output`, `coding-output` and `web-hunter-downloads` objects and download Redis keys of the tenant, the crawl data of the tenant (crawl results in `web-hunter-crawls`, job records, crawl progress and recrawl state) through the erase call `DELETE /api/v1/crawl/data` that this change adds to ascend-web-hunter (design D12), which cancels the tenant's running crawl jobs first, the `obsidian_vault_file` rows with their connector (never a file in a vault folder), and every integration with its runner objects, repository folder and build reports. Tenant export holds every user's export and adds the skill folders, the subagent definitions and the personality file, each with a `git bundle`, every `subagent_run` and `sandbox_workspace` row with the `sandbox-output` objects, both approval tables, the `obsidian_vault_file` rows (never a file of the vault folder), every temporary download and kept file with its record, the crawl data of the tenant (every retained crawl job with its record, its crawl results, crawl progress and recrawl state) from the export call `GET /api/v1/crawl/data/export` that this change adds to ascend-web-hunter (design D12), every coding row and object of the tenant with one archive of every project folder, every self-improvement row as JSON, and every integration of the tenant with its rows, its repository folder (files plus a `git bundle`) and its build reports, so export covers every store erasure covers. Per user erasure deletes no skill, no subagent definition, no download and no crawl result, because those belong to the tenant and hold no user id.
- **Log redaction (new).** Prompt bodies never appear in logs at any level under the docker/production posture: `PromptController` switches to length + hash, `application-docker.yaml` pins `org.springframework.ai` (and the corrected application logger) to INFO, and a written redaction convention covers all seven services, `ascend-openclaw-host` of `add-openclaw-plugin-host` included - the Python services' `[ServiceName]`-prefixed logging gets audited for content leakage as part of this change (AscendMemory's REST layer was spot-checked clean; the sweep makes it a guarantee).
- **Retention policy (new).** Configurable, scheduled retention for Postgres `chat_history` and `audit_log` rows, with documented defaults (owner decision 65.1 of 2026-10-04): chat history is kept forever in the `personal` preset through the keep-forever value `forever` and 180 days in the company presets, and audit rows are kept 730 days everywhere. The same nightly job deletes conversations left with no messages. User facts are not in it: they are a profile kept until the user deletes them, and `add-agent-soul` drops the `user_instructions` table. The retention job is the system task `retention` of `add-shared-scheduler`, with its cron from `app.scheduler.system-tasks.retention.*` (default `0 3 * * *` in `Europe/Warsaw`), run by exactly one agent instance through the shared scheduler even when the agent runs with more than one instance. The cleanup of produced export archives is the system task `export-archive-cleanup`. Redis already expires via the `chat-history-persistence` TTL; Loki is already bounded at 2160h and Tempo at 2160h by default, Prometheus at 72h (`add-observability` D13) - this change closes the Postgres gap and documents the whole retention matrix in one place, including the bounds the agent changes set: notifications 30 days, final scheduled jobs 30 days, `self_review` 90 days and `self_change` 365 days (system task `self-improvement-retention`), temporary downloads 24 hours after the last download (the retention sweep inside ascend-web-hunter of `add-file-download`, `DOWNLOAD_RETENTION_SECONDS`, no agent system task) with kept files until deleted, and crawl results 7 days (`CRAWL_JOB_RETENTION_SECONDS` of `enhance-web-search-crawl-at-scale`).
- **Erasure and export of every store are written here (ruling 13.3 of the dependency fix of 2026-10-05).** The earlier changes keep their layouts and tables. This change writes each erasure and export step and lists them by name in design D9: among them `SoulTenantStore`, `SkillTenantStore`, `SubagentDefinitionStore`, `OwnerNotificationErasure`, `ApprovalErasure`, `CodingErasure`, `ScheduledJobErasure` and `IntegrationErasure`.
- **Two internal calls for one tenant's crawl data in ascend-web-hunter (owner answer 57 of 2026-10-03, moved here by owner answer 70.3 of 2026-10-04).** `DELETE /api/v1/crawl/data` cancels the tenant's running jobs and deletes its crawl results, job records, crawl progress and recrawl state, and `GET /api/v1/crawl/data/export` streams all of it as one archive. Both take the tenant from the header `X-Ascend-Tenant` that the agent sends with the service token, and neither is an MCP tool. No call works on one user, because a crawl job belongs to a tenant and holds no user id (design D12).
- **Tenant delete (moved here from `add-tenant-administration` in the dependency fix of 2026-10-05).** `DELETE /api/v1/admin/tenants/{tenantId}` for `PLATFORM_ADMIN`: suspend through the lifecycle service of `add-tenant-administration`, run the per-tenant erasure job, disable (never delete) the tenant's Keycloak users and clear their personal attributes, then remove the `tenants` row, stopping with the job id when erasure ends `PARTIAL` or `FAILED` (design D10). User removal of `add-tenant-administration` gains the option to chain the per-user erasure job.
- **Cross-tenant audit query (moved here from `add-tenant-administration`).** A caller holding `PLATFORM_ADMIN` of `add-tenant-administration` reads every tenant's audit rows with an optional `tenant` filter, and a tenant `ADMIN` stays on their own tenant (design D8).
- **Its own parts of the deployment.** `add-deployment-modules` keeps audit out of the always-on core, so this change adds its own parts to the deployment when it lands: the two migrations, the `AuditEventPort` implementation, the erasure and export endpoints, the system tasks `retention` and `export-archive-cleanup`, and the `app.audit.*` and `app.retention.*` configuration with the pepper secret.
- **Compliance walkthrough doc** (`docs/COMPLIANCE.md`): what is audited, how to serve an erasure request, retention defaults, and what survives erasure.

Build order (owner build order of 2026-10-04, which supersedes the earlier orders): build group 5 (company), position 5. It needs `upgrade-spring-boot-4` (Flyway, owner decision of 2026-10-02), `add-keycloak-login` (trustworthy actor identity, the `ADMIN` role, token-rejection events), `add-deployment-modules` (`AuditEventPort` and `ModuleState`), `add-shared-scheduler` (the system tasks `retention` and `export-archive-cleanup`, and `OwnerNotificationErasure`), every personal change whose stores and actions it covers (`add-agent-skills`, `add-agent-subagents`, `add-agent-sandbox`, `add-agent-soul`, `add-action-approvals`, `add-connector-framework`, `add-obsidian-vault`, `add-openclaw-plugin-host`, `add-download-ingestion`, `add-coding-agent-delegation`, `add-scheduled-tasks`, `add-self-improvement`, `add-self-built-integrations`), the web-hunter changes `add-file-download` and `enhance-web-search-crawl-at-scale`, and the company changes `add-auth-and-identity` (the `tenant` claim), `add-tenant-isolation` (tenant-scoped resource attribution), `add-tenant-policy` (whose events it stores) and `add-tenant-administration` (`PLATFORM_ADMIN`, the lifecycle service and the Keycloak admin client that tenant delete uses). All of them land earlier. `add-usage-metering-and-quotas` lands after this change: it records `QUOTA_REJECTED` through `AuditEventPort` and adds its `usage_ledger` rows to erasure and export itself. The orders of 2026-10-01 and 2026-10-02, which put `add-usage-metering-and-quotas` before this change and `add-tenant-administration` after it, are superseded by the owner build order of 2026-10-04.

Role split: in this change `ADMIN` always means the tenant administrator role from `add-keycloak-login`, constrained server-side to the caller's own tenant. The cross-tenant `PLATFORM_ADMIN` role of `add-tenant-administration` lands before this change, and this change uses it for two things only: tenant delete (design D10) and the cross-tenant audit query (design D8). Sibling changes own adjacent surfaces: single-conversation delete is `add-chat-streaming-and-conversations`, single-document delete is `add-document-management-api`, the usage ledger schema is `add-usage-metering-and-quotas`, which lands after this change and adds its own erasure and export step to the `StoreWalker` of this change.

## Capabilities

### New Capabilities

- `audit-logging`: append-only audit trail of security-relevant events with actor/tenant/action/resource/outcome/IP/timestamp, service-layer recorder, ADMIN-only query API with filters and pagination.
- `data-erasure`: asynchronous per-user and per-tenant erasure jobs spanning Postgres, Redis, the Floci `knowledge-base` and `ocr-results` buckets, Qdrant, AscendMemory, the Keycloak user record, and the stores of the agent changes, with status endpoint, completion audit event, and pseudonymized audit-row survival.
- `log-redaction`: prompt and document content never logged in the production/docker posture; length-and-hash convention; per-service redaction rules for all seven services.
- `data-retention`: configurable scheduled retention for chat history and audit rows with documented platform-wide retention matrix; the retention job is the system task `retention` of `add-shared-scheduler`, run by exactly one agent instance.
- `data-portability`: asynchronous per-user and per-tenant export jobs that assemble the subject's data across Postgres, the Floci buckets, AscendMemory, the Keycloak user record, and the stores of the agent changes into a downloadable archive with a manifest, sharing the erasure store-walker so export and erasure cover the same stores.

### Modified Capabilities

- `web-search-crawl-jobs`: the internal tenant crawl data erase and export calls of design D12 (the capability is created by `enhance-web-search-crawl-at-scale`, which is archived before this change).
- `chat-history-persistence`: the "TTL configuration is documented" requirement currently mandates a comment saying Postgres pruning is deferred to "a separate retention policy" - that policy now exists, so the documented comment must point at the concrete `app.retention.*` configuration instead of a placeholder.

(`semantic-memory-client` reviewed and left unchanged - erasure consumes its existing `wipeUserMemory` contract as-is. `ingestion-security` reviewed and left unchanged - upload hygiene requirements don't change; the audit events emitted on upload live in `audit-logging` to keep one source of truth.)
